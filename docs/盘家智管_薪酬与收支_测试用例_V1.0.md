# 盘家智管 · 薪酬与收支模块 · 测试用例

> **版本：** V1.0
> **依据：** 《业务需求说明书 V4.6》《产品化架构设计 V1.10》《业绩域详细设计 V1.3》《结佣域详细设计 V1.5》《薪酬结算域详细设计 V1.0》
>
> **组织方式：** 以**业务场景**为维度，每个场景给出「前置 → 步骤 → 预期 → 对应需求/设计锚点」。
>
> **基准数据：** 2026-08《经纪人业绩结算明细表》318 行 / 应收 206,274.04 / 实收 192,556.89 / 36 人 / 6 门店；其中 52 行实收 = 0（已签约未实收）。
> **角色：** 经纪人 / 店长 / 店助 / **财务** / 总监 / 人事。
> **月度节奏：** N 月业绩 → N+1 月核对、结佣、核算并发放 **N 月工资批次**（批次 `period` 记 N 月）。

## S1 贝壳数据导入与合同归集

### S1-1 首次导入自动归集为合同

| 项 | 内容 |
|---|---|
| **前置** | 系统无该合同数据；导入《2026-08 经纪人业绩结算明细表》318 行 |
| **步骤** | 导入 → 预览确认 → 提交 |
| **预期** | ① 按聚合键（一手房取订单号、其余取合同号）归集为合同；② 318 行生成角色人业绩行，挂 `contract_id`；③ 每行生成 2 条事实：`PERF_EXPECT`（当月应收）、`PERF_REAL`（当月实收）；④ 合同级 `expect_total` / `real_total` 自下而上汇总；⑤ 合同 `first_period` = 202608；⑥ 合同 `dept_id` = 业绩占比最高角色人所属门店 |
| **锚点** | V4.6 §9.3 / 业绩域 §4.1 ⑥⑦ |

### S1-2 应收实收总额与三表勾稽

| 项 | 内容 |
|---|---|
| **预期** | `Σ PERF_EXPECT = 206,274.04`、`Σ PERF_REAL = 192,556.89`；与贝壳结算明细表、汇总表、合同明细表三表页脚完全一致（差异 0.00） |
| **锚点** | 业绩域 §1 基准数据 |

### S1-3 实收为 0 的行正常入库、不进结佣

| 项 | 内容 |
|---|---|
| **预期** | ① 52 行实收 = 0 的 `PERF_REAL` 事实正常生成（不因金额为 0 被拒）；② 结佣拉取时因 `amount <> 0` 过滤被排除；③ 业绩域可查，下月实收后进入下月结佣 |
| **锚点** | 结佣域 §4.1 ④ / ADR B14 |

### S1-4 重复导入同一批次幂等

| 项 | 内容 |
|---|---|
| **步骤** | 同一 Excel 重复导入两次 |
| **预期** | 第二次按 `batch_id` 幂等跳过（`consume_log` 已 SUCCESS）；不产生重复事实与重复结佣申请单 |
| **锚点** | 业绩域 §4.1 ② |

### S1-5 重导同月批次（supersede）不丢新签

| 项 | 内容 |
|---|---|
| **前置** | 8 月已导入；9 月又发生部分数据修正 |
| **步骤** | 重新导入 8 月修正后数据 |
| **预期** | ① 旧批次事实 REVERSED、新批次重建；② `contract.first_period` 仍为 202608，**不改为 202609**；③ 重建行 `new_sign_period` 仍 = 202608，8 月新签不丢失；④ `source = MANUAL` 的行不被删除 |
| **锚点** | 业绩域 §2.12 / A45 / 测试 P-85 |

### S1-6 工号匹配失败进待对齐

| 项 | 内容 |
|---|---|
| **预期** | 匹配失败行进「待对齐」列表，不生成事实；人工指定员工后可重跑匹配；重跑后正常生成事实 |
| **锚点** | 业绩域 §4.5 |

| 项 | 内容 |
|---|---|
| **测试数据** | 同一 `period` 的贝壳全量明细，**每天导入一次**（截至当天的整月数据） |

### S1-8 已审事实不被冲销 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 周一建 100 条事实，其中 2 条实收**已被人工审批通过**；周三导入全量 |
| **预期** | ① 那 **2 条保留不动**（不被 REVERSED）；② 其余 97 条正常冲销 + 重建（金额未变则跳过）；③ 已审确认单指向的事实仍有效，**不等于白审** |
| **锚点** | 业绩域 §4.2.1 / §4.2.2 / P-112 |

### S1-9 自动待审确认单不保护

| 项 | 内容 |
|---|---|
| **测试数据** | 周一自动提交的确认单**尚无任何人工动作**；周三导入全量 |
| **预期** | ① 对应事实**正常冲销**，确认单一并删除；② 按新数据重建并重新自动提交；③ **不得**因"系统自动提交"而锁死数据（否则后续新数据永远进不来） |
| **锚点** | 业绩域 §4.2.2 / P-113 / A52 |

### S1-10 新增实收当天进入审批

| 项 | 内容 |
|---|---|
| **测试数据** | 周三全量导入中出现**新的实收行**（周一尚无） |
| **预期** | ① 正常新建事实；② 自动提交实收确认单 → 财务 → 总监；③ 月底无需集中审核 |
| **锚点** | 业绩域 §4.2.3 / P-114 |

## S3 实收业绩确认流程

### S3-1 导入有实收 → 自动提交确认单

| 项 | 内容 |
|---|---|
| **前置** | 导入含实收的合同 |
| **预期** | ① 系统**自动**按「合同 × 到账月」生成实收确认单，无需人工点"发起"；② 状态 `DRAFT` → 流转**财务**；③ 实收 = 0 的合同**不生成**确认单 |
| **锚点** | V4.6 §9.4.2 / 业绩域 §3.7 |

### S3-2 按发起人决定首节点

| 发起人 | 预期链路 |
|---|---|
| 店长 / 店助 | 财务 → 总监 → `CONFIRMED` |
| **财务** | **总监** → `CONFIRMED`（不自审） |
| **总监** | **直接 `CONFIRMED`**（无需审批） |
| 导入自动 | 财务 → 总监 → `CONFIRMED` |

| **锚点** | V4.6 §9.4.3 / ADR-029 |
|---|---|

### S3-3 未确认实收不得进结佣 ★

| 项 | 内容 |
|---|---|
| **前置** | 合同有实收但确认单未审批 |
| **预期** | ① 结佣域**不生成**结佣申请单；② 财务/总监在结佣侧查不到该实收；③ 确认通过后才发 `RealConfirmedEvent` 并触发结佣 |
| **锚点** | ADR-029 硬约束 / 结佣域 C-29 |

### S3-4 Excel 按合同号+金额自动审批

| 项 | 内容 |
|---|---|
| **步骤** | 导入贝壳 Excel → 匹配合同号 + 金额 |
| **预期** | ① 金额一致 → 自动审批通过；② 金额不一致或合同号找不到 → 进**异常清单**，人工处理，**不静默跳过**；③ 幂等：重复导入不重复审批 |
| **锚点** | V4.6 §9.4.4 |

### S3-5 分期回款多次确认

| 项 | 内容 |
|---|---|
| **前置** | 合同 X 8月到账 50,000、9月到账 50,000 |
| **预期** | 生成**两张**确认单（`period` 分别 202608 / 202609），各自独立审批 |
| **锚点** | 业绩域 §3.7 粒度 |

### S3-6 确认单可驳回

| 项 | 内容 |
|---|---|
| **预期** | 财务或总监可驳回；驳回后状态 `REJECTED`，不触发结佣；修正后可重新发起 |
| **锚点** | 业绩域 §3.7 状态机 |

## S4 结佣发起与审批（合同 × 到账月）

### S4-1 申请单粒度 = 合同 × 到账月

| 项 | 内容 |
|---|---|
| **预期** | ① 一份合同一次到账 → 一张申请单；分多次到账 → 各次分别一张；② 不同合同同月到账 → 各一张；③ 唯一键 `uk_capp_contract_period` |
| **锚点** | ADR-028 / 结佣域 C-24 |

### S4-2 跨店合同不拆分 ★

| 项 | 内容 |
|---|---|
| **前置** | 合同含 A/B 两店角色人 |
| **预期** | ① **一张**申请单（不按店拆子单）；② 总监一次性审批；③ 申请单**无** `dept_id`，门店只在明细行冻结（各行可不同） |
| **锚点** | ADR-028 / 结佣域 C-25、C-26 |

### S4-3 从已审实收业绩发起

| 项 | 内容 |
|---|---|
| **步骤** | 选择已 `CONFIRMED` 的实收业绩 → 发起结佣 |
| **预期** | 生成结佣申请单，流转到**总监**；明细按当期生效业绩比例分摊到各角色人 |
| **锚点** | V4.6 §9.5.1 / §9.4 |

### S4-4 Excel 批量发起

| 项 | 内容 |
|---|---|
| **步骤** | 导入贝壳 Excel → 按合同号匹配 |
| **预期** | ① 批量生成/发起申请单；② 合同号找不到 → 进异常清单；③ 幂等：重复导入不重复发起 |
| **锚点** | 结佣域 §4.2.3 / C-34 |

### S4-5 审批链 = 总监 → 财务 ★

| 项 | 内容 |
|---|---|
| **预期** | ① 提交后先到**总监**；② 总监通过 → 进 `FINANCE_VERIFY`；③ 财务通过 → `APPROVED` → `LOCKED`；④ **无核验节点**（原 `PENDING_VERIFY` 已取消） |
| **锚点** | ADR-030 / 结佣域 C-31 |

### S4-6 无差异跳过财务

| 项 | 内容 |
|---|---|
| **前置** | 合同实收累计 == 应收总额（全额回款、无折无退） |
| **预期** | 总监通过 → **直接 `APPROVED`**，不进财务节点 |
| **锚点** | V4.6 §9.5.3 / ADR-030 |

### S4-7 批量审批

| 项 | 内容 |
|---|---|
| **步骤** | 总监勾选多张 `DRAFT`/`SUBMITTED` 申请单 → 批量通过 |

### S4-8 Excel 批量审批

| 项 | 内容 |
|---|---|

## S5 实收应收差异与自动对齐

### S5-1 有差异自动对齐（合同级 + 明细级）★

| 项 | 内容 |
|---|---|
| **前置** | 合同应收 100,000 / 实收 92,000 |
| **预期** | ① 系统**自动**将实收对齐为 100,000；② **合同级** `real_total` = 100,000；③ **明细级**按 `biz_key` 逐行对齐：甲 60,000、乙 25,000、丙 15,000；④ 对齐后**流转财务**审批 |

### S5-2 对齐不覆盖原始 ★

| 项 | 内容 |
|---|---|
| **预期** | ① 对齐生成**新 `PERF_REAL` 行**（`align_flag = true`、`align_source = COMMISSION_DIFF`）；② 原始实收行仍 `ACTIVE` 可查；③ 合同页时间线可见对齐记录 |
| **锚点** | 结佣域 C-38 / 业绩域 P-74 |

### S5-3 对齐幂等

| 项 | 内容 |
|---|---|
| **预期** | 同一合同 + 同一到账月重复发起 → 只对齐一次，金额不叠加 |
| **锚点** | 结佣域 C-39 |

### S5-4 有退单不自动对齐（默认）⚠

| 项 | 内容 |
|---|---|
| **前置** | 差异来自真实退单 |
| **预期** | 默认**不自动对齐**，转财务人工判断（避免抹掉退单效果） |
| **锚点** | V4.6 待确认 T / 结佣域 C-40 |

### S5-5 对齐经 Port 受控写入

| 项 | 内容 |
|---|---|
| **预期** | 结佣域经 `PerformanceAlignPort` 调用，**不直连**业绩域表；对齐仅此场景可用，不作为通用写通道 |
| **锚点** | ADR-031 / CR-C18 |

## S6 业绩调整（只改应收）

### S6-1 只改应收，拒绝改实收 ★

| 项 | 内容 |
|---|---|
| **预期** | ① 对 `PERF_REAL` 发起调整 → **拒绝**；② 仅 `PERF_EXPECT` 可调整；③ 实收变化只来自红冲或新到账 |
| **锚点** | V4.6 §9.6 / ADR-032 / 业绩域 P-64 |

### S6-2 合同维度调整按比例分摊

| 项 | 内容 |
|---|---|
| **前置** | 合同应收 120,000：甲 72,000(60%) / 乙 30,000(25%) / 丙 18,000(15%) |
| **步骤** | 合同金额改为 100,000 |
| **预期** | 甲 60,000 / 乙 25,000 / 丙 15,000（= 新金额 × **原比例**） |
| **锚点** | V4.6 §9.6.1 / 业绩域 P-65 |

### S6-3 明细维度调整不联动他人

| 项 | 内容 |
|---|---|
| **步骤** | 乙 30,000 → 25,000 |
| **预期** | 甲 72,000、丙 18,000 **不变**；合同合计自动重算为 115,000 |
| **锚点** | V4.6 §9.6.1 / 业绩域 P-66 |

### S6-4 发起与审批权限

| 项 | 内容 |
|---|---|
| **预期** | ① **店长 / 店助 / 总监**均可发起；② 审批人固定为**总监**；③ 待审批调整单**对经纪人不生效、不展示** |
| **锚点** | V4.6 §9.6.2 / 业绩域 P-67 |

### S6-5 整单折扣（85 折）

| 项 | 内容 |
|---|---|
| **预期** | ① 合同下所有角色人按折扣生成调整行；② **常规导入不得重复打 85 折**（贝壳导出值已含 85 折）；③ 本功能仅用于**额外**折扣个案 |
| **锚点** | V4.6 §9.6.6 / 85 折说明 |

### S6-6 补录角色人

| 项 | 内容 |
|---|---|
| **预期** | 允许补录（标记"人工补录"），**仅限该合同对应工资未锁定前**；已锁定只能走补发单 |
| **锚点** | V4.6 待确认 B |

### S6-7 作废角色人

| 项 | 内容 |
|---|---|
| **预期** | 该行金额置 0，生成反向调整记录；原行保留可查 |
| **锚点** | 业绩域 §3.3 |

### S6-8 生效值公式含全部变更 ★

| 项 | 内容 |
|---|---|
| **预期** | **当期生效值 = 原始行 + 全部已生效调整行 + 全部红冲行**（漏算红冲会导致生效值偏高）；合同级 `expect_total` / `real_total` 同样含红冲 |
| **锚点** | 业绩域 §1.7 / ADR A33 / 测试 P-51 |

### S6-9 二次调整只认「调整当时的值」，不看原始值 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 合同 F3：甲 600 / 乙 250 / 丙 150，合同 1,000 |
| **前置** | 第 1 次调整已审批生效：合同 1,000 → 800（甲 480 / 乙 200 / 丙 120） |
| **步骤** | 第 2 次调整：合同改为 640 |
| **预期** | ① 第 2 次**只认「调整当时的合同金额 800 → 调整后 640」**，**不回溯**原始 1,000；② 比例取**当时**各人金额占当时合同金额之比（甲 480/800=60% 等）；③ 结果：甲 384 / 乙 160 / 丙 96；④ **与第几次调整无关**，第 N 次算法完全相同；⑤ **合同原始业绩 1,000 永不改变** |
| **锚点** | V4.6 §9.6.1（最终调整值口径） |

> **★ 口径定论**：界面与计算**一律取「最终调整值」（当前生效值）**；每次调整仅在调整单上记录「调整前 → 调整后」，系统**不回溯、不依赖**合同原始业绩。**合同的原始业绩永不改变**（原始行只读，§S6-13）。

### S6-10 合同维度：以当时各人金额占当时合同金额的比例分摊 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 合同 F3，当前生效：甲 480 / 乙 200 / 丙 120，合同 800 |
| **步骤** | 合同维度调整：1,000 → 800（首次调整场景） |
| **预期** | ① 比例 = **当时每人金额 ÷ 当时合同金额**（甲 600/1000=60%）；② **新合同金额 × 该比例** = 甲 480 / 乙 200 / 丙 120；③ 调整单记录 **调整前金额 1,000 → 调整后金额 800**；④ 不依赖"原始比例"或"第几次调整"；⑤ **原始业绩 1,000 保持不变**，仅新增调整行 |
| **锚点** | V4.6 §9.6.1 / 需求 4.2 |

## S15 导入撤销与重导（归属月选错）

> **★ 主控方：`panjia-import`（导入域）** —— 撤销入口 `POST /api/import/batches/{id}/revoke`。
> 业绩域 / 结佣域**消费 `ImportBatchRevokedEvent`** 做级联处理，**不提供撤销接口**。
>
> **★ 撤销与导入同构**：发事件 → 下游监听消费 → 幂等 → **直接删除派生数据**（不引入新概念）。
>
> | | 导入（重跑） | 撤销 |
> |---|---|---|
> | 机制 | 事件 + 幂等 + 监听 | **完全相同** |
> | 派生数据 | 先删后建 | **只删不建** |
> | `source=MANUAL` 行 | 绝不删 | **绝不删** |
>
> **★ 禁止删除的前提（命中任一即拒绝）：业绩已有调整单 / 实收已提交审批 / 结佣单已生成 / 已封账。**
>
> 本场景按**域**分三组，每组对应一个模块的测试包，可直接落位：
>
> | 组 | 域 | 测试包（建议） | 用例 |
> |---|---|---|:---:|
> | **S15-A** | import | `panjia-import` `ImportBatchRevokeTest` | 8 |
> | **S15-B** | performance | `panjia-performance` `ImportRevokeCascadeTest` + `BatchConsumptionAdapterTest` | 6 |
> | **S15-C** | commission | `panjia-commission` `ImportRevokeCascadeTest` | 6 |

#### S15-B4 `BatchRevocableQueryPort` 可删判定 ★

| 场景 | `isRevocable` | 阻塞码 |
|---|:---:|---|
| 该批**从未有任何人工介入** | ✅ `true` | — |
| **实收确认单系统自动生成、尚无任何人工动作**（DRAFT / 待审未处理） | ✅ `true` | — |
| **业绩提交过调整审批**（待审批 / 通过 / **驳回** / 撤回 / 作废） | ❌ `false` | `FACT_ADJUSTED` |
| **实收确认单已有人工审批动作**（通过 / **驳回** / 撤回） | ❌ `false` | `REAL_CONFIRM_HANDLED` |
| 已生成结佣申请单（DRAFT） | ❌ `false` | `COMMISSION_EXISTS` |
| `period` 已封账 | ❌ `false` | `PERIOD_CLOSED` |

> **★ 定论：只要"有人动过"，就永久阻塞删除，与审批结果无关（驳回、撤回、作废均算）。**
> 该阻塞**不可解除** —— 不能靠撤回单据恢复可删。
>
> **★ 关键区分（易错点）**：导入有实收时系统会**自动提交**确认单，但**未经任何人工处理前仍属派生数据**，**不阻塞**（否则导入瞬间即被自己触发的单据堵死，撤销形同虚设）。
> **"有任务" = 有人动过**，不是"系统生成过"。
>
> **实现要求**：调整单 / 确认单**不物理删除**（作废仅置状态、保留记录），否则无从判定"是否有人动过"。

| **锚点** | 导入域 §5.6.3 / 业绩域 §4.10.2 |
|---|---|

## S16 审批入口与工作流集成

> **引擎**：Warm-Flow 1.8.1（RuoYi-Plus 官方 `ruoyi-workflow`，7 张表）。
> **双入口**：我的待办 + 业务明细直接审批，**共用同一 `completeTask`**。
> **状态归属**：**业务单据状态为准**，工作流只驱动流转（ADR-037）。

### S16-1 我的待办审批 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 总监待办中有 5 张结佣申请单 |
| **步骤** | 「我的待办」→ 勾选 → 批量通过 |
| **预期** | ① 调用 `pageWaitingTasks` 取 `taskId`；② 走 `completeTask` 完成；③ 业务单据状态同步回写 |
| **锚点** | 需求 §9.11.1 / 架构 §2.8.2 |

### S16-2 业务明细直接审批 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 正在查看合同 F3 的结佣申请单明细 |
| **步骤** | 在明细页直接点「通过」 |
| **预期** | ① 经 `getByBusinessId(单据ID)` 取 `taskId`；② 调用**同一个** `completeTask`；③ 结果与留痕同待办入口**完全一致** |
| **锚点** | 需求 §9.11.1 / 架构 §2.8.2 / P-119、C-45 |

### S16-3 业务明细入口仍鉴权 ★

| 项 | 内容 |
|---|---|
| **前置** | 操作人**不在**当前节点审批人范围内 |
| **预期** | ① **服务端拒绝**（403）；② **不得**因从业务明细进入而放松鉴权；③ 前端隐藏按钮 ≠ 安全，须服务端校验 |
| **锚点** | 架构 §2.8.2 / P-120、C-46 |

### S16-4 业务单据状态为准 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 流程已流转到"通过"，但业务单据状态**未回写**（模拟监听器失败） |
| **预期** | ① payroll 取数、结佣、封账**以业务单据状态为准**；② 不直接读 `flow_task`；③ 出现不一致时**告警**，而非按流程状态算薪 |
| **锚点** | 架构 §2.8.3 / ADR-037 / P-121、C-47 |

### S16-5 监听器回写幂等

| 项 | 内容 |
|---|---|
| **步骤** | 监听器被重复触发（重试 / 补偿 / 消息重投） |
| **预期** | ① 按 `bizId + 目标状态` 幂等；② 业务状态**不重复变更**；③ 不产生重复审批记录 |
| **锚点** | 架构 §2.8.5 / P-122、C-48 |

### S16-6 总监超时自动通过 ★

| 项 | 内容 |
|---|---|
| **测试数据** | 节点扩展属性 `autoApproval = 72`（小时）；单据流转到总监节点后 72 小时未处理 |
| **预期** | ① 系统**自动审批通过**；② 记录为「超时自动审批」，**区别于人工审批**，审计可查；③ 继续触发后续节点（财务）或生效动作；④ 用 `ignore(true)` 跳过办理人权限校验 |
| **锚点** | 需求 §9.11.2 / 架构 §2.8.5 / P-123 |

### S16-7 超时用「创建监听器」而非任务监听器 ★

| 项 | 内容 |
|---|---|
| **预期** | ① 定时任务在**创建监听器**中启动（A→B 时 A 办理即触发 B 的创建监听器）；② **不得**用任务监听器（会错过时机）；③ 超时后按 `autoApproval_skipType` 执行 `PASS` / `REJECT` |
| **锚点** | 架构 §2.8.5 ① |

### S16-8 条件跳过财务节点

| 项 | 内容 |
|---|---|
| **测试数据** | 结佣申请单，实收 == 应收（无差异） |
| **预期** | ① 互斥网关按 `skipCondition` 判定；② 直接跳到下一节点，**不经过财务**；③ 有差异时正常走财务 |
| **锚点** | 需求 §9.11.3 / §9.5.3 |

### S16-9 换引擎不影响业务代码

| 项 | 内容 |
|---|---|
| **预期** | ① 业务域只依赖 `ApprovalPort`（定义在 `panjia-contracts`）；② CI 断言 performance / commission 不出现 `org.dromara.workflow` 包路径；③ 替换适配器即可换引擎 |
| **锚点** | 架构 §2.8.4 / ADR-038 / P-124 |
