## 一、部署全景

```
┌─────────────────────────────────────────────────────┐
│ 客户机器（每客户一套，Docker Compose 单节点）           │
│   panjia-admin + postgres + redis + minio + nginx    │
│   挂载：/etc/machine-id（只读）+ panjia-license 数据卷 │
│   首次启动：PANJIA_AUTH_CODE 自动激活                  │
└───────────────────┬─────────────────────────────────┘
                    │ 仅出站 HTTPS 443（心跳/激活/check）
                    ▼
┌─────────────────────────────────────────────────────┐
│ 我方授权服务器（单 ECS 2C4G/5M）                       │
│   Nginx :443 → panjia-console（customer+license 同进程）│
│   PostgreSQL 16 单库 panjia_platform（auth+customer 两 schema）│
│   jks 私钥 权限 600，永不离开本机                       │
└─────────────────────────────────────────────────────┘
```

**两条线，一次装好：**

| 线 | 部署对象 | 频率 |
|---|---|---|
| A 线 | 我方授权服务器（panjia-console） | **一次性**，之后只升级 |
| B 线 | 客户机器（panjia-app 全家桶） | **每个客户一次**，由 `panjia-deploy` 一键完成 |

### 3.2 后端打包（panjia-app）——先分清「已落地」与「目标流水线」

> ⚠️ **铁律现状（务必先读）**：混淆/加密三环节是详设《License 客户端校验 V1.3》§4.2 的**目标设计**，其构建脚本属于**交付物 #4（尚未完成）**。截至 V1.1，本仓库**只落地了部分环节**，`mvn package` 目前**不会**执行混淆与加密：
>
> | 环节 | 落地状态 | 证据 |
> |---|---|---|
> | LicenseMode 编译期注入 | ✅ 已落地 | `panjia-modules/panjia-license/pom.xml`：templating-maven-plugin 3.0.0（generate-sources，把 `src/main/templates/…/LicenseMode.java` 渲染到 `target/generated-sources/license`，注入 `${license.dev}`） |
> | checksum-gen | ✅ 已落地 | 同 pom：exec-maven-plugin 3.3.0（process-classes → 运行 `com.panjia.license.tools.ChecksumGenerator`，对 16 个关键类 + `com/panjia/license` 全包算 SHA-256 → 写 `target/classes/META-INF/panjia-checksums.txt`） |
> | ProGuard（混淆） | ❌ 未落地 | 全仓库 pom / Dockerfile 无任何 proguard 配置（含 ruoyi-admin/Dockerfile，仅 ADD jar + java -jar） |
> | ClassFinal（加密） | ❌ 未落地 | 同上，无 classfinal 配置。属详设交付物 #4，落地指引见 §3.2.3 |

#### 3.2.1 构建命令（当前真实可执行）

```bash
cd /Users/shengwei/workspace/panjia-server

# 生产构建（关键：必须带 -Pprod）
mvn clean package -Pprod -DskipTests
```

> ⚠️ **漏带 `-Pprod` = 发雷**：`panjia-license/pom.xml` 里 `dev` profile 是 `activeByDefault=true`（默认激活），只有显式 `-Pprod` 才注入 `license.dev=false` → `LicenseMode.DEV=false` → 编译器消除 dev 分支。漏带 `-Pprod` 时 DEV=true，devToken 直通、跳过心跳、authCode 自动激活守卫（`!DEV || testMode`）全部失效，且编译进字节码后无法靠配置补救。**生产构建禁止不带 `-Pprod`。**

真实阶段映射（可对照 pom 逐条核对）：

```
generate-sources    templating-maven-plugin → LicenseMode.java（DEV=${license.dev}）
compile             javac 编译；DEV=false 时对 if(DEV) 分支做死代码消除
process-classes     exec-maven-plugin → ChecksumGenerator → META-INF/panjia-checksums.txt
package             spring-boot-maven-plugin → ruoyi-admin.jar（fat jar，panjia-license 打成嵌套 jar）
```

#### 3.2.2 打包后自检（修正版命令）

> ⚠️ V1.0 的自检命令是错的：checksum 文件在 **panjia-license 嵌套 jar** 内（`BOOT-INF/lib/panjia-license-*.jar` 的 `META-INF/`），boot jar 外层的 `unzip -l` 永远查不到，会误报"缺失"。运行时 IntegrityChecker 通过 `getResourceAsStream("META-INF/panjia-checksums.txt")` 读取，嵌套 jar 可正常加载。

```bash
JAR=$(ls ruoyi-admin/target/ruoyi-admin-*.jar | head -1)

# 0) 先取出 panjia-license 嵌套 jar
unzip -p "$JAR" 'BOOT-INF/lib/panjia-license-*.jar' > /tmp/pl-license.jar

# 1) 校验和文件必须存在（缺失 → prod 启动抛 IntegrityException → 全受限）
unzip -l /tmp/pl-license.jar | grep panjia-checksums

# 2) LicenseMode.DEV 必须为 false（javap -constants 应输出 DEV=false / 常量 0）
unzip -p /tmp/pl-license.jar com/panjia/license/LicenseMode.class > /tmp/LicenseMode.class
javap -constants -p /tmp/LicenseMode.class | grep DEV

# 3) 公钥资源存在（license-public-key.pem 在 classpath，不在 application.yml）
unzip -l /tmp/pl-license.jar | grep -i 'public-key\|\.pem'
unzip -l "$JAR" | grep -i '\.pem'   # 若公钥放在外层 BOOT-INF/classes，二者任一命中即可
```

#### 3.2.3 ProGuard / ClassFinal 落地指引（目标流水线，交付物 #4，当前未实现）

**铁律出处（抄送评审/改构建脚本的人）：**

- 详设《盘家智管_License 客户端校验_详细设计_V1.3.md》**§4.2 构建流程（顺序钉死）**：实现陷阱警告 + 顺序图 + **铁律 11**——"`panjia-checksums` 必须在 ClassFinal **之前**执行；构建脚本改顺序前须对照此铁律"
- 同文档 **§十二 安全设计铁律表 #11**（`panjia-checksums` 必须在 ClassFinal 加密之前生成）
- 同文档 **§十 验收判据**：构建顺序 `ProGuard → checksum-gen → ClassFinal` 正确；**先加密后算 hash → 启动即全受限，不合格**
- 同文档 **§十四 交付物 #4**：ProGuard + ClassFinal 构建脚本（含 checksum-gen 顺序铁律注释）——即本节内容是"待完成"而非"已完成"

**顺序与原理（写死，不可协商）：**

```
ProGuard（混淆） → checksum-gen（对混淆后、加密前的 class 算 SHA-256） → ClassFinal（加密）
```

- checksum 记录的是**加密前**的字节码值；运行时 ClassFinal 靠 agent 解密后才执行。若顺序写反（先加密再算 hash），运行期 `IntegrityChecker` 读到的流是加密态/解密态字节码，与记录值**全部不匹配** → 抛 `IntegrityException` → 受限模式。届时**先查构建顺序，别当业务 bug 排查**。
- 现状挂点提醒：checksum-gen 目前挂在 `process-classes`（编译后立即，天然早于任何混淆/加密）。引入 ProGuard 时必须保证其输出在 checksum-gen 之前；引入 ClassFinal（一般在 package 之后对 jar 加密）时必须保证 checksum-gen 仍在 ClassFinal 之前。**任何把 checksum 挂点后移/新增后处理插件的改动，先对照铁律 11。**

**落地时应补的内容（本手册不给虚构配置，落地后回填）：**

1. ProGuard / ClassFinal 的插件坐标与版本（详设未选型，交付物 #4 时确定；注意 ClassFinal 若用 agent 模式，ruoyi-admin/Dockerfile 的 ENTRYPOINT 需加 `-javaagent`）；
2. 落地后的顺序验证：临时把 ClassFinal 调至 checksum-gen 之前构建一次 → 启动应如预期全受限 → 还原顺序，作为守卫生效的回归证据；
3. §3.6 验收清单补充"三环节顺序已核对"项。

## 四、A 线：我方授权服务器部署（一次性）

### 4.1 服务器准备

- ECS：2C4G / 5M 带宽（详设 V1.5 §2.1）
- 域名：`license.panjia.com` 解析到 ECS 公网 IP，签发 HTTPS 证书（Let's Encrypt 或云厂商免费证书）
- 安全组：**仅开放 22 / 443**；管理面 `/api/panjia/*` 靠 Nginx 白名单（下述）

### 4.2 部署步骤

```bash
# 1. 上传并解包
tar xzf panjia-console_1.5.0.tar.gz -C /opt/ && cd /opt/panjia-console-1.5.0

# 2. 安全传输 jks（密码走独立渠道，永远不进安装包、不进 Git）
mkdir -p /opt/panjia-console/script/keys
# scp / 安全即时通讯加密通道 上传 panjia-license.jks
chmod 600 /opt/panjia-console/script/keys/panjia-license.jks

# 3. 配置 .env（数据库密码、JKS_PASSWORD 等，权限 600）
cp .env.example .env && vim .env && chmod 600 .env

# 4. 启动（Flyway 自动建库迁移 auth/customer 两 schema）
docker compose up -d

# 5. 观察启动日志确认 Flyway 迁移完成、三接口注册
docker compose logs -f console
```

### 4.3 Nginx 关键配置（部署强制检查项，详设 §6.0）

```nginx
# 鉴权面（公网，限流）
location /api/auth/ {
    limit_req zone=auth burst=20 nodelay;
    proxy_pass http://127.0.0.1:8080;
}

# 管理面（仅内网/VPN/我家宽 IP 白名单）
location /api/panjia/ {
    allow 10.0.0.0/8;
    allow 192.168.0.0/16;
    allow <我家/办公出口IP>/32;   # ← 部署时填写
    deny all;
    proxy_pass http://127.0.0.1:8080;
}
```

### 4.4 上线验证（A 线验收）

```bash
# 1. 鉴权面公网可达
curl -s https://license.panjia.com/api/auth/check -X POST -H 'Content-Type: application/json' -d '{}'
#    → 应返回业务错误（BAD_REQUEST），证明路由通

# 2. 管理面公网必须被拒
curl -s -o /dev/null -w '%{http_code}\n' https://license.panjia.com/api/panjia/customer
#    → 必须 403/444。返回 200 = 重大安全事故，立即整改

# 3. jks 权限
stat -c '%a' /opt/panjia-console/script/keys/panjia-license.jks   # 必须 600

# 4. 管理后台（VPN/白名单内）可登录看板、签发授权码
```

- 数据库 + jks **每日备份**（授权服务备份模块/`pg_dump` 脚本），jks 备份与密码分开存放；
- 监控：心跳缺失告警（T4 每 10 分钟扫描）推送给我方；

## 五、B 线：panjia-deploy 一键部署工具（客户机器）

### 5.1 工具定位

`panjia-deploy` = **一个 bash 脚本 + 离线安装包**，随发版一起产出。选型理由：

| 候选方案 | 结论 |
|---|---|
| **bash + Docker Compose + 离线镜像 tar（采用）** | 零依赖、离线可装、单文件可审计；中小客户 Linux 通吃 |
| Ansible / K8s / Helm | ❌ 过度设计，客户机各不相同，还要装控制端 |
| 图形化安装器 | ❌ 客户不自己装，我方远程 SSH 执行，CLI 足够 |

支持子命令：`install`（首次部署）、`upgrade`（升级）、`status`（体检）、`backup`（备份）、`restore`（恢复）、`doctor`（诊断）。

### 5.2 install 一键流程（内部步骤）

```
panjia-deploy install --auth-code PJ-XXXX-XXXX --version 2.5.0
  ├─ ① 环境预检：OS 版本 / 2C4G+ / 磁盘 40G+ / 端口占用
  ├─ ② Docker 安装（离线包内置 docker rpm/deb + docker compose plugin，无外网也可装）
  ├─ ③ machine-id 校验：/etc/machine-id 必须存在，缺失即报错退出（不静默降级）
  ├─ ④ docker load images.tar 导入全部镜像
  ├─ ⑤ 生成 .env（随机强密码：PG/Redis/MinIO，落盘 600，留档我方密码库）
  ├─ ⑥ 创建 panjia-license 数据卷；docker compose up -d（健康检查通过才继续）
  ├─ ⑦ 注入 PANJIA_AUTH_CODE，等待自动激活
  ├─ ⑧ 验收：容器健康 / 授权服务器连通 / 激活成功（token 已落盘）
  └─ ⑨ 输出《客户交付单》：访问地址、管理员账号、备份策略
```

### 5.3 客户云服务器标准部署（完整操作，约 15 分钟）

```bash
# ===== 0. 我方本机：上传离线包（scp 或 oss 中转）=====
scp panjia-app_2.5.0.tar.gz root@<客户ECS公网IP>:/root/

# ===== 1. SSH 登录客户服务器 =====
ssh root@<客户ECS公网IP>

# ===== 2. 解压并执行一键部署 =====
tar xzf /root/panjia-app_2.5.0.tar.gz -C /opt/
cd /opt/panjia-app-2.5.0
./panjia-deploy.sh install --auth-code PJ-XXXX-XXXX

# ===== 3. 观察输出，全部绿灯即完成 =====
# ===== 4. 交付验收（§5.5）=====
```

> 指纹要点：挂载 `/etc/machine-id:ro` + `panjia-license` 数据卷（instanceId/token/monotonic）。**重启容器、重建容器、升配降配均不影响授权**；只有换服务器/删数据卷才需换机流程。

### 5.4 低配机器调整（2C2G）

`docker-compose-prod.yml` 各服务内存限额按比例下调：admin `-Xmx1g`、postgres 1G、redis 512M、minio 512M。

- [ ] `.env` 密码已录入我方密码库；ECS root 密码已录入
- [ ] 数据卷已规划到云盘/快照策略（见 §八）

## 六、Windows 电脑场景（客户有 Windows 电脑）

### 6.1 定位与红线

- **红线**：Windows 宿主机**不作为生产环境**（详设 §6.4：machine-id 校验不支持时明确报错，不静默降级）。
- **允许**：体验/演示。两条路：

### 6.2 玩法一（推荐）：Windows 只当"浏览器访问端"

Windows 电脑装什么都不用装，浏览器访问客户云服务器地址即可。**销售演示也用这个**：我方演示环境跑在一台演示 ECS 上。

### 6.3 玩法二：Windows 本机体验（Docker Desktop + WSL2）

```powershell
# 管理员 PowerShell
wsl --install -d Ubuntu-22.04
# 安装 Docker Desktop（启用 WSL2 集成）
# WSL Ubuntu 内执行与 §5.3 相同流程（WSL 内 /etc/machine-id 存在，可正常部署）
wsl -d Ubuntu-22.04
cd /mnt/c/Users/<客户用户名>/Downloads/panjia-app-2.5.0
./panjia-deploy.sh install --auth-code PJ-TEST-XXXX
```

**必须告知客户的局限**（也是我们引导转云的理由）：
1. 电脑关机系统就停；数据在 WSL 虚拟磁盘里，误删即丢；
2. WSL 重装/重置后 `machine-id` 变化 → 触发换机，需我们重新处理；
3. 演示授权码到期自动失效。

### 6.4 Windows 场景授权口径

体验部署一律使用 **TRIAL/TEST 授权码**（短有效期 + 可手动立即失效），绝不给正式 PRODUCTION 码。

## 九、故障速查表

| 现象 | 首查 | 常见原因 |
|---|---|---|
| 容器反复重启 | `docker compose logs panjia-admin` | 内存不足 / 数据库未就绪 / License 启动校验失败 |
| 启动报 "machine-id 未挂载" | `docker inspect` 看 volumes | compose 挂载被改动 → 修正后重启 |
| 激活失败 | 授权码是否已消费 / `end_date` 是否有效 / 服务器 443 连通性 | authCode 一次性，重复用需重新签发 |
| 心跳超时告警 | 客户机出站 443 是否通（`curl https://license.panjia.com`） | 安全组出站限制 / SSL 中间人代理拦截（须加解密白名单） |
| 算薪结果系统性偏差 | 本地告警日志 `trigger` 字段 | **受限模式生效**（T1/T2/T3）→ 排查授权状态，勿当业务 bug |
| 升级后 `/check` 拒绝 | token 内 `versionRange` | 新版本号越界 → 后台调授权版本范围 |

## 附录 A：panjia-deploy.sh 骨架（实现要点）

```bash
#!/usr/bin/env bash
set -euo pipefail
# 子命令: install | upgrade | status | backup | restore | doctor

cmd_install() {
  precheck_os_and_resources        # OS/2C4G/磁盘/端口
  install_docker_offline           # 离线装 docker + compose plugin
  check_machine_id                 # /etc/machine-id 缺失即 fail，绝不静默降级
  docker load -i images.tar
  gen_env_with_random_passwords    # openssl rand，落盘 .env (600)，回显留档
  compose_up_and_wait_healthy      # depends_on healthcheck 全绿
  wait_license_activated           # 轮询 /data/panjia-license/.panjia_token 出现
  print_delivery_note              # 访问地址/账号/备份策略
}

cmd_upgrade() {
  do_backup_first                  # 铁律：先备份
  docker load -i images-new.tar
  sed -i 's/panjia\/admin:.*/panjia\/admin:NEW_TAG/' docker-compose-prod.yml
  compose_up_and_wait_healthy
  smoke_test_calculate             # 冒烟：导入→算薪→导出
}
```

实现约束：**幂等**（重复执行不破坏数据卷）、**失败即停**（不产生半部署状态）、所有密码 `openssl rand -base64 24` 现场生成、`PANJIA_AUTH_CODE` 只在 install 时注入（激活后从 .env 移除亦可，token 已持久化）。
