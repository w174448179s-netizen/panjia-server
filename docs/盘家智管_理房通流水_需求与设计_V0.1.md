# 盘家智管 · 理房通流水接入（部门收支）需求与设计 V0.2

> 状态：已基于 5 份真实流水样例复核，待业务确认剩余口径
> 日期：2026-11-21
> 关联模块：部门收支（panjia-ledger）、实收业绩（panjia-received）、数据导入（panjia-import）

---

## 1. 背景与名词

财务需要按门店管理理房通**对公账户流水**，并接入三类信息：

1. **收入对账**：流水收入与系统内「实收业绩」按合同匹配对比；
2. **去化模式入账**：流水「交易备注 = 售前房屋美化」的收入，自动形成实收业绩；
3. **支出归集**：流水支出分类后进入「部门收支分析表」。

| 名称 | 含义 | 系统现状 |
|---|---|---|
| **理房通到账明细表** | 贝壳导出，含角色人、业绩比例、业务类型、当月实收业绩 | 已存在，`KE_RECEIVED`，落 `pj_received_contract/detail` |
| **理房通流水表** | 本次新增，对公账户**账户明细**（收入、支出、提现、余额） | 尚未接入 |

> 两者不是同一份文件。本需求只新增流水表，不改现有到账明细导入。

### 2.2 关键结论

1. **文件可能包含多个月，也可能只包含部分月份**：本次样例覆盖约 12~13 个月，但不能假定每次导出都是全量；文件名不含月份，只有「前缀_账户明细_导出编号」。
2. **文件名判定可行**：文件名以账户前缀开头，规则可用「前缀精确匹配文件名开头」。
3. **「提现」不是业务支出**：是从理房通账户转到公司银行账户的资金划转，应排除在收入/支出统计之外。
4. **「支出」里混有两类**：
   - 真实费用：400话务费、电子章、平台代招、品质保证金；
   - 业绩冲减：合同解约、业绩变更、退款、退款追回、补足手续费、应付账单-中介费、佣金调账等，本质是负收入，应冲减实收业绩。
5. **「业务系统订单号」列全空**：收入匹配必须用「合同编号」。
6. **收入匹配已被数据验证**：以 2026-08 花照云庭店为例，流水按「合同编号 + 动账月」汇总「收入 + 支出（排除提现）」，与贝壳到账明细的「合同当月到账金额」**65 个合同全部一致（0 差异）**。
7. **售前房屋美化不在贝壳到账明细中**：必须由流水补入实收业绩。

## 4. 映射配置：建议独立菜单

建议在「部门收支」下新增「理房通账户配置」菜单 + 独立表，不使用 `sys_config` 存 JSON。

理由：需要多字段、前缀唯一性校验、换账户历史（生效/失效日期），参数管理的 JSON 方案无法可靠支持。

```sql
CREATE TABLE pj_lf_account (
    id             BIGINT PRIMARY KEY,
    dept_id        BIGINT NOT NULL,
    file_prefix    VARCHAR(200) NOT NULL,
    account_name   VARCHAR(200) NOT NULL,
    bank_name      VARCHAR(100),
    account_no     VARCHAR(64),
    effective_date DATE,
    expire_date    DATE,
    status         CHAR(1) DEFAULT '0',
    remark         VARCHAR(500),
    create_by      BIGINT,
    create_time    TIMESTAMP,
    update_time    TIMESTAMP
);

CREATE UNIQUE INDEX uk_lf_account_prefix
    ON pj_lf_account (LOWER(file_prefix))
    WHERE status = '0';
```

换账户：旧行停用并填失效日期，新增一行填生效日期；按动账时间落在哪个区间判定账户名称。

## 5. 导入设计

### 5.1 导入口径与文件名判定

**导入按门店进行**（门店 = sys_dept 中的门店节点，不是组）。

1. 界面选择门店（必选）；
2. 取文件名（不含路径），忽略大小写；
3. 文件名以配置的 `file_prefix` 开头（或包含）即命中；
4. 命中唯一 → 得到门店 + 账户名称，并与所选门店校验一致，防止传错；
5. 命中多个 / 未命中 → 拒绝导入，提示先配置或前缀冲突。

样例均符合：`前缀_账户明细_导出编号.xlsx`。

### 5.2 归属月

- 文件可能跨多个月，**归属月不由文件名决定**，按每行「动账时间」归入 `YYYY-MM`；
- 查询、匹配、报表均按动账月过滤；
- 一个文件可包含多个月，也可能只包含个别月份。

### 5.3 重复导入规则（按记账流水号幂等）

文件不保证全量，可能只包含部分月份，因此**不能按批次或月份整批替换**。以「**账户（门店）+ 记账流水号**」作为幂等键：

1. 系统已存在该记账流水号 → **覆盖更新**该行（金额、备注、业务描述、余额等以本次文件为准）；
2. 系统不存在 → **新增**该行；
3. 本次文件里没有的历史流水 → **保留不动**，不删除；
4. 已存在行被覆盖后，重新执行分类、费用归集，并自动重新匹配该行涉及的合同；
5. 导入批次仅作为操作日志保留，不参与数据过滤。

**兜底去重匹配**（防止理房通导出规则变化导致记账流水号变化）：

1. 先按 `(dept_id, 记账流水号)` 匹配；
2. 未命中时，再按 `(dept_id, 动账时间, 金额, 合同编号)` 匹配；
3. 兜底命中唯一一行 → 覆盖更新，同时记录流水号变更；
4. 兜底命中多行 → 不自动合并，标记 `DUPLICATE_CANDIDATE`，转人工处理。

这样既能补导缺失月份，也不会因为某次导出少了几个月而清空历史。

### 5.4 校验

- 记账流水号在账户内唯一（样例中唯一）；
- 兜底键 `(动账时间, 金额, 合同编号)` 在同一账户内不应重复；重复时告警并转人工，不自动合并；
- 金额解析：去掉 `+`，保留负数；
- 收支类型仅允许 收入 / 支出 / 提现；
- 提现行照常入库，但标记 `NON_BUSINESS`，不参与匹配和报表；
- 账户余额连续性校验（可选告警）：上一行余额 + 本行金额 = 本行余额；
- 整批校验通过才落库，避免半批数据。

## 7. 收入与实收业绩匹配

### 7.1 匹配口径（已确认）

**两边都按合同汇总，不按月拆开；正负全部计入；包括实收调整单。**

```
流水侧（按合同编号汇总，不限门店、不限动账月）：
  流水合同净额 = Σ收入 + Σ支出
  范围：category 为 BUSINESS / REVERSAL 的行
  排除：WITHDRAW（提现）、FEE（话务费/电子章/平台代招/品质保证金）、NON_BUSINESS

实收侧（按合同编号汇总，不限门店、不限归属月）：
  实收合同金额 = Σ pj_received_detail.performance_amount
                 （detail_status = ACTIVE，已含退款/红冲产生的负数行）
              + Σ 未执行的实收调整单影响额
                 （status = SUBMITTED 且 execute_time 为空：
                  target_amount - original_amount）

比对：
  差异 = 流水合同净额 - 实收合同金额
  容差 0.01 元
```

说明：

1. **不看审批状态**：实收审批单、在途调整单先全部参与比对，报表展示状态，避免因流程未走完产生假差异。
2. **调整单不重复计算**：已执行（`execute_time` 有值）的调整单，其效果已通过明细红冲/新增体现在 `pj_received_detail` 中，不再叠加；只有未执行的在途调整单才按 `target_amount - original_amount` 预估计入。
3. **合同解约、业绩变更、退款、退款追回、补足手续费、应付账单、佣金调账**等负流水，按合同编号自动归并到同一合同，与正流水一起汇总。
4. 被拒绝的实收调整单不计入金额，但在差异报表中展示状态。
5. 2026-08 花照云庭店按月验证时 65 个合同全部一致；改为合同全周期汇总后口径更宽，可覆盖跨月退款。

### 7.2 分类规则（收入侧）

| 分类 | 判定 | 处理 |
|---|---|---|
| BUSINESS | 收入 + 合同编号有效 + 对应佣金/服务费分账 | 参与匹配 |
| REVERSAL | 支出 + 合同解约/业绩变更/退款/退款追回/补足手续费/应付账单/佣金调账 | 负金额参与匹配 |
| WITHDRAW | 收支类型 = 提现 | 排除 |
| FEE | 话务费、电子章、平台代招、品质保证金 | 不进收入匹配，按第 9 节处理 |
| NON_BUSINESS | 无有效合同编号、非佣金类 | 排除，标记 |

### 7.3 匹配状态

`MATCHED` / `AMOUNT_DIFF` / `NOT_FOUND` / `MULTI_MATCH` / `PENDING_SIGN_ROLE`（去化待补新签角色人）/ `MANUAL_CONFIRMED`（多匹配人工指定）/ `IGNORED` / `NON_BUSINESS`

### 7.4 差异报表（必须提供）

匹配结果单独提供「理房通对账差异」报表：

**汇总表**（按合同一行）：

| 列 | 说明 |
|---|---|
| 门店 | 流水所属门店 |
| 合同编号 | 匹配主键 |
| 流水笔数 / 流水净额 | 收入、支出、冲减合计 |
| 实收明细金额 / 在途调整金额 / 实收合计 | 实收侧构成（已执行调整已含在明细中，不重复加） |
| 差异金额 | 流水净额 - 实收合计 |
| 匹配状态 | 一致 / 金额差异 / 未找到 / 多匹配 / 人工确认 / 忽略 |
| 审批状态 | 实收审批单、调整单状态汇总 |
| 最近动账时间 | 便于定位 |

**明细下钻**（点击合同展开）：

- 流水侧：动账时间、收支类型、交易类型、金额、业务描述、交易备注、记账流水号、批次；
- 实收侧：实收合同、角色人明细（含负数行）、实收审批单及状态、调整单号/原因/状态/影响金额。

筛选条件：门店、合同编号、匹配状态、差异金额区间、动账时间范围。
支持导出。

### 7.5 匹配触发方式（已确认）

**导入一次，全量匹配一次，不需要用户手工点击。**

1. 导入成功后，自动对本次文件中出现的**所有合同号**执行匹配；
2. 对每个合同号：查询该合同的**全部理房通流水**（不限门店、不限月份），与系统中该合同的**全部实收**（不限归属月，含调整单）汇总比对；
3. 一个实收合同可能由多个组/门店共同完成，因此不做单店、单月局部匹配，始终按合同全量汇总；
4. 下次再导入，自动重算本次涉及的合同，结果覆盖上一次；
5. 去化模式也在导入后自动处理：识别美化收入 → 找新签角色人 → 分摊 → 生成实收 → 提交审批；未找到新签角色人则挂起 `PENDING_SIGN_ROLE`；
6. 匹配按合同维度加锁，避免并发重复计算；完成后返回本次匹配的合同数及结果统计。

### 7.6 已确认

- 导入即自动匹配，不需要手工点击；
- 按合同号汇总**全部流水**与**全部实收**，不限门店、不限月份，正负都计入；
- 无论审批状态，先全部比对，再展示审批状态；
- 合同金额按合同汇总，正负都计入，两边一致；
- 实收调整单也按合同汇总：已执行的已含在明细中，在途的单独预估计入；
- 提供差异报表，并可查看差异明细。

### 7.7 每日定时匹配（已确认）

除导入后自动匹配外，每天凌晨 00:00 再按合同全量重跑一次，用于补触发新签导入、历史流水变更等场景。

1. 调度开关与执行时间在「系统管理 → 参数设置」维护，不写死在 `application.yml`：
   - `panjia.lf.match.schedule.enabled`：默认 `true`，关闭后定时任务跳过（导入后自动匹配不受影响）；
   - `panjia.lf.match.schedule.cron`：默认 `0 0 0 * * ?`，按 `Asia/Shanghai` 执行，非法表达式回退默认值。
2. 每次触发时重新读取参数，修改后无需重启；
3. 任务按 200 个合同分批执行，每批独立事务，避免长事务；
4. 多实例部署时通过 Redis 分布式锁保证只有一个实例执行；
5. 日志输出本次统计：合同数、一致、差异、未找到、待补角色人。

## 8. 去化模式（售前房屋美化）

### 8.1 样例事实

| 字段 | 值 |
|---|---|
| 收支类型 | 收入 |
| 交易类型 | 收款 |
| 业务描述 | `贝壳找房-二手买卖-房屋美化-标准` |
| 交易备注 | `售前房屋美化` |
| 对方户名 | 成都方源房地产咨询服务有限公司 |
| 合同编号 | 10 位数字，如 `1792190089` |
| 房屋编号 | 空 |
| 业务系统订单号 | 空 |

样例分布：花照云庭 2 笔、龙湖 2 笔、锦城名都 1 笔、西派少城 5 笔、长庆 0 笔；单笔 2020.75 / 2040.96 / 3061.44。

### 8.2 业务链路（已确认）

去化模式在新签导入时已有新签业绩（`pj_perf_fact`，`fact_type = PERF_EXPECT`，`biz_type = 去化模式`），包含合同号、角色人和分摊比例；但贝壳实收导入没有这部分实收，必须由理房通流水补入。

处理流程：

1. **识别**：导入后自动筛出 `业务描述` 含「房屋美化」或 `交易备注` = 「售前房屋美化」的收入行；
2. **找新签**：按 `合同编号` 匹配 `PERF_EXPECT` 的去化模式合同（合同号未命中时用订单号兜底），只取 `fact_status = ACTIVE`；
3. **按动账月汇总**：同一合同同一动账月的多笔美化收入合并为一笔实收；
4. **匹配角色人**：取该合同新签业绩的全部角色人；
5. **金额分摊**：
   - 分摊权重 = 该角色新签业绩金额 ÷ 合同新签业绩合计；
   - 角色金额缺失时，退化为 `share_ratio` 归一化；
   - 分摊尾差调整到金额最大的角色，保证角色合计 = 流水金额；
6. **落实收**：
   - 实收合同：`biz_type = 去化模式`，`contract_no` / `order_no` 取新签合同，`period = 动账月`，`source_type = LF_STATEMENT`，`contract_amount = 新签合同金额`，`period_total_received = 本笔流水金额`；
   - 实收明细：每个角色人一行，`employee_id / role_type / role_name / share_ratio` 取新签，`performance_amount = 分摊金额`；
   - 幂等键：`合同号 + 角色人 + 归属月 + LF_STATEMENT`，重复导入覆盖更新；
7. **自动审批**：复用现有 `autoCreateForReceivedBatch` 分流逻辑，与贝壳实收保持一致；
8. **负数流水**：美化退款/冲减同样按角色比例分摊为负数实收，走负数审批分支；
9. 去化收入不参与贝壳到账明细匹配（贝壳文件中没有该业务）；
10. 若流水先导入、新签后导入：新签导入成功后，自动对相关合同补触发一次流水匹配，补生成去化实收，不需要用户再手工操作。

### 8.3 自动审批规则

**去化模式按「合同全周期、同角色人」比较**（回款晚于新签月属正常，不按同期间）：

- 汇总该合同全部新签应收：`PERF_EXPECT`、`ACTIVE`、全周期；
- 汇总该合同全部去化实收：全周期，含本笔；
- 按角色人比较累计值：
  - 累计实收 ≥ 累计新签应收 → `APPROVED` 直建（自动通过）；
  - 累计实收 < 累计新签应收 → `SUBMITTED` 转人工审批；
  - 累计实收为负且比负应收更负 → `APPROVED`；否则转人工；
- 整单从严：同一订单下任一人需人工，整单转人工；
- 已审批、已结佣、已封账的数据不因再次导入被覆盖，只提示差异；
- 普通实收（贝壳）仍沿用现有 `autoCreateForReceivedBatch` 的同期间逻辑，本次不改。

### 8.4 去化专项口径

**已确认：**

- 回款月与新签月不一致属正常（常见次月到账），自动审批按**合同全周期**比较；
- 门店与公司名称按用户提供的对应关系，不再作为问题；
- 审批通过后流水金额变化，沿用「已审数据不动、只提示差异」。

**按建议默认执行（如有异议再调整）：**

- 同一合同多次回款：按动账月分期生成实收（每月一条），不累计成一笔；
- 分摊权重：以新签业绩金额占比为准，角色金额缺失时用 `share_ratio` 归一化；
- 流水合同号在新签中找不到：不新建合同，标记 `PENDING_SIGN_ROLE` 挂起，等新签导入后自动补算。

## 9. 支出归集到部门收支分析表

### 9.1 样例中的支出分类

| 业务描述 | 交易备注 | 对方户名 | 分类 | 科目处理 |
|---|---|---|---|---|
| 400话务费 | 话务费转账 | 贝壳找房科技 | 真实费用 | 按系统现有科目映射 |
| 电子章 | 电子章收费 | 贝壳找房科技 | 真实费用 | 按系统现有科目映射 |
| 平台代招 | 空 | 北京小贝优服 / 安徽东杰人力 | 真实费用 | **已在系统中配置科目** |
| 品质保证金 | 品质保证金 | 贝壳找房科技 | 真实费用 | **已在系统中配置科目** |
| 租赁/二手/省心租/家装荐客 | 合同解约、业绩变更、退款、退款追回、补足手续费、应付账单-中介费、佣金调账 | 本方公司 | 业绩冲减 | 不进费用，冲减收入 |
| 商户门户 | 提现 | 本方公司 | 资金划转 | 排除 |

> 科目不在代码里写死，统一以「收支科目配置」中已启用的科目为准。

### 9.2 归集方式建议

不直接写 `pj_ledger_entry`，而是在 `LedgerReportService` 增加「理房通流水费用」数据源：

- 按 `period + dept + subject_id` 汇总 `category = FEE` 的支出；
- 直接读取按记账流水号 upsert 后的最新行；
- 重复导入时同一条流水覆盖更新，不会重复累计；
- 避免与手工录入重复。

**科目匹配顺序**：

1. 按维护的「业务描述 / 交易备注 → 收支科目」规则匹配；
2. 规则未命中时，按科目名称精确匹配；
3. 仍未命中 → `subject_id` 留空，标记 `PENDING_SUBJECT`，**不静默归入「其他」**；
4. 导入结果中返回未匹配清单（业务描述、交易备注、笔数、金额），并提示：
   「以下支出在收支科目中不存在，请先在『收支科目配置』新增或启用科目：平台代招 2 笔 / 品质保证金 1 笔」；
5. 新增科目后，可在流水页面执行「重新归集」，或下次导入时自动重算。

### 9.3 已确认

- 「平台代招」「品质保证金」等科目已在系统中配置好，直接映射，不再新增；
- 流水收入**不进入**部门收支分析表，避免与实收佣金重复；
- 费用类支出未匹配到科目时，导入成功后提示用户新增科目，不阻断导入。

### 9.4 费用划归规则（已确认）

费用流水先归属到**门店**，再决定落到哪个组：

| 门店下组数 | 处理 |
|---|---|
| 只有 1 个组 | 导入时**自动划归**到该组，`alloc_status = AUTO` |
| 有多个组 | 导入后进入**待划归**，`alloc_status = PENDING`，由用户手工划归到组 |

手工划归：

- 在流水列表提供「费用划归」入口，支持单条或批量选择支出行，指定归属组；
- **整笔划归一个组，不做金额拆分**；
- 划归后 `alloc_status = MANUAL`，记录划归人、划归时间；
- 未划归的支出在部门收支报表中进入「未分配/待划归」列，并高亮提示；
- 划归完成后自动进入对应组列；
- 重复导入时，已手工划归的行**保留原划归结果**，不因导入被重置（仅金额、备注等流水字段更新）。
