## 三、T-INF-01：仓库初始化与命名域规约

### 3.1 仓库模型

```
upstream  = dromara/RuoYi-Vue-Plus（官方仓库，只读 remote）
origin    = 盘家智管私有仓库（产品主线）
            ├── main                产品主线（始终可发布）
            ├── upgrade/ruoyi-{ver} 底座升级测试分支（用完即删）
```

### 3.5 命名域铁律

| 规则 | 说明 |
|------|------|
| 底座内核保留 `ruoyi-*` 原名 | 官方原目录，不新增/不改名/不挪动 |
| 盘家业务域全部 `panjia-*` 前缀 | `panjia-modules/` 顶层聚合 |
| 底座包名 `org.dromara.**` | 零修改 |
| 盘家包名 `com.panjia.**` | 全部自建代码 |
| `ruoyi-*` 目录不得出现 `com.panjia` 包 | CI 强制校验 |
| 盘家模块不得反向依赖底座 | 仅允许 `panjia-*` → `ruoyi-*`，反过来禁止 |

## 四、T-INF-02：底座升级治理机制

### 4.1 仓库配置

```bash
git clone https://gitee.com/dromara/RuoYi-Vue-Plus.git --branch v6.0.0 panjia-server
cd panjia-server

git remote rename origin upstream
git remote add origin git@github.com:w174448179s-netizen/panjia-server.git

git switch -c main

git push -u origin main --force

# 后续同步 upstream
git fetch upstream
git checkout -b upgrade/ruoyi-6.0.1 upstream/v6.0.1
# 在升级分支上解决冲突、验证后合入 main
```

### 4.2 Flyway 基线建立

**步骤：**

1. 从官方 `script/sql/postgres/` 目录获取全量初始化脚本
2. 校验脚本在 PostgreSQL 15 上可执行
3. 合并为单一基线脚本，命名 `V1__ruoyi_baseline.sql`
4. 在 `ruoyi-admin` 的 `pom.xml` 中引入 Flyway 依赖：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

5. 配置 `application.yml`：

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    # 基线版本 V1 已存在，后续脚本从 V000001 开始
```

### 4.3 Flyway 版本号段位

| 段位 | 范围 | 用途 | 示例 |
|------|------|------|------|
| V1 | 基线 | 官方 PostgreSQL 全量脚本 | `V1__ruoyi_baseline.sql` |
| `00xxxx` | 底座域 | 底座升级增量 SQL（PG 方言转译） | `V000001__ruoyi_upgrade_6.0.1.sql` |
| `10xxxx` | 薪酬业务域 | `panjia-salary` 业务表 | `V100001__salary_employee.sql` |
| `20xxxx` | 平台域 | license/backup/customer/im | `V200001__license_key.sql` |
| `30xxxx` | 预留 | 未来扩展 | — |

### 4.4 底座改动清单模板

```markdown
# 底座改动清单

| 序号 | 文件路径 | 改动类型 | 改动原因 | 绕过方案评估 | 升级处理方式 | 登记日期 |
|------|---------|---------|---------|-------------|-------------|---------|
| 1 | ruoyi-admin/.../SecurityConfig.java | 新增 Bean | License 校验注入 | 无法绕过，扩展点不可用 | 升级时 merge 后验证 | 2026-08-26 |
```

### 4.5 CI 双链路验证

CI 流水线必须执行以下两条验证链路：

**链路 1：全新初始化**
```
空 PostgreSQL 数据库
  → Flyway migrate（V1 → V000001 → ... → 最新）
  → 应用启动
  → 验证所有表存在
```

**链路 2：升级链路**
```
上一产品版本的数据库副本
  → Flyway migrate 到目标版本
  → 应用启动
  → 冒烟测试（登录 / 算薪主链路 / License 校验）
```

### 4.6 升级纪律

| 规则 | 说明 |
|------|------|
| 所有库变更走 Flyway | 禁止手工执行 SQL |
| 基线不可变 | V1 及已合入 main 的 migration 不可修改 |
| 缺陷修复用新增脚本 | 不修改旧 migration |
| 底座增量 SQL 须 PG 方言转译 | 官方脚本以 MySQL 为主，须人工转译 |
| 升级前自动全量备份 | 由 `panjia-backup` 模块触发 |
| 升级分支先行 | `upgrade/ruoyi-{ver}` 分支验证通过后才合入 main |
| 不追新 | 仅安全补丁（CVE）及时跟进，版本升级需明确收益 |

## 五、T-INF-07：API 版本化与横切关注点

### 5.1 API 版本化

**策略：URL 路径版本化**

| 项 | 设计 |
|----|------|
| 版本化方式 | `/api/v1/`、`/api/v2/` |
| 版本粒度 | 按模块独立版本号 |
| 兼容性 | 每个 API 版本向后兼容至少 2 个产品版本 |
| 废弃通知 | 响应头 `Deprecation: true` + `Sunset: <日期>` |
| 当前版本 | 全部接口使用 `/api/v1/` |

**路由配置示例：**

```java
@RestController
@RequestMapping("/api/v1/salary")
public class SalaryController {
    // 算薪相关接口
}

@RestController
@RequestMapping("/api/v1/employee")
public class EmployeeController {
    // 员工档案相关接口
}
```

### 5.2 全局雪花 ID

所有业务主键使用雪花 ID（RuoYi-Vue-Plus 6.x 默认集成），不暴露自增主键。为未来多租户演进提供主键无冲突保障。

```java
// MyBatis-Plus 实体基类
@Data
public class BaseEntity {
    @TableId(type = IdType.ASSIGN_ID)  // 雪花 ID
    private Long id;
}
```

### 5.3 Sa-Token 认证叠加 License 校验

**拦截链：**

```
请求 → Sa-Token 认证（登录态校验）
     → License 有效性校验（未授权拒绝，已到期降级只读）
     → 数据权限（门店维度 @DataPermission）
     → 业务逻辑
```

**License 校验切入点：**

```java
// 全局拦截器或 AOP 切面
@Component
public class LicenseInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, 
                             HttpServletResponse response, 
                             Object handler) {
        // 1. 校验 License 有效性
        // 2. 到期保护期：仅允许 GET 请求 + 导出操作
        // 3. 完全过期：拒绝所有请求
        return true;
    }
}
```

### 5.4 操作审计强制留痕

以下操作**必须**记录审计日志（写入 `sys_oper_log`）：

| 操作类型 | 记录内容 |
|---------|---------|
| 授权变更 | License 签发/吊销/更新，操作人，时间 |
| 工资锁定 | 锁定/解锁操作，工资批次号，操作人 |
| 备份恢复 | 恢复操作，备份文件标识，审批人，客户确认 |
| 业绩调整 | 调整单创建/审批，金额，关联结佣单号 |
| 员工变更 | 升职/降级/转店/离职操作，操作人，变更前后值 |

**实现方式：** 使用 `@Log` 注解（RuoYi 内置）或自定义 `@AuditLog` 注解 + AOP。

### 5.5 数据权限（门店维度）

**门店 = `sys_dept` 中的部门节点。** 使用 `@DataPermission` 注解实现行级数据隔离：

```java
// 店长只能查看本店数据
@GetMapping("/employees")
@DataPermission(deptAlias = "e.dept_id")
public List<Employee> listEmployees() {
    // 自动注入 dept_id 过滤条件
}
```

**角色权限映射：**

| 角色 | 数据范围 |
|------|---------|
| 经纪人 | 仅本人（`user_id = 当前用户`） |
| 店长 | 本店（`dept_id = 当前用户部门`） |
| 总监 / 算薪人员 | 全部（不过滤） |
| 人事 | 全部（考勤/积分管理），但无审批权限 |

### 5.6 Redisson 分布式锁与幂等

**适用场景：**

| 场景 | 锁 Key | 说明 |
|------|--------|------|
| 工资计算 | `salary:calc:{batchId}` | 防止同一批次重复计算 |
| 结佣审批 | `commission:approve:{commissionId}` | 防止并发审批 |
| 贝壳数据导入 | `commission:import:{batchNo}` | 防止同一文件重复导入 |
| 工资锁定 | `salary:lock:{batchId}` | 防止并发锁定 |

**幂等实现：**

```java
// 基于 Redis 的幂等注解
@Idempotent(key = "#batchId", expire = 3600)
public void calculateSalary(String batchId) {
    // 重复调用直接返回，不重复计算
}
```

幂等键有效期 24 小时，失败可重触发。

### 5.7 全局异常处理

```java
@RestControllerAdvice
public class PanjiaExceptionHandler {
    
    @ExceptionHandler(LicenseExpiredException.class)
    public Result licenseExpired() {
        // 返回 License 到期提示
    }
    
    @ExceptionHandler(DataPermissionException.class)

        // 返回无权限提示
    }
    
    @ExceptionHandler(DuplicateOperationException.class)

        // 幂等拦截，返回"操作已处理"
    }
}
```

## 六、CI 三条守卫规则

CI 流水线必须强制执行以下三条规则，任一失败则阻断构建：

### 守卫 1：目录边界

```
规则：ruoyi-* 目录中不得出现 com.panjia 包
实现：ArchUnit 测试
      classes().that().resideInAPackage("..ruoyi..")
              .should().notDependOnClassesThat()
              .resideInAPackage("com.panjia..")
```

### 守卫 2：交付包边界

```
规则：客户交付包构件清单不得包含 panjia-customer / ruoyi-gen / ruoyi-demo
实现：Maven Profile 打包后扫描 JAR 列表
```

### 守卫 3：底座改动白名单

```
规则：PR diff 不得触及底座目录（白名单 = 《底座改动清单》已登记项）
实现：CI 脚本检测 git diff 中 ruoyi-* 文件的变更
```
