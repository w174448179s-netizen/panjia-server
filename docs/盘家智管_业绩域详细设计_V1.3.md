## 一、定位与职责边界

### 1.1 一句话目标

> **以「合同」为业绩的唯一载体，把贝壳导入的每一条业绩记录原样记成"某合同下、某角色人、某口径、业绩多少钱"的业绩行；业绩行一经生成，只可冲销、不可改写。**

V4.3 确立的核心设计：**贝壳明细行不再作为独立操作对象**，只作为合同下的角色人业绩行存在。查看、调整、结佣、溯源**一律以合同为入口**。

### 1.2 数据来源：贝壳《经纪人业绩明细表》

以《2026-08-经纪人业绩明细表-246555.xlsx》为样本。文件含 **4 个 Sheet**：

| Sheet | 行数 | 列数 | 粒度 | 在本设计中承担的角色 |
|---|---|---|---|---|
| 导出说明 | 4 | 2 | — | 表格说明，**非数据表**，不导入 |
| 经纪人业绩汇总表 | 40（38 数据） | 46 | 人 × 加盟商 × 月 | 归档对账（12 个分业务业绩列 + **合同单量**唯一来源） |
| 经纪人合同明细表 | 159（157 数据） | 19 | 人 × 合同 | 归档对账（物业地址、过户/完结日期） |
| **经纪人业绩结算明细表** | **320（318 数据）** | **30** | **合同 × 角色人 × 费用项 × 角色类型** | **★ 业绩事实正源** |

#### 为什么选结算明细表作正源

三张数据表是**同一份数据的三种视图**。已按角色人汇总做过金额勾稽：

```
                  应收业绩        实收业绩
结算明细表      206,274.04      192,556.89
汇总表          206,274.04      192,556.89
合同明细表      206,274.04      192,556.89
逐人比对差异均为 0.00
```

任选其一都不会算错，选结算明细表的理由：

| 理由 | 说明 |
|---|---|
| 粒度最细 | 318 行，可精确定位到"某角色人在某合同的某费用项、以某角色身份贡献了多少业绩" |
| **唯一含费用项** | `费用项` 列（居间代理费 / 居间服务费 / 中介费 / 贷款服务费） |
| **唯一含角色类型** | `角色类型` 列，本样本 **16 种**取值 |
| **唯一含业绩比例** | `业绩比例` 列，本样本 **30 种**取值 |
| **唯一含到账与手续费** | `合同当月到账金额` / `合同当月支付手续费` / `合同总到账金额` / `合同总支付手续费` |
| **唯一含双口径** | `当月应收业绩` / `总应收业绩` / `当月实收业绩` / `总实收业绩` |

> **各 Sheet 全部导入归档**（满足追溯），但**只有结算明细表生成业绩事实**，否则同一笔业绩会被重复记录。各 Sheet 通过 `source_type` 区分（CR-7）。

#### 贝壳原文：表格说明

```
【经纪人业绩汇总表】  统计方式：按照经纪人汇总统计对应月份的应收业绩、实收业绩、合同量，
                    并按照各个业务分类汇总。
【经纪人合同明细表】  统计方式：按照经纪人展示对应月份结算业绩的合同，
                    以及经纪人在该合同产生的应收业绩、实收业绩汇总。
【经纪人业绩结算明细表】合同范围：对应月份产生应收业绩或实收业绩的全部合同。
                    数据来源：与 A+ 签约管理-业绩、A+ 签约管理-其他-应收业绩、
                    A+ 签约管理-其他-实收业绩信息一致。
```

#### 结算明细表列结构（30 列，6 组）

```
基本信息    结算月、业务类型、订单号、合同号、签约(成销)时间、过户日期(仅二手)、完结日期(仅二手)、
            物业地址、费用项
角色人信息  角色人系统号、角色人姓名、角色类型、业绩比例
应收业绩    ★当月应收业绩、总应收业绩
实收业绩    ★当月实收业绩、总实收业绩
合同到账金额 合同当月到账金额、合同总到账金额
支付手续费  合同当月支付手续费、合同总支付手续费
其他        备注、店组编码、店组名称、门店编码、门店名称、
            加盟商编码、加盟商mdmCode、加盟商名称、分账主体理房通商户号
```

#### 另两张表列结构

```
汇总表（46列）：结算月 | 角色人系统号 | 角色人姓名
              当月应收业绩 + 12 个分业务列（二手/租赁/新房/好赞/金融分润/家装荐客/
              新房装修/省心租/自如/公寓/其他）
              当月实收业绩 + 12 个分业务列（同上）
              业绩合同单量 + 12 个分业务列（★ 合同量指标的唯一来源）
              店组编码 | 店组名称 | 门店编码 | 门店名称 | 加盟商编码 | mdmCode | 名称

合同明细表（19列）：结算月 | 业务类型 | 订单号 | 合同号 | 物业地址 | 签约(成销)时间 |
              过户日期(仅二手) | 完结日期(仅二手) | 角色人系统号 | 角色人姓名 |
              应收业绩-合同汇总 | 实收业绩-合同汇总 | 店组/门店/加盟商各列
```

> **三张表均为双层表头**（第 1 行分组名如"基本信息/角色人信息/应收业绩"，第 2 行真实列名）。解析必须按 2 行表头处理，否则列名错位（CR-12）。

#### 从真实数据得到的十四条结论

| # | 观察 | 对设计的约束 |
|---|---|---|
| 1 | 本文件是**业绩口径**（应收/实收业绩），不是到账金额口径 | `amount` 取业绩值，到账金额另存备查 |
| 2 | 期间字段是**结算月**（`202608`），全表唯一值 | `period` = 结算月 |
| 3 | 业务类型本样本 **5 种**：租赁 200 / 二手买卖 56 / 租赁轻托管 33 / 轻托管推房 28 / **写字楼租赁** 1 | 枚举按 6 类建（补入 V4.3 的一手房），见 §2.6 |
| 4 | **角色类型 16 种** | `role_type` 按 16 种建 |
| 5 | **费用项 4 种**：居间代理费 196 / 居间服务费 87 / 中介费 33 / 贷款服务费 2 | 新增 `fee_item` 字段 |
| 6 | 业绩比例 **30 种取值** | 仅随原始行留存，不参与运算 |
| 7 | **无缺角色人**（318 行角色人系统号与姓名均非空） | 待对齐机制仅用于**员工匹配失败**（§4.5） |
| 8 | **实收可能大于应收**（35 行）；**应收=0 但实收>0**（34 行）；实收=0（52 行） | ★ 应收与实收是**两个独立指标**（§1.4） |
| 9 | 同一 合同+角色人+费用项+角色类型 才唯一（318 唯一） | `source_key` 必须含四要素（§3.1） |
| 10 | 三表金额完全勾稽（应收 206,274.04 / 实收 192,556.89，逐人差异 0.00） | 选最细的结算明细表作正源 |
| 11 | 店组（CD_15）与门店（CD_14）是两级，一门店下挂 A/B 组 | 归属以**门店**为口径，店组冗余备查 |
| 12 | 加盟商编码 ≠ mdmCode（花照天街 `CDYTA10037` vs `V2019008292`） | 两个编码都要存 |
| 13 | **★ 同一人可跨加盟商**（严文浩、李建华各挂 2 个加盟商），但**不跨门店** | 加盟商**不能**作归属维度；门店可靠 |
| 14 | **签约时间跨月**：269 行在 202608、39 行在 202607、10 行在 202606 | `period` 与 `business_date` 必须分离（§2.5） |

> ⚠ 金融分润、家装荐客、好赞、省心租等是**汇总表的业绩拆分维度**，**不是** `biz_type`。

#### 三处数据特征

| 特征 | 真实样本 | 处置 |
|---|---|---|
| **① 一合同多角色人多费用项** | 合同 `100015972443` / 王聪：考核陪签 1113.71、信息完备 668.22、房源录入人 2227.42… 共 7 行 | 印证已按角色拆分，系统**不做拆分**；每行独立成事实 |
| **② 过户/完结日期多为空** | 318 行中过户仅 4 行有值、完结仅 3 行有值 | 字段可空，不作必填校验 |
| **③ 合同当月到账金额可为空/0** | 部分行合同当月到账金额为 0（未到账） | 备查字段，不参与业绩金额计算 |

#### 双口径数据源

| 口径 | 贝壳字段 | 全表合计 |
|---|---|---|
| 新签业绩 `PERF_EXPECT` | `当月应收业绩` | **206,274.04** |
| 结佣业绩 `PERF_REAL` | `当月实收业绩` | **192,556.89** |
| （备查） | `合同当月到账金额` | 820,052.10（合同级重复计，勿直接用） |

> **一行业绩结算明细 → 生成 2 条业绩事实**（`PERF_EXPECT` 取当月应收业绩、`PERF_REAL` 取当月实收业绩）。本样本月度事实量 ≈ **636 条**（318 × 2）。

**★ 导入即归集为合同（V4.3 §9.2）**：系统按「订单号 / 合同号」将明细行自动聚合为合同，业绩事实挂到合同下成为**角色人业绩行**。聚合规则：

| 聚合键 | 适用业务类型 |
|---|---|
| **订单号** | 一手房（新盘）、房产金融、家装荐客 |
| **合同号** | 二手买卖、租赁、轻托管推房、去化模式、租赁轻托管、写字楼租赁 |

> 聚合键由 `biz_type` 决定，落库即确定，不可变更。

### 1.3 职责边界

| ✅ 负责 | ❌ 严禁 |
|---|---|
| 消费 `NormalizedRecord` / 手工录入 → 业务语义校验 | 提成金额 / 提点 / 保底计算（→ **payroll**） |
| 业绩口径分离（实收 / 应收）+ 原样记录金额 | 工资、社保、公积金、个税（→ **payroll**） |
| 归属补齐（员工、门店） | 收支凭证、台账（→ **ledger**） |
| 产出 `PerformanceFact` + 事实生命周期（生效 / 冲销重建） | 维护员工主数据（→ **people**，只读快照） |
| 业绩调整单（**合同维度**，审批 + 执行） | Excel 解析、raw 归档（→ **import**） |
| 期间封账 | 反向依赖 commission / payroll / ledger |

### 1.4 双口径（第一铁律）

| 口径 | fact_type | 贝壳字段 | 下游用途 |
|---|---|---|---|
| **结佣业绩（实收）** | `PERF_REAL` | `当月实收业绩` | 经纪人 / 店长个人 / 总监个人提成、招聘奖励基数 |
| **新签业绩（应收）** | `PERF_EXPECT` | `当月应收业绩` | 店长团队提成与保底、总监门店提成（跳点） |

**★ 二者是两个独立指标，不是"应收递减为实收"的转化关系。** 真实数据支撑：

| 现象 | 行数 | 说明 |
|---|---|---|
| 实收 > 应收 | 35 | 往月应收在本月补收，或本期实收高于当期应收 |
| 应收 = 0 但实收 > 0 | 34 | 往月产生的应收在本月实收，本月无新增应收 |
| 实收 = 0 | 52 | 已签约未实收 |
| **实收 < 0** | （退单时） | **红冲行**，合法事实，见 §2.8 |

> **含义**：结佣不是"把应收改成实收"，而是"**确认本月实收业绩可以进入工资**"。两个口径各自独立统计、独立冲销、独立使用，**绝不合并**，也**不允许用一个去推导另一个**。

### 1.5 事实 vs 规则（与 payroll 的分界）

| 类别 | 内容 | 归属 |
|---|---|---|
| **事实** | 业绩金额（贝壳原样值）、归属门店/店组、结算月、业务类型、费用项、角色类型、签约时间 | **performance** |
| **规则** | 提点（A0~A5 / 店长 70%）、团队提点 10%、保底 7000/8000、总监跳点 6%/7%/8%、底薪、社保成本、公积金、考勤、积分、个税、**新签折算系数** | **payroll** |

**三条硬分界：**

1. **社保成本不进本域**：`团队新签计薪业绩 = 门店全员新签合计 − 社保成本 − 店长个人`，社保成本归 payroll 规则，本域只出**门店全员合计**与**按人明细**。
2. **保底 / 跳点 / 提点 / 提成金额不进本域**：只回答"业绩是多少"。
3. **员工兼职、职级不进本域**：由 people 的 `salary_fact` 提供。

### 1.6 与结佣域的接口

| 方向 | 契约 | 说明 |
|---|---|---|
| perf → comm | `PerformanceFactCreatedEvent`（`factIds` / `factType`） | 新事实生成通知 |
| perf → comm | `PerformanceFactReversedEvent`（`factIds` / `reason`） | 事实冲销通知 |
| perf → comm | `CommissionPerformanceQueryPort` | 结佣域只读查询事实（**禁直连 `pj_perf_*` 表**） |
| perf → comm | `PeriodCloseQueryPort` | 结佣域查询期间是否封账（`isClosed` = 该月**终态关闭**，定义见 §4.7） |
| perf → 界面 | `ContractQueryPort` | 合同详情只读查询（含字段级可见性，见 §9） |

### 1.7 合同：业绩的唯一载体（V4.3 §9.3）

系统中一切业绩操作（**查看、调整、结佣、溯源**）都以**合同**为入口。

```
导入批次（贝壳 Excel，只读存档）
   └── 合同（订单号 / 合同号 唯一）
         ├── 合同主信息：业务类型、门店、归属月、应收总额、实收累计
         ├── 角色人业绩行 ×N
         │     ├── 导入原始行（只读，永不修改）
         │     ├── 调整行（人工发起，新增，形成版本链）
         │     ├── 红冲行（贝壳导入，新增，负数增量）
         │     └── 当期生效值 = 原始行 + 全部已生效调整行 + 全部红冲行
         ├── 结佣记录 ×N（合同 × 到账月）
         └── 调整 / 结佣操作日志（时间线）
```

**合同主信息：**

| 字段 | 说明 | 来源 |
|---|---|---|
| `contract_no` / `order_no` | 唯一标识，按 `biz_type` 取其一 | 贝壳导入 |
| `biz_type` | 业务类型（决定聚合键用订单号还是合同号） | 贝壳导入 |
| `dept_id` | 所属门店 = **取业绩占比最高角色人所属门店**，可人工修正 | 系统判定 + 人工 |
| `period` | 归属月（新签业绩计入哪个月），**可调整** | 贝壳「到账月」 |
| `first_period` | ★ **合同首次导入月**（首次建合同时写入，**永不修改**） | 判定新签计入月的基准，见 §2.12 |
| `expect_total` | 应收业绩总额（= 新签业绩），**合同级共享** | ∑ 角色人 `PERF_EXPECT` |
| `real_total` | 实收累计，**合同级共享** | ∑ 角色人 `PERF_REAL` |
| `settle_status` | `UNSETTLED` 未结佣 / `PARTIAL` 部分结佣 / `SETTLED` 已结清 | 系统计算 |

**角色人业绩行（= 业绩事实）：**

| 字段 | 说明 |
|---|---|
| 角色人（系统号 + 姓名 / `employee_id`） | 关联员工档案 |
| `role_type` 角色类型 | 客源成交人 / 房源维护人 / 房源录入人等（16 种） |
| `share_ratio` 业绩比例 | 该角色人在合同中的业绩占比（**仅随 `raw_payload` 留存，不参与运算**，见 §2.1） |
| `PERF_EXPECT` 应收业绩（新签） | 贝壳原样值 |
| `PERF_REAL` 结佣业绩 | 贝壳原样值 |
| 行状态 | `ACTIVE` 有效 / `REVERSED` 已作废 / `MANUAL` 人工补录 |
| `is_reversal` | ★ **是否红冲行**（退单负数行，见 §2.8） |
| `baseline_flag` | **是否基线数据**（上线补导的历史业绩，见 §4.9） |
| `orphan_flag` | **孤儿红冲**（匹配不到原单，见 §4.9） |
| `align_flag` / `align_source` | **实收对齐标记**（结佣差异触发，见 §2.11） |
| `is_reversal_adjust` | **业绩冲销行**（跨月调整产生，与退单红冲 `is_reversal` 区分，§2.10） |
| `new_sign_period` | ★ **新签计入月**（仅应收行）：= `period` 或 **NULL**，见 §2.12 |

> **合同级共享字段的红线**：`expect_total` / `real_total` / `settle_status` 对合同下**所有角色人一致**，不存在"某人的结佣实收"。

#### 新签链与结佣链同挂一份合同，但分开走

| | 新签链（应收业绩） | 结佣链（实收到账） |
|---|---|---|
| 生成时机 | 贝壳明细导入即生成 | 贝壳实收到账后**逐期**生成 |
| 粒度 | 合同 × 角色人（整单一次） | **合同 × 到账月**（整单结佣，角色人按比例分摊） |
| 算薪用途 | 店长团队提成 / 保底、总监门店提成 | 经纪人提成、店长/总监个人结佣提成 |
| 调整入口 | 合同详情 →「新签业绩」Tab | 合同详情 →「结佣记录」Tab |
| 红冲入口 | 贝壳导入自动生成（无审批） | 贝壳导入自动生成（无审批） |

## 二、业绩口径与数据处理原则

### 2.1 核心原则：零加工，只做原样记录

> **贝壳给什么就记什么，一行不落；系统不引入"业绩比例"、"折算系数"这类加工参数。**

贝壳每一行**已经是某个角色人以某种角色身份、在某费用项下分到的业绩金额**——拆分在贝壳侧完成，系统不需要、也不应该再乘一次业绩比例。

**已验证：贝壳确实用业绩比例把金额拆好了**

合同 `100015972443` / 王聪 / 居间服务费：

| 角色类型 | 业绩比例 | 当月应收业绩 | 当月实收业绩 |
|---|---|---|---|
| 考核陪签 | 0.05 | 1,113.71 | 1,113.69 |
| 信息完备 | 0.03 | 668.22 | 668.21 |
| 房源录入人 | 0.10 | 2,227.42 | 2,227.40 |
| 房源委托书人 | 0.02 | 445.47 | 445.46 |
| 房源实勘预约人 | 0.02 | 445.47 | 445.46 |
| 房源维护人 | 0.05 | 1,113.71 | 1,113.69 |
| 房源推广 | 0.05 | 1,113.71 | 1,113.69 |

> **验证**：1,113.71 × 2 = 2,227.42（0.10 恰为 0.05 的两倍），各角色金额与业绩比例严格对应 —— **贝壳已按"业绩比例 × 角色类型"完成拆分**。
> ⚠ 应收与实收存在**分位级差异**（如 1113.71 vs 1113.69），这是贝壳的两个独立统计值，系统**原样各记各的，不做任何推导**。

**因此表内不存在这些字段：**

| 不存在的字段 | 原因 |
|---|---|
| `share_ratio`（业绩比例） | 金额已拆好，再乘即重复计算；原始值随 `raw_payload` 留存 |
| `conversion_rate`（折算系数） | 属 payroll 规则层（§2.2） |
| `origin_amount`（原值） | 无加工则与业绩金额同值，冗余 |
| `discount_rate`（折扣系数） | 85 折改为直接存折后金额 |

> **一句话**：本域存的是"**贝壳说这笔业绩是多少**"；至于"按什么比例算提成、要不要打折"——那是 payroll 拿到事实之后的事。

#### 与 V4.3 §9.4「按业绩比例分摊」的关系

V4.3 §9.4 给出：`单角色人当期结佣业绩 = 当期实收金额 × 该角色人当期生效业绩比例`。本域**不按此公式重算**，理由与处置如下：

| 场景 | 处置 | 理由 |
|---|---|---|
| **贝壳有原始行**（常规） | 直接取贝壳「当月实收业绩」**原样落库** | 贝壳已按"比例 × 角色类型 × 费用项"拆好（上表已验证）。按单一比例重算会**丢掉费用项维度**，与 P-8 三表勾稽基准 192,556.89 对不上 |
| **人工补录角色人**（V4.3 §9.5） | 才用「当期实收 × 比例」算 | 此时无贝壳原值，只能用公式兜底 |
| **整单折扣（85折）** | 在行原值上按折扣生成调整行 | 折扣是新增事实，不是重算分摊 |

> **合同级实收累计 = ∑ 角色人行实收**（自下而上汇总），**不是**先有合同级数字再往下摊。这样既满足 V4.3「合同级共享、所有角色人一致」，又不破坏"原样落库、零加工"的铁律。
> ⚠ **多费用项场景**：同一角色人在同一合同下可跨 4 类费用项各贡献一笔（王聪 7 行），其"业绩比例"是**每行一个值**而非合同内单一值。故"合同实收 × 单一比例"在本样本中不成立，必须以行原值为准。

### 2.2 折算：真实业务，但属 payroll 规则层

| 口径 | 是否折算 | 系数 |
|---|---|---|
| 结佣业绩（实收）`PERF_REAL` | ❌ 不折算 | — |
| 新签业绩（应收）`PERF_EXPECT` | ✅ 折算 | 一手房 `0.94 × 0.96 = 0.9024`；其他业务 `0.96` |

依据 V4.3：§7.1 明确结佣金额"系统直接采用贝壳提供的结佣金额"；§5.2 明确新签业绩需折算为计薪业绩。二者针对不同口径，不冲突——**钱已实收时无需再折，应收尚未到账需扣增值税与运营费用**。

**折算在 payroll 规则层完成：**

- 本域原样记录贝壳金额，不折算、不存系数；
- payroll 取到业绩金额后按 `biz_type` 应用折算系数得到"计薪业绩"，再叠加提点 / 保底等规则算工资；
- 折算系数属**客户级规则**（与团队提点 10%、保底、总监跳点同类），归 payroll 配置。

> **为什么不在业绩域折**：一旦把系数固化进 Fact 行，客户调整系数时历史数据就被"钉死"；放在 payroll 规则层，规则变更只影响新算的工资，历史工资本来已锁定。

### 2.3 金额精度红线

| 规则 | 说明 |
|---|---|
| 存储 | 金额统一 `NUMERIC(18,2)`；**表内不存任何系数 / 比例字段** |
| Java | 统一 `BigDecimal`，**禁用 `double` / `float`**（CI 检查） |
| 取整 | 本域不做金额加工，无取整逻辑；`setScale` 只出现在 payroll |
| 汇总 | `SUM()` 直接对记录值求和（与人工 Excel 口径一致） |
| 分位差异 | 应收与实收的分位差（如 1113.71 / 1113.69）属贝壳原值，**原样保留，不做对齐** |

### 2.4 归属门店：取数时冻结 + 纠偏通道

**背景约束**：员工域 `fact_type` 8 类（`LEVEL / STATUS / SOCIAL / HOUSING / COMMERCIAL / DORMITORY / PARTTIME / MENTOR`）中**不含 `DEPT`**，`dept_id` 仅存在于 `pj_people_employee` 当前态 —— **部门不是时序数据，无法取历史时点值**。

处理方式：

1. `dept_id` = **消费取数时**员工所属门店，落地即冻结在 Fact 行上（结佣明细继承）；
   ★ **两级组织**：以**门店**（`CD_14_*`）为归属与汇总口径；**店组**（`CD_15_*`）编码 / 名称冗余落行备查，不参与汇总、不参与鉴权。
   ★ **加盟商不能作归属维度**：已验证同一人可跨加盟商（严文浩、李建华各挂 `C26030136497` 与 `CDYTA10037`），而**同一人不跨门店**（0 人跨门店）。故加盟商三列仅冗余落行。
2. 月中调店造成归属偏差 → 用**合同门店人工修正**纠偏；若结佣已锁定，走结佣 `DIFF` 差额调整单。
3. 可选增强见 CR-4（请 people 域为 `fact_type` 增加 `DEPT` 使部门可时序化）。

> 薪资相关事实（职级 / 社保 / 公积金等）**是**时序的（`salary_fact` 闭开区间），payroll 算薪取历史值不受影响；本问题**仅影响业绩归属门店**。

### 2.5 结算月 `period` 与业务发生日 `business_date`

两组日期语义不同，**不可混用**：

| 字段 | 贝壳来源 | 本域字段 | 取值 | 用途 |
|---|---|---|---|---|
| 结算月 | `结算月`（`202608`） | **`period`** | YYYY-MM | 业绩归属月、封账维度、结佣分组维度 |
| 签约时间 | `签约(成销)时间`（`2026-08-05 18:09:33`） | **`business_date`** | 日期部分 | 取员工时点快照 |

> **业绩归属月 = 结算月**（贝壳口径，与结佣和算薪周期一致）；**快照取数日 = 签约日**（反映成交发生时该员工的归属与状态）。

**已验证必须分离** —— 本样本 318 行的签约月分布：

| 签约月 | 行数 |
|---|---|
| 202608（与结算月同月） | 269 |
| 202607 | 39 |
| 202606 | 10 |

> 49 行（15%）签约月早于结算月。若用结算月取快照，这部分业绩会取到错误的时点状态。

**`business_date` 取值优先级：**

| 优先级 | 条件 | 取值 |
|---|---|---|
| ① | 有 `签约(成销)时间`（CR-2 落地后） | 该日期 |
| ② | 仅有 `过户日期` / `完结日期`（少量二手单有） | 该日期 |
| ③ | 以上皆无（兜底） | `LAST_DAY(period)` |

> 本样本 `签约(成销)时间` 覆盖全部 318 行，故 ① 即可满足，③ 仅为兜底。

### 2.7 原始数据全留存（追溯底线）

> **贝壳导出的原始行，一个字段都不能丢。** 业务人员核对业绩时必须能看到"贝壳原始那一行长什么样"。

#### 三层留存责任

| 层 | 归属 | 存什么 |
|---|---|---|
| ① 原始文件 | import 域 | 贝壳 Excel 原文件（含各 Sheet、表格说明），权威源，永久归档 |
| ①.5 归一化记录 | import | `NormalizedRecord.payload_json` 透传原始行全列 —— **★ 追溯链最脆弱一环，丢字段则全链路不可恢复**（CR-9） |

| ③ 结构化字段 | performance | 高频查询 / 有业务语义的列建成正式字段 |

> 本域 `raw_payload` 是**只读快照**，权威源仍是 import 域原始文件；本域永不修改，仅用于展示与核对。

### 2.8 退单与红冲（负数行）

> **业务现实**：已成交的单子可能**退一部分业绩**，也可能**整单退完**（退单）。退了单就要重新核算。

**贝壳的数据形态 = 导出负数行红冲**（非"原行消失"、非"原行金额改小"）。

| 场景 | 贝壳导出表现 | 本系统处置 |
|---|---|---|
| 部分退单 | 新增一行**负数**实收（如 `-3,000`） | 落为负数事实，与合同号关联 |
| 整单退完 | 新增一行**负数**实收（= 原金额取负，如 `-10,000`） | 同上 |

#### ★ 退单必须能回溯到原合同与原归属月

用户明确要求：**一个合同号的单子退单了，必须回溯到当月的这个合同的情况；回退的是当时的提成金额，而不是按最新提成比例来算。**

本域为此提供**回溯锚点**（金额计算在 payroll）：

| 锚点 | 作用 |
|---|---|
| `contract_id` | 红冲行与原行挂**同一合同**，据此找到该合同的全部历史业绩与结佣记录 |
| `source_key` / `deal_key` | 定位到具体角色人业绩行（含费用项、角色类型维度） |
| `raw_payload` | 红冲行保留贝壳原始负数行全 30 列，可查原退单来源 |
| **不修改原行** | 原正行保持原值 `ACTIVE`，红冲行为新增事实 —— 回溯时"原始值 + 全部红冲行"即为完整历史 |

```
合同 X（8月）  ：正行 +10,000（ACTIVE，永不改）
合同 X（10月） ：红冲行 -10,000（新增事实，挂同一 contract_id）

回溯 = 查 contract_id = X 的全部事实 → 得到 8月 +10,000、10月 -10,000 完整链条
```

> **不修改原行 ≠ 不回溯**：恰恰因为原行永不改，payroll 才能拿到"当时到底发了多少"的完整依据，用**原快照**算出应回退的提成（结算域 §2.10）。

#### 三条处理原则

**① 负数金额合法，不得整批拒绝**

`amount < 0` 是**有效业绩事实**（红冲行），不是脏数据。仅 `amount` 为空才拒绝。

**② 红冲行是新增事实，不是对原行的 UPDATE**

```
批次 A（8月） ：行 R1 = +10,000
批次 B（10月）：行 R2 = -10,000    ← 独立的新归一化记录，独立事实
```

二者 `source_key` 可能相同，但 **`normalized_record_id` 不同**，互不冲突、不互相抵消，各自作为独立事实留存。唯一索引 `uk_perf_fact_record (normalized_record_id, fact_type)` 按 NR 区分，插入不撞键。

**③ 每次导入 = 最新业绩快照**

一次导入即该结算月的全量最新状态（supersede 语义，§4.2）。

#### 归属月与回溯的关系（★ 易混淆，务必分清）

| 概念 | 说明 |
|---|---|
| **红冲行的 `period`** | 该负数行在贝壳导出中标注的结算月。若退 8 月的单，可能标 `202608` 也可能标导出当月（**待实测确认**，见 §14.1 口径 I） |
| **回溯的目标月** | **原合同的原业绩归属月**（如 8 月）—— 这是**算钱**时回溯的方向，由 payroll 按 `contract_id` 完成 |
| 二者的关系 | 红冲行落在哪个月份集合，不影响 payroll 按 `contract_id` 回溯到原月并用**原快照**算回退额 |

> 简言之：**业绩域负责"红冲行完整留存 + 与原合同关联"；payroll 负责"按合同回溯到原月、用原快照算回退额"**。两者配合实现"回溯到当月、回退当时的金额"。

#### 与业绩调整的关系（★ 模型统一，流程有别）

**底层模型完全同一套**：二者都是"合同下新增一行业绩变更"，都遵循"原行永不改 + 新增行形成版本链"。

| 维度 | 业绩调整（§3.3） | **退单红冲（本节）** |
|---|---|---|
| 改原始行 | ❌ 新增 | ❌ 新增 |
| 载体 | `PerformanceFact` 新事实 | `PerformanceFact` 新事实 |
| 挂 `contract_id` | ✅ | ✅ |
| 保留 `raw_payload` | 继承原行 | 保留贝壳原始负数行 |
| **来源** | **人工发起** | **贝壳导入**（外部客观事实） |
| **是否需审批** | ✅ 需要（`SUBMITTED → APPROVED → EXECUTED`） | ❌ **不需要，导入即生效** |
| 是否建 `PerformanceAdjust` 单 | ✅ 建 | ❌ **不建**（无审批可走） |
| 金额形态 | 绝对值（`new_amount` = 调整后最终值） | **负数增量**（如 `-3,000`） |
| 口径 | 人工填新值 | **镜像原单冻结口径**（`dept_id` / `origin_amount` / `share_ratio` / `conversion_rate`） |
| 定位原行 | 指定 `fact_id` 或整单 | 业务键 `biz_key` 精确匹配 |

> **为什么不合并为同一种单据**：红冲是**已发生的客观事实**，无需审批；强行套 `SUBMITTED → APPROVED` 流程语义错误。二者保留各自的产生方式，但**共享同一套事实模型与展示口径**。

**因此，凡是涉及"合同业绩怎么变了"的地方，二者必须一并计入：**

| 位置 | 处理 |
|---|---|
| **当期生效值** | `= 原始行 + 全部已生效调整行 + **全部红冲行**`（§1.7） |
| 合同级 `expect_total` / `real_total` | 汇总时**包含红冲行**（可为负） |
| 合同详情「调整/操作日志」时间线 | **红冲行一并列出**，标记来源「贝壳导入」以区分人工调整 |
| 合同详情「新签业绩」「结佣记录」Tab | 红冲行正常展示，标记"红冲" |

#### 影响面

| 层 | 影响 |
|---|---|
| 业绩域 | 允许 `amount < 0`；红冲行挂原 `contract_id`；`expect_total` / `real_total`**含红冲行**（可为负） |
| 结佣域 | 入单过滤 `amount <> 0` **天然保留负数**（负数 ≠ 0）；结佣明细可为负 |
| payroll | **按合同回溯到原归属月**，用**原 `RuleSnapshot`** 算回退额（结算域 §2.10） |

### 2.9 月度作业节奏（★ 时序基准）

```
N 月        ：业绩发生（签约 / 实收），period = N
N+1 月上旬  ：导入 N 月贝壳数据、核对、处理待对齐与退单
N+1 月中    ：发起并审批 N 月结佣（approved_month 记为 N+1，仅供审计）
N+1 月下旬  ：算【N 月工资批次】(period = N) → 审批 → 锁定 → 发放
              锁定同时 → 封【N 月】业绩
N+2 月      ：重复，处理 N+1 月
```

| 要点 | 说明 |
|---|---|
| **批次 `period` = 业绩归属月** | 8 月工资在 9 月发，但批次记 `202608` |
| **核对窗口在发薪之前** | 因此**不存在"工资已发还要改该月业绩"**——发现退单/漏算，在当期工资直接吸收 |
| **锁定即封账** | 钱发完，该月业绩关门，后续只能走调整单 + 补发到未封账月 |
| **封账不影响下月** | 9 月底封 `202608` 时，`202609` 仍 `OPEN`，10 月可正常结 9 月业绩 |

> 这条时序是「退单不回溯」「封账自动触发」「结佣按 `period` 取」三条规则的共同前提。

### 2.10 新签业绩的增量口径（★ 核心）

> **业务规则**：新签业绩**只计算一次**。若某单在签约后发生修改，**修改的那部分业绩计入「修改当月」的新签业绩**，不回改签约月。

**示例（用户原话场景）：**

```
7月：新签 10,000  → 计入【7月新签】10,000（店长团队提成/保底、总监门店提成基数）
     └ 7月工资已按此发放
8月：该单调整 -5,000 → 计入【8月新签】-5,000（8月基数做扣减）
     └ 7月不变，不回改、不追回
```

#### 落地方式：调整行的 `period` = 调整生效月

| 事实行 | `period` 取值 | 说明 |
|---|---|---|
| **原始行** | **签约月**（如 `202607`） | 永不改变，即使后续被调整 |
| **调整行（新事实）** | **调整生效月**（如 `202608`） | 默认 = 审批通过月；可指定 `target_period` |
| 红冲行 | 贝壳标注的结算月 | 见 §2.8 |

```
7月新签合计 = Σ period=202607 的 PERF_EXPECT = +10,000   ← 只算一次
8月新签合计 = Σ period=202608 的 PERF_EXPECT = 8月新签 + (-5,000)
```

> **payroll 无需改造**：已按 `findNewSignByDept(period, deptId)` 取 `PERF_EXPECT`，调整行落在哪个月就计入哪个月，天然满足增量口径。

#### 与「合同当期生效值」的关系（★ 易混淆）

| 视角 | 口径 | 用途 |
|---|---|---|
| **合同详情页「当期生效值」** | **存量**：原始行 + 全部调整行 + 红冲行（跨月累计） | 看"这笔合同现在值多少" |
| **payroll 按月取新签** | **流量**：仅取 `period = 该月` 的事实行（含该月产生的调整行） | 算"这个月店长/总监该计提多少" |

> 二者**不矛盾**：一个是合同维度的当前状态，一个是月份维度的当期发生额。

#### ★ 两种调整类型（V4.6 §9.6.3，原 `PERIOD` 类型的替代方案）

合同的业绩**只计算一次**。修改已计入某月的业绩时，按**是否跨月**选择调整类型：

| 归属模式 | 适用场景 | 系统行为 | 归属月 |
|---|---|---|---|
| **金额调整** | **同月修改**（7月的业绩，7月内修改） | 新行 `amount` = 调整后**总业绩金额**（原行 expire） | 仍 `202607` |
| **业绩冲销** | **跨月修改**（7月的业绩，8月才修改） | 新增**冲销行** `amount` = 差额（如 `-5,000`）；**原行不动** | `202608`（修改当月） |

```
场景①：7月单，7月内改 -5,000（金额调整）
  7月：原始 +10,000（expire）→ 新行 +5,000（period=202607）
  → 7月业绩合计 = 5,000

场景②：7月单，8月改 -5,000（业绩冲销）
  7月：原始 +10,000（保持 ACTIVE，不动）
  8月：新增冲销行 -5,000（period=202608）
  → 7月合计 10,000；8月合计含 -5,000
```

**判定规则**（发起调整时由系统自动判定，无需人工选）：

```java
AdjustMode resolveMode(String originPeriod, String effectivePeriod) {
    return originPeriod.equals(effectivePeriod)
        ? AMOUNT_ADJUST    // 同月 → 金额调整（改总金额）
        : REVERSE_ADJUST;  // 跨月 → 业绩冲销（新增冲销行）
}
```

| 约束 | 说明 |
|---|---|
| 归属月判定 | 同 = 金额调整；不同 = 业绩冲销 |
| 冲销行标记 | `is_reversal_adjust = true`，与退单红冲（`is_reversal`）区分 |
| **合同归属月不改写** | `pj_perf_contract.period` 保持签约月，仅作展示与归属标识 |

> **为什么废止 `PERIOD`**：`PERIOD` 会同步改写所有行的 `period`，导致签约月凭空减少、目标月凭空增加，破坏"只计算一次"。两种调整类型已覆盖其场景（跨月 = 业绩冲销）。

#### 经纪人的结佣业绩不受影响

经纪人提成基于**结佣业绩（实收）**，按结单时点计算——此时调整基本已完成，取值自然是调整后的值（§2.1 原样落库）。本节的增量口径**只针对新签业绩**（店长 / 总监的团队提成、保底、门店提成基数）。

#### `PERIOD`（跨月归属调整）类型的处置

原设计的 `PERIOD` 类型会"改合同归属月 + 同步改所有行的 `period`"，**与增量口径冲突**——它会让签约月凭空减少、目标月凭空增加，破坏"只算一次"。

**处置：废止 `PERIOD` 类型。** 若确需将某笔业绩整体挪到另一个月，用**两笔调整**实现（仍符合增量口径）：

```
原月：-10,000（反向调整，period = 生效月1）
新月：+10,000（新增行，period = 生效月2）
```

> 合同归属月（`pj_perf_contract.period`）仅用于**展示与归属标识**，不再随调整同步改写事实行的 `period`。

| `adjust_type` | 见下表 6 种 |
| `payload_json` | 变更前后值快照 |
| `new_amount` / `new_ratio` / `target_period` / `discount_rate` | 按类型使用（详见下表） |
| `take_effect` | `CURRENT`（计入当期工资）/ `SUPPLEMENT`（补发到指定月份，配 `target_period`）；★ **决定调整行的 `period`**（§3.3） |
| `reason` | **必填**（下拉 + 文本），审计 |
| `remark` | 附件说明（文本备注，**不上传图片**，V4.3 §十二-5） |
| `status` | `SUBMITTED → APPROVED → EXECUTED`（终态）／`REJECTED`／`CANCELLED` |
| `process_instance_id` / `applicant_id` / `approver_id` | Warm-Flow / 发起人 / 审批人 |

#### ★ 只改应收，不改实收（V4.5 §9.6）

| 口径 | 是否可调整 | 理由 |
|---|:---:|---|
| **应收业绩（`PERF_EXPECT`）** | ✅ **可调整** | 反映公司内部认定的业绩归属与金额，可因协商、折扣、补录而变 |
| **实收业绩（`PERF_REAL`）** | ❌ **不可调整** | 贝壳已到账的**客观事实**，不因内部协商而变动 |

> 实收的变化只通过两条路径产生：① 贝壳导出**负数行红冲**（退单，§2.8）；② 新一期到账。均非"调整"。

**因此调整单的 `fact_id` 一律指向 `PERF_EXPECT`；对 `PERF_REAL` 的调整请求一律拒绝。**

#### 两种调整维度（V4.5 §9.6.1）

**① 合同维度（整单调整）**：修改**合同应收金额**，按**原各人比例**分摊：

```
调整前：合同应收 120,000
        甲 72,000（60%）  乙 30,000（25%）  丙 18,000（15%）
改为：合同应收 100,000
调整后：甲 60,000   乙 25,000   丙 15,000
        ↑ 新合同金额 × 原各人比例
```

**② 明细维度（按人调整）**：改**某人/某几人**应收，其他人不联动，合同合计自动重算：

```
调整前：合同应收 120,000（甲 72,000 / 乙 30,000 / 丙 18,000）
将乙改为 25,000
调整后：合同应收 115,000（甲 72,000 / 乙 25,000 / 丙 18,000）
```

> 系统实现：`WHOLE` 用比例分摊，`ROW` 直接改指定行 —— 二者共用同一套"新行 + 版本链"机制。

#### 发起与审批（V4.5 §9.6.2）

| 项 | 说明 |
|---|---|
| **发起人** | **店长 / 店助 / 总监**（均含），提交审批 |
| **审批人** | **总监**（单一节点） |
| 生效 | 刷新合同"当期生效值"，触发受影响月份工资重算提示 |

#### 调整类型（V4.3 §9.5 / V4.6 §9.6.3）

| 调整类型 | `scope` | 入参 | 系统行为 | 典型场景 |
|---|---|---|---|---|
| `DISCOUNT` 整单折扣（如 85 折） | `WHOLE` | `discount_rate` | 对合同下**所有**角色人业绩行按折扣新增调整行，标记"85后" | 公司统一让利、平台扣点 |
| `RATIO` 改业绩比例 | `ROW` | `new_ratio` | 新增调整行，按新比例**重算该行应收业绩** | 角色贡献重新协商 |
| `AMOUNT` 改金额（直接填写） | `WHOLE` / `ROW` | `new_amount` | 新增调整行，记录原值 → 新值 | 特殊个案 |
| `ADD_ROW` 补录角色人 | `WHOLE` | 角色人 + 比例 | 新增角色人业绩行，标记"**人工补录**"（`source=MANUAL`） | 贝壳数据漏人（★待确认 B） |
| `VOID_ROW` 作废角色人 | `ROW` | — | 该行金额置 0，生成**反向调整记录** | 挂错人、重复计入 |

> **★ 归属模式（同月 / 跨月）—— 上表所有类型均适用**，系统按「原归属月 vs 生效月」自动判定，**无需人工选择类型**：
>
> | 模式 | 条件 | 行为 | 归属月 |
> |---|---|---|---|
> | **金额调整** | 生效月 == 原归属月（**同月修改**） | 原行 expire + 新行 = 调整后**总金额** | **不变** |
> | **业绩冲销** | 生效月 ≠ 原归属月（**跨月修改**） | 新增**冲销行**（`amount` = 差额）；**原行不动** | **修改当月** |
>
> 详见 §2.10。

> **`TRANSFER`（门店纠偏）**：V4.3 未列此类型，但合同级门店本身"取业绩占比最高角色人所属门店、可人工修正"（§3.0），故门店纠偏归入**合同主信息修正**，不再作为独立调整类型。

#### EXECUTED 同事务动作

| 类型 | 动作 |
|---|---|
| `DISCOUNT` | 合同下所有 `ACTIVE` 行：旧行 expire + 新行（`amount` = 原值 × `discount_rate`，`raw_payload` 继承） |
| `RATIO` | 目标行：旧行 expire + 新行（`amount` = 合同应收 × `new_ratio`，仅 `PERF_EXPECT`） |
| `AMOUNT` | 目标行：旧行 expire + 新行（`amount` = `new_amount`） |
| 任意类型 · **同月模式（金额调整）** | 目标行 expire + 新行（`amount` = 调整后**总金额**，`period` **不变**） |
| 任意类型 · **跨月模式（业绩冲销）** | 新增**冲销行**（`amount` = 差额，可正可负；`period` = **修改当月**）；**原行不动** |
| `ADD_ROW` | 新增 `source=MANUAL` 事实行，挂合同下 |
| `VOID_ROW` | 目标行 expire + 反向调整记录（`amount` = 0） |

> **调整永不丢原始**：新事实必须继承原事实的 `raw_payload`；调整内容另记在 `payload_json`。
> **不可逆**：所有调整记录永久存档、不可删除，错误通过**反向调整**修正。

#### ★ 调整行的 `period` 取值（增量口径落地点）

调整生成的**新事实行**，`period` 一律取 **调整生效月**，不是原业绩归属月：

| `take_effect` | `period` 取值 |
|---|---|
| `CURRENT`（计入当期） | **审批通过月** |
| `SUPPLEMENT`（补发到指定月） | **`target_period`** |

```
7月原始行 +10,000  period=202607  ← 永不变
8月调整行  -5,000  period=202608  ← 审批通过月
```

> 因此 **7月新签 = +10,000、8月新签含 -5,000**，各自只算一次（§2.10）。
> **合同归属月**（`pj_perf_contract.period`）不随调整改写，仅作展示与归属标识。

#### 守恒口径（★待确认 A，默认不守恒）

调整某一角色人业绩行时，其他角色人行的金额**保持不变**，合同合计随之变动。合同详情页**实时展示**：

```
原始合计 / 调整后合计 / 差额   ← 差额产生时必须填写原因
```

> 若客户要求锁死合同总额（差额分摊给其他角色人），需在此处确认后调整实现。

#### 前置校验

1. `period` 未封账；
2. 原事实为 `ACTIVE`（`ADD_ROW` 除外）；
3. 同一 `fact_id` 无未完成调整单；
4. **补录角色人（★待确认 B）**：允许，但仅限该合同对应工资**未锁定**前；工资已锁定则只能走补发单；
5. 幂等（重复回调先查状态）。

#### 生效与联动

- 审批链：店长 / 算薪发起 → **总监审批** → 生效；
- 生效后刷新合同"当期生效值"，并**触发受影响月份工资重算提示**；
- **待审批的调整单对经纪人不生效、不展示**（§9 可见性红线）；
- **历史月份差额（★待确认 C）**：调整后若相关月份工资已锁定，统一**生成补发单**，并入发起人指定的发放月份，**不回改历史锁定数据**。

### 3.4 `PerformanceConsumeLog`（消费日志）

一表三用：**幂等锚点、行数对账、失败留痕**。

| 字段 | 说明 |
|---|---|
| `batch_id` + `event_type` | **联合唯一** → 幂等（`ARCHIVED` / `RENORMALIZED`） |
| `event_id` | 事件全局唯一 ID（CR-3），兜底幂等 |
| `period` / `source_type` | 检索与展示 |
| `status` | `RUNNING` / `SUCCESS` / `PARTIAL` / `FAILED` |
| `total_rows` / `normal_rows` / `abnormal_rows` | NR 条数 / 生成事实条数 / 跳过行数 → **差异即告警**（§6.5） |
| `pending_align_json` | **待对齐行明细**（角色人系统号 / 姓名 / 金额 / 原始行号 / `raw_payload`），见 §4.5 |
| `message` | 失败原因 |

> **行数口径**：`total_rows` 为 NormalizedRecord 行数；`normal_rows` 为**生成的事实条数（= 行数 × 2）**。对账时按 `normal_rows ÷ 2` 与 `total_rows` 比对。

### 3.5 `PerformancePeriodClose`（期间封账）

| 字段 | 说明 |
|---|---|
| `period` | UK（结算月） |
| `status` | `OPEN` / `CLOSED` |
| `close_reason` | `MANUAL` / `PAYROLL_LOCKED` |
| `ref_batch_id` / `operator_id` / `close_time` | 溯源 |

**★ 封账语义（唯一，不得二义）：`CLOSED` = 该结算月终态关闭，不是"数据定稿可以结佣了"。**

| 状态 | 含义 | 禁止清单 |
|---|---|---|
| `OPEN` | 数据未定稿，仍可导入 / 补录 / 冲销 | — |
| `CLOSED` | 该结算月**终态关闭**（由 `PayrollLockedEvent` 自动触发，或总监手工封） | ① 重新消费批次；② 业绩调整单 `EXECUTED`；③ 手工录入作废；④ 业绩域人工调整；⑤ **结佣域发起结佣**；⑥ **结佣域增量重拉**；⑦ **结佣调整单 `EXECUTED`** |

**★ 自动触发为什么不会封错月（关键澄清）：**

实际作业节奏是「**N 月业绩 → N+1 月核对、结佣、算 N 月工资并发放**」。工资批次的 `period` **就是业绩归属月**，发放动作虽然在次月，但不改变批次归属。

```
8月业绩（period=202608）
   → 9月：核对 → 结佣审批 → 算【8月工资批次】(period=202608) → 发放
   → 锁定 → PayrollLockedEvent(period=202608) → 封【202608】✅
```

`PayrollLockedEvent` 携带的 `period` 与 `pj_perf_period_close.period` **同义**（都是业绩归属月），因此自动封账语义正确：封住的正是"钱已发完"的那个月。

> ⚠ **易错点**：若把工资批次记成**发放月**（`202609`），则封的是 `202609`，而 9 月业绩要 10 月才结佣 → **提前一个月被封死**。故批次 `period` 必须取业绩归属月，禁止取发放月。

> ⑤~⑦ 由结佣域经 `PeriodCloseQueryPort.isClosed(period)` 自行判定（§4.7），本域不感知结佣。
> 解封需总监二次确认 + `AuditPort` 留痕；解封后 `isClosed` 实时返回新状态，**消费域每次实时查，禁止缓存**。

> ⚠ **由此推出的结佣时间窗**：结佣必须在 `CLOSED` **之前**完成（导入 → 发起结佣 → 审批锁定 → payroll 锁定 → 自动封账）。某月已 `CLOSED` 仍有实收未结时，只能以 `DIFF` 补发到未封账月份，或解封后重走 —— 详见结佣域 §2.5。

## 四、核心流程

### 4.1 消费主流程（幂等、可重跑）

```
① 消费 ImportBatchArchivedEvent(batchId, sourceType, supersededBatchIds, eventId)
     ├─ sourceType == EMPLOYEE              → 忽略（防御性过滤，对齐导入域）
     └─ sourceType ∈ ATTENDANCE/POINTS/OTHERS → 忽略（非业绩类，归 payroll 扣款项）
② 幂等：consume_log(batchId, eventType) 已 SUCCESS → 跳过
③ 期间校验：period 已 CLOSED → 拒绝 + 告警
④ 【冲销旧批次】supersededBatchIds 非空 → 其全部事实 expire（§4.2）
⑤ 拉 NormalizedRecord（ImportNormalizedRecordQueryPort，只读，分页 500）
⑥ 【★ 合同归集 V4.3 §9.2】按 biz_type 取聚合键（订单号 / 合同号）
       → 已存在则用，不存在则建 pj_perf_contract（**写入 first_period = 本批次 period**）
       → 事实行挂 contract_id
⑦ 逐行：业务校验 → 员工/门店归属 → 生成 2 条事实
       PERF_EXPECT ← 当月应收业绩
       PERF_REAL   ← 当月实收业绩
       （金额原样取，不做任何加工）
       ★ 同时生成 deal_key = source_key 去 fact_type 后缀
       ★ 【新签计入月判定 §2.12】PERF_EXPECT 行：
         new_sign_period = (period == contract.first_period) ? period : NULL
         重复导入月份的应收 → NULL，不参与新签计算
⑧ 【合同级合计回算】expect_total = ∑ PERF_EXPECT；real_total = ∑ PERF_REAL
       （自下而上汇总，不按"合同实收 × 比例"重算，见 §2.1）
⑨ 合同 dept_id 判定：业绩金额最高角色人所属门店（首次写入，后续可人工修正）
⑩ 写 consume_log（total / normal / abnormal）→ 差异告警
⑪ 发布 PerformanceFactCreatedEvent（传 factIds + **contractIds** + **dealKeys**）
```

> **落地细节见附录 A** —— 含链路总览、`NormalizedRecord` 结构、**30 列字段映射表**、代码骨架与三个常见坑。

**幂等实现：** 重跑 = 先按 `batch_id` 删除派生行（`source = IMPORT`），再重建。**绝不删 `source = MANUAL` 的行**（人工成果）。`normalized_record_id` 唯一索引做 DB 兜底。

### 4.2 supersede（批次替换）

```
ImportBatchArchivedEvent.supersededBatchIds = [旧批次...]
   ↓ 同一事务，串行
① 旧批次全部 Fact → REVERSED（reversed_reason = SUPERSEDE）
② 基于新批次重建
③ 发布 reversed（旧 id）+ created（新 id）事件
```

默认 **全量替换** —— 旧批次被 supersede 即其全部事实作废。增量模式留参数 `panjia.perf.supersede-mode=INCREMENTAL`。

> **唯一触发源是事件**，禁止轮询 import 库。

### 4.3 重归一化（reNormalize）

独立事件 `ImportBatchRenormalizedEvent`（CR-5）→ 冲销本批次全部事实（`reversed_reason = RENORMALIZE`）→ 重建。与 supersede 复用同一冲销闭环，仅 `reversed_reason` 不同（审计可区分）。

### 4.4 手工录入业绩

| 环节 | 规则 |
|---|---|
| 来源 | `source = MANUAL`，`batch_id = null`，`normalized_record_id = null`；`raw_payload` 存录入内容快照，`import_file_name = null` |
| 流水线 | **必须复用** §4.1 ⑦ 同一套（校验 → 归属 → 原样记录金额 → Fact） |
| **合同归属** | ★ 必须指定 `contract_id`（V4.3：一切业绩操作以合同为入口）；无外部单号时 `source_key = "MANUAL-" + UUID`，但 `contract_id` 不可空 |
| 作废 | **禁止物理删除** → 走调整单 `VOID_ROW` 或直接冲销（`reversed_reason = PERIOD_VOID`） |
| supersede | **不参与**（仅针对 `source = IMPORT`） |

### 4.4.1 合同维度调整流程（V4.3 §9.5）

```
合同详情页 → 选择调整范围（整单 / 指定角色人业绩行）
   → 选调整类型（6 种）→ 填调整后值 + 原因 + 生效方式
   → 提交（status = SUBMITTED）
   → Warm-Flow：店长/算薪发起 → 总监审批
   → APPROVED → EXECUTED（同事务）
        ├─ 冲销旧行 + 生成新行（raw_payload 继承）
        ├─ 回算合同级 expect_total / real_total
        └─ 触发受影响月份工资重算提示（CR-15）
   → 历史已锁定月份 → 按待确认 C 生成补发单（不改历史）
```

| 约束 | 说明 |
|---|---|
| 调整入口唯一 | 必须带 `contract_id`；不提供"脱离合同的事实级调整" |
| 原始行永不改 | 一律新增记录形成版本链（V4.3 §9.5 铁律） |
| 待审批不可见 | 经纪人在审批通过前看到的是**旧生效值**，且看不到调整单（§9.3） |
| 不可逆 | 记录永久存档、不可删除，错误走反向调整 |
| 生效方式 | `CURRENT` 计入当期 / `SUPPLEMENT` 补发到 `target_period` 指定月 |

### 4.5 业务语义校验

区别于 import 域的**格式/类型校验**，业绩域做**业务语义校验**：

| 校验 | 处置 |
|---|---|
| `source_key` 批次内重复 | 整批拒绝 |
| 业务日期非法（空 / 早于上线日） | 整批拒绝 |
| `biz_type` 不在六类枚举内 | 整批拒绝 |
| `role_type` 不在 16 种枚举内 | 整批拒绝 |
| `fee_item` 不在四类枚举内 | 整批拒绝 |
| 金额为空 | 整批拒绝 |
| 业务日期早于上线日 | 整批拒绝；**基线批次豁免**（`baseline_flag = true`，见 §4.9） |
| **金额为负** | **允许**（★ 红冲行，见 §2.8） |
| ★ **员工匹配失败**（工号在系统内找不到） | **进「待对齐」列表** |
| ★ 快照缺 `dept_id` | **进「待对齐」列表** |

**默认策略：整批原子** —— 任一失败则本批次不生成任何 Fact，原因写 `consume_log.message`，人工修正后重跑。

> 理由：财务系统最危险的是"看似导入成功、实则少业绩"，部分成功会让对账差异延迟暴露。
> 开关 `panjia.perf.partial-accept-enabled = false`，置 true 时切"合法单据生成、非法跳过"。

#### ★「待对齐」机制（V4.3 §13.1 硬性验收项）

> V4.3 §13.1：*"导入时按工号匹配员工档案；匹配失败人员进入「待对齐」列表，可手动指定对应员工"*

分两步执行：

```
① 消费时：按角色人系统号（工号）匹配员工
     ├─ 匹配成功          → 正常生成 Fact
     └─ 匹配失败          → 该行不生成 Fact，落入「待对齐」列表（pending_align_json）
② 人工在「待对齐」页面：
     ├─ 指定已有员工      → 该行重新入流水线，生成 Fact
     └─ 确认为新员工/无效 → 标记忽略，记 consume_log.abnormal_rows
```

| 设计点 | 说明 |
|---|---|
| **本样本无缺角色人** | 318 行角色人系统号与姓名均非空，故待对齐主要因**员工匹配失败**触发 |
| 落库位置 | `consume_log.abnormal_rows` 计数 + `pending_align_json` 存明细 |
| 不建独立表 | 与"不建 issue 表"决策一致（ADR A8） |
| 待对齐期间 | 批次状态 `PARTIAL`，**不阻断**其他正常行入库 |
| 人工指定后 | 走同一流水线，事实 `source = IMPORT`，仍带原 `batch_id` 与 `raw_payload` |

> **为什么不能整批拒绝**：员工匹配失败多因新入职/离职，整批拒绝会导致"一个人没建档 → 全店业绩停摆"。

### 2.12 新签只计算一次：重复导入的应收不参与计算（★ 核心）

**问题**：贝壳导出**每月都带应收列**，同一合同会在多个月份反复出现。

```
8月导入合同 X：PERF_EXPECT(period=202608) = 100,000   实收 = 0
9月导入合同 X：PERF_EXPECT(period=202609) = 100,000   实收 = 100,000
                              ↑ 同一笔应收，贝壳又带了一遍
```

若 payroll 按 `period` 取 `PERF_EXPECT`，9 月会**重复计入** 100,000 → 店长团队提成、总监门店跳点虚高。而业务规则是**新签只计算一次**。

#### 解法：`new_sign_period`（新签计入月）

| 应收事实行 | `new_sign_period` | 是否计入新签基数 |
|---|:---:|:---:|
| **合同首次导入月**的应收 | = `period` | ✅ 计入（**唯一一次**） |
| **后续月份重复导入**的应收 | **NULL** | ❌ 不计入 |
| 人工调整行 / 冲销行 | = 调整生效月 | ✅ 计入（增量差额，§2.10） |

**判定规则**（导入时自动计算，无需人工干预）：

```java
// contract.first_period：合同首次建单时写入，永不修改
newSignPeriod = (factPeriod.equals(contract.getFirstPeriod()))
    ? factPeriod      // 首次导入月 → 计入
    : null;           // 重复导入月 → 不计入
```

> **为什么用 `first_period` 而不是"合同是否已有 ACTIVE 应收行"**：后者在**重导同月批次**（supersede）时会误判——重导时 9 月的行可能仍 ACTIVE，导致 8 月重建的行被判为"重复"而丢失新签。`first_period` 不随批次变化，重导无影响。

#### ★ 重复导入的应收：只展示，不比对、不冲销

重复导入月份的应收行（`new_sign_period = NULL`）**仅作记录与展示**，系统**不做任何差异比对或自动冲销**。

**为什么不能冲销（重要）**：

```
8月：新签 100,000（计入8月）→ 人工调整为 95,000
9月：贝壳导入仍是 100,000（贝壳不知道我们调整过）

✗ 若做差异冲销：95,000 − 100,000 = −5,000 → 9月凭空多一笔冲销
   这 −5,000 是"贝壳老值 vs 调整后值"的差，不是业务变动，
   且 8 月那次调整已通过自身机制（同月金额调整 / 跨月冲销）正确处理
```

重复导入值**不参与计算**，拿它做比对毫无意义，反而制造错误冲销。

> 这正是需求 1.2 的落地：**应收应取「历史调整后的值」，并展示「本次导入的应收」做记录** —— 本次导入值只展示，不参与任何计算。

#### payroll 取数

`findNewSignByDept(period, deptId)` 改为按 **`new_sign_period = :period`** 取（Port 签名不变）：

```
8月新签 = Σ new_sign_period = 202608 的应收行 = 100,000   ← 只此一次
9月新签 = Σ new_sign_period = 202609 的应收行 = 9月新签的合同（不含合同X重复行）
```

#### 场景验证

| 场景 | 处置 | 结果 |
|---|---|---|
| 8月导入无实收，9月导入有实收 | 新签在 **8月**计一次；9月实收走确认+结佣 | ✅ 新签不重复，结佣正常 |
| 8月调整应收，9月导入仍是老值 | 9月行 `new_sign_period=NULL`，**不比对不冲销**；合同页展示"本次导入 100,000 / 调整后 95,000" | ✅ 无凭空冲销 |
| 重导 8 月批次（supersede） | `first_period` 不变，重建行仍判为首次 | ✅ 新签不丢失 |

### 3.7 `PerformanceRealConfirm`（实收业绩确认单，★ V4.5 §9.4）

**粒度 = 合同 × 到账月**（与结佣申请单一致）。实收是"贝壳已到账"的客观事实，但需经公司内部确认后才能作为结佣依据。

| 字段 | 说明 |
|---|---|
| `contract_id` / `period` | 合同 × 到账月（唯一键） |
| `amount_total` | 本期实收合计 |
| `fact_ids` | 本期实收事实集合 |
| `status` | `DRAFT → FINANCE_AUDIT → DIRECTOR_AUDIT → CONFIRMED`（终态）／`REJECTED` |
| `initiator_role` | 发起人角色（决定首节点，见下） |
| `process_instance_id` / `approver_id` | Warm-Flow / 当前审批人 |
| `confirm_time` | 确认通过时间 |

**流转规则（按发起人身份，V4.5 §9.4.3）：**

| 发起人 | 首个节点 | 链路 |
|---|---|---|
| 店长 / 店助 | **财务** | 财务 → 总监 → `CONFIRMED` |
| **财务** | **总监** | 总监 → `CONFIRMED`（财务自己发起，无需再审） |
| **总监** | — | **直接 `CONFIRMED`**（总监发起即生效） |
| **导入自动提交** | **财务** | 财务 → 总监 → `CONFIRMED` |

**落定后发 `RealConfirmedEvent`**（携带 `contractIds` / `factIds` / `dealKeys`）→ 结佣域消费并自动生成结佣申请单（结佣域 §4.1 ①）。

> **★ 关键约束**：**未确认的 `PERF_REAL` 不得被结佣域拉取**。这是 V4.5 §9.4 的落地点——否则实收审批环节形同虚设。

#### Excel 自动 / 批量审批（V4.5 §9.4.4）

导入贝壳导出 Excel → 系统按 **合同号 + 金额** 匹配确认单 → 自动审批通过。

| 规则 | 说明 |
|---|---|
| 匹配键 | 合同号（订单号）+ 金额 |
| 金额一致 | 自动通过 |
| 金额不一致 / 合同号找不到 | 进**异常清单**，人工处理，**不静默跳过** |
| 幂等 | 按合同 × 到账月；重复导入不重复审批 |

### 4.9 上线基线导入（冷启动）

**问题**：系统上线时，历史月份的业绩不在系统内，导致两类问题：

1. **退单匹配不上**：9 月导出红冲 `-10,000`，退的是 8 月的单，但系统无 8 月原正行 → `biz_key` 匹配落空 → **口径无法镜像**（`dept_id` / `share_ratio` / `conversion_rate` 拿不到）
2. **首个核算月工资算不出**：按 §2.9 时序「N月业绩 → N+1月核算并发N月工资」，若上线首月就要算上月工资，上月业绩必须已在系统内

**解法：上线时补导历史月份的贝壳导出**（建议覆盖 ≥6 个月，具体视客户退单周期而定）。

| 处置 | 说明 |
|---|---|
| 标记 `baseline_flag = true` | 与常规导入区分（落 `pj_perf_fact` 与批次） |
| **豁免"早于上线日"校验** | 否则基线数据被整批拒绝（§4.5） |
| **基线期间一律置 `CLOSED`** | 历史月的钱已线下发过，封账可防止结佣域自动生成申请单（结佣域 §4.1.1） |
| 不触发结佣自动生成 | 由封账状态自然拦截，无需关闭事件监听 |

**上线配置示例：**

```
pj_perf_period_close  202601 ~ 202607  →  CLOSED（基线，钱已线下发过）
pj_perf_period_close  202608（首个系统核算月）→  OPEN
```

**基线数据的三个用途：**

1. 供红冲按 `biz_key` 匹配原单（直接解决退单问题）
2. 合同详情页展示完整历史业绩链
3. 基准回归验证（V4.4 §13.9 要求用 2026-07 真实数据核对 Excel 工资表）

#### 孤儿红冲（匹配不到原单时的兜底）

即便补导基线，仍可能匹配不上（退的很早的单、历史数据不全）。三级降级：

| 级别 | 条件 | 处置 |
|---|---|---|
| **L1** | `biz_key` 命中原事实 | 正常镜像口径（`origin_fact_id` 有值） |
| **L2** | 匹配不到 → 人工补录原单 | 重跑匹配，转 L1 |
| **L3** | 无原单且暂不补录 | `orphan_flag = true`，进**待对齐**列表（复用现有机制，不建表） |

**硬约束：孤儿红冲 `orphan_flag = true` 时不得进结佣**，直到处理完成——否则算薪口径必然错（拿不到镜像口径与原快照）。

人工三种处置：

1. 补录原单（转 L1）
2. 直接指定 `dept_id` / 口径（人工兜底）
3. 标记「上线前退单，线下处理」→ **不进系统工资**（钱已线下结清）

> **为什么复用「待对齐」而不建表**：与 ADR A8「不建 issue 表」一致；待对齐机制已有页面、已有处理流程。

## 六、事务、并发、幂等、重算

### 6.1 事务边界

| 场景 | 策略 |
|---|---|
| 批次消费 | 分页 500 拉取、批量 INSERT 300；`MAX_ROWS_PER_BATCH = 5000`；**单批次一个事务** |
| supersede 冲销 + 重建 | **同一事务**：先冲销旧事实再建新事实，杜绝"旧已过期、新未生成"中间态 |
| 业绩调整单 `EXECUTED` | 单事务：冲销 + 新建 + 状态变更 |

> 进程内 Port 调用失败直接抛异常 → `consume_log = FAILED` → 重跑（幂等）。**不引入 MQ / 死信队列**（模块化单体，Spring 事件 + Outbox 已足够）。

### 6.2 并发控制

| 风险 | 防护 |
|---|---|
| 同一 `eventId` / 批次重复消费 | `uk_pcl_batch_event` + `uk_pcl_event_id` |
| 重复导入同一归一化记录 | `uk_perf_fact_record(normalized_record_id, fact_type)` |
| 同一事实并发调整 | Fact `version` 乐观锁；冲突重试 3 次后告警 |

### 6.3 幂等锚点

| 入口 | 锚点 |
|---|---|
| `ImportBatchArchivedEvent` | `uk_pcl_batch_event(batch_id, event_type)` |
| `ImportBatchRenormalizedEvent` | 同上 |
| 批次重跑 | 先删 `batch_id` 派生行（`source = IMPORT`）再重建，**绝不删 MANUAL** |
| 业绩调整单回调 | 调整单 `status` + `version` |

### 6.4 四类重算（隔离定义，不提供"一键重算"）

| # | 场景 | 触发源 | 范围 | 是否改写历史事实 | 默认策略 |
|---|---|---|---|---|---|
| 1 | supersede / reNormalize | import 事件 | 本 `batchId` | ✅ 冲销 + 重建 | 自动执行 |
| 2 | 手工修改 / 作废单据 | 页面 + 审批 | 单条 Fact | ✅ 冲销 + 重建 | 需审批；**已封账期间禁止** |
| 3 | 折算配置变更 | 实施改配置 | — | ❌ **不回溯** | 折算在 payroll 规则层，本域无系数，**天然不受影响** |
| 4 | 员工主数据回溯修复 | people 域变更 | — | ❌ **不重算** | 事实冻结取数时结果；确需重算走**人工审批专项任务** |

### 6.5 对账（消费时比对，不建表不跑批）

`consume_log` 中 `total_rows`（NR 行数）与 `normal_rows ÷ 2` 不一致 → **立即写 `FAILED` / `PARTIAL` + 告警**。不建离线对账任务、不自动修复。

> **额外校验**：批次内 `∑ amount` 与贝壳 Excel 页脚合计比对，可捕获"少导行"这类最危险的问题（开关：`panjia.perf.footer-check-enabled`，默认 true）。
> 本样本基准值：`PERF_EXPECT` 合计 **206,274.04**、`PERF_REAL` 合计 **192,556.89**。

## 七、事件、依赖与包结构

### 7.1 事件

| 方向 | 事件 | 来源 | 字段 | 处理 |
|---|---|---|---|---|
| in | `ImportBatchArchivedEvent` | import | `eventId` / `batchId` / `sourceType` / `period` / **`supersededBatchIds`（CR-1）** | `EMPLOYEE` 与 `ATTENDANCE/POINTS/OTHERS` 忽略 |
| in | `ImportBatchRenormalizedEvent` | import（CR-5） | `eventId` / `batchId` | 冲销重建 |
| in | `PayrollLockedEvent` | **contracts** | `period` / `batchId` | **期间自动封账 `CLOSED`**；`period` = 业绩归属月（= 工资批次月），与 `pj_perf_period_close.period` 同义，见 §3.5 |
| out | `PerformanceFactCreatedEvent` | → commission | `eventId` / `period` / `factIds` / `factType` / `deptIds` / `source` / **`contractIds`** / **`dealKeys`** | 只传 ID |
| out | **`RealConfirmedEvent`** | → commission | `eventId` / `period` / `factIds` / **`contractIds`** / **`dealKeys`** / `deptIds` | ★ 实收确认通过后发布；**结佣域唯一触发源**（V4.5 §9.4） |
| out | `PerformanceFactReversedEvent` | → commission | `eventId` / `period` / `factIds` / `reason` / **`contractIds`** | 只传 ID |

> 消费 `contracts` 事件**不构成对 payroll 模块的依赖** —— 事件定义在叶子模块。
> **事件只做通知**：下游收到后调 Port 拉取，避免消息体过大。

## 九、合同详情页与字段级可见性（V4.3 §9.6）

### 9.1 统一入口

合同详情页是**业绩查看、调整、结佣、溯源的唯一页面**。所有角色从此进入，权限只控制"能否看到本店/本人"与"能否点操作按钮"。

**经纪人进入路径（唯一）：**

```
我的业绩明细 → 某笔到账贡献 → 「查看完整合同」→ 合同详情页（只读）
```

| 约束 | 说明 |
|---|---|
| **强制成员校验** | 「当前用户 ∈ 该合同角色人集合」，不属于该合同的经纪人一律拒绝访问 |
| **不提供全局搜索** | 经纪人不提供合同全局搜索功能，只能从本人业绩下钻进入 |
| 店长 / 总监 / 算薪 | 可按门店 / 全量检索合同 |

### 9.2 页面结构

```
合同：CD202607xxxx  业务类型：二手买卖  门店：龙湖店  归属月：2026-07
应收业绩（新签）：120,000.00   实收累计：96,000.00   状态：部分结佣
────────────────────────────────────────────────────────
[新签业绩]  [结佣记录]  [调整/操作日志]
────────────────────────────────────────────────────────
角色人   角色类型     业绩比例   应收业绩    调整后     状态
王五     客源成交人    60%      72,000     72,000     有效
李四     房源维护人    25%      30,000     25,500     已调整
赵六     房源录入人    15%      18,000     18,000     有效
李四     房源维护人    25%      -4,500     -4,500     红冲
────────────────────────────────────────────────────────
合计      100%      120,000    111,000   （差额 -9,000）
```

三个 Tab 对应两条链 + 审计：

| Tab | 内容 |
|---|---|
| 新签业绩 | 合同下各角色人 `PERF_EXPECT`：**原始行 / 调整行 / 红冲行 / 当期生效值**（生效值含红冲，§1.7） |
| 结佣记录 | 合同 × 到账月 的结佣记录（结佣域数据，本域只读展示）；负向结佣正常展示 |
| 调整/操作日志 | **统一时间线**：人工调整（谁发起、审批人、原因、变更前后值）+ **红冲行**（来源「贝壳导入」，无审批人） |

> **时间线口径**：红冲与人工调整**并列展示**，用「来源」列区分。用户看到的是"这笔合同的业绩怎么变的"一条完整链，不区分内部操作与外部事实。

### 9.3 字段级可见性矩阵（同一份合同，不同角色看到不同字段）

| 字段 | 经纪人（同合同） | 店长（本店） | 总监 / 算薪 |
|---|:---:|:---:|:---:|
| 合同号、业务类型、签约日期、门店 | ✅ | ✅ | ✅ |
| 合同应收总额、实收累计、结佣状态 | ✅（合同级共享） | ✅ | ✅ |
| 各角色人姓名 | ✅ | ✅ | ✅ |
| 各角色人角色类型 | ✅ | ✅ | ✅ |
| 各角色人业绩比例 | ✅ | ✅ | ✅ |
| 各角色人业绩金额（新签） | ✅ | ✅ | ✅ |
| 各角色人**提点 / 提成金额** | ❌ | ✅ | ✅ |
| 各角色人**工资** | ❌ | ✅ | ✅ |
| 调整前原值、调整原因、审批人 | ❌ 仅显示"已调整"标记 | ✅ | ✅ |
| **待审批中的调整单** | ❌ 完全不显示 | ✅ | ✅ |

**三条不可逾越的红线：**

1. **只给结果，不给过程** —— 经纪人看到最终生效值，看不到"谁把谁的业绩从 3 万改到 2.55 万、为什么改"
2. **只给生效值，不给审批流** —— 待审批调整单对经纪人不可见，审批通过后才刷新
3. **业绩可见，薪酬不可见** —— 金额可以给，提点、提成、工资一律屏蔽

> **实现要求**：可见性在**服务端**按角色裁剪字段（返回 DTO 时置空），**禁止**依赖前端隐藏——前端隐藏等于数据已出网。

### 9.4 系统开关（仅保留一个）

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `panjia.perf.agent-view-peer-enabled` | **true** | 系统**唯一**相关开关。关闭后经纪人只能看到自己那一行的业绩，其余行隐藏姓名与金额 |

以下行为**固化为规则，不提供开关**：

- 可见范围固定为「本人参与的合同」，不提供本店 / 全量范围切换
- 经纪人不可全局搜索合同，只能从本人业绩下钻进入
- 他人提点、提成、工资、**他人全年业绩汇总**永久不可见
- **不提供历史月度业绩趋势展示**（任何角色、任何维度均不提供）

### 9.5 查看留痕与异议申诉

**查看留痕**：见 §3.6 `PerformanceViewLog`。合同页顶部固定提示"业绩信息属公司机密，禁止截图外传"。

**异议申诉闭环**：

```
经纪人对合同内业绩比例或他人业绩有异议
   → 合同详情页点「对这笔业绩有异议」
   → 生成业绩调整申请单（§3.3，带 contract_id 与来源标记 APPEAL）
   → 走店长 / 总监审批
```

> 把"私下争执"变成"系统内提单"——这是开放透明的真正价值。

### 9.6 风险提示（需客户知悉）

**业绩金额可见 ≈ 提成可推算**。职级提点（A1=55%、A2=60%…）在公司内难以保密，同事看到某人这一单 72,000 元、又是 A2 职级，可推算出其提成约 4.3 万元。

系统**无法阻断此类推算**，只能靠制度约束：

- 合同页顶部固定保密提示；
- 查看留痕做实，出问题时可追溯；
- 若客户认为该风险不可接受，可关闭 §9.4 的唯一开关，改为只显示业绩比例、不显示金额。

## 十二、架构决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| **A1** | 单层 Fact 模型，**不引入 Bill / SplitItem** | 贝壳已按"角色 × 合同 × 费用项"拆行；系统再拆分属重复 |
| **A2** | **零加工**：只原样记录金额，不存 `share_ratio` / `conversion_rate`，只有一个 `amount` | 已验证贝壳用"业绩比例 × 角色类型"完成拆分（1113.71 × 2 = 2227.42），自算必错 |
| **A3** | 事实**闭开区间不可原地修改**，修正 = 旧事实 expire + 新事实 | 财务审计刚需；与员工域 `salary_fact` 同构 |
| **A4** | 双口径独立：**一行原始记录生成 2 条事实** | 真实数据显示实收可大于应收（35 行）、应收=0 但实收>0（34 行），二者是独立指标，合并会丢失信息、无法独立冲销 |
| **A5** | **业绩事实正源 = 经纪人业绩结算明细表**，另两张表全部归档 | 三表金额完全勾稽（应收 206,274.04 / 实收 192,556.89，逐人差异 0.00）；结算表粒度最细且**唯一含费用项、角色类型、业绩比例、到账金额、支付手续费** |
| **A6** | `period` = **结算月**，`business_date` = 签约日，两者分离 | 已验证 49 行（15%）签约月早于结算月；前者是归属与结佣口径，后者是快照取数口径 |

## 十四、业务口径与实施可选项

### 14.1 业务口径定论

| # | 口径问题 | 结论 | 说明 |
|---|---|---|---|
| 1 | 业绩域是否**只**导入《经纪人业绩明细表》？另有《理房通到账明细表》（到账金额口径，应收 173,834.83 / 实收 171,537.62 / 到账 248,193.32），两者数值不同 | **只导入业绩明细表**，理房通表**不导入** | 两表都导会业绩翻倍，必须二选一 |
| 2 | 本样本无一手房（0 行），但 V4.3 §5.2 有一手房折算规则；`biz_type` 是否保留一手房与写字楼租赁 | **保留**（六类） | 不保留则一手房业务无法落库 |

| 6 | 调整引发历史已锁定月份工资差额如何发放（★V4.3 待确认 C） | **统一生成补发单**，并入发起人指定的发放月份，**不回改历史锁定数据** | 与 V4.3 §10.5 一致 |
| 7 | 合同跨月分批回款（★V4.3 待确认 D） | 按「**合同 × 到账月**」**分批结佣**，各角色人按业绩比例分摊每期实收 | V4.3 默认假设；需结佣域配合（CR-13） |

## 附录 A：数据落地全链路（import → performance）

> 本附录回答"**数据是怎么从导入域落到业绩域的**"，是 T4 / T5 的直接编码依据。

### A.1 链路总览：谁在什么时机做什么

```
① 用户上传贝壳 Excel（4 个 Sheet）
        ↓
【panjia-import】
② 多 Sheet 识别 → 跳过「导出说明」                       （CR-10）
③ 双层表头解析 → 第 1 行分组名 + 第 2 行真实列名          （CR-12）
④ 逐行归一化 → 一条原始行 = 一条 NormalizedRecord
⑤ 落 pj_normalized_record（权威源，永久保留，含 payload_json 全列）
⑥ 归档 → 发布 ImportBatchArchivedEvent
        { batchId, sourceType, period, supersededBatchIds, eventId }
        ↓
【panjia-performance】消费事件
⑦  幂等检查（uk_pcl_batch_event）
⑧  期间封账检查
⑨  冲销旧批次（supersededBatchIds 非空时）
⑩  分页拉 NormalizedRecord（每批 500）
⑪  【★ 合同归集】按 biz_type 取聚合键（订单号/合同号）→ 建或用 pj_perf_contract
⑫  逐行：业务语义校验 → 员工/门店归属 → 生成 2 条 PerformanceFact（挂 contract_id、生成 deal_key）
⑬  回算合同级 expect_total / real_total；判定合同 dept_id
⑭  写 consume_log（行数对账）
⑮  发布 PerformanceFactCreatedEvent（factIds + contractIds + dealKeys）
```

**职责分界：**

| import 域 | performance 域 |
|---|---|
| 知道 Excel、Sheet、表头、行数 | **不碰 Excel**，只认 `NormalizedRecord` |
| 做**格式 / 类型校验** | 做**业务语义校验** |
| 不知道什么是"应收 / 实收" | 知道业绩口径、归属、冲销 |

### A.5 落地代码骨架（`PerformanceEngine.build`）

```java
@Transactional
public void build(Long batchId, String eventId, List<Long> supersededBatchIds) {
    // ① 幂等（uk_pcl_batch_event）
    if (!consumeLog.tryLock(batchId, "ARCHIVED")) return;

    // ② 期间封账校验
    if (periodClose.isClosed(period)) throw new PeriodClosedException(period);

    // ③ 冲销旧批次（与重建同一事务）
    reverseService.reverseByBatches(supersededBatchIds, SUPERSEDE);

    // ④ 分页拉取 + 逐行处理
    int total = 0, normal = 0, abnormal = 0;
    for (List<NormalizedRecordDTO> page : importPort.page(batchId, 500)) {
        for (NormalizedRecordDTO nr : page) {
            total++;
            try {
                validate(nr);                                   // 业务语义校验
                EmployeeSnapshot emp = peoplePort.snapshotAt(     // 按签约日取快照
                        nr.getEmployeeCode(), nr.getBillDate());
                save(factOf(nr, emp, PERF_EXPECT, amt(nr, "当月应收业绩")));
                save(factOf(nr, emp, PERF_REAL,   amt(nr, "当月实收业绩")));
                normal += 2;
            } catch (AlignPendingException e) {
                abnormal++;      // 进待对齐，不阻断其他行（§4.5）
            }
        }
    }
    // ⑤ 行数对账：normal ÷ 2 应等于 total - abnormal
    consumeLog.finish(batchId, total, normal, abnormal);
}
```
