## 一、定位与职责边界

### 1.1 一句话目标

> **将 PERF_REAL 事实（贝壳实收）按合同聚合为审批单，经店长 → 财务 → 总监审批后锁定；审批通过的实收事实才能进入结佣与工资计算。**

### 1.2 核心职责

| # | 职责 | 说明 |
|---|---|---|
| ① | **实收审批单生命周期** | 自动建单（导入归档后）、手工提交、审批流转（Warm-Flow）、驳回重提、作废 |
| ② | **审批路由** | 发起人角色决定路由：店长/店助 → 财务 → 总监；财务 → 总监；总监 → 直接落点（APPROVED） |
| ③ | **贝壳实收分流建单** | `KE_RECEIVED` 来源：按「订单到账合计 vs 跨月新签应收合计」自动判定直建 APPROVED 还是走人工审批 |
| ④ | **历史工资直建** | `HISTORY_PAYROLL` 来源：历史已结算数据，跳过人工审批直建 APPROVED |
| ⑤ | **手工提交实收** | 业务人员从业绩域选 PERF_REAL 事实 → `PerformanceEngine` 调用本域端口建单 |
| ⑥ | **审批回调处理** | `ReceivedWorkflowListener` 监听工作流事件：finish → APPROVED + 发 `ReceivedApprovedEvent`；back → REJECTED；cancel → CANCELLED |
| ⑦ | **批量审批** | 总监勾选多张 SUBMITTED 审批单 → 线程池异步逐单办理（50 个分片并行） |

### 1.3 不负责什么（边界）

| ✅ 负责 | ❌ 严禁 |
|---|---|
| PERF_REAL 事实聚审批单 | **PERF_REAL 事实的生成、修改、冲销**（→ **performance**） |
| 审批流 + 状态机 | 提成金额 / 提点 / 保底计算（→ **payroll**） |
| 实收金额快照落审批单 | **改写 PERF_REAL 的 amount**（审批时金额已冻结，只读） |
| 审批通过后发布 `ReceivedApprovedEvent` | **结佣明细生成**（→ **commission** 域监听事件） |
| 合同号 / 订单号聚合 | **合同主信息维护**（→ **performance** 域 `pj_perf_contract`） |
| 审批链路按业务角色路由 | 反向依赖 payroll / ledger |
| | 直接读 `pj_perf_received_apply` 以外的 `pj_perf_*` 表做写操作 |

### 1.4 与业绩域的接口（ReceivedApplyPort 端口契约）

**为什么要引入端口接口？**

拆分前，实收审批 Service 直接依赖 `ImportBatchArchivedHandler`（performance 域）。拆分后若让 performance 域直接 `import IReceivedApplyService`，会形成 `panjia-performance → panjia-received` + `panjia-received → panjia-performance`（Entity/Mapper 临时依赖）的**循环依赖**。端口接口定义在独立的 `panjia-contracts` 叶子模块，performance 域只依赖 contracts，打破循环。

```
panjia-contracts          ← 唯一依赖点（端口接口 + DTO）
   ↑              ↑
   │              │
performance   received     （各自独立模块，互不直接依赖）
```

| 方向 | 契约 | 说明 |
|---|---|---|
| performance → received | `ReceivedApplyPort`（contracts） | 导入归档 / 手工提交时调用本域建单 |
| received → contracts | `ApprovalPort` | 发起工作流、办理任务 |
| received → contracts | `EventPort` + `ReceivedApprovedEvent` | 审批通过后发布事件，结佣域消费 |

### 1.5 业务锚点

| 锚点 | 规则 | 落地 |
|---|---|---|
| **聚合键** | 全部业务类型统一**订单号优先**；合同号为空时仍按订单号聚合 | `autoCreateForBatch` / `autoCreateForReceivedBatch` 均按 `fact.orderNo` 分组 |
| **UI 列标题** | 列表页仍叫「合同号」（历史习惯），实际取值优先 `contractNo`、为空回退 `orderNo` | 前端展示层处理，后端保持订单号优先聚合 |
| **审批单粒度** | 同一 `(period, contractNo)` 或 `(period, orderNo)` 只允许一张未完结实收审批单 | 部分唯一索引 `uk_rapp_period_contract` / `uk_rapp_period_order` |
| **并发建单防护** | `DuplicateKeyException` 捕获 → 告警跳过，不阻塞批次 | 所有自动建单入口统一捕获 |
| **幂等合并** | 同订单号当月已有 DRAFT / SUBMITTED 单 → 新事实绑定并入（不新建） | `createApplyForRealFactsInternal` |
| **已 APPROVED 跳过** | 同订单号当月已 APPROVED → 拒绝新事实合入（防绕过审批） | `autoCreateForReceivedBatch` |

## 三、核心流程

### 3.1 导入归档自动建单（ImportBatchArchivedHandler → ReceivedApplyPort）

```
OutboxDispatcher
    └── 消费 ImportBatchArchivedEvent
         └── ImportBatchArchivedHandler.handle()
              ├── ① sourceType 过滤（KE_SIGNED / KE_RECEIVED / HISTORY_PAYROLL 其余忽略）
              ├── ② PerformanceEngine.buildFromBatch()   ← 业绩事实生成
              └── ③ 按 sourceType 分发到 ReceivedApplyPort 不同方法：
                   │
                   ├── HISTORY_PAYROLL
                   │    └── receivedApplyPort.autoCreateApprovedForBatch()  ← APPROVED 直建
                   │
                   ├── KE_RECEIVED
                   │    └── receivedApplyPort.autoCreateForReceivedBatch()  ← 分流建单（§3.2）
                   │
                   └── 其余（KE_SIGNED / 默认）
                        └── receivedApplyPort.autoCreateForBatch()          ← DRAFT + 工作流
```

**autoCreateForBatch 内部流程（通用建单）：**

```
① 查批次内未绑定 PERF_REAL 事实（batchId + factType=PERF_REAL + factStatus=ACTIVE + receivedApplyId IS NULL）
② 按 orderNo 分组
③ 批量预加载：活跃审批单（DRAFT/SUBMITTED/APPROVED）+ PERF_EXPECT 应收合计
④ 逐订单号：
   ├── 无活跃单 → 新建 ReceivedApply（DRAFT）→ 绑定事实 → startWorkflow
   ├── 已有 DRAFT/SUBMITTED → merge（追加事实、重算 item_count + received_amount）
   └── 已有 APPROVED → 跳过（日志记录）
⑤ DuplicateKeyException 捕获 → 跳过
```

### 3.2 贝壳实收分流建单（KE_RECEIVED：直建 APPROVED vs 人工审批）

**触发源：** `ImportBatchArchivedEvent` 的 `sourceType = KE_RECEIVED`

**分流判定规则（合同维度，不再按经纪人拆分）：**

```java
boolean needManualReview = needManualReview(realSum, expectTotal);

private static boolean needManualReview(BigDecimal arrival, BigDecimal expectTotal) {
    BigDecimal amt = arrival == null ? BigDecimal.ZERO : arrival;
    if (amt.signum() >= 0) {
        // 到账合计 ≥ 0：到账 < 订单跨月新签合计 → 人工；≥ → 自动通过
        return amt.compareTo(expectTotal == null ? BigDecimal.ZERO : expectTotal) < 0;
    }
    // 到账合计 < 0（事后扣减负到账）：该订单存在正当数新签（负 < 正恒成立）→ 自动通过
    // 无正当数新签（数据异常）→ 人工
    return expectTotal == null || expectTotal.signum() <= 0;
}
```

**判定口径：**

| 订单到账合计 | 订单跨月新签应收合计 | 判定 | 建单方式 |
|---|---|---|---|
| ≥ 0 | 到账 ≥ 应收 | ✅ 自动通过 | APPROVED 直建（无流程实例）+ 发 `ReceivedApprovedEvent` |
| ≥ 0 | 到账 < 应收 | ❌ 需人工审批 | DRAFT + startWorkflow |
| < 0（负到账） | 有正当数新签 | ✅ 自动通过 | APPROVED 直建 |
| < 0（负到账） | 无正当数新签 | ❌ 数据异常 | DRAFT + startWorkflow |

**幂等策略：**

| 已有活跃单状态 | 分流结果 | 处理 |
|---|---|---|
| APPROVED | — | 跳过（防绕过审批） |
| DRAFT / SUBMITTED | 任何分流 | **从严合并**：新事实并入人工审批流程（不改变审批状态） |
| 无 | 直建 | APPROVED 直建 + 发事件 |
| 无 | 人工 | DRAFT + startWorkflow |

### 3.3 手工提交实收（PerformanceEngine → ReceivedApplyPort.createApplyForRealFacts）

**入口：** 业务人员（店长 / 算薪）从业绩域选 PERF_REAL 事实 → 调用 `PerformanceEngine` 手工提交路径

**PerformanceEngine 改动（V1.0 首拆）：**

```java
// ★ 删除死代码 ReceivedApplyMapper 字段（以前直接依赖，改为走端口）
// private final ReceivedApplyMapper receivedApplyMapper; ← 已删

// ★ 手动提交实收路径：从 createApplyForRealFacts(List<PerformanceFact>, ...)
//          改为 receivedApplyPort.createApplyForRealFacts(factIds, period, operatorId, null)
//          参数用 factIds 替代 PerformanceFact 实体，避免跨域传递实体
```

**factIds → PerformanceFact 委托链：**

```
ReceivedApplyPort.createApplyForRealFacts(Collection<Long> factIds, ...)
    │
    ▼
ReceivedApplyServiceImpl.createApplyForRealFacts()
    │  从 performance 域（临时）：factMapper.selectByIds(factIds) → List<PerformanceFact>
    ▼
createApplyForRealFactsInternal(List<PerformanceFact>, ...)
    │  复用 §3.1 的公共建单段（按 orderNo 分组 → 预加载 → 逐订单号建/合并 → 绑定 → startWorkflow）
    ▼
返回新建审批单数量
```

### 3.4 审批流转（按发起人身份：店长→财务→总监；总监直接落定）

**发起人路由规则：**

| 发起人角色 | 审批链路 | 说明 |
|---|---|---|
| 店长 / 店助 / 系统自动 | **财务 → 总监 → 生效** | 走 `panjia.flow.skip_finance` 配置可跳过财务 |
| 财务 | **总监 → 生效** | 直达终审 |
| 总监 | **直接生效**（APPROVED） | 不进入工作流 |

**状态机：**

```
DRAFT ──startWorkflow──▶ SUBMITTED ──总监通过──▶ APPROVED
    │                        │                          │
    │                        └──驳回──▶ REJECTED        └──发 ReceivedApprovedEvent
    │                                                    │
    └──作废──▶ CANCELLED                                 └──驳回重提 → DRAFT → 重走流程
```

**工作流节点常量：**

```java
NODE_FINANCE  = "rcv_finance"    // 财务审批节点
NODE_DIRECTOR = "rcv_director"   // 总监审批节点
CONFIG_SKIP_FINANCE = "panjia.flow.skip_finance"  // 跳过财务开关
```

**审批回调处理（ReceivedWorkflowListener → handleWorkflowEvent）：**

| 工作流事件 | 审批单状态变更 | 后续动作 |
|---|---|---|
| `finish` | → `APPROVED` | 落 `approver_id` + `approve_time` + 发 `ReceivedApprovedEvent` |
| `back` | → `REJECTED` | 落 `approver_id` + `approve_time`（驳回留痕） |
| `cancel` | → `CANCELLED` | 终止运行中的流程实例 |
| `invalid` / `termination` | → `CANCELLED` | 同 cancel |

**总监节点回调：**

```java
stampApproverOnDirectorNode(applyId, handlerId)
// 财务节点办理完成后，总监节点进入前回填最近审批人/审批时间
// 覆盖「我的待办 → 去处理 → 通过」原生路径不经过业务 approve 入口的场景
```

**批量审批：**

```
POST /received/apply/batch-approve
① 同步预检：一条 IN 查询取所有 SUBMITTED 单 + myCurrentTasks 鉴权
② 异步分片：50 个一片 → TaskExecutor 并行 → completeTaskAsSys 逐单办理
③ 单失败不中断整批，返回 success/skipped/failed 清单
```

## 四、数据模型

### 4.1 Entity 归属（留在 panjia-performance 域）

**V1.0 当前态：** 所有数据层代码暂不迁出，实收域 pom 临时依赖 performance 域访问。

### 4.2 表结构（pj_perf_received_apply）

表名暂保持 `pj_perf_received_apply`（Flyway V140002 已创建），不重命名为 `pj_received_*`——V1.1 迁入时同步改表名或保持均可（当前不做物理迁移）。

```sql
CREATE TABLE pj_perf_received_apply (
    id                      BIGINT                 PRIMARY KEY,   -- 雪花 ID
    apply_no                VARCHAR(32)            NOT NULL,      -- RCV+yyyyMMddHHmmssSSS
    period                  VARCHAR(7)             NOT NULL,      -- 结算月 YYYY-MM
    contract_no             VARCHAR(64)            NOT NULL,      -- 合同号（业务聚合键之一）
    order_no                VARCHAR(64),                          -- 订单号（一手房/家装荐客等纯订单聚合）
    biz_type                VARCHAR(32),                          -- 业务类型（建单时从实收事实快照）
    property_address        VARCHAR(255),                         -- 物业地址（快照）
    business_date           TIMESTAMP,                            -- 签约/业务时间（快照）
    dept_id                 BIGINT,                               -- 归属门店（跨门店合作单为空）
    batch_id                BIGINT,                               -- 首次生成该单的导入批次（手工可空）
    received_amount         NUMERIC(18,2)          NOT NULL DEFAULT 0, -- 实收业绩合计
    expected_amount         NUMERIC(18,2)          NOT NULL DEFAULT 0, -- 应收业绩合计（留痕快照）
    item_count              INT                    NOT NULL DEFAULT 0, -- 明细条数（PERF_REAL 事实条数）
    status                  VARCHAR(16)            NOT NULL,      -- DRAFT/SUBMITTED/APPROVED/REJECTED/CANCELLED
    current_node            VARCHAR(16),                          -- FINANCE/DIRECTOR（终审/驳回后回写 null）
    process_instance_id     VARCHAR(64),                          -- Warm-Flow 实例 ID
    applicant_id            BIGINT,                               -- 发起人（系统自动为空）
    approver_id             BIGINT,                               -- 终审人
    approve_time            TIMESTAMP,                            -- 终审时间
    version                 INT                    NOT NULL DEFAULT 0,  -- 乐观锁
    create_time             TIMESTAMP              NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time             TIMESTAMP              NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**状态枚举：**

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `DRAFT` | 草稿（新建未提交） | 提交、作废、合并新事实 |
| `SUBMITTED` | 审批中（工作流运行） | 等待审批人办理、作废、合并新事实 |
| `APPROVED` | 审批通过 | 拒绝新事实合并（防绕过） |
| `REJECTED` | 已驳回 | 重新提交、作废 |
| `CANCELLED` | 已作废 | 终态 |

### 4.3 Mapper 归属（留在 panjia-performance 域）

| Mapper | 全限定类名 | 作用 | 本域使用场景 |
|---|---|---|---|
| `ReceivedApplyMapper` | `com.panjia.performance.mapper.ReceivedApplyMapper` | 审批单 CRUD | 本域 Service 直接注入使用 |
| `PerformanceFactMapper` | `com.panjia.performance.mapper.PerformanceFactMapper` | 事实查询（按 batchId 查未绑定 PERF_REAL、按订单号查应收合计等） | 本域 Service 临时注入；V1.3 抽成 contracts 端口后移除 |

## 五、ReceivedApplyPort 端口契约

### 5.1 接口定义（4 方法 + 参数说明）

定义位置：`panjia-contracts/src/main/java/com/panjia/contracts/port/ReceivedApplyPort.java`

```java
public interface ReceivedApplyPort {

    /** ① 通用建单：导入归档后自动建单并提交（DRAFT + 工作流） */
    int autoCreateForBatch(Long batchId, String period, Long operatorId);

    /** ② 历史直建：HISTORY_PAYROLL 来源直建 APPROVED（跳过人工审批） */
    int autoCreateApprovedForBatch(Long batchId, String period, Long operatorId);

    /** ③ 贝壳实收分流：KE_RECEIVED 按到账 vs 新签自动判定直建/人工审批 */
    int autoCreateForReceivedBatch(Long batchId, String period, Long operatorId);

    /** ④ 手工提交：从 factIds 建实收审批单，跨域传 ID 不传实体 */
    int createApplyForRealFacts(Collection<Long> factIds, String period,
                                 Long operatorId, Long batchId);
}
```

**参数说明：**

| 参数 | 类型 | 说明 | 可空 |
|---|---|---|---|
| `batchId` | `Long` | 导入批次 ID；手工提交可 null | ✅（方法④） |
| `period` | `String` | 归属期间 `YYYY-MM` | ❌ |
| `operatorId` | `Long` | 操作人 ID；事件驱动场景可 null（内部兜底） | ✅（方法①②③④ 均会兜底） |
| `factIds` | `Collection<Long>` | PERF_REAL 事实 ID 集合（已 ACTIVE、已造好） | ❌（方法④） |

**返回值：** 新建审批单数量（合并不计；并发撞唯一索引时返回小于预期）

### 5.2 实现类（ReceivedApplyServiceImpl 同时实现 IReceivedApplyService + ReceivedApplyPort）

```java
@Service
@RequiredArgsConstructor
public class ReceivedApplyServiceImpl
        implements IReceivedApplyService, ReceivedApplyPort {

    // ===== 同时实现两个接口 =====
    // IReceivedApplyService：对内 Service 接口（提供 list / detail / approve / resubmit / cancel / batchApprove 等）
    // ReceivedApplyPort：跨域端口接口（4 个建单方法）

    private final ReceivedApplyMapper applyMapper;        // ← 来自 performance 域（临时）
    private final PerformanceFactMapper factMapper;       // ← 来自 performance 域（临时）
    private final ApprovalPort approvalPort;              // ← 来自 contracts
    private final EventPort eventPort;                    // ← 来自 contracts（发 ReceivedApprovedEvent）
    private final ConversionFactorPort conversionFactorPort;  // ← 来自 contracts（折算因子）
    private final FactConversionResolver factConversionResolver; // ← 来自 performance（临时）
    private final DeptService deptService;                // ← ruoyi-system（部门树）
    private final ConfigService configService;            // ← ruoyi-system（配置开关）
    private final TaskExecutor taskExecutor;              // ← Spring（批量审批异步）
}
```

**两个接口方法的对应关系：**

| ReceivedApplyPort 方法 | 内部委托 | IReceivedApplyService 同名方法 | 实现差异 |
|---|---|---|---|
| `autoCreateForBatch` | → `createApplyForRealFactsInternal(List<PerformanceFact>, ...)` | 无 | 查事实 → 委托公共段 |
| `autoCreateApprovedForBatch` | → 独立批量预加载逻辑 | 无 | 直建 APPROVED，不走工作流 |
| `autoCreateForReceivedBatch` | → 独立批量预加载 + 分流判定 | 无 | `needManualReview()` 判定分支 |
| `createApplyForRealFacts(Collection<Long> factIds, ...)` | → 查事实 → 公共段 | `createApplyForRealFacts(List<PerformanceFact>, ...)` | Service 版本直接收实体；Port 版本先查再委托 |

### 5.3 factIds → PerformanceFact 委托链

```
PerformanceEngine（手工提交路径）
    │
    │  receivedApplyPort.createApplyForRealFacts(factIds, period, operatorId, null)
    │  ↑ 只传 factIds（contracts 层不得依赖 performance 域实体）
    ▼
ReceivedApplyPort (contracts)
    │
    ▼
ReceivedApplyServiceImpl.createApplyForRealFacts(Collection<Long> factIds, ...)
    │  factMapper.selectBatchIds(factIds) → List<PerformanceFact>
    │  ↑ 临时依赖 performance 域 Mapper
    ▼
createApplyForRealFactsInternal(List<PerformanceFact> realFacts, ...)
    │  与 autoCreateForBatch 完全共用的公共建单段
    │  ① 按 orderNo 分组
    │  ② 批量预加载：活跃审批单 + PERF_EXPECT 应收合计
    │  ③ 逐订单号：新建 / 合并 / 跳过
    │  ④ DuplicateKeyException 捕获
    ▼
返回新建数量
```

> **V1.3 解耦目标：** 第 ② 步 `factMapper.selectBatchIds(factIds)` 改为 `performanceFactQueryPort.listByIds(factIds)`（contracts 端口），Service 不再注入 `PerformanceFactMapper`。

## 六、CI / ArchUnit 约束

| # | 规则 | 说明 |
|---|---|---|
| R1 | **禁止 `import com.panjia.performance.service.*` / `import com.panjia.performance.handler.*`** | 本域不可反向依赖 performance 域的 Service / Handler |

## 十、事务、并发、幂等

### 10.1 事务边界

| 场景 | 策略 |
|---|---|
| 自动建单（4 个 Port 方法） | `@Transactional`：查活跃单 + INSERT + bindFacts + startWorkflow |
| 审批回调 handleWorkflowEvent | `@Transactional`：审批单状态更新 + 发事件 |
| 作废 cancel | `@Transactional`：解绑事实 + 终止工作流 + 置 CANCELLED |
| 驳回重提 resubmit | `@Transactional`：置 SUBMITTED + 重走流程 |
| 批量审批 | **每张单各自独立事务**（`completeTaskAsSys` 逐单）；分片并行在事务外 |

### 10.2 并发控制

| 风险 | 防护 |
|---|---|
| 同一订单号同一 period 重复建单 | `uk_rapp_period_contract` / `uk_rapp_period_order` 部分唯一索引；`DuplicateKeyException` 捕获跳过 |
| 导入归档事件重复消费 | performance 域消费日志幂等（`IMPORT_BATCH_ARCHIVED` 已有 SUCCESS/PARTIAL 则跳过） |
| 批量审批同一单据被多人同时办理 | 端口 `completeTaskAsSys` 底层任务锁；单据 version 乐观锁兜底 |
| 驳回重提与审批回调并发 | 审批单状态机守卫（SUBMITTED 状态允许走工作流，REJECTED 只允许 resubmit） |

### 10.3 幂等锚点

| 入口 | 锚点 |
|---|---|
| autoCreateForBatch | 先查 `receivedApplyId IS NULL AND status=ACTIVE` → 只处理未绑定事实 |
| autoCreateApprovedForBatch | 批量预加载活跃单 → 存在即跳过 |
| autoCreateForReceivedBatch | 同 autoCreateForBatch + 分流判定幂等 |
| createApplyForRealFacts | 同上 |
| 审批回调 | 审批单 `status + version`（APPROVED/REJECTED/CANCELLED 终态不重复处理） |
| 作废 | `status IN (DRAFT, SUBMITTED)` 守卫 |
| startWorkflow | 重入防护：`processInstanceId` 非空时不重复 start |
