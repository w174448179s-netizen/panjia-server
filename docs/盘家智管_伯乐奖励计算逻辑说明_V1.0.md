# 盘家智管 · 伯乐奖励（千里马提成）计算逻辑说明

> 版本：V1.0（2026-11-07）
> 适用代码：panjia-server `panjia-payroll` 当前实现
> 口径基准：2026-11 客户确认口径（千里马入职当月生效、离职次月失效；两种模式均按**新签导入月**逐期回溯：金额比例为「该期千里马折算后结佣业绩 × 该期伯乐职级配置比例」逐期累加，不封顶）
> 关联文档：《盘家智管_薪酬结算域详细设计_V1.0》《盘家智管_薪酬与收支_产品化架构设计_V1.10》《盘家智管_薪酬与收支_测试用例_V1.0》

## 1. 结论摘要

1. 伯乐奖励有**两套模式**，按**职级**的 `ruleContent` 配置，**不限角色**：
   - `RATE_ADD`：在师傅本人对应新签月的结佣提点链上，增加「加点费率 × 该月有效千里马数」，封顶 `mentorBonusRateCap`（默认 +10%）。
   - `AMOUNT_RATIO`：按**新签导入月逐期**计算「该期千里马折算后结佣业绩 × 该期师傅职级配置比例」，逐期累加，**不封顶**；仅该期规则为 `AMOUNT_RATIO` 时计入。
2. **金额比例的基数只与「结佣业绩」有关**：每期取该期结佣明细按 `bizType` 折算后的金额（一手房 90.24%、其他 96%），**与职级提点、绩效扣减、招聘加点、自购加成、人工调整全部无关**；自购单业绩**计入**基数。
3. **比例 X% 是规则里配置的 `mentorBonusAmountRatio`**：取**该新签月规则快照**中师傅**该期职级**的配置值；7 月与 8 月配置不同则分别按 7 月、8 月计算；缺失期间切片时回退算薪月职级/快照。
4. 师傅与千里马的关系来自员工域 `MENTOR` 事实；判定口径为**千里马入职当月生效、离职次月失效**。两种模式均取**对应新签月的关系切片**。
5. **两种模式都需要按新签导入月逐期回溯**：`RATE_ADD` 取该月规则快照、职级、积分、人工调整、有效千里马数；`AMOUNT_RATIO` 取该月关系、该月师傅职级与该月规则比例，不取积分/人工调整（不影响基数）。
6. 伯乐奖励在所有明细算完后**统一回加应发并重算个税/实发**，避免依赖员工计算顺序。
7. 两种模式按「职级 × 期间」互斥，同一职级同一期间只生效一种；`RATE_ADD` 期间不重复发放金额比例奖励。
8. **新旧口径差异**：`AMOUNT_RATIO` 由「结佣月口径」改为「新签导入月期间口径」。某新签月规则不是 `AMOUNT_RATIO`（如 `RATE_ADD` 或未配置）则该期**不计入金额奖励**；7 月配 2%、8 月配 3% 时，7 月业绩按 2%、8 月业绩按 3%。

## 2. 名词与口径

| 名词 | 含义 |
|---|---|
| 千里马 / 徒弟 | `MENTOR` 事实中「员工 → 师傅」关系的员工一方（apprentice） |
| 伯乐 / 师傅 | `MENTOR` 事实指向的员工（mentor） |
| 新签导入月 `rulePeriod` | 结佣明细所绑定的新签业绩事实的归属月；不是签约月，也不是结佣导入月。**两种模式均按该月切片回溯**；未绑定事实的结佣归到算薪月 |
| 结佣月 | 本次算薪的归属月（算薪月）。未绑定新签事实的结佣归到该月，并使用主快照/当前职级/算薪月关系 |
| 折算后结佣业绩 `periodPerf` | 该新签月结佣明细按 `bizType` 折算后的金额合计；就是算薪里的「结佣业绩」，**不含任何提点/扣减** |
| 最终提点 `finalRate` | `baseRate`（店长为 `personalRate`）+ 绩效比例扣减 + 招聘加点 + 人工提点调整 |
| 结佣提成金额 `periodIncome` | `periodPerf × 该期间最终提点`，月度合计即 `commissionIncome`；**仅用于个人提成，不作为伯乐金额比例基数** |
| 有效千里马数 | 在新签月月末切片中，`MENTOR` 事实指向该师傅、且该千里马按在岗规则仍计入的员工数 |

> 「合格千里马」在代码中的实际含义 = **有效伯乐关系 + 入职/离职月规则命中**，**不包含**业绩门槛、从业年限门槛。原「徒弟须从业 ≥ 2 年」门槛已按 2026-11 口径取消。

## 3. 数据来源与装配

### 3.1 员工域：按月份取有效伯乐关系

代码：`SalaryFactMapper#selectActiveFactsWithEmployedAt`、`EmployeeServiceImpl#findMentorRelationsAt`

```sql
SELECT DISTINCT ON (f.employee_id) f.*
FROM pj_people_salary_fact f
JOIN pj_people_employee e ON e.employee_id = f.employee_id
WHERE f.fact_type = 'MENTOR'
  AND f.effective_date <= 月末
  AND (f.expire_date IS NULL OR 月末 < f.expire_date)
  AND f.value <> ''
  AND e.status <> 'VIRTUAL'
  AND (e.hire_date IS NULL OR e.hire_date <= 月末)
  AND (e.leave_date IS NULL OR e.leave_date >= 月初)
ORDER BY f.employee_id, f.effective_date DESC, f.create_time DESC
```

返回 `千里马员工ID → 师傅员工ID`。每人每月最多一条有效关系。

### 3.2 算薪批次：按新签月构建关系与人数

代码：`PayrollBatchService#buildCalcInput`

- 先收集本批次所有结佣、新签明细的 `rulePeriod`，加上算薪月本身，得到 `requiredPeriods`。
- 对每个 `rulePeriod`：
  - 构建该月规则快照 `periodSnapshots`；
  - 调 `findMentorRelationsAt(该月1日)` 得到该月有效关系，反向计数写入 `periodApprenticeMap[rulePeriod]`（师傅 → 千里马数），同时写入 `periodMentorRelationMap[rulePeriod]`（千里马 → 师傅，两种模式共用）；
  - 非算薪月再查该月职级切片 `periodLevelMap`、积分 `periodScoreMap`、人工调整 `periodAdjustMap`；职级切片覆盖「有明细员工 + 全部伯乐」，用于金额比例取伯乐该期职级。
- `periodApprenticeMap` 仅供 `RATE_ADD` 逐期回溯使用；`periodMentorRelationMap` + `periodLevelMap` + `periodSnapshots` 供 `AMOUNT_RATIO` 逐期计算。
- `AMOUNT_RATIO` 不使用积分、人工调整、招聘加点，也不使用算薪月的主快照/当前职级（仅作缺失兜底）。

### 3.3 为什么必须「全员按月份切片」

历史实现只从「当期有结佣的员工」里取千里马关系。千里马当月没有结佣时取不到关系，引擎会回退到算薪月的千里马数，导致**千里马入职前的历史新签月被错误加上加点**（生产实例：毕凤树 2026-04 新签月被算 +2%，但牟真琴 7 月才入职）。当前改为员工域全员按月份切片，关系在哪个新签月有效就在哪个新签月生效。

## 4. 生效 / 失效判定

以「新签月」为单位，取该月**月末**的关系快照：

| 场景 | 是否计入该新签月 | 判定条件 |
|---|---|---|
| 千里马入职当月 | 计入 | `hire_date <= 月末` |
| 千里马离职当月 | 计入 | `leave_date >= 月初` |
| 千里马离职次月 | 不计入 | `leave_date < 月初` |
| 师傅关系生效当月 | 计入 | `effective_date <= 月末` |
| 师傅关系失效月 | 不计入 | `expire_date <= 月末`（闭开区间，失效日为失效月 1 号） |
| 关系值为空（无师傅） | 不计入 | `value <> ''` |
| 虚拟员工 | 不计入 | `status <> 'VIRTUAL'` |
| 月中变更师傅 / 职级 | 按月末快照，整月归属月末关系持有者 | 不按天拆分 |
| 入职日期为空的历史员工 | SQL 放行，可能计入 | 见 §11 问题 H |

> 边界提醒：`expire_date` 是**闭开区间**的右端。若把关系失效日维护成「7 月 31 日」，则 7 月整月都不计；应维护为「8 月 1 日」。

## 5. 逐新签月回溯流程（两种模式）

> `RATE_ADD` 与 `AMOUNT_RATIO` 都按新签导入月切片；差异仅在 `AMOUNT_RATIO` 不使用积分/人工调整，且只在该期规则为 `AMOUNT_RATIO` 时计入（见 §6、§7）。

```
结佣明细（lockedItems）
  └─ 绑定新签业绩事实 → 新签导入月 rulePeriod
       ├─ 期间规则快照            periodSnapshots[rulePeriod]
       ├─ 期间职级（月末切片）      periodLevelMap[rulePeriod]（含伯乐）
       ├─ 期间积分 → 绩效比例扣点   periodScoreMap[rulePeriod]（仅 RATE_ADD）
       ├─ 期间人工提成点调整        periodAdjustMap[rulePeriod]（仅 RATE_ADD）
       ├─ 期间有效千里马数          periodApprenticeMap[rulePeriod]（RATE_ADD）
       ├─ 期间千里马→伯乐关系        periodMentorRelationMap[rulePeriod]（AMOUNT_RATIO）
       ├─ 期间折算业绩              applyConversion(明细, 期间快照) = periodPerf
       └─ 期间结佣提成              periodIncome = periodPerf × 期间最终提点
```

- **伯乐金额比例取的是 `periodPerf`（折算后结佣业绩），不是 `periodIncome`。**
- 算薪月本身（未绑定新签事实的结佣）：使用主快照、员工当前职级、算薪月积分、算薪月调整单、算薪月千里马数/关系。
- `RATE_ADD`：某期间切片存在时**以切片为准**（该月无千里马即 0）；切片缺失按 0（失败关闭，见 §11 问题 B）。
- `AMOUNT_RATIO`：某期间关系切片缺失则该期不计入（失败关闭）；该期伯乐职级/规则快照缺失时分别回退算薪月职级/主快照。
- 明细落地的 `commissionCalcProcess` 逐期记录 `{month, perf, rate, income}`；若该期有 RATE_ADD 加点，额外记录 `mentorAdd`。
- 伯乐奖励落地的 `mentorBonusCalcProcess` 按期间逐条记录 `{month, base, ratio, bonus}`，见 §9。

## 6. RATE_ADD（提点加点）

### 6.1 公式

```
加点前最终提点 = baseRate（店长用 personalRate）+ 绩效比例扣减 + 人工提点调整
招聘加点       = MIN(mentorBonusRateAdd × 该新签月有效千里马数, mentorBonusRateCap)
该期间最终提点 = 加点前最终提点 + 招聘加点
periodIncome   = 期间折算结佣业绩 × 该期间最终提点
```

- 默认值：`mentorBonusRateAdd = 0.02`，`mentorBonusRateCap = 0.10`（以职级 `ruleContent` 配置为准）。
- 模式不是 `RATE_ADD` 时加点为 0。
- **不限角色**：经纪人、店长、总监只要对应职级配置为 `RATE_ADD` 都会计算。
  - 店长：加在 `personalRate` 口径的**个人结佣**上，不加到团队提成 `teamRate`。
  - 总监：加在 `baseRate` 口径的**个人结佣**上，不加到门店跳点提成。
  - 详见 §11 问题 D。
- 加点结果会写入明细 `mentor_add`（仅当前算薪月职级为 `RATE_ADD` 时落库），并已包含在 `finalRate` / `commissionIncome` 中。

### 6.2 示例

| 条件 | 取值 |
|---|---|
| 师傅 P：A2，`baseRate=60%`，RATE_ADD 2%，封顶 10% | — |
| 千里马 A：2026-07 入职，`MENTOR=P` 自 2026-07 起生效 | — |
| P 本月结佣：2026-04 新签月折算业绩 100,000 | 4 月有效千里马数 0 → 提点 60% → **60,000** |
| P 本月结佣：2026-07 新签月折算业绩 50,000 | 7 月有效千里马数 1 → 提点 62% → **31,000** |
| `commissionIncome` | **91,000** |
| 明细 `mentor_add` | **0.02**（算薪月/7 月口径） |
| `commissionCalcProcess` | 4 月 `rate=0.60`；7 月 `rate=0.62, mentorAdd=0.02` |

> **原生产问题修复点**：4 月新签月不受 7 月才入职的千里马影响，不会被错误加 2%。

## 7. AMOUNT_RATIO（金额比例）

### 7.1 公式（新签导入月期间口径）

```
师傅奖励 = Σ(新签导入月 p) [ 该期千里马折算后结佣业绩 × 该期师傅职级配置比例 ]

其中：
  该期千里马折算后结佣业绩 = applyConversion(p 期结佣明细, periodSnapshots[p])
  该期师傅职级            = periodLevelMap[p][师傅ID]（缺失回退算薪月职级）
  该期师傅配置比例        = periodSnapshots[p].rank(该期职级).ruleContent.mentorBonusAmountRatio
成立条件：
  ① 该期伯乐关系有效：periodMentorRelationMap[p] 将千里马指向该师傅；
  ② 该期师傅职级规则模式为 AMOUNT_RATIO（RATE_ADD 期不计金额，避免重复激励）；
  ③ 该期折算后结佣业绩 > 0。
```

- **逐期计算后累加，不封顶**；每期金额 `round2` 后相加，溯源 JSON 各期 `bonus` 之和等于 `mentor_bonus`。
- **不同新签月配置比例不同时分别计算**：7 月业绩按 7 月比例、8 月业绩按 8 月比例；算薪月主快照/当前职级只作缺失兜底。
- 基数就是该期明细的折算后结佣业绩，与前端展示的「结佣业绩」同源；自购单业绩**计入**基数，自购加成点数不改变伯乐奖励。
- 负数业绩照算：退单/冲红会按该期负业绩产生负奖励，直接冲减应发（不退单时已发过的奖励在此冲回）。
- 基数不含任何提点/扣减：不看 `finalRate`、不看绩效扣减、不看招聘加点、不看人工调整。
- 比例默认 0.02，以该期职级规则为准。
- 奖励金额在全部明细算完后回加 `gross`，并重算个税、实发。
- **关系口径**：按新签导入月关系切片。千里马入职前的新签月、离职次月及以后的新签月、或该期规则不是 `AMOUNT_RATIO` 的月份，均**不计入**。
- 未绑定新签事实的结佣归到算薪月，使用算薪月关系、当前职级、主快照。

### 7.2 基数包含 / 不包含

| 项目 | 是否进入基数 | 说明 |
|---|---|---|
| 结佣业绩（按 bizType 折算后） | **计入（就是基数本身）** | 一手房 90.24%，其他 96% |
| 职级提点 `baseRate` / 店长 `personalRate` | **不计入** | 基数与提点无关 |
| 绩效比例扣减（可正可负） | **不计入** | 基数与扣减比例无关 |
| 招聘加点 `RATE_ADD` | **不计入** | 基数是业绩，不是提成 |
| 自购单加成 | **不计入** | 只影响提成，不影响结佣业绩 |
| 人工提成点调整 | **不计入** | 同上 |
| 绩效金额扣款 `perfDeductFee` | **不计入** | 支出项 |
| 团队提成 / 门店提成 | **不计入** | 不是结佣业绩 |
| 底薪 / 保底补足 / 奖金 / 其他收入 | **不计入** | — |
| 社保、公积金、考勤、商保、宿舍、负工资、积分、其他支出 | **不计入** | 支出项 |
| 千里马自己的伯乐奖励（两种模式） | **不计入** | 奖励在所有明细算完后回加，不参与基数 |

### 7.3 示例

| 条件 | 取值 |
|---|---|
| 师傅 P：S1，2026-07 规则 `AMOUNT_RATIO=2%`，2026-08 规则 `AMOUNT_RATIO=3%`，不封顶 | — |
| 千里马 A：2026-07 入职，`MENTOR=P` 自 2026-07 起生效 | — |
| A 本算薪月结佣：新签 2026-07 折算业绩 24,000 | 7 月关系有效且模式为 AMOUNT_RATIO：24,000 × 2% = **480.00** |
| A 本算薪月结佣：新签 2026-08 折算业绩 24,000 | 8 月关系有效且模式为 AMOUNT_RATIO：24,000 × 3% = **720.00** |
| 基数/奖励合计 | 48,000 / **1,200.00**（不是 48,000 × 3%，也不是 48,000 × 2%） |
| 同期 A 的 `commissionIncome`（举例 14,400） | **不参与**，基数仍是 48,000 |
| `mentor_bonus` | **1,200.00** |
| `mentor_bonus_calc_process` | `[{"month":"2026-07","base":24000.00,"ratio":0.02,"bonus":480.00},{"month":"2026-08","base":24000.00,"ratio":0.03,"bonus":720.00}]` |

> 若 2026-07 师傅职级规则仍为 `RATE_ADD`，则 7 月业绩**不进入金额奖励**，仅按 8 月 24,000 × 3% = 720.00；7 月业绩只走 §6 的提点加点。

## 8. 与应发、个税、批次汇总的关系

### 8.1 应发

```
应发 gross = 结佣提成 + 团队提成 + 保底补足 + 门店提成 + 底薪 + 奖金 + 其他收入
            + 伯乐奖励（后处理回加）
```

- `RATE_ADD` 的加点不单独生成金额，而是在计算 `commissionIncome` 时已进入提点链。
- `AMOUNT_RATIO` 的奖励是独立金额，主循环先按「无奖励」落地，全部明细算完后统一回加。

### 8.2 个税与实发

```
应发扣减 deduct = 社保 + 公积金 + 考勤 + 商保 + 宿舍 + 负工资结转 + 积分 + 绩效金额扣款 + 其他支出
应纳税所得额     = gross - deduct
个税             = ENGINE 模式：累计预扣；EXTERNAL 模式：0（后续外部导入回补）
实发 net         = gross - deduct - tax
```

回加伯乐奖励后，按新的 `gross - deduct` 重算个税与实发；`tax_source` 保持主循环口径。

### 8.3 批次汇总

批次 `gross_total / deduct_total / tax_total / net_total` 在引擎返回明细后由明细汇总，因此伯乐奖励已包含在应发和实发中。

## 9. 落库字段与前端展示

| 字段 | 含义 |
|---|---|
| `pj_payroll_detail.mentor_bonus` | `AMOUNT_RATIO` 的奖励金额；`RATE_ADD` 时为 0 |
| `pj_payroll_detail.mentor_add` | `RATE_ADD` 的加点比例（仅该模式落库，已包含在 `finalRate`） |
| `pj_payroll_detail.mentor_bonus_calc_process` | 伯乐奖励逐期计算过程 JSON：`[{month, base, ratio, bonus}]`，`month` = 新签导入月，`base` = 该期千里马折算后结佣业绩，`ratio` = 该期师傅职级配置比例 |

## 11. 已识别问题与待确认项

> 以下为当前代码复核结果。`AMOUNT_RATIO` 已改为「新签导入月期间口径」，A/E 按新口径重新确认；D/F/I 为设计口径；剩余为数据维护类问题（G、H）与命名说明（J）。

### 问题 A（已消解）：无新签事实绑定的结佣基数漏算

- 原问题：以 `""` 为 key 记录基数，反向汇总只遍历真实 `rulePeriod`，导致无新签事实绑定的结佣被金额比例漏掉。
- 现状：无绑定的结佣**统一归到算薪月**（`basePeriod = 算薪月`），按算薪月关系、当前职级、主快照计算，**不会漏算**；已保留 `testMentorBonusUnboundPeriodFallsBackToPayrollMonth` 用例锁定。

### 问题 B（已修复，两种模式）：期间切片缺失不再回退算薪月

- 原实现：`periodApprenticeMap` 缺失时回退算薪月千里马数，历史新签月切片构建失败会**重演「入职前新签月被加点」**。
- 修复：改为**失败关闭**——`RATE_ADD` 该期间千里马数按 0；`AMOUNT_RATIO` 该期间关系切片缺失则该期不计入。仅「未绑定新签事实的结佣」按算薪月处理；切片构建失败时由批次服务记录告警。
- `AMOUNT_RATIO` 的伯乐期间职级/规则快照缺失时，分别回退算薪月职级/主快照（这两项只影响比例与职级，不回退基数与关系）。
- 理由：缺失既可能是该月确实无千里马，也可能是构建失败；回退方向是多发，薪酬应宁可少发后重算。

### 问题 C（已删除）：员工政策覆盖的 `rate` 分支

- 原复核误把 `policy.employeeOverride` 当成「一级一价」提点覆盖。该节点实际只承载员工级政策（个人社保基数、公积金、专项附加扣除），没有提点配置入口。
- 引擎中原有的 `rate` 覆盖分支从未有配置写入，属于死代码，已删除（主循环与 `computeFinalRateForCommission` 两处），`RuleService` 中仅供该分支使用的 `employeeOverride` 访问器一并删除。

### 问题 D（已确认为设计口径）：RATE_ADD 只作用于伯乐本人个人结佣提点

- 团队提成（店长 `teamRate`）与门店跳点（总监 `brackets`）是基于团队/门店业绩的独立收入项，与伯乐关系无关；
- `mentorAdd` 只进入伯乐本人个人结佣的 `personalRate` / `baseRate`，这才是「伯乐奖励」的本意；
- 业务已确认：伯乐加点不作用于团队提成、门店提成。

### 问题 E（低，已接受）：分期间奖励四舍五入差额

- 现象：按新签月逐期 `round2` 后相加，与「全期合计后一次 `round2`」理论上可能差 0.01。
- 现状：为保证 `mentor_bonus_calc_process` 各期 `bonus` 之和与 `mentor_bonus` **完全一致（可核对）**，采用「逐期 round2 后累加」；差额上限 0.01，可接受。
- 提示：若后续对账要求与理论值严格一致，需改为全精度累加、JSON 展示值单独 round2，并接受展示合计差 0.01。

### 问题 F（已确认为设计口径）：按月粒度快照，不按天拆分

- 伯乐关系、职级、积分均以**月**为粒度：`findMentorRelationsAt`、`getEmployeeSnapshots` 内部统一取月末切片；
- 月中换伯乐、月中升职整月按月末状态归属，不做按天比例拆分；业务已确认按月口径。

### 问题 G（低）：`expire_date` 边界与维护口径

- 现象：`point < expire_date`，若失效日维护为当月最后一天，则当月整月失效。
- 建议：制度上统一维护为「失效月 1 号」；可加数据校验/导入提示。

### 问题 H（低）：`hire_date` 为空的历史员工会被放行

- 位置：SQL `e.hire_date IS NULL OR e.hire_date <= 月末`。
- 影响：缺失入职日期的员工可能被计为有效千里马。
- 建议：数据清洗并逐步要求 `hire_date` 必填；或在算薪前校验。

### 问题 I（已确认为设计口径）：切换月两种模式并存

- 切换月（如 10 月 `RATE_ADD`、11 月 `AMOUNT_RATIO`）表现为：
  - 11 月结算的 10 月新签业绩 → 按 10 月新签月规则走 `RATE_ADD` 提点加点，**不发放金额比例奖励**；
  - 11 月新签业绩 → 按 11 月规则走 `AMOUNT_RATIO` 金额比例。
- 两者按「新签月」各自归口，逻辑自洽，业务已确认无需处理；验收按各新签月规则配置检查即可。

### 问题 J（文档/命名）

- 「合格千里马」易被理解为有业绩门槛；实际为「有效关系且在岗」。建议在规则说明中固定定义。
- 旧口径文档已在本轮同步为「折算后结佣业绩」，若在其他制度文件中仍有「最终结佣提成金额」表述，以本文档为准。

### 问题 K（已按现状处理）：伯乐不在本次算薪名单

- 场景：伯乐在算薪月前离职、被标 `VIRTUAL` 或无 LEVEL 事实，未进入本次算薪名单；但其名下千里马的历史新签月仍有结佣在本月结算。
- 现状：引擎能算出金额比例基数，但发放只遍历本批次明细，**没有该伯乐的明细行可落，奖励不发放**。
- 处理：引擎记录 WARN 日志（伯乐ID、新签月、基数合计），便于排查并确认是否需补发；未新增挂账/补发机制。
- 若制度要求离职伯乐仍享受后续结佣奖励，需另行设计挂账/补发流程。

## 12. 回归验收清单

1. **入职前新签月（仅 RATE_ADD）**：千里马 7 月入职，师傅 4 月新签月不得出现 `+2%`。
2. **入职当月**：千里马 7 月 31 日入职，7 月新签月应享受 RATE_ADD 加点。
3. **离职当月**：千里马 7 月离职，7 月新签月仍享受；8 月不享受。
4. **多千里马封顶**：RATE_ADD 2%/人、封顶 10%，6 人时仍为 +10%。
5. **金额比例不封顶**：超过 10% 等价金额不截断。
6. **基数与提点无关**：同一算薪月结佣业绩 96,000，无论师傅/千里马职级提点、绩效扣减、招聘加点、人工调整如何变化，2% 奖励恒为 1,920。
7. **金额比例期间口径**：7 月配 2%、8 月配 3%，则 7 月业绩按 2%、8 月业绩按 3%，不得用算薪月比例串算；某期规则不是 `AMOUNT_RATIO` 时该期不计入。
8. **切换月**：10 月 RATE_ADD、11 月 AMOUNT_RATIO，11 月结算的 10 月新签业绩只走 RATE_ADD 加点、不发金额比例；11 月新签业绩按 11 月比例发金额。
9. **跨新签月结佣**：明细 `commissionCalcProcess` 按新签月逐期展示；`mentorBonusCalcProcess` 也按新签月逐期多条展示，各期 `bonus` 之和等于 `mentor_bonus`。
10. **无新签事实绑定**：`performanceFactId` 为空的结佣归到算薪月，`AMOUNT_RATIO` 使用算薪月关系/当前职级/主快照，`RATE_ADD` 按算薪月千里马数加点。
11. **个税**：ENGINE 模式下回加奖励后个税与实发同步变化；EXTERNAL 模式保持 0 待导入。
12. **旧批次重算**：历史批次重算后 `mentor_bonus_calc_process` 能正确生成；旧批次展示不报错。
13. **无有效关系**：算薪月无伯乐关系时 `mentor_bonus=0`（已覆盖）。
14. **伯乐历史职级**：7 月伯乐为 A2、8 月升 S1，7 月按 A2 规则（RATE_ADD 不计金额）、8 月按 S1 规则发金额（已覆盖）。
15. **伯乐不在名单**：日志出现 WARN（含伯乐ID、新签月、基数合计），批次明细与合计不含该奖励。
