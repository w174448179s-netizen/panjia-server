> **版本：** V1.4（落地版 · 员工导入融合）
> **编制日期：** 2026 年 9 月
> **定位：** 基于《薪酬与收支架构设计 V1.6》§4 +《业务需求说明书 V4.2》+《AI 总规约 V3.0》+《员工域详细设计 V5.2》，将 `panjia-import` 落地为可直接编码的详细设计。

> **依赖边界：** 本域只依赖 people —— 对 people 为「读 + 受控写」（通过 `EmployeeImportSink` Port 写入），不依赖任何下游域。

## 〇、设计目标与边界（一句话对齐）

导入域负责 **`外部数据 → RawData（只读归档）→ NormalizedRecord（标准化）`** 这一段链路；**不构造业务事实、不理解业绩/薪酬语义**。下游 `panjia-performance` 消费 `NormalizedRecord` 生成 `PerformanceFact`。

贝壳模板/格式变更**只影响本域内部**（新增/调整 DataSource 实现），不波及其他域——这是本域独立的全部价值。

**员工导入（EMPLOYEE）是本域的第 6 个 source_type，但属于主数据，不走 NormalizedRecord 流水线**：导入域负责「批次 + RawData 原始归档」，通过 `EmployeeImportSink`（写入 Port）在 people 域落地业务对象（部门树 / Employee / salary_fact / sys_user 岗位角色）。详见 §3.6、§5.7、§8.2。

## 一、数据源与模板全景（对齐 V4.2 数据来源）

按 V4.2 §3~§6，V1 导入域覆盖以下数据源。**每一类 = 一个 DataSource 实现 + 一套模板（pj_import_template）+ 一种归一化产物。**

| 编码（source_type） | 中文名 | 文件/来源 | 归一化产物 | 对应下游业务 | V1 |
|---|---|---|---|---|:--:|
| `KE_SIGNED` | 贝壳·理房通到账明细（结佣） | 贝壳后台 Excel 导出 | `NormalizedRecord`（SIGNED） | 经纪人/店长/总监个人结佣提成 | ✅ |
| `KE_NEW_SIGN` | 贝壳·新签业绩明细（应收） | 贝壳后台 Excel 导出 | `NormalizedRecord`（NEW_SIGN） | 店长团队提成、总监门店提成、店长保底 | ✅ |
| `ATTENDANCE` | 考勤 Excel | 人事整理标准模板 | `NormalizedRecord`（ATTENDANCE） | 考勤扣款 | ✅ |
| `POINTS` | 积分 Excel | 人事整理标准模板 | `NormalizedRecord`（POINTS） | 积分扣款 + 绩效等级（A/B/C） | ✅ |
| `OTHERS` | 手工录入/其他费用 | 系统手工录入兜底 | `NormalizedRecord`（MANUAL） | 商业保险、宿舍管理、其他支出等 | ✅ |
| `EMPLOYEE` | 员工主数据 | 人事整理标准模板（Excel） | **不产 NormalizedRecord**，走 `EmployeeImportSink` 落地业务对象 | 员工/部门/职级/社保/公积金/宿舍/兼职/师傅 | ✅ |

> **重要口径（V4.2 §7.1、§5.2）：**
> - **结佣**走 `KE_SIGNED`（实收到账），用于个人结佣提成；
> - **新签**走 `KE_NEW_SIGN`（应收业绩），用于店长团队提成/保底、总监门店提成；
> - 两者**同源但语义不同**，必须拆成两个 DataSource，**绝不可混为一张"业绩表"**——这是下游 performance 正确分流的前提。
> - 考勤/积分系统**不对接钉钉**（V4.2 修订说明第7条），统一由人事整理为标准模板导入。
> - **EMPLOYEE 是唯一不产生 NormalizedRecord 的 source_type**，它是主数据，产物是 people 域的业务对象。

### 1.1 贝壳到账明细关键字段（RawData 原始列）

对齐 V4.2 §7.1，原始归档**原样保留**：

| 原始列（raw） | 类型 | 说明 | 归一化映射 |
|---|---|---|---|
| `arrive_month` | varchar | 到账月（数据归属月份） | `period`（YYYY-MM） |
| `biz_type` | varchar | 业务类型（一手房/二手买卖/租赁/租赁轻托管/轻托管推房） | `biz_type` + 折算规则码 |
| `order_no` | varchar | 订单号（一手房/房产金融/家装荐客的关联键） | `source_key`（关联键之一） |
| `contract_no` | varchar | 合同号（二手买卖/租赁/轻托管等的关联键） | `source_key`（关联键之一） |
| `role_sys_no` | varchar | 角色人系统号（经纪人唯一标识） | `employee_external_code` → 关联 Employee |
| `role_name` | varchar | 角色人姓名（辅助展示） | `employee_name`（校验用） |
| `role_type` | varchar | 角色类型（客源成交人/房源维护人/房源录入人） | `role_type` + `share_ratio` |
| `share_ratio` | numeric | 业绩比例 | `share_ratio` |
| `current_receivable` | numeric(18,2) | 当月应收业绩 | `receivable_amount`（原值） |
| `current_received` | numeric(18,2) | 当月实收业绩 | `received_amount`（原值） |

> RawData **原样存原始列名与原始值**（不做业务语义转换），仅做类型规整；业务字段含义的解析下沉到 Normalize 阶段，由模板配置（`pj_import_template`）驱动——贝壳改列名/加列只改模板，不改代码。

### 1.2 手工录入兜底（OTHERS）

无 Excel 文件时，由算薪人员/人事在页面逐条录入（如商业保险费、宿舍管理费、其他支出等）。此类**不产 RawData 文件**，但仍受同一批次与校验约束。手工新增/修改**强制走 `AuditPort`**（操作人/前后快照/时间戳），无需 RawData 文件存证。

手工录入去重为**编码硬约束**，判重键 `(batch_id, employee_external_code, period, item_type)`：同一批次内同一员工、同一月份、同一费用类型不允许重复录入；插入前先 SELECT，命中则抛 `BizException`，前端提示改为"编辑已有行"；跨批（含新批次替换旧批次）允许共存。

> 该规则在 DO 字段注释、`uk_norm_source_key` SQL 注释、本文档三处同步（缺一不可），Task-2-6 单测覆盖。

### 1.3 员工导入原始列（RawData，EMPLOYEE）

对齐《员工域详细设计 V5.2》，员工 Excel 原始列：

| 原始列（raw） | 类型 | 说明 | Sink 落地映射 |
|---|---|---|---|
| `employee_code` | varchar | 工号（= sys_user.username） | `Employee.employeeCode` |
| `name` | varchar | 姓名（= nickname） | `Employee.name` |
| `phone` | varchar | 手机号 | `Employee.phone` |
| `id_card` | varchar | 身份证号 | `Employee.idCard` |
| `dept_path` | varchar | 部门全路径，用 `-` 分隔（如 `富房-龙湖店-一组`） | 按 `-` 拆分**自动建部门树** → `Employee.deptId` + `sys_user.deptId` |
| `post_names` | varchar | 岗位名，用 `/` 分隔（如 `经纪人/培训师`） | **多岗位 → 多角色**（见 §3.6） |
| `level` | varchar | 职级 | `SalaryFact.level` |
| `social_insured` | varchar | 社保是否缴纳（是/否） | `SalaryFact.socialInsured` |

| `commerce_insurance` | numeric | 商业保险金额 | `SalaryFact.commerceInsurance` |
| `dormitory` | varchar | 宿舍（有/无） | `SalaryFact.dormitory` |
| `part_time` | varchar | 是否兼职（是/否） | `Employee.status`（兼职=2） |
| `master` | varchar | 师傅（工号，可空） | `SalaryFact.masterEmployeeCode` |
| `entry_date` | date | 入职日期 | `Employee.entryDate` |

## 二、导入数据链路（细化版）

```
  贝壳/人事 Excel        标准模板下载
       │                      │
       ▼                      ▼
  ┌────────────┐        ┌──────────────┐
  │ DataSource │        │ TemplateEngine│  ← 模板 = 列映射 + 类型 + 校验规则
  │ （SPI 适配）│        │  (pj_import_  │     每 source_type 一个版本
  └─────┬──────┘        │   template)  │
        │ parse          └──────┬───────┘
        ▼                      │ 列映射配置
  ┌────────────┐               │
  │  RawData    │◀─────────────┘  解析 + 校验（不转换业务语义）
  │  （只读归档）│
  └─────┬──────┘
        │ Normalize（按 template 列映射 + 类型转换 + 校验）
        ▼
  ┌──────────────────┐   校验失败 → ImportIssue（批次级，可修复）
  │ NormalizedRecord  │  ← 业绩类 source_type 的产物
  │  / EmployeeSink   │  ← EMPLOYEE 走 Sink 落地业务对象（§3.6、§5.7）
  └─────┬────────────┘
        │ 返回（导入域边界止步）
        ▼
  panjia-performance 消费 NormalizedRecord → PerformanceFact
  panjia-people       接收员工业务对象（EMPLOYEE 专用）
```

**三不原则（边界）：**

| 环节 | 职责 | 禁止 |
|---|---|---|
| 导入域 | Excel → RawData → NormalizedRecord / EmployeeSink | 构造 PerformanceFact / 理解提成/业绩语义 |
| 业绩域 | 消费 NormalizedRecord → PerformanceFact | 解析 Excel / 依赖具体数据源格式 |
| 导入域对下游 | **只返回 NormalizedRecord / 发事件（contracts 类型）**；EMPLOYEE **不发**业绩事件 | import 下游具体类 |
| 导入域金额处理 | 只做**类型转换（string→numeric）**，原值透传 | 业绩折算、分成计算、金额二次加工 |

> **金额透传是关键边界**：折算（如"一手房×94%×96%"）**不属于**导入域职责——导入域只把金额原样存入 RawData / NormalizedRecord，折算下沉到 performance 域。

## 三、领域对象设计

### 3.1 聚合根：`ImportBatch`（一次导入的批次）

**聚合根**，统领 RawData / NormalizedRecord / ImportIssue。批次是"导入事务"的原子单位：**同一批次要么整体可见，要么整体回滚/归档**。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long（雪花） | 主键 |
| `batchNo` | varchar(32) | 批次号（`IMP + yyyyMMdd + 序列`） |
| `sourceType` | varchar(20) | 数据源类型（见 §一），枚举 `ImportSourceType`（**含 EMPLOYEE**） |
| `templateVersion` | varchar(20) | 使用的模板版本（**创建/解析时快照冻结**，见下） |
| `fileName` / `originalFileName` | varchar | 存储文件名 / 上传原名 |
| `storagePath` | varchar | 文件原文存储路径（S3/MinIO 或本地） |
| `period` | varchar(7) | 数据归属月（YYYY-MM），**唯一性约束核心维度**（EMPLOYEE 可空） |
| `totalRows` / `successRows` / `failedRows` | int | 总行数 / 成功 / 失败 |
| `status` | smallint | 批次状态（见 §3.5 状态机） |
| `archiveStatus` | smallint | 归档状态：`RAW_WRITTEN` |
| `operatorId` | Long | 操作人（RuoYi sys_user.id） |
| `deptId` | Long | 归属部门（RuoYi sys_dept.id） |
| `remark` | varchar | 备注 |
| `version` | int | 乐观锁版本号 |
| `supersededByBatchId` | Long | 本批次被新批次废弃（SUPERSEDED）时指向新批次；null 表示未被废弃 |
| `createTime` / `updateTime` | timestamp | 自动填充 |

**关键不变量：**
- 批次内 `source_type + period + dept_id` 决定业务唯一性；重复导入走"归档旧批次 + 新建批次"（见 §5.6）。
- **`template_version` 在批次创建/解析时快照冻结**（构建 ImportBatch 即读取当时激活模板版本写入），而非归档时冻结——避免"解析逻辑"与"模板版本"不一致。唯一索引 `uk_import_batch_type_period_dept` 不含 `template_version`（同一口径月只允许一个活跃批次）。
- **`superseded_by_batch_id` 语义**：仅由重复导入流程在新批次归档成功**后**回填旧批次，指向新批次；一经设置不可再改。下游据此 + `archive_status != SUPERSEDED` 双条件过滤失效数据。

### 3.2 实体：`RawData`（原始记录 · 只读）

解析后的**逐行原始记录**。**只追加、不可 UPDATE/DELETE**（应用层 insert-only + AuditPort；**禁止触发器**）。

按 source_type **分表**（`pj_import_raw_{source_type}`）：

| 表 | 承载 | 关键原始列 |
|---|---|---|
| `pj_import_raw_signed` | KE_SIGNED 结佣明细 | order_no/contract_no/role_sys_no/role_type/share_ratio/current_received |
| `pj_import_raw_new_sign` | KE_NEW_SIGN 新签明细 | contract_no/role_sys_no/biz_type/current_receivable |
| `pj_import_raw_attendance` | 考勤 | employee_code/attend_date/late_count/absent_days/leave_amount |
| `pj_import_raw_points` | 积分 | employee_code/point_date/score/violation_count |
| `pj_import_raw_manual` | 手工录入 | item_type/employee_code/amount/reason |
| `pj_import_raw_employee` | **EMPLOYEE 员工** | employee_code/name/phone/dept_path/post_names/level/social_insured/... |

公共列（每张 raw 表都有）：`id, batch_id, row_no, raw_json(jsonb), create_time`。业务列按数据源展开；**所有原始列允许 NULL（原样保留，不做业务校验）**。

> **raw_json 用途：** 全量原始行以 JSONB 冗余存储，保证"列映射变更后仍能回溯原始文件"，是审计与重归一化的锚点。
>
> **EMPLOYEE RawData：** 原始归档仍保留（对齐审计锚点），但其业务产物（Employee 等）由 Sink 落地，见 §3.6。
>
> **OTHERS（MANUAL）：** 无文件、无 RawData 记录，`NormalizedRecord.raw_data_id = null`，审计靠 AuditPort。

### 3.3 实体：`NormalizedRecord`（归一化记录 · 业绩类专用）

**标准化后的结构化记录**——业绩类 source_type 的产物。它是导入域对外的**唯一交付物**（EMPLOYEE 除外）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long（雪花） | 主键 |
| `batchId` | Long | 所属批次 |
| `recordType` | varchar(20) | `NormalizedRecordType`：SIGNED/NEW_SIGN/ATTENDANCE/POINTS/MANUAL（**不含 EMPLOYEE**） |
| `period` | varchar(7) | 归属月 |
| `employeeId` | Long | 关联 Employee.id；无法匹配时 null + 产生 ImportIssue |
| `employeeExternalCode` | varchar | 外部编码（角色人系统号/工号），匹配键 |
| `sourceKey` | varchar | 业务唯一键（订单号/合同号/考勤日期），下游去重依据 |
| `bizType` | varchar | 业务类型 |
| `receivableAmount` | numeric(18,2) | 应收业绩（原值） |
| `receivedAmount` | numeric(18,2) | 实收业绩（原值） |
| `shareRatio` | numeric(10,4) | 业绩比例 |
| `roleType` | varchar | 角色类型 |
| `extraJson` | jsonb | 扩展字段（扣款金额、考勤细分等） |
| `rawDataId` | Long | 对应 RawData 行（手工录入为 null） |
| `validationStatus` | smallint | PENDING / PASSED / FAILED |
| `validationMsg` | varchar | 校验失败原因 |

> **不含业务语义字段**（如"提点""提成金额"），只有结构化数据 + 关联键 + 金额原值。业绩口径/折算由 performance 域负责。

> **`source_key` 规则骨架：** 由 `biz_type` 决定——一手房/房产金融/家装荐客用**订单号**，二手买卖/租赁/轻托管用**合同号**，同一合同多角色拼接 `contract_no + role_type` 保证行级唯一。完整映射**待贝壳真实 Excel 样本到位后固化**（§11.2-1）。编码前必须验证，否则下游 performance 去重失真。

#### 3.3.1 员工导入的派生产物（EMPLOYEE 不产生 NormalizedRecord）

EMPLOYEE 是主数据，**不产出 NormalizedRecord**。`ImportBatch` 归一化阶段对 EMPLOYEE 走专属分支：

```
EMPLOYEE 行 → 解析 → 事务 B → EmployeeImportSink.apply(row)
                                    ↓
                          people 域落地：
                          • Employee（含 dept_id、user_id）
                          • 部门树（dept_path 自动建）
                          • SalaryFact（职级/社保/公积金/商保/宿舍/兼职/师傅）
                          • sys_user（通过 AccountPort）
                          • sys_user_post（多岗位）
                          • sys_user_role（岗位名=角色名，多角色）
```

EMPLOYEE 的唯一性由 `employee_code` + Sink 幂等保证（详见 §3.6、§8.2）。

### 3.4 值对象：`ImportIssue`（导入问题）

批次级校验/归一化失败的**问题清单**，不阻塞批次落库，供"待对齐匹配"修复。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long | 主键 |
| `batchId` | Long | 所属批次 |
| `rowNo` | int | 原始行号 |
| `issueType` | varchar(20) | `EMPLOYEE_NOT_MATCH` / `COLUMN_TYPE_ERR` / `REQUIRED_MISSING` / `DUPLICATE_KEY` / `PERIOD_MISMATCH` / **`DEPT_NOT_MATCH`**（EMPLOYEE 专用：部门路径解析失败）/ **`POST_NOT_MATCH`**（EMPLOYEE 专用：岗位名未匹配到 sys_post） |
| `fieldName` | varchar | 问题字段 |
| `rawValue` | varchar | 原始值 |
| `message` | varchar | 可读说明 |
| `status` | smallint | `OPEN / RESOLVED / IGNORED` |

**`ImportIssueStatus` 语义：**
- `OPEN`：未处理，批次停留 `PENDING_CONFIRM`，不可归档；
- `RESOLVED`：已人工修复数据，重归一化重新生成 NormalizedRecord，通过校验则转 RESOLVED；
- `IGNORED`：业务确认可忽略（如历史脏数据），**仅限算薪人员、总监**可标记，经纪人/店长禁止；标记走 `AuditPort` 留痕。离职/历史人员匹配失败默认走"补齐档案后重归一化（RESOLVED）"，确需放过才由总监标记 IGNORED。

> `IGNORED` ≠ `RESOLVED`：前者是"承认问题但业务放过"，后者是"问题已被数据修复消除"。两者均脱离阻塞清单，但审计含义不同。

### 3.5 状态机：`ImportBatchStatus`

对齐 AI 总规约「状态字段必须定义 Enum（`code` + `desc` + `canTransitTo` + `isTerminal` + `isRunning`）」。

```
  PARSING ──▶ NORMALIZING ──▶ PENDING_CONFIRM ──▶ ARCHIVED
                                  │
                                  └──▶ FAILED（终态，可重建新批次重试）
```

| code | desc | 说明 |
|---|---|---|
| `PARSING` | 解析中 | 读取文件、落 RawData |
| `NORMALIZING` | 归一化中 | 列映射 + 校验 → NormalizedRecord / Sink |
| `PENDING_CONFIRM` | 待确认 | 有 ImportIssue，需人工处理 |
| `ARCHIVED` | 已归档 | 原始数据只读落定，**对外可见/可被下游消费** |
| `FAILED` | 失败（终态） | 致命错误，不可直接修改，需新建批次重试 |

`canTransitTo` 规则：`PARSING→NORMALIZING→PENDING_CONFIRM→ARCHIVED`；`FAILED` 为终态；`PENDING_CONFIRM` 修复后回到 `NORMALIZING`（重归一化）。**禁止业务代码直接 `setStatus`，统一走状态机方法。**

**强制固化规则：**
1. **`FAILED` 是终态**：一旦进入只能**新建批次**重试，禁止状态回退（`FAILED.canTransitTo` 恒返回 false，单元测试固化）。
2. **重归一化只重建派生数据，绝不改动原始归档**：`PENDING_CONFIRM → NORMALIZING` 重跑时 RawData 完全不动；只重建 NormalizedRecord + ImportIssue；EMPLOYEE 则重建 Employee/salary_fact（Sink 内部处理，RawData 不动）。
3. 跨月检测在解析阶段（`PARSING`）前置执行，命中即置 `FAILED`（EMPLOYEE 无 period，跳过此检测）。

```java
public enum ImportBatchStatus {
    PARSING(0, "解析中", Set.of(NORMALIZING, FAILED), false, true),
    NORMALIZING(1, "归一化中", Set.of(PENDING_CONFIRM, FAILED), false, true),
    PENDING_CONFIRM(2, "待确认", Set.of(NORMALIZING, ARCHIVED, FAILED), false, false),
    ARCHIVED(3, "已归档", Set.of(), true, false),
    FAILED(4, "失败", Set.of(), true, false);

    private final int code;
    private final String desc;
    private final Set<ImportBatchStatus> next;
    private final boolean terminal;
    private final boolean running;

    public boolean canTransitTo(ImportBatchStatus target) { return next.contains(target); }
    public boolean isTerminal() { return terminal; }
    public boolean isRunning()  { return running; }
}
```

状态转换收口在 `ImportBatch` 聚合根方法（`archive()` / `fail()` / `reNormalize()`），方法内先调 `status.canTransitTo(target)`，不合法抛 `IllegalStateTransitionException`。

### 3.6 员工导入特殊规则（EMPLOYEE · 冻结结论）

EMPLOYEE 是主数据，与业绩类 source_type 存在结构性差异，以下规则为**编码硬约束**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | **不产 NormalizedRecord** | EMPLOYEE 走 `EmployeeImportSink`，产物是 people 域业务对象（§3.3.1） |
| R2 | **不产生 `import.archived` 事件** | EMPLOYEE 归档**不发布**该事件（员工不供 performance 消费）；`ImportSourceType` 事件开关需排除 EMPLOYEE |
| R3 | **主数据物理清理** | 重复导入（SUPERSEDED）时，Sink 必须**物理删除**被废弃批次的员工业务对象（`Sink.purgeByBatch`），而非逻辑失效 |
| R4 | **部门按 `-` 自动建** | `dept_path`（如 `富房-龙湖店-一组`）按 `-` 拆分，逐级查/建 `sys_dept`，最末级为员工归属部门 |
| R5 | **岗位名 = 角色名（同名匹配）** | 岗位挂在**客户根节点**（初始化已建），`post_name → role_name`；匹配不到的角色**不绑、不报错**，HR 自行去 RuoYi 后台赋权 |
| R6 | **多岗位 → 多角色** | `post_names` 用 `/` 分隔（如 `经纪人/培训师`）；每个岗位绑一条 `sys_user_post`，每个匹配到的岗位名绑一条 `sys_user_role`（先清后绑，**不取主岗位**） |
| R7 | **两段式事务** | 事务 A 落 RawData（通用）；事务 B Sink 落地业务对象（EMPLOYEE 专属，见 §5.7） |
| R8 | **EMPLOYEE 不做业绩折算/金额加工** | salary_fact 金额字段（商保等）原值透传，符合 §二 三不原则 |

> **R3 详解（物理清理 vs 逻辑失效）：** 业绩类 RawData 保留 + SUPERSEDED 过滤（逻辑失效，保留审计）；EMPLOYEE 是主数据，**同一 `employee_code` 只能有一条有效记录**，故废弃批次的员工必须在 people 域**物理删除**（Employee + salary_fact + sys_user 关联），再由新批次重建。这是 EMPLOYEE 与业绩类的**核心差异**，详见 §5.6、§8.2。

### 3.7 派生产物表（EMPLOYEE 写入 people 域）

EMPLOYEE 导入最终在 people 域落地的对象（由 `EmployeeImportSink` 通过 Port 写入，**不在导入域本地建表**）：

| 对象 | 来源 | 写入方式 |
|------|------|----------|
| `sys_dept`（部门树） | `dept_path` 拆分 | 逐级查/建（查不到则 INSERT） |
| `pj_people_employee` | employee_code/name/phone/dept_id/... | upsert by employee_code |
| `pj_people_salary_fact` | level/social_insured/housing_insured/commerce_insurance/dormitory/part_time/master | upsert by employee_id |
| `sys_user` | employee_code→username, name→nickname, dept_id | AccountPort.createUser |
| `sys_user_post` | post_names（多岗位） | 先清后绑 |
| `sys_user_role` | post_names → 角色名（多角色） | 先清后绑（R6） |

> 全部通过 people 域的 Port（AccountPort / EmployeeWritePort）写入，**导入域不直接连 people 的业务表**。

## 五、导入流程

### 5.1 通用主流程（两段式事务）

```
UploadFile / ManualEntry
  ↓
① 创建 ImportBatch（解析时快照冻结 template_version）
  ↓
② 【事务 A】解析 + 分批落 RawData
   - 分批粒度 BATCH_INSERT_SIZE = 300
   - 失败仅回滚当前子批次；残留 RawData 属审计保留
   - V1 不做行级幂等，走新批次隔离
   - 跨月检测前置（命中 → FAILED）
  ↓ PARSING → NORMALIZING
③ 【事务 B】归一化 → NormalizedRecord（业绩类）/ Sink（EMPLOYEE）
   - 生成 ImportIssue（校验失败）
  ↓
④ 状态推进：全部成功 → ARCHIVED；有 issue → PENDING_CONFIRM
```

> **大事务风险：** V1 限制单批次最大行数 `MAX_ROWS_PER_BATCH = 5000`；解析落 RawData 与归一化拆分两段式事务。

### 5.2 归一化流水线（含 EMPLOYEE 分支）

```
NormalizeService.normalize(batch)
  ↓
按 batch.sourceType 路由：
  ├── 业绩类（KE_SIGNED / KE_NEW_SIGN / ATTENDANCE / POINTS / OTHERS）
  │     → 列映射 + 类型转换 + 员工匹配（employee_external_code → Employee.id）
  │     → 生成 NormalizedRecord
  │     → 匹配失败 → ImportIssue(EMPLOYEE_NOT_MATCH)，employee_id 留 null
  │
  └── EMPLOYEE
        → 解析员工原始列（§1.3）
        → 部门路径解析（dept_path → 逐级查/建，失败 → ImportIssue(DEPT_NOT_MATCH)）
        → 岗位解析（post_names 用 `/` 分隔）
        → 【事务 B】EmployeeImportSink.apply(rows)   ← 见 §5.7
        → 岗位/角色匹配失败的岗位 → ImportIssue(POST_NOT_MATCH)，但不阻断整批
```

### 5.3 校验规则

- **必填缺失（REQUIRED_MISSING）**：关键列（业绩类：employee_external_code/period/金额；EMPLOYEE：employee_code/name/dept_path）
- **类型转换（COLUMN_TYPE_ERR）**：string → numeric/date 失败
- **重复键（DUPLICATE_KEY）**：`source_key` 重复；手工录入走业务层判重键（§1.2）
- **跨月（PERIOD_MISMATCH）**：同一批次 RawData 的 `arrive_month` 不一致 → FAILED（EMPLOYEE 无 period，跳过）
- **员工未匹配（EMPLOYEE_NOT_MATCH）**：external_code 在 people 域查不到
- **EMPLOYEE 专属：** DEPT_NOT_MATCH（部门路径非法）、POST_NOT_MATCH（岗位名未匹配到 sys_post/sys_role）

### 5.4 重归一化（reNormalize）

`PENDING_CONFIRM → NORMALIZING` 重跑时：
- **RawData 完全不动**（只读，禁止 UPDATE/DELETE）；
- 业绩类：先按 `batch_id` 删除旧 NormalizedRecord + ImportIssue，再重新生成；
- **EMPLOYEE：** 调用 `EmployeeImportSink.replay(batchId)` —— Sink 内部重建 Employee/salary_fact（基于该批次 RawData），RawData 不动；全程走 AuditPort 留痕（操作人/前后快照/改动范围）。

### 5.5 重复导入与 SUPERSEDED（EMPLOYEE 物理清理）

**业绩类（逻辑失效）：**
新批次归档成功后，回填旧批次 `superseded_by_batch_id` → 旧批次 RawData 保留 + 下游按 `archive_status=ARCHIVED AND superseded_by_batch_id is null` 过滤。

**EMPLOYEE（物理清理 · R3）：**
新批次归档成功后，导入域调用 `EmployeeImportSink.purgeByBatch(oldBatchId)`：
- **物理删除**旧批次对应的 Employee、salary_fact、sys_user 关联（按该批次导入的 employee_code 范围）；
- 再由新批次 Sink 重建最新业务对象；
- 原因：同一 `employee_code` 只能有一条有效记录，无法逻辑失效。

> 物理清理**不可逆**，必须事务包裹 + AuditPort 全量留痕；失败则整批回滚并告警。

### 5.6 事务 B 分支：EMPLOYEE Sink 落地（V1.4 关键）

```
【事务 B · EMPLOYEE】
  ↓
EmployeeImportSink.apply(rows)
  ↓
逐行处理（在 people 域内同事务）：
  1. DeptService.upsertByPath(dept_path)          → 逐级查/建 sys_dept
  2. AccountPort.createUser(employee_code, name, dept_id)  → sys_user
  3. EmployeeWritePort.upsert(employee, userId)   → pj_people_employee + user_id 回填
  4. SalaryFactWritePort.upsert(employee_id, fact) → pj_people_salary_fact
  5. AccountPort.assignPosts(userId, post_names)   → sys_user_post（先清后绑）
  6. AccountPort.assignRoles(userId, post_names)   → sys_user_role（岗位名=角色名，先清后绑，R6）
  ↓
异常 → 事务 B 回滚 → batch 置 FAILED → 前端提示重试
```

> **两段事务中间态风险：** 事务 A 成功、事务 B 失败 → RawData 已落但业务对象未建，批次停留在 NORMALIZING/失败；重试时事务 B 需**幂等**（upsert by employee_code + 先清后绑岗位角色），避免重复创建 sys_user。

### 8.2 `EmployeeImportSink`（V1.4 新增 · 受控写 Port）

定义在 `panjia-people-api`，由 people 域实现。导入域**只依赖接口，不引实现**。

```java
public interface EmployeeImportSink {
    /** 事务 B：将 EMPLOYEE 原始行落地为业务对象（§5.7、§3.7） */
    void apply(List<EmployeeRawRow> rows, ImportContext ctx);

    /** 重归一化时重建本批次的员工业务对象（RawData 不动） */
    void replay(Long batchId);

    /** SUPERSEDED：物理清理本批次的员工业务对象（R3，不可逆） */
    void purgeByBatch(Long batchId);

    /** 对账：用 people 数据覆盖 sys_user（dept/岗位/角色/离职禁用），不碰 sys_role_dept */
    ReconcileResult reconcile(Long batchId);
}
```

**写入范围（允许）：** Employee、salary_fact、sys_user（创建/部门/状态）、sys_user_post（先清后绑）、sys_user_role（岗位名=角色名，先清后绑）。

**禁止项：** 直接连 people 业务表（必须经 Port）、修改 sys_role_dept（预置不改）、对 RawData 做任何 UPDATE/DELETE、在 Sink 外自行构造 Employee。

**CI 白名单：** people 依赖从"只读"扩展为"读 + 受控写"——仅允许引用 `panjia-people-api` 中的 `EmployeeImportSink` / `EmployeeQueryPort`，禁止引入 people `domain` 包。

### 8.3 事件范围（contracts）

| 事件 | 触发 | 说明 |
|---|---|---|
| `import.parsed` | 事务 A 完成 | 内部驱动归一化 |
| `import.archived` | 批次归档 | **EMPLOYEE 不发布**（R2） |
| `import.superseded` | 批次被废弃 | **V1 不发布**（下游自行过滤 SUPERSEDED，见 §5.6） |

**下游消费侧契约：** 失败重试 + 按 eventId 幂等 + 并发去重。

### 8.4 事件表归属

`pj_event_outbox` **归属公共底座统一管理**（RuoYi 事件表），导入域不建表，仅按规约写入。

## 十、架构决策记录（ADR · 精选）

| 编号 | 决策 | 结论 |
|---|---|---|
| IMP-001 | 导入域边界 | Excel → RawData → NormalizedRecord，不构造业务事实 |
| IMP-002 | RawData 分表 | 按 source_type 分表，避免宽表稀疏列 |
| IMP-003 | RawData 只读 | insert-only + AuditPort，禁止触发器与 UPDATE/DELETE |
| IMP-004 | 重复导入策略 | 归档旧 + 新建；业绩类逻辑失效，EMPLOYEE 物理清理 |
| IMP-005 | 金额处理 | 只做类型转换，折算下沉 performance |
| IMP-011 | Raw 静态分表 | V1 静态分表，新增 source_type 属版本迭代变更 |
| IMP-012 | 模板激活 | V1 同 source_type 单套激活模板 |
| **IMP-013** | **EMPLOYEE 融合** | **作为第 6 个 source_type 纳入导入域，复用批次机制，但走 Sink 不产 NormalizedRecord** |
| **IMP-014** | **主数据物理清理** | **EMPLOYEE 废弃批次物理删除业务对象（vs 业绩类逻辑失效）；不可逆 + AuditPort + 事务** |

## 十一、风险、演进与待确认

### 11.1 风险清单（V1.4 更新）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 两段事务中间态 | 事务 A 成功、事务 B 失败 → RawData 已落业务对象未建 | 事务 B 幂等（upsert + 先清后绑）+ 重试 |
| EMPLOYEE 物理清理不可逆 | purgeByBatch 删除业务对象 | 事务包裹 + AuditPort 全量留痕 + 失败回滚告警 |
| 岗位/角色匹配失败 | 客户改了角色名导致匹配不到 | 不绑不报错，HR 后台手动赋权；ImportIssue(POST_NOT_MATCH) |
| dept_path 解析失败 | 路径非法/分隔符不一致 | ImportIssue(DEPT_NOT_MATCH)，人工修复后重归一化 |
| source_key 去重失真 | 规则未固化 | **待贝壳真实 Excel 样本到位后固化**（见 §11.2-1） |
| 大事务 | 单批 > 5000 行 | 分批 300 + 两段事务；V1 限制 5000 |
| 监控/告警/限流 | V1 暂不做 | 记录风险，后续演进 |

### 11.2 待确认项

1. **`source_key` 完整映射：** 租赁轻托管/写字楼租赁等细分关联键，**待贝壳真实 Excel 样本到位后固化**进 §1.1 与 Task-2-5；编码前必须验证。
2. **跨月检测：** V1 固化为"检测到跨月行 → 批次置 FAILED"；是否允许配置豁免待实施确认。
3. **IGNORED 权限：** 仅算薪人员/总监（对齐 V4.2 §二），Controller 层鉴权；具体角色编码待 RuoYi 角色体系确认。

### 11.3 演进计划

- V1.5：补齐 source_key 完整映射（样本到位后）
- V1.6：监控/告警/限流/回滚预案（§11.1 风险项）
- V2：考虑行级幂等 + 更大批次支持

### 11.4 最终结论（V1.4）

导入域 V1.4 将**员工导入（EMPLOYEE）完整融合**为第 6 个 source_type，复用全部批次机制（状态机/模板/校验/重归一化/SUPERSEDED），同时明确其与业绩类的**结构性差异**：

- **不产 NormalizedRecord** → 走 `EmployeeImportSink` 落地 people 业务对象；
- **不产生 `import.archived`** → 员工不供 performance 消费；
- **主数据物理清理**（`purgeByBatch`）→ 与业绩类逻辑失效（RawData 保留）相对立；
- **部门自动建、岗位名=角色名、多岗位→多角色** → 全部对齐《员工域详细设计 V5.2》。

导入域对 people 的依赖从"只读"扩展为"**读 + 受控写**"，通过 Port 边界保持架构整洁，可直接驱动编码。
