## 〇、前置约定

### 0.1 设计目标

> **一套员工主数据 + 算薪事实模型，适配 N 家中介公司，换客户不改代码、只改导入数据与规则配置。**

### 0.2 核心原则（产品化命脉）

| 原则 | 落地 |
|------|------|
| **事实归 people，规则归 payroll** | 人身上只存"是什么"，不存"怎么算" |
| **原子数据** | 本域产出的是算薪规则的**原子事实**，payroll 据此 + 规则配置 = 算薪 |
| **闭开区间** | 所有带时效的事实用 `[effective_date, expire_date)` 表达 |
| **变更即结束旧 + 新增** | 不 UPDATE 历史，只追加 |
| **底座协作走 Port-Adapter** | people 零 `import com.ruoyi.*` |

### 0.3 事实 vs 规则边界（★ 本版冻结）

**绑定到人（salary_fact，只有开关/标签/关系）：**
`social_insured` / `housing_insured` / `commercial_insured` / `dormitory` / `is_part_time` / `social_tag` / `level_code` / `status` / `mentor_employee_id`

**归客户级规则（payroll `rank_rule.rule_content` JSONB）：**
社保基数、社保比例（个人/公司）、公积金金额、公积金比例、**兼职是否豁免**、徒弟奖励上限等。

> **换客户 = 只改规则 JSON，人身上 0 改动。**

## 一、整体设计

### 1.1 表结构总览（4 张表）

| 表 | 粒度 | 职责 |
|----|------|------|
| `pj_people_employee` | 一人一行 | 员工**基本信息**（当前态） |
| `pj_people_salary_record` | 一人一行 | **界面展示**用，永远最新 |
| `pj_people_salary_fact` | **一项一条** | **真正算薪用**，闭开区间 |
| `pj_people_change_log` | 一变更一行 | 变更审计（变更项/前/后/生效/结束） |

**算薪永远读 `salary_fact`，不读 `salary_record`。**

### 1.2 record 与 fact 的关系

```
salary_record  ── 当前态快照，界面查询快，冗余但方便
salary_fact    ── 历史真相，算薪唯一数据源
                ↑
         每次变更：刷新 record + 追加 fact + 写 log（同一事务）
```

`salary_record` 是 `salary_fact` 按员工**最新一条**各 fact_type 的**物化视图**，可由 fact 全量重建，允许冗余。

### 1.3 算薪事实枚举（fact_type，冻结 8 类）

| fact_type | value 含义 | 示例 | 归属 |
|-----------|-----------|------|------|
| `LEVEL` | 职级编码 | `A2` / `S1` | 事实 |
| `STATUS` | 状态 | `ACTIVE`/`PARTTIME`/`LEFT` | 事实 |
| `SOCIAL` | 是否参保 | `true`/`false` | 事实（开关） |
| `HOUSING` | 是否缴公积金 | `true`/`false` | 事实（开关） |
| `COMMERCIAL` | 是否买商业保险 | `true`/`false` | 事实 |
| `DORMITORY` | 是否住宿舍 | `true`/`false` | 事实 |
| `PARTTIME` | 是否兼职 | `true`/`false` | 事实 |
| `MENTOR` | 师傅员工 ID | `1000148441` | 关系 |

> **无 `HOUSING_AMOUNT` / `SOCIAL_BASE` / `SOCIAL_RATIO`** —— 金额比例全在规则侧。

### 1.4 闭开区间协议

```
[effective_date, expire_date)
  effective_date = 闭（含）
  expire_date    = 开（不含），NULL = 至今
```

算薪取数 SQL（标准写法，见 §4.2）：

```sql
WHERE fact_type = 'LEVEL'
  AND effective_date <= :point
  AND (expire_date IS NULL OR :point < expire_date)
ORDER BY effective_date DESC
LIMIT 1;   -- 同日分组变更取最新
```

**边界验证：** `point = 2026-09-01` 恰好命中 `effective_date=2026-09-01` 的记录，无重叠、无间隙。

## 三、变更模型

### 3.1 通用变更方法（所有改动走这一个入口）

```java
@Transactional
public void changeFact(Long empId, String factType, String newValue, LocalDate effect) {
    // 1. 结束旧记录（把当前活跃记录的 expire_date 置为 effect）
    List<SalaryFact> active = repo.findActive(empId, factType, effect);
    for (SalaryFact f : active) {
        f.setExpireDate(effect);          // 闭开区间：旧记录到此结束
    }
    // 2. 新增记录
    repo.add(new SalaryFact(empId, factType, newValue, effect, null, factType));
    // 3. 刷新 salary_record 对应字段
    recordRefresher.refresh(empId, factType, newValue);
    // 4. 写变更日志
    logRepo.add(new ChangeLog(empId, factType, oldValue, newValue, effect, null, currentUser));
}
```

**分字段独立时间线：** 改职级只动 `LEVEL` 记录，改保险只动 `COMMERCIAL` 记录，生效时间各自独立，算薪时点自动取正确切片。

### 3.2 入职 = 生成初始 fact

入职（导入/手动）走同一个变更方法：为 8 个算薪项**各生成一条**，`change_field = 'ALL'`，`effective_date = 入职日期`。

> **不单独初始化**——入职与变更**同构**，全部走 fact + log。

### 3.3 算薪取数伪码

```java
public Map<String, String> getSnapshotAt(Long empId, LocalDate month) {
    LocalDate point = month.plusDays(1);  // 取该月任意一天（如 08-15）
    Map<String, String> snap = new HashMap<>();
    for (String type : FACT_TYPES) {
        snap.put(type, repo.findValueAt(empId, type, point));  // 闭开区间 SQL
    }
    return snap;
}
```

**验证结果（王青松：8月入职 S2，9月改 S1，10月停商业保险）：**

```
2026-08: level=S2, social=true, commercial=true   ✅ 入职态
2026-09: level=S1, social=true, commercial=true   ✅ 只改了职级
2026-10: level=S1, social=true, commercial=false  ✅ 只改了保险
```

## 五、架构协作（★ V3.1 定稿）

### 5.1 员工↔账户同步：Port-Adapter 同事务

**方案：走 Port-Adapter，不走 panjia-contracts 事件。**

**理由（见附录 B）：**
1. 导入需**强一致**（员工建了账户必须同时建好），事件=最终一致不适合；
2. 账户是 people 与 **RuoYi 底座**的协作，底座不算业务域，contracts 放的是跨业务域契约；
3. 架构 V1.7 §9 已为"业务↔底座"定义了 Port-Adapter 模式。

**包结构：**

```
com.panjia.people/
├── controller/       EmployeeController
├── service/          EmployeeService（接口）
├── impl/             EmployeeServiceImpl  ← 只依赖 Port 接口
├── mapper/           EmployeeMapper / SalaryFactMapper
├── domain/           Employee / SalaryFact / ChangeLog（POJO，无行为）
├── port/             AccountPort / DeptPort / PostRolePort（接口）
└── adapter/          RuoYiAccountAdapter / RuoYiDeptAdapter / RuoYiPostRoleAdapter
                        ↑ 唯一 import com.ruoyi 的地方
```

**导入事务伪码（impl，只依赖 Port 接口）：**

```java
@Transactional
public Employee importEmployee(ImportRow row) {
    // 1. 解析门店/组别（- 分隔），自动建部门树
    Long deptId = buildDeptTree(row.getDeptFull());  // "云庭店-花照云庭店A组"

    // 2. 建员工
    Employee emp = repo.save(row.toEmployee(deptId));

    // 3. 同步账户（Port-Adapter，同事务）
    if (emp.getUserId() == null) {
        Long uid = accountPort.createUser(row.getCode(), row.getName(), deptId, row.getPosition());
        accountPort.assignRole(uid, row.getPosition());  // 角色名 = 岗位名
        emp.setUserId(uid);
        repo.update(emp);
    }

    // 4. 生成算薪事实（8 项各一条，change_field=ALL）
    factInitializer.init(emp.getId(), row);

    // 5. 写变更日志
    logRepo.add(ChangeLog.ALL(emp.getId(), row.getHireDate()));
    return emp;
}
```

**Port 接口定义（domain 层，零 RuoYi）：**

```java
public interface AccountPort {
    Long createUser(String username, String nickname, Long deptId, String postName);
    void assignRole(Long userId, String roleName);   // 角色名 = 岗位名
    void updateDept(Long userId, Long deptId);
}
```

**Adapter 实现（adapter 层，唯一接触 sys_*）：**

```java
@Component
public class RuoYiAccountAdapter implements AccountPort {
    @Autowired private SysUserMapper sysUserMapper;
    @Autowired private SysRoleMapper sysRoleMapper;
    // ...

    @Override
    public Long createUser(String username, String nickname, Long deptId, String postName) {
        SysUser u = new SysUser();
        u.setUserName(username);          // 工号 = 账号
        u.setNickName(nickname);
        u.setDeptId(deptId);
        u.setPostIds(new Long[]{ ensurePost(postName) });
        sysUserMapper.insertUser(u);
        return u.getUserId();
    }

    @Override
    public void assignRole(Long userId, String roleName) {
        Long roleId = ensureRole(roleName);   // 角色名 = 岗位名（经纪人/店长/总监）
        sysUserRoleMapper.insert(userId, roleId);
    }
}
```

### 5.2 DTO 上移至 panjia-contracts

对齐架构 V1.7 §3.3，`EmployeeId`（普通 POJO + Long，禁止 record）、`EmployeeSnapshot` 定义在 `panjia-contracts`，people 域实现并产出，payroll/commission 消费。

### 5.3 部门自动建（- 分隔）

```java
private Long buildDeptTree(String deptFull) {
    Long parentId = null;
    for (String name : deptFull.split("-")) {   // "门店-组别"
        parentId = deptPort.ensureDept(parentId, name.trim());  // 门店一级，组别二级
    }
    return parentId;
}
```

## 附录 B：架构对齐论证（为何不走 panjia-contracts）

**命题：** 同步系统账户要不要通过 panjia-contracts？

**结论：不要。** 三条硬理由：

1. **contracts 定位**：架构 V1.7 §3 = "跨业务域协作的共享类型（事件/ID/Snapshot）"，而账户是 people 与 **RuoYi 底座**的协作，底座非业务域；
2. **一致性要求**：导入需强一致，事件=最终一致会产生"员工已建、账户未建"的中间态；
3. **架构已有先例**：V1.7 §9 的 LicensePort/BackupPort/AuditPort/EventPort 都是"业务↔底座"的 Port-Adapter，账户同步是第 5 个实例，**与架构完全一致**。

**contracts 在员工域的真正用途：** 承载跨业务域的 `EmployeeSnapshot` / `EmployeeId` 类型——这正是它的本职。

**方案对比：**

| 方案 | 评价 |
|------|------|
| A. people 直连 sys_user | ❌ 违反架构 §10.5"people 禁止写 sys_user" |
| B. 走 contracts 事件 | ❌ 过度设计 + 最终一致不适合导入 |
| **C. Port-Adapter 同事务** | ✅ **正解**，对齐架构 §9 |
