# 盘家智管 · 审批集成设计说明（Warm-Flow）

> **版本：** V1.0
> **日期：** 2026-09-16
> **依据：** 《业务需求说明书 V4.6 §9.11》《产品化架构设计 V1.10 §2.8》
>
> **解决问题**：
> ① 审批是在「我的待办」里审，还是在业务明细里直接审？
> ② RuoYi-Plus 的工作流引擎是什么，能力是否够用？
> ③ 引入工作流后，状态以谁为准？

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| **入口** | **两个都要**：我的待办 + 业务明细直接审批，共用同一审批服务 |
| **引擎** | **Warm-Flow 1.8.1**（RuoYi-Plus 官方内置，7 张表） |
| **状态归属** | **业务单据状态为准**，工作流只驱动流转 |
| **依赖** | 业务域经 `ApprovalPort` 依赖，**禁止直接依赖 `ruoyi-workflow`** |

## 二、引擎选型：Warm-Flow（不是 Flowable）

### 2.1 一个必须澄清的认知

| | **RuoYi-Plus**（本项目选型） | RuoYi-Flowable-Plus（另一社区项目） |
|---|---|---|
| 引擎 | **Warm-Flow 1.8.1** | Flowable 6.7.2 |
| 表数量 | **7 张** | 数十张 `ACT_*` |
| 模块 | `ruoyi-workflow` | `ruoyi-flowable` |

两者是**不同的开源项目**，容易混淆。RuoYi-Plus 官方文档明确其工作流模块基于 **Warm-Flow** 深度定制。

### 2.2 Warm-Flow 表结构（7 张）

| 表 | 用途 |
|---|---|
| `flow_definition` | 流程定义（编码、版本、发布状态、`ext`） |
| `flow_node` | 流程节点（开始/中间/结束/网关） |
| `flow_skip` | 节点跳转规则（`skipType` + `skipCondition`） |
| `flow_instance` | 流程实例 |
| `flow_task` | 待办任务 |
| `flow_his_task` | 历史任务（审计追溯） |
| `flow_user` | 任务办理人/权限 |

### 2.3 需求与原生能力对照

| 需求 | Warm-Flow 原生能力 | 是否需自研 |
|---|---|:---:|
| **总监超时自动通过** | 节点扩展属性 `autoApproval`（小时）+ `autoApproval_skipType`（`PASS`/`REJECT`） | ❌ 原生 |
| **可配置跳过财务** | `flow_skip.skipCondition` 支持 SpEL / 内置表达式（`eq@@`、`gt@@`）+ 互斥网关 | ❌ 原生 |
| 我的待办 | `pageWaitingTasks` / `pageByTaskWait` | ❌ 原生 |
| 业务明细审批 | `getByBusinessId(businessId)` → `taskId` → 同一 `completeTask` | ❌ 原生 |
| 已办查询 / 抄送 / 催办 | 均有现成接口 | ❌ 原生 |

> **结论**：两个可配置需求若自研，需自行实现定时器与条件分支；Warm-Flow 原生支持，且仅 7 张表，远轻于 Flowable。

## 三、双入口：待办 + 业务明细

### 3.1 两个入口解决不同场景

| 入口 | 模式 | 适合场景 |
|---|---|---|
| **我的待办** | 拉：系统推给我 | 总监/财务每天集中清一批，跨业务混着审，支持批量 |
| **业务明细直接审批** | 推：我在场景里顺手办 | 正看着这个合同/这笔结佣，直接点掉，不用跳出去再找一遍 |

**只用待办**：看到某笔业务想审，还得跳出去再找一遍，很烦。
**只用明细**：总监一天几十笔，得挨个点进详情页，也很烦。

→ **两个都要，互补。**

### 3.2 引擎层面本就同一路径

```
【我的待办】 pageWaitingTasks ──→ taskId ─┐
                                          ├→ completeTask(taskId, ...)  ← 同一 API
【业务明细】 getByBusinessId(单据ID) ──────┘
```

`FlowInstanceBizExt` 已将 `businessId` 与 `instanceId` 绑定，因此：

> **业务明细页点审批 = 先用 `businessId` 查出 `taskId`，再走待办那条路。**

**不存在两套审批逻辑**，这是 Warm-Flow 的结构性保证，不是靠约定。

### 3.3 三条实现底线

| # | 底线 |
|---|---|
| 1 | 两个入口调用**同一审批服务方法**，结果与留痕完全一致 |
| 2 | 两个入口均做**服务端鉴权**（校验操作人在当前节点审批人范围内） |
| 3 | 待办只是**视图**，删除待办列表不影响业务审批能力 |

> **前端隐藏按钮 ≠ 安全**，必须是服务端校验。

## 四、状态归属：业务单据为准（★ 核心）

### 4.1 引入工作流后出现两套状态

| | 状态存在哪 | 谁依赖 |
|---|---|---|
| 流程状态 | `flow_instance` / `flow_task` | 工作流引擎 |
| **业务单据状态** | 实收确认单 / 结佣申请单 / 业绩调整单 | **payroll 取数、结佣、封账** |

### 4.2 铁律

> **★ 业务单据状态为准，工作流只负责"下一步流转给谁"。**

payroll 算薪依赖结佣申请单的 `LOCKED`，**不读 `flow_task`**。

**反例**：若两边双写且不一致（流程已通过、业务状态未回写），会出现——

> **"流程显示已通过，但工资算不到这笔"**

这是引入工作流后最典型的诡异故障。

### 4.3 落地方式

```
流程节点变更
   → 监听器回写业务单据状态
   → 业务侧（payroll / commission / 封账）只读业务单据状态
```

**监听器回写必须幂等**：按 `bizId + 目标状态` 判定，因监听器可能被重复触发（重试、补偿、消息重投）。

## 五、依赖隔离：ApprovalPort

`ruoyi-workflow` 属**框架层**，业务域直接依赖会被绑死。

```java
// 定义在 panjia-contracts
public interface ApprovalPort {
    void start(String bizType, Long bizId, Map<String, Object> vars);
    void complete(String bizType, Long bizId, ApprovalAction action, String comment);
    void cancel(String bizType, Long bizId);
}
```

| bizType | 业务 |
|---|---|
| `REAL_CONFIRM` | 实收业绩确认 |
| `COMMISSION` | 结佣申请 |
| `PERF_ADJUST` | 业绩调整 |

```
业务域 → contracts（ApprovalPort）← infrastructure 适配器 → Warm-Flow
```

> 换引擎时**只替换适配器**，业务代码零改动。
> **CI 断言**：performance / commission 不得出现 `org.dromara.workflow` 包路径。

## 六、两个实现坑（必须遵守）

### 坑 ① 超时自动审批要用「创建监听器」

**原因**：A→B 流转时，B 的**创建**监听器在 A 办理时就触发，此时启动定时任务才准确；用任务监听器会错过时机。

**实现要点**：

```java
@Component
public class AutoApprovalListener implements Listener {
    @Override
    public void notify(ListenerVariable v) {
        Map<String, Object> ext = nodeService.getExt(v.getNode());
        String autoApprovalTime = (String) ext.get("autoApproval");   // 单位：小时
        if (StringUtils.isEmpty(autoApprovalTime)) return;

        // 启动超时定时任务（小时 → 秒）
        long seconds = (long) (Double.parseDouble(autoApprovalTime) * 3600);
        schedule(() -> {
            if (taskNotExecuted(v.getTask().getId())) {
                FlowParams params = FlowParams.build()
                    .ignore(true)                                    // 跳过办理人权限校验
                    .skipType(SkipType.PASS.getKey())                // 或按 autoApproval_skipType
                    .message("超时自动审批");                          // 与人工审批区分
                taskService.skip(taskId, params);
            }
        }, seconds);
    }
}
```

| 要点 | 说明 |
|---|---|
| `ignore(true)` | 超时执行无办理人，必须跳过权限校验 |
| `message("超时自动审批")` | 审计可查，区别于人工审批 |
| `autoApproval_skipType` | 决定超时后是 `PASS` 还是 `REJECT` |

### 坑 ② 业务状态回写必须幂等

监听器会被重复触发（重试、补偿、消息重投），回写逻辑须按 `bizId + 目标状态` 幂等，否则状态错乱、产生重复审批记录。

## 七、三个业务流对应的流程定义

| 业务 | bizType | 节点（按需求 §9.4 / §9.5 / §9.6） |
|---|---|---|
| 实收业绩确认 | `REAL_CONFIRM` | 按发起人定首节点：店长/导入→财务→总监；财务发起→总监；**总监发起→直接落定** |
| 结佣申请 | `COMMISSION` | 发起 → **总监 → 财务**；无差异时**跳过财务** |
| 业绩调整 | `PERF_ADJUST` | 店长/店助/总监发起 → **总监审** |

**通用配置**：

- 总监节点挂 `autoApproval`（小时）+ 创建监听器 → 超时自动通过
- 结佣流程在财务节点前加**互斥网关**，`skipCondition` 判定"实收 == 应收"→ 跳过财务

## 十、测试用例（S16 · 9 条）

| # | 用例 | 预期 |
|---|---|---|
| **S16-1** | 我的待办审批 | `pageWaitingTasks` 取 taskId → `completeTask` → 业务状态同步回写 |
| **S16-2** | 业务明细直接审批 | `getByBusinessId` 取 taskId → 调用**同一** `completeTask`，结果与留痕一致 |
| **S16-3** | 明细入口仍鉴权 | 非审批人 → **服务端拒绝**；前端隐藏 ≠ 安全 |
| **S16-4** | 业务单据状态为准 | 流程已过但业务未回写 → payroll **以业务单据为准**并告警，不按流程状态算薪 |
| **S16-5** | 监听器回写幂等 | 重复触发 → 状态不重复变更、无重复审批记录 |
| **S16-6** | 总监超时自动通过 | 自动通过 + 标记「超时自动审批」+ 继续触发后续节点 |
| **S16-7** | 超时用创建监听器 | 定时任务在**创建**监听器启动；按 `autoApproval_skipType` 执行 |
| **S16-8** | 条件跳过财务 | 实收 == 应收 → 网关跳过财务；有差异正常走 |
| **S16-9** | 换引擎不影响业务 | 只依赖 `ApprovalPort`；CI 断言无 `org.dromara.workflow` 引用 |
