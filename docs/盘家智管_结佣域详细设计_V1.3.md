## 一、定位与职责边界

### 1.1 一句话目标

> **确认"本月哪些实收业绩可以进入工资"，并把这个确认结果审批锁定；锁定的结果不随上游业绩变动而变动。**

### 1.2 结佣的真实语义

V4.2 中"结佣"易被误解为"计算佣金金额"。实际业务语义是：

> **结佣 = 确认本月「实收业绩」可以进入工资计算的动作。**

结合贝壳真实文件（《2026-08-经纪人业绩明细表》）：每一行同时提供**应收业绩**与**实收业绩**两个指标。结佣就是确认"本月实收的这部分业绩，可以计入工资了"。

★ **应收与实收是两个独立指标，不是"应收递减为实收"的转化关系**（业绩域 §1.4 已用真实数据论证）：

| 现象 | 行数 | 说明 |
|---|---|---|
| 实收 > 应收 | 35 | 往月应收在本月补收 |
| 应收 = 0 但实收 > 0 | 34 | 往月应收在本月实收，本月无新增应收 |
| 实收 = 0 | 52 | 已签约未实收 |

| 口径 | 含义 | 贝壳字段 | 数据落点 |
|---|---|---|---|
| 结佣业绩（实收） | 本月已实收、可进工资 | `当月实收业绩` | 业绩域 `PERF_REAL` 事实 |
| 新签业绩（应收） | 本月新增签约应收 | `当月应收业绩` | 业绩域 `PERF_EXPECT` 事实 |

### 1.3 职责边界

| ✅ 负责 | ❌ 严禁 |
|---|---|
| 从业绩域拉取本店本月实收业绩事实，生成结佣明细 | **提成金额 / 提点 / 保底计算**（→ **payroll**） |
| 结佣申请单（门店 + 月）聚合与生命周期 | 工资、社保、公积金、个税（→ **payroll**） |
| 审批流（Warm-Flow）与审批后锁定 | 收支凭证、台账（→ **ledger**） |
| 结佣明细冻结（金额、员工、门店、业务类型、结算月） | 折算系数 / 提成规则快照（→ **payroll**） |
| 新签业绩（应收）只读透传，供 payroll 算店长/总监提成 | 直接读 `pj_perf_*` 表（只能走 Port） |
| 结佣调整单（折扣 / 差额 / 作废） | 修改已审批结佣金额（只能走调整单） |
| 工资-结佣溯源 | 反向依赖 payroll / ledger |

### 1.4 为什么不算提成

V4.2 §5.2 / §7.1 中的提成公式是：

```
业绩提成 = 结佣计薪业绩 × 当月最终提点
当月最终提点 = 基础提点 + 绩效扣点 + 招聘奖励加点
```

其中**提点规则在 payroll**（`pj_payroll_rank_rule` 等），架构 §5.1 亦明确快照链属 payroll 内部。因此本域：

- 只做**确认、审批、锁定、冻结事实**；
- **一分钱提成不算**，表内不出现提点 / 提成金额字段（CI 扫描）。

### 1.5 V4.2 四条硬要求（本域存在理由）

| # | 要求 | 出处 | 落地 |
|---|---|---|---|
| 1 | **审批通过的月份 = 工资归属月** | §9.3 | 结佣明细落 `approved_month`，payroll 按此归月 |
| 2 | **已审批结佣对应的原始数据永不覆盖** | §9.2-4 | 已审批明细金额冻结；后续导入金额不同只提示差异 |
| 3 | 结佣锁定即**冻结事实快照**（员工、门店、金额、业务类型） | §10.1 | 明细行冗余落 `employee_id` / `dept_id` / `amount` / `biz_type` |
| 4 | 已审批数据**只走调整单**变更，不自动修复 | §9.4 | 见 §4.5 |

### 1.6 域依赖

```
panjia-performance ──(CommissionPerformanceQueryPort)──▶ panjia-commission
panjia-people      ──(EmployeeSnapshotQueryPort)──────▶ panjia-commission
panjia-commission  ──(CommissionQueryPort)────────────▶ panjia-payroll
```

| 约束 | 说明 |
|---|---|
| commission 依赖 performance，**performance 不反向依赖 commission** | 事件单向 |
| **payroll 只依赖 people + commission** | 架构 §2.3：payroll 不穿透依赖 performance（但可只读依赖 import 取考勤/积分，ADR-026） |
| commission 是 payroll 的**唯一计薪业绩出口** | 结佣业绩（走审批锁定）+ 新签业绩（只读透传）都由本域提供 |

> ★ **为什么新签业绩也由本域透传**：V4.2 §10.2 中店长团队提成、总监门店提成用 `PERF_EXPECT`（应收），但架构规定 payroll 只能依赖 people + commission。若 payroll 直接读 performance 就破了依赖图。故本域作为唯一出口，**结佣业绩走审批锁定，新签业绩做只读透传**。

## 二、结佣口径与数据处理原则

### 2.1 零加工：本域不二次折算

业绩域已按"贝壳给什么记什么"原样落库（业绩域 §2.1）。本域：

- **直接透传业绩域的 `amount`，不折算、不乘任何系数**；
- 折算（一手房 ×0.9024 / 其他 ×0.96）属 **payroll 规则层**（业绩域 §2.2）；
- 表内**不出现**除 `conversion_rate` / `discount_rate` 之外的任何系数（CI 扫描）。

> 原因：若业绩域折一次、本域再折一次，会**双重折算**。折算只允许发生一次，且在 payroll。

### 2.2 结佣金额口径

| 项 | 取值 |
|---|---|
| 结佣明细金额 | 业绩域 `PERF_REAL` 事实的 `amount`（= 贝壳「当月实收业绩」原样值） |
| **★ 入单过滤** | 仅拉取 **ACTIVE 且 `amount <> 0`** 的 `PERF_REAL` 事实。`amount = 0` 的"已签约未实收"行**不生成结佣明细**（§4.1 ④ / ADR B14） |
| 本样本基准 | 全表实收合计 **192,556.89** — 结佣明细 **266 行**（318 − 52 条实收 = 0）／**36 人**／**6 门店** |
| 金额加工 | **无**。85 折等折扣通过 `DISCOUNT` 调整单**直接存折后金额** |

> **行数口径**：按 §3.2 定义（一行 = 一条 `PERF_REAL` 事实），本样本结佣明细为 **266 行**，与文首"月度结佣明细数百行"的体量自洽（0 值行不贡献金额，合计 192,556.89 不受影响）。
>
> **验收锚点**：导入《2026-08》全量 318 行 → 6 张申请单明细行数合计 = **266**，`total_amount` 合计 = **192,556.89**（契约测试 C-16 / X-5）。

> **折扣不存系数**：发起 `DISCOUNT` 调整时算好折后值直接存 `amount = 8500`，`reason` 里写"85折"供审计追溯。这样折扣种类不受限（想打几折填几折），系统不认识"系数"这个概念。

### 2.3 结佣明细不用闭开区间

| 对比 | 业绩域 `PerformanceFact` | 本域 `CommissionItem` |
|---|---|---|
| 时间模型 | 闭开区间 `[effective_date, expire_date)` | **三态状态机** |
| 原因 | 需支持历史时点回放查询（"某日有效的业绩是多少"） | 离散结算凭证，时点语义由 `approved_month` 承载 |
| 状态 | `ACTIVE` / `REVERSED` | `PENDING` / `APPROVED` / `REVERSED` |

> 取舍记录见 ADR B7。二者在"**不可原地改写、变更走冲销+新增**"上一致。

### 2.4 冻结什么、不冻结什么

| 冻结（落明细行） | 不冻结（payroll 时点取） |
|---|---|
| 业绩金额 `amount` | 提点 / 提成金额 |
| 员工 `employee_id` | 职级、社保、公积金开关 |
| 归属门店 `dept_id` | 绩效等级、招聘奖励加点 |
| 业务类型 `biz_type` | 保底、跳点、团队提点 |
| 结算月 `period` / 审批月 `approved_month` | 折算系数 |
| 角色类型、费用项（冗余备查） | 个税 |

> **快照定位**：本域存的是"**事实 + 时点**"，不是"规则"。规则版本由 payroll 按算薪时点自行取（CR-C6），本域不存规则快照 —— 保住"不存规则"的红线。

### 2.5 期间封账语义与结佣窗口

`PeriodCloseQueryPort.isClosed(period)` 的语义**唯一，不得二义**：

| 状态 | 含义 | 结佣域可做什么 |
|---|---|---|
| `OPEN` | 该结算月业绩数据**未定稿**，仍可导入 / 补录 / 冲销 | ✅ **结佣窗口开启**：发起结佣、增量重拉、调整单执行 |
| `CLOSED` | 该结算月**终态关闭**（业绩已定稿；通常由 `PayrollLockedEvent` 自动触发，见业绩域 §3.5 / §4.7） | ❌ **结佣窗口关闭**：拒绝发起结佣、拒绝增量重拉、拒绝调整单执行 |

**结佣时间窗：**

```
导入 / 补录（OPEN）──▶ 发起结佣 ──▶ 审批锁定 ──▶ payroll 算薪并锁定 ──▶ PayrollLockedEvent ──▶ 期间 CLOSED
                    └─────────────── 结佣窗口（OPEN 期间）────────────────┘
```

**三条判定规则（消歧义，编码按此实现）：**

| 动作 | 校验哪个月 | 说明 |
|---|---|---|
| 发起结佣 / 增量重拉 | **`period`（业绩归属月）** | 工资都发完了，不允许再为这个月发起结佣 |
| `DIFF` 差额调整 | **`target_period`（补发到哪个月）** | 8 月已封账但要补发到 9 月 → 只要 9 月未封账即允许 |
| `DISCOUNT` / `VOID` | **明细自身所属 `period`** | 作用于已存在明细，随明细走 |

> ★ **封账不是"数据齐了、可以结佣了"，而是"这个月彻底关门了"**。因此**结佣必须在封账之前完成**；若某月已 `CLOSED` 仍有实收未结，只能：① 以 `DIFF` 补发到某个未封账月份（如次月），或 ② 由总监解封后重走 —— **严禁系统自动放行**。

> 本域**不建封账表**（ADR B9），一切以业绩域 `pj_perf_period_close` 为准，经 Port 只读查询，每次实时调（不缓存、不感知解封）。

## 三、领域模型（4 表）

**`CommissionApplication`（申请单）/ `CommissionItem`（结佣明细）/ `CommissionAdjust`（调整单）/ `CommissionConsumeLog`（消费日志）**

### 3.1 聚合根：`CommissionApplication`（结佣申请单）

粒度 = **门店 + 业绩归属月（结算月）**。

| 字段 | 说明 |
|---|---|
| `id` | 雪花主键 |
| `apply_no` | `CAPP + yyyyMMdd + 序列` |
| `period` | 业绩归属月（结算月，如 `2026-08`） |
| `dept_id` | 门店（汇总口径，与业绩域一致） |
| `item_count` / `total_amount` | 明细条数 / **结佣业绩金额合计**（非佣金金额） |
| `status` | `DRAFT → PENDING_VERIFY → SUBMITTED → APPROVED → LOCKED`（终态）／`REJECTED`／`CANCELLED` |
| `process_instance_id` / `applicant_id` / `approver_id` | Warm-Flow / 发起人 / 审批人 |
| `approved_month` | **审批通过月 = 工资归属月**（V4.2 硬要求 1） |
| `lock_time` | 锁定时间 |
| `version` | 乐观锁（发起 / 增量重拉 / 审批回调并发守卫，§6.2） |

**状态机：**

```
DRAFT ──提交──▶ PENDING_VERIFY ──核验通过──▶ SUBMITTED ──审批通过──▶ APPROVED ──锁定──▶ LOCKED（终态）
                    │                            │                        │
                    └──核验驳回──▶ REJECTED       └──驳回──▶ REJECTED      └──作废──▶ CANCELLED
```

> ★ **`PENDING_VERIFY`（待核验）** —— V4.2 §9.3「待核验 → 核验通过 → 审批通过/驳回」，核验人 = V4.2 五类角色中的**算薪人员**（原"助理核验"）。
>
> **跳过核验开关**：配置 `panjia.commission.skip-verify`（默认 `false`）。置 `true` 时提交**直接进 `SUBMITTED`**，跳过算薪人员核验环节，由总监直接审批（V4.2 §9.3 明确要求支持该开关）。
>
> **幂等口径不变**：`uk_capp_period_dept` 排除的仍是非终态集合，`PENDING_VERIFY` 一并纳入占位状态。

### 3.2 实体：`CommissionItem`（结佣明细）

一行 = 一条 `PERF_REAL` 业绩事实的结佣确认。

| 字段 | 说明 |
|---|---|
| `id` | 雪花主键 |
| `application_id` | 所属申请单 |
| `performance_fact_id` | 关联业绩事实（`pj_perf_fact.id`，**只存 ID 不建 FK**） |
| `period` / `approved_month` | 业绩归属月 / 工资归属月 |
| `employee_id` / `dept_id` | 冻结的归属人 / 门店 |
| `biz_type` / `role_type` / `fee_item` | 冻结的业务类型 / 角色类型 / 费用项 |
| `amount` | **结佣业绩金额**（业绩域原样透传，非佣金金额） |
| `status` | `PENDING` / `APPROVED` / `REVERSED` |
| `origin_reversed` | boolean，★ 源业绩事实已被冲销（已审批时置 true + 告警，金额不动） |
| `adjust_id` | 来源调整单 |
| `reversed_reason` | `SUPERSEDE` / `RENORMALIZE` / `MANUAL_ADJUST` / `PERIOD_VOID` |
| `version` | 乐观锁 |

**关键不变量：**

- **已审批明细金额不可变** —— 变更只能走调整单（新行）；
- `REVERSED` 行**永久保留**；
- 部分唯一索引 `uk_citem_fact_active` **排除 `REVERSED` 行**：

```sql
CREATE UNIQUE INDEX uk_citem_fact_active ON pj_commission_item(performance_fact_id)
  WHERE performance_fact_id IS NOT NULL AND status <> 'REVERSED';
```

> **为什么必须排除 `REVERSED`**：`DISCOUNT` 调整是"旧行 REVERSED + 新行关联**同一个** `performance_fact_id`"。若唯一索引不排除 REVERSED 行，新行插入必然撞键失败。
>
> **`DIFF` 差额行不挂 `performance_fact_id`** —— 它是差额凭证，不指向具体事实。

### 3.3 实体：`CommissionAdjust`（结佣调整单）

| 字段 | 说明 |
|---|---|
| `adjust_no` | `CADJ + yyyyMMdd + 序列` |
| `application_id` / `item_id` | 调整对象（`item_id` 为空表示整单级调整） |
| `adjust_type` | `DISCOUNT`（折扣）/ `DIFF`（差额补发）/ `VOID`（作废） |
| `new_amount` | `DISCOUNT` 用（**折后最终金额**，非系数） |
| `diff_amount` / `target_period` | `DIFF` 用（差额 / 补发到哪个月） |
| `payload_json` | 变更前后值快照 |
| `reason` | 必填，审计 |
| `status` | `SUBMITTED → APPROVED → EXECUTED`（终态）／`REJECTED`／`CANCELLED` |
| `process_instance_id` / `applicant_id` / `approver_id` | Warm-Flow |

**EXECUTED 同事务动作：**

| 类型 | 动作 |
|---|---|
| `DISCOUNT` | 旧明细 `REVERSED` + 新明细（`amount` = 折后值，`performance_fact_id` **沿用原值**，`status = PENDING`） |
| `DIFF` | 新增差额明细（`performance_fact_id = NULL`，`period` = `target_period`） |
| `VOID` | 旧明细 `REVERSED` |

**前置校验：**

1. **封账校验（按 §2.5 三条判定规则）** —— 经 `PeriodCloseQueryPort` 实时查：
   - `DIFF`：校验 **`target_period`（补发到哪个月）** 未封账（8 月已 `CLOSED`、补发到 9 月 → 只要 9 月未封账即允许）；
   - `DISCOUNT` / `VOID`：校验**明细自身所属 `period`** 未封账；
2. 原明细为 `PENDING` 或 `APPROVED`；
3. 同一 `item_id` 无未完成调整单；
4. 幂等（重复回调先查状态）。

> ⚠ **不校验工资批次是否锁定** —— 那是 payroll 的职责。结佣域**严禁反向依赖 payroll**；工资批次锁定由 payroll 在算薪时自行决定。

### 3.4 `CommissionConsumeLog`（消费日志）

消费业绩域事件，做**幂等锚点 + 冲销联动留痕**。

| 字段 | 说明 |
|---|---|
| `event_id` | **唯一索引** → 幂等 |
| `event_type` | `FACT_CREATED` / `FACT_REVERSED` |
| `period` / `fact_ids` | 检索与留痕 |
| `status` | `SUCCESS` / `PARTIAL` / `FAILED` |
| `affected_items` | 受影响的结佣明细数 |
| `message` | 失败原因 |

## 四、核心流程

### 4.1 发起结佣（拉取业绩 → 生成明细）

```
【主路径：导入后系统自动生成，V4.2 §9.3】
① 消费 PerformanceFactCreatedEvent（PERF_REAL）→ 按 (period, deptId) 分组
   → 该组无未完成申请单 → 自动生成 DRAFT 申请单并拉取明细（状态 = 待审批）
   → 该组已有 DRAFT/PENDING_VERIFY/SUBMITTED 单 → 走增量重拉（§4.1.1）
   → 该组已有 APPROVED/LOCKED 单 → 不新建，标记「待补事实」提示算薪人员（§7.1）
   ※ 人工入口保留：算薪人员可手动选门店+月发起，逻辑完全相同（幂等）

② 期间校验：PeriodCloseQueryPort.isClosed(period) → CLOSED 则拒绝（§2.5）
③ CommissionPerformanceQueryPort.findActiveByDept(period, deptId, PERF_REAL)（只返回 ACTIVE）
④ ★ 过滤：仅保留 amount <> 0 的事实
   - 本样本 318 条结算明细中 52 条「当月实收业绩 = 0」（已签约未实收）→ 不生成结佣明细（ADR B14）
   - 0 值事实仍留在业绩域可查，下月实收后自然进入「下月」的结佣
⑤ 逐条生成 CommissionItem（status = PENDING）
   - amount 原样透传，不折算
   - 冻结 employee_id / dept_id / biz_type / role_type / fee_item
⑥ 生成/复用 CommissionApplication（status = DRAFT → SUBMITTED），重算 item_count / total_amount
⑦ ★ 幂等分三种情形（ADR B15）：
   - 该 (period, deptId) 无未完成申请单          → 新建申请单
   - 已有 DRAFT / SUBMITTED 单                    → 提示「已存在未审批申请单」，走 **增量重拉**（§4.1.1），不新建单
   - 已有 APPROVED / LOCKED 单                    → 拒绝；新增或变更一律走调整单（§4.5）
```

> **一句话口径（V4.2 §9.1 链路落地）**：导入后有实收 → **每一条 `amount > 0` 的 `PERF_REAL` 事实，都应能在「门店 + 结算月」的申请单中被拉出、被审批、被锁定**。审批通过月即工资归属月（`period=2026-08` → `approved_month=2026-09` 则计入 9 月工资）。

#### 4.1.1 增量重拉

**场景**：8 月已发起结佣（拉了 266 行）→ 又补导入一个批次（新增若干 `amount > 0` 的实收事实）→ 这些补录事实要进**同一个**申请单，而不是让算薪人员手工开 `DIFF` 补。

**规则**：仅 `DRAFT` / `SUBMITTED` 申请单可增量重拉；`SUBMITTED` 单重拉后**保留审批流程不重置**（明细追加，提示审批人重新确认）。

```
① 查本单已有「未 REVERSED」明细的 performance_fact_id 集合 S
② 重新拉取 (period, deptId, PERF_REAL) 中 ACTIVE 且 amount <> 0 的事实集合 F
③ 差集 F − S → 逐条生成新明细（status = PENDING），追加到本单
④ 重算 item_count / total_amount，写消费日志
⑤ ★ 只追加、不删除、不修改：已生成明细的金额永不因重拉而变化
```

> **为什么不做"全量重建"**：已生成的明细可能已被人工核对；全量重建会导致明细 ID 漂移、审批中页面跳动。只追加最安全，且**天然幂等**（重复重拉 → 差集为空 → 零副作用）。

> **`uk_capp_period_dept` 保持不变** —— 增量重拉复用同一申请单，不新增申请单，故不撞键；已有 `APPROVED`/`LOCKED` 单时重拉请求直接被状态机拒绝，也不撞键。

#### 4.1.2 异常结佣（V4.2 §9.3）

**场景**：V4.2 §9.3 ——「实际已满足结佣条件**但贝壳未实收** → 人工发起申请 → 填写原因说明 → 走审批流程 → 审批通过后生效」。

> **为什么必须单独开通道**：ADR B14 规定"`amount = 0` 的实收事实不进结佣明细"，而贝壳未实收即 `PERF_REAL.amount = 0`，会被 0 值过滤挡在门外。不能靠"放开 0 值过滤"解决（那会把 266 行正常数据污染成 318 行）。

**处理方式：不绕过滤，而是给事实补金额。**

```
① 算薪人员在业绩域对该笔业绩手工录入 PERF_REAL 事实（source = MANUAL，带原因说明）
   —— 业绩域已支持手工录入（source = MANUAL，重跑时绝不删除，见业绩域 §4.1 幂等实现）
② 该事实 amount > 0 → 自然满足 §4.1 ④ 的过滤条件 → 随当批进入结佣申请单
③ 结佣明细落 performance_fact_id 指向该 MANUAL 事实，溯源时可见"人工补录 + 原因"
④ 走正常审批链路（含 PENDING_VERIFY 核验）
```

**关键约束：**

| 约束 | 说明 |
|---|---|
| **绝不删除 MANUAL 事实** | 业绩域重跑只删 `source = IMPORT` 的派生行，MANUAL 行是人工成果，必保 |
| **原因说明必填** | 落业绩域调整单 `reason`，随溯源链路一并展示（V4.2 §13.8 要求可追溯） |
| **不新增申请单类型** | 异常结佣与正常结佣共用 `CommissionApplication`，只是明细来源为 MANUAL 事实 |
| **不走 `DIFF` 调整单** | `DIFF` 是"已审批后发现漏算"的补救；异常结佣发生在**审批前**，应随正常批次一起审批 |

> **与普通补录的区别**：普通补录 = 贝壳后来实收了（IMPORT 事实）；异常结佣 = 贝壳一直未实收但公司确认可结（MANUAL 事实）。二者在结佣域都表现为"一条 `amount > 0` 的 `PERF_REAL` 事实"，**结佣域无需区分**，差异只在业绩域的 `source` 字段。

### 4.2 审批与锁定

```
DRAFT ──提交──▶ PENDING_VERIFY（算薪人员核验）
   │                │
   │                ├─ skip-verify=true ─────────┐（跳过核验开关）
   │                ▼                            │
   │          核验通过 ──▶ SUBMITTED ◀───────────┘
   │                │
   │                └──核验驳回 ──▶ REJECTED
   │
   └──（skip-verify=true 时也可直接）──▶ SUBMITTED

SUBMITTED ──Warm-Flow 审批（总监）──▶ APPROVED（落 approved_month = 当前月）
   ↓
LOCKED（明细 status = APPROVED，金额冻结）
   ↓
发布 CommissionApprovedEvent → payroll 消费
```

> **V4.2 §9.3 对齐**：审批链路「待核验 → 核验通过 → 审批通过/驳回」= `PENDING_VERIFY → SUBMITTED → APPROVED`；「跳过助理核验，直接总监审批」= `panjia.commission.skip-verify=true` 时 `DRAFT → SUBMITTED`。
> **审批通过月 = 工资归属月**（V4.2 硬要求 1 / ADR B3）。

> **审批通过月 = 工资归属月**（V4.2 硬要求 1）。若 8 月业绩在 9 月才审批通过，则 `period=2026-08`、`approved_month=2026-09`，工资计入 9 月。

### 4.3 新签业绩透传（不进审批）

```
payroll 需要门店新签业绩（店长团队提成 / 保底 / 总监门店提成基数）
   ↓
CommissionQueryPort.findNewSignByDept(period, deptId)
   ↓
本域转调 CommissionPerformanceQueryPort.findActiveByDept(period, deptId, PERF_EXPECT)
   ↓
原样返回，不折算、不加工
```

> 新签业绩**不生成结佣明细、不走审批**（它不参与结佣确认），只做只读透传。

### 4.4 业绩冲销的联动（分治表）

业绩域发布 `PerformanceFactReversedEvent(factIds, reason)` → 本域消费：

| 明细当前状态 | 动作 | 理由 |
|---|---|---|
| `PENDING`（未审批） | 随动作废 → `REVERSED` | 未锁定，可随上游变动 |
| `APPROVED`（已审批） | **金额一动不动**，只置 `origin_reversed = true` + 告警 | V4.2 §9.2-4：已审批数据永不覆盖 |
| `REVERSED`（已冲销） | 忽略 | 终态 |

**三种冲销来源：**

| 来源 | `reversed_reason` | 说明 |
|---|---|---|
| 批次替换 supersede | `SUPERSEDE` | 导入新批次替换旧批次 |
| 重归一化 reNormalize | `RENORMALIZE` | 导入域重跑归一化 |
| 业绩域人工调整 / 作废 | `MANUAL_ADJUST` / `PERIOD_VOID` | 业绩调整单执行 |

> **已审批明细不自动修复** —— 是否调整由人工走 `DIFF` 调整单决定。自动修复会破坏"已审批数据不覆盖"的合规底线。

### 4.5 调整单流程

```
发起（店长/总监/算薪）→ Warm-Flow 审批 → EXECUTED（同事务：冲销旧行 + 生成新行）
```

> V4.2 §9.4：已审批数据变更走调整单，不自动修复。

### 4.6 对外 Port：`CommissionQueryPort`（给 payroll）

```java
public interface CommissionQueryPort {                  // panjia-commission-api

    /** ② 按期间 + 员工查已锁定结佣明细 */
    List<CommissionItemDTO> findLockedByEmployee(String period, Long employeeId);

```

**约束：**

- ①② 只返回 `status = APPROVED` 的结佣明细；
- ③④ 返回的是业绩域 `PERF_EXPECT` 事实的**原样透传值**，**本域不做折算**；DTO **必须带 `biz_type`**，供 payroll 按业务类型应用折算系数；
- ①②⑤ 的 `findLocked(period, ...)` 入参 `period` = **`approved_month`（工资归属月）**，非业绩归属月（★CR-C10）；
- DTO 需含 `factId` / `dealKey` / `bizType` / `amount` / `employeeId` / `deptId` / `period` / `approvedMonth` / `roleType` / `feeItem`（★CR-C9）；`dealKey` = 业绩域 `source_key` 去掉 `fact_type` 后缀；
- ⑤ 返回全量，Javadoc 标注"仅供审计对账"；
- 返回**只读 DTO**，无写方法；
- **payroll 禁直连 `pj_commission_*` 表**（ArchUnit 校验）。

## 六、事务、并发、幂等

### 6.1 事务边界

| 场景 | 策略 |
|---|---|
| 发起结佣 | 单事务：写申请单 + 批量写明细 + 写消费日志 |
| 审批回调 | 单事务：申请单状态 + 明细状态批量 `APPROVED` + 落 `approved_month` |
| 调整单 `EXECUTED` | 单事务：旧行 `REVERSED` + 新行生成 + 状态变更 |
| 冲销联动 | 单事务：批量更新受影响明细 + 写消费日志 |

> 不引入 MQ / 死信队列，Spring 事件 + Outbox 已足够（模块化单体）。

### 6.2 并发控制

| 风险 | 防护 |
|---|---|
| 同一事件重复消费 | `uk_ccl_event(event_id)` |
| 同一 (period, deptId) 重复发起申请单 | `uk_capp_period_dept` 部分唯一索引（重复**发起**走增量重拉，不新建单） |
| 增量重拉与审批回调并发 | 申请单状态机守卫（仅 `DRAFT`/`SUBMITTED` 允许重拉）+ 申请单 `version` 乐观锁；`uk_citem_fact_active` 兜底防同一事实重复插入 |
| 同一明细并发调整 | 明细 `version` 乐观锁；冲突重试 3 次后告警 |
| 审批与冲销同时发生 | 明细乐观锁 + 状态机守卫（`REVERSED` 为终态） |

### 6.3 幂等锚点

| 入口 | 锚点 |
|---|---|
| `PerformanceFactCreatedEvent` | `uk_ccl_event(event_id)` |
| `PerformanceFactReversedEvent` | 同上 |
| 审批回调 | 申请单 `status` + `version` |
| 发起结佣 | `uk_capp_period_dept` |

## 七、事件、依赖与包结构

### 7.1 事件

| 方向 | 事件 | 来源 | 字段 | 处理 |
|---|---|---|---|---|
| in | `PerformanceFactCreatedEvent` | performance | `eventId` / `period` / `factIds` / `factType` / `deptIds` | ★ **主触发器**：仅 `PERF_REAL` 触发，按 (period, deptId) 分组 —— ① 无未完成单 → **自动生成 `DRAFT` 申请单 + 明细**（§4.1 ①，V4.2 §9.3）；② 已有 `DRAFT`/`PENDING_VERIFY`/`SUBMITTED` 单 → **增量重拉**（§4.1.1）；③ 已有 `APPROVED`/`LOCKED` 单 → 标记「待补事实」提示（不自动改已审批数据）。`PERF_EXPECT` 忽略（透传不走明细） |
| in | `PerformanceFactReversedEvent` | performance | `eventId` / `period` / `factIds` / `reason` | 按 §4.4 分治表处理 |
| out | `CommissionApprovedEvent` | → payroll | `eventId` / `period` / `approvedMonth` / `deptId` / `itemIds` / **`dealKeys`**（★CR-C11） | 只传 ID；`dealKeys` 供 payroll 按业绩业务键匹配递延台账（`fact_id` 无法匹配，应收/实收是两条事实） |

> 事件只做通知，下游收到后调 Port 拉取，避免消息体过大。
> 消费 performance 事件**不构成反向依赖**（performance 不依赖 commission）。

### 7.2 对内依赖 Port

| Port | 目标 | 约束 |
|---|---|---|
| `CommissionPerformanceQueryPort` | performance | 只读；**禁直连 `pj_perf_*` 表** |
| `PeriodCloseQueryPort` | performance | 只读查期间是否封账；**本域不建封账表** |
| `EmployeeSnapshotQueryPort` | people | 只读，按 `business_date` 取时点快照 |

## 十一、架构决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| **B1** | 结佣域**只做确认与锁定，不计算提成金额** | V4.2 中"结佣"= 确认实收业绩进入工资的动作；提点规则属 payroll |
| **B2** | 申请单粒度 = **门店 + 业绩归属月（结算月）** | 与业绩域汇总口径一致；审批按店进行 |
| **B3** | **审批通过月 = 工资归属月**（`approved_month`） | V4.2 §9.3 硬要求 |
| **B4** | **已审批结佣不随业绩冲销变动**，只置 `origin_reversed` + 告警 | V4.2 §9.2-4：已审批原始数据永不覆盖；自动修复会破坏合规底线 |
| **B5** | 未审批明细随业绩冲销作废 | 未锁定，可随上游变动，避免脏数据进入审批 |
| **B6** | 新签业绩**只读透传不进审批** | 新签不参与结佣确认；但 payroll 需要它算店长/总监提成，本域是唯一出口 |
| **B7** | 结佣明细用**三态状态机**，不用闭开区间 | 离散结算凭证，时点语义由 `approved_month` 承载；业绩域闭开区间是为历史时点回放 |
| **B8** | **不存规则快照**，只冻结事实 + 时点 | 提点/保底/折算归 payroll 规则层；本域存规则会越界且规则变更需回溯 |
| **B9** | **封账复用业绩域 `pj_perf_period_close`**，经 `PeriodCloseQueryPort` 只读查（语义见 §2.5） | 两处封账状态必然不一致；本域不建封账表 |
| **B10** | `DISCOUNT` 存**折后金额**不存系数 | 折扣种类不受限；系统不认识"系数"概念 |
| **B11** | **折算只发生一次**（在 payroll），本域不二次折算 | 业绩域已原样落库，本域再折会双重折算 |
| **B12** | `uk_citem_fact_active` **必须排除 `REVERSED`** | DISCOUNT 调整会"旧行 REVERSED + 新行沿用同一 fact_id"，不排除则插入撞键 |
| **B13** | 调整单不校验工资批次锁定 | 工资批次锁定是 payroll 职责；本域严禁反向依赖 payroll |
| **B14** | **`amount = 0` 的实收事实不进结佣明细** | "已签约未实收"尚未产生可进工资的业绩，入单只会虚增 `item_count`、干扰审批；业绩域仍可查，下月实收后自然进入**下月**结佣 |
| **B15** | **未审批申请单支持「增量重拉」（只追加），已审批一律走调整单** | 补录批次是常态，全靠 `DIFF` 人工补会累死算薪；但一旦审批锁定，任何变更必须走审批过的调整单（V4.2 §9.4） |
| **B16** | **封账 = 该结算月终态关闭，结佣必须在封账前完成** | 封账由 `PayrollLockedEvent` 触发，工资已发即不可追溯变更；与业绩域 §3.5「封账后拒绝一切写入」保持一致，杜绝"工资发完又补一笔结佣" |
| **B17** | **导入后系统自动生成申请单（`DRAFT`），人工入口保留** | V4.2 §9.3："系统自动识别可结佣业绩，生成结佣申请单（状态=待审批）"。事件驱动自动生成 + 幂等，人工发起作为等价入口 |
| **B18** | **异常结佣走"业绩域补 MANUAL 事实"，不放松 0 值过滤** | V4.2 §9.3 要求"已满足条件但贝壳未实收"可人工申请结佣，而 ADR B14 过滤 `amount = 0`。放开过滤会污染 266 行正常数据；补 MANUAL 事实则天然满足过滤条件，且保留原因说明与溯源 |
| **B19** | **状态机含 `PENDING_VERIFY`（待核验），支持跳过核验开关** | V4.2 §9.3 审批链路为"待核验 → 核验通过 → 审批通过"，并要求支持"跳过助理核验直接总监审批"的开关配置 |

## 十三、业务口径与实施可选项

### 13.1 业务口径定论

> 以下为**执行口径**，编码与验收按此执行。

| # | 口径问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | 新签业绩是否参与算薪 | **参与**——店长团队提成 / 保底、总监门店提成**均以新签业绩（应收）为基数**；V4.2 §12.13/§13.2 的"新签不参与算薪、仅展示"**仅指经纪人个人提成**（经纪人的提成基数只有结佣业绩） | V4.2 §5.2 / §9.1 / §10.2 / §13.3 / §13.4 |
| 2 | §6.5 总监验算表是否作验收锚点 | **不作锚点**——该表 6 店有 5 店算不对（龙湖 119,274.92×7% = 8,349.24 vs 表列 7,665.17），且 §6.2 定总监底薪 6,000、验算却用 3,500+500+2,000。改用 **V4.2 §13.4 验收标准**（跳点阶梯正确、逐店汇总、与《总监工资表》"新签业绩"列一致）+ 真实文件原始金额回归 | V4.2 §13.4 / §13.9 |
| 3 | 团队提成扣减的社保成本口径 | **社保成本 = 1637.15 × 计缴人数**；`实际缴费金额` = **每人全额 1637.15**（个人 + 公司合计）；`计缴人数` = 本店**个人社保比例 > 30%** 且**非兼职**的人数（A0 20% 不计、S1/S2/总监 30% 不计、兼职不计）。本域不感知该计算——由 payroll 在算薪时完成 | V4.2 §5.2 / §7.2；架构 §5.3.2 |
| 4 | 数据源与是否导入《理房通到账明细表》 | **只导入《2026-08-经纪人业绩明细表》**（应收 206,274.04 / 实收 192,556.89）。该文件即 V4.2 §7.1 所述"理房通到账明细表 → …→ **经纪人到账贡献明细表**"链路中的**结算明细表**，含需求列出的全部字段（应收/实收业绩、角色人系统号、角色类型、业绩比例、订单号/合同号）。《理房通到账明细表》**不导入**，避免业绩翻倍 | V4.2 §7.1；业绩域 ADR A5 |
