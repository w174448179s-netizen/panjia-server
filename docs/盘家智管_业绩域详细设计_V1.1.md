## 一、定位与职责边界

### 1.1 一句话目标

> **把贝壳导入的每一条业绩记录，原样记成"某人在某结算月、某口径、业绩多少钱"的业绩事实；事实一经生成，只可冲销、不可改写。**

### 1.2 数据来源：贝壳《经纪人业绩明细表》

以《2026-08-经纪人业绩明细表-246555.xlsx》为样本。文件含 **4 个 Sheet**：

| Sheet | 行数 | 列数 | 粒度 | 在本设计中承担的角色 |
|---|---|---|---|---|
| 导出说明 | 4 | 2 | — | 表格说明，**非数据表**，不导入 |
| 经纪人业绩汇总表 | 40（38 数据） | 46 | 人 × 加盟商 × 月 | 归档对账（12 个分业务业绩列 + **合同单量**唯一来源） |
| 经纪人合同明细表 | 159（157 数据） | 19 | 人 × 合同 | 归档对账（物业地址、过户/完结日期） |
| **经纪人业绩结算明细表** | **320（318 数据）** | **30** | **合同 × 角色人 × 费用项 × 角色类型** | **★ 业绩事实正源** |

#### 为什么选结算明细表作正源

三张数据表是**同一份数据的三种视图**。已按角色人汇总做过金额勾稽：

```
                  应收业绩        实收业绩
结算明细表      206,274.04      192,556.89
汇总表          206,274.04      192,556.89
合同明细表      206,274.04      192,556.89
逐人比对差异均为 0.00
```

任选其一都不会算错，选结算明细表的理由：

| 理由 | 说明 |
|---|---|
| 粒度最细 | 318 行，可精确定位到"某角色人在某合同的某费用项、以某角色身份贡献了多少业绩" |
| **唯一含费用项** | `费用项` 列（居间代理费 / 居间服务费 / 中介费 / 贷款服务费） |
| **唯一含角色类型** | `角色类型` 列，本样本 **16 种**取值 |
| **唯一含业绩比例** | `业绩比例` 列，本样本 **30 种**取值 |
| **唯一含到账与手续费** | `合同当月到账金额` / `合同当月支付手续费` / `合同总到账金额` / `合同总支付手续费` |
| **唯一含双口径** | `当月应收业绩` / `总应收业绩` / `当月实收业绩` / `总实收业绩` |

> **各 Sheet 全部导入归档**（满足追溯），但**只有结算明细表生成业绩事实**，否则同一笔业绩会被重复记录。各 Sheet 通过 `source_type` 区分（CR-7）。

#### 贝壳原文：表格说明

```
【经纪人业绩汇总表】  统计方式：按照经纪人汇总统计对应月份的应收业绩、实收业绩、合同量，
                    并按照各个业务分类汇总。
【经纪人合同明细表】  统计方式：按照经纪人展示对应月份结算业绩的合同，
                    以及经纪人在该合同产生的应收业绩、实收业绩汇总。
【经纪人业绩结算明细表】合同范围：对应月份产生应收业绩或实收业绩的全部合同。
                    数据来源：与 A+ 签约管理-业绩、A+ 签约管理-其他-应收业绩、
                    A+ 签约管理-其他-实收业绩信息一致。
```

#### 结算明细表列结构（30 列，6 组）

```
基本信息    结算月、业务类型、订单号、合同号、签约(成销)时间、过户日期(仅二手)、完结日期(仅二手)、
            物业地址、费用项
角色人信息  角色人系统号、角色人姓名、角色类型、业绩比例
应收业绩    ★当月应收业绩、总应收业绩
实收业绩    ★当月实收业绩、总实收业绩
合同到账金额 合同当月到账金额、合同总到账金额
支付手续费  合同当月支付手续费、合同总支付手续费
其他        备注、店组编码、店组名称、门店编码、门店名称、
            加盟商编码、加盟商mdmCode、加盟商名称、分账主体理房通商户号
```

#### 另两张表列结构

```
汇总表（46列）：结算月 | 角色人系统号 | 角色人姓名
              当月应收业绩 + 12 个分业务列（二手/租赁/新房/好赞/金融分润/家装荐客/
              新房装修/省心租/自如/公寓/其他）
              当月实收业绩 + 12 个分业务列（同上）
              业绩合同单量 + 12 个分业务列（★ 合同量指标的唯一来源）
              店组编码 | 店组名称 | 门店编码 | 门店名称 | 加盟商编码 | mdmCode | 名称

合同明细表（19列）：结算月 | 业务类型 | 订单号 | 合同号 | 物业地址 | 签约(成销)时间 |
              过户日期(仅二手) | 完结日期(仅二手) | 角色人系统号 | 角色人姓名 |
              应收业绩-合同汇总 | 实收业绩-合同汇总 | 店组/门店/加盟商各列
```

> **三张表均为双层表头**（第 1 行分组名如"基本信息/角色人信息/应收业绩"，第 2 行真实列名）。解析必须按 2 行表头处理，否则列名错位（CR-12）。

#### 从真实数据得到的十四条结论

| # | 观察 | 对设计的约束 |
|---|---|---|
| 1 | 本文件是**业绩口径**（应收/实收业绩），不是到账金额口径 | `amount` 取业绩值，到账金额另存备查 |
| 2 | 期间字段是**结算月**（`202608`），全表唯一值 | `period` = 结算月 |
| 3 | 业务类型本样本 **5 种**：租赁 200 / 二手买卖 56 / 租赁轻托管 33 / 轻托管推房 28 / **写字楼租赁** 1 | 枚举按 6 类建（补入 V4.2 的一手房），见 §2.6 |
| 4 | **角色类型 16 种** | `role_type` 按 16 种建 |
| 5 | **费用项 4 种**：居间代理费 196 / 居间服务费 87 / 中介费 33 / 贷款服务费 2 | 新增 `fee_item` 字段 |
| 6 | 业绩比例 **30 种取值** | 仅随原始行留存，不参与运算 |
| 7 | **无缺角色人**（318 行角色人系统号与姓名均非空） | 待对齐机制仅用于**员工匹配失败**（§4.5） |
| 8 | **实收可能大于应收**（35 行）；**应收=0 但实收>0**（34 行）；实收=0（52 行） | ★ 应收与实收是**两个独立指标**（§1.4） |
| 9 | 同一 合同+角色人+费用项+角色类型 才唯一（318 唯一） | `source_key` 必须含四要素（§3.1） |
| 10 | 三表金额完全勾稽（应收 206,274.04 / 实收 192,556.89，逐人差异 0.00） | 选最细的结算明细表作正源 |
| 11 | 店组（CD_15）与门店（CD_14）是两级，一门店下挂 A/B 组 | 归属以**门店**为口径，店组冗余备查 |
| 12 | 加盟商编码 ≠ mdmCode（花照天街 `CDYTA10037` vs `V2019008292`） | 两个编码都要存 |
| 13 | **★ 同一人可跨加盟商**（严文浩、李建华各挂 2 个加盟商），但**不跨门店** | 加盟商**不能**作归属维度；门店可靠 |
| 14 | **签约时间跨月**：269 行在 202608、39 行在 202607、10 行在 202606 | `period` 与 `business_date` 必须分离（§2.5） |

> ⚠ 金融分润、家装荐客、好赞、省心租等是**汇总表的业绩拆分维度**，**不是** `biz_type`。

#### 三处数据特征

|---|---|---|

### 1.3 职责边界

| ✅ 负责 | ❌ 严禁 |
|---|---|
| 消费 `NormalizedRecord` / 手工录入 → 业务语义校验 | 提成金额 / 提点 / 保底计算（→ **payroll**） |
| 业绩口径分离（实收 / 应收）+ 原样记录金额 | 工资、社保、公积金、个税（→ **payroll**） |
| 归属补齐（员工、门店） | 收支凭证、台账（→ **ledger**） |
| 产出 `PerformanceFact` + 事实生命周期（生效 / 冲销重建） | 维护员工主数据（→ **people**，只读快照） |
| 业绩调整单（审批 + 执行） | Excel 解析、raw 归档（→ **import**） |
| 期间封账 | 反向依赖 commission / payroll / ledger |

### 1.4 双口径（第一铁律）

| 口径 | fact_type | 贝壳字段 | 下游用途 |
|---|---|---|---|
| **结佣业绩（实收）** | `PERF_REAL` | `当月实收业绩` | 经纪人 / 店长个人 / 总监个人提成、招聘奖励基数 |
| **新签业绩（应收）** | `PERF_EXPECT` | `当月应收业绩` | 店长团队提成与保底、总监门店提成（跳点） |

**★ 二者是两个独立指标，不是"应收递减为实收"的转化关系。** 真实数据支撑：

| 现象 | 行数 | 说明 |
|---|---|---|
| 实收 > 应收 | 35 | 往月应收在本月补收，或本期实收高于当期应收 |
| 应收 = 0 但实收 > 0 | 34 | 往月产生的应收在本月实收，本月无新增应收 |
| 实收 = 0 | 52 | 已签约未实收 |

> **含义**：结佣不是"把应收改成实收"，而是"**确认本月实收业绩可以进入工资**"。两个口径各自独立统计、独立冲销、独立使用，**绝不合并**，也**不允许用一个去推导另一个**。

### 1.5 事实 vs 规则（与 payroll 的分界）

| 类别 | 内容 | 归属 |
|---|---|---|
| **事实** | 业绩金额（贝壳原样值）、归属门店/店组、结算月、业务类型、费用项、角色类型、签约时间 | **performance** |
| **规则** | 提点（A0~A5 / 店长 70%）、团队提点 10%、保底 7000/8000、总监跳点 6%/7%/8%、底薪、社保成本、公积金、考勤、积分、个税、**新签折算系数** | **payroll** |

**三条硬分界：**

1. **社保成本不进本域**：`团队新签计薪业绩 = 门店全员新签合计 − 社保成本 − 店长个人`，社保成本归 payroll 规则，本域只出**门店全员合计**与**按人明细**。
2. **保底 / 跳点 / 提点 / 提成金额不进本域**：只回答"业绩是多少"。
3. **员工兼职、职级不进本域**：由 people 的 `salary_fact` 提供。

### 1.6 与结佣域的接口

| 方向 | 契约 | 说明 |
|---|---|---|
| perf → comm | `PerformanceFactCreatedEvent`（`factIds` / `factType`） | 新事实生成通知 |
| perf → comm | `PerformanceFactReversedEvent`（`factIds` / `reason`） | 事实冲销通知 |
| perf → comm | `CommissionPerformanceQueryPort` | 结佣域只读查询事实（**禁直连 `pj_perf_*` 表**） |
| perf → comm | `PeriodCloseQueryPort` | 结佣域查询期间是否封账（`isClosed` = 该月**终态关闭**，定义见 §4.7） |

## 二、业绩口径与数据处理原则

### 2.1 核心原则：零加工，只做原样记录

> **贝壳给什么就记什么，一行不落；系统不引入"业绩比例"、"折算系数"这类加工参数。**

贝壳每一行**已经是某个角色人以某种角色身份、在某费用项下分到的业绩金额**——拆分在贝壳侧完成，系统不需要、也不应该再乘一次业绩比例。

**已验证：贝壳确实用业绩比例把金额拆好了**

合同 `100015972443` / 王聪 / 居间服务费：

| 角色类型 | 业绩比例 | 当月应收业绩 | 当月实收业绩 |
|---|---|---|---|
| 考核陪签 | 0.05 | 1,113.71 | 1,113.69 |
| 信息完备 | 0.03 | 668.22 | 668.21 |
| 房源录入人 | 0.10 | 2,227.42 | 2,227.40 |
| 房源委托书人 | 0.02 | 445.47 | 445.46 |
| 房源实勘预约人 | 0.02 | 445.47 | 445.46 |
| 房源维护人 | 0.05 | 1,113.71 | 1,113.69 |
| 房源推广 | 0.05 | 1,113.71 | 1,113.69 |

> **验证**：1,113.71 × 2 = 2,227.42（0.10 恰为 0.05 的两倍），各角色金额与业绩比例严格对应 —— **贝壳已按"业绩比例 × 角色类型"完成拆分**。
> ⚠ 应收与实收存在**分位级差异**（如 1113.71 vs 1113.69），这是贝壳的两个独立统计值，系统**原样各记各的，不做任何推导**。

**因此表内不存在这些字段：**

| 不存在的字段 | 原因 |
|---|---|
| `share_ratio`（业绩比例） | 金额已拆好，再乘即重复计算；原始值随 `raw_payload` 留存 |
| `conversion_rate`（折算系数） | 属 payroll 规则层（§2.2） |
| `origin_amount`（原值） | 无加工则与业绩金额同值，冗余 |
| `discount_rate`（折扣系数） | 85 折改为直接存折后金额 |

> **一句话**：本域存的是"**贝壳说这笔业绩是多少**"；至于"按什么比例算提成、要不要打折"——那是 payroll 拿到事实之后的事。

### 2.2 折算：真实业务，但属 payroll 规则层

| 口径 | 是否折算 | 系数 |
|---|---|---|
| 结佣业绩（实收）`PERF_REAL` | ❌ 不折算 | — |
| 新签业绩（应收）`PERF_EXPECT` | ✅ 折算 | 一手房 `0.94 × 0.96 = 0.9024`；其他业务 `0.96` |

依据 V4.2：§7.1 明确结佣金额"系统直接采用贝壳提供的结佣金额"；§5.2 明确新签业绩需折算为计薪业绩。二者针对不同口径，不冲突——**钱已实收时无需再折，应收尚未到账需扣增值税与运营费用**。

**折算在 payroll 规则层完成：**

- 本域原样记录贝壳金额，不折算、不存系数；
- payroll 取到业绩金额后按 `biz_type` 应用折算系数得到"计薪业绩"，再叠加提点 / 保底等规则算工资；
- 折算系数属**客户级规则**（与团队提点 10%、保底、总监跳点同类），归 payroll 配置。

> **为什么不在业绩域折**：一旦把系数固化进 Fact 行，客户调整系数时历史数据就被"钉死"；放在 payroll 规则层，规则变更只影响新算的工资，历史工资本来已锁定。

### 2.3 金额精度红线

| 规则 | 说明 |
|---|---|
| 存储 | 金额统一 `NUMERIC(18,2)`；**表内不存任何系数 / 比例字段** |
| Java | 统一 `BigDecimal`，**禁用 `double` / `float`**（CI 检查） |
| 取整 | 本域不做金额加工，无取整逻辑；`setScale` 只出现在 payroll |
| 汇总 | `SUM()` 直接对记录值求和（与人工 Excel 口径一致） |
| 分位差异 | 应收与实收的分位差（如 1113.71 / 1113.69）属贝壳原值，**原样保留，不做对齐** |

### 2.4 归属门店：取数时冻结 + 纠偏通道

**背景约束**：员工域 `fact_type` 8 类（`LEVEL / STATUS / SOCIAL / HOUSING / COMMERCIAL / DORMITORY / PARTTIME / MENTOR`）中**不含 `DEPT`**，`dept_id` 仅存在于 `pj_people_employee` 当前态 —— **部门不是时序数据，无法取历史时点值**。

处理方式：

1. `dept_id` = **消费取数时**员工所属门店，落地即冻结在 Fact 行上（结佣明细继承）；
   ★ **两级组织**：以**门店**（`CD_14_*`）为归属与汇总口径；**店组**（`CD_15_*`）编码 / 名称冗余落行备查，不参与汇总、不参与鉴权。
   ★ **加盟商不能作归属维度**：已验证同一人可跨加盟商（严文浩、李建华各挂 `C26030136497` 与 `CDYTA10037`），而**同一人不跨门店**（0 人跨门店）。故加盟商三列仅冗余落行。
2. 月中调店造成归属偏差 → 用 **`TRANSFER` 调整单**纠偏；若结佣已锁定，走结佣 `DIFF` 差额调整单。
3. 可选增强见 CR-4（请 people 域为 `fact_type` 增加 `DEPT` 使部门可时序化）。

> 薪资相关事实（职级 / 社保 / 公积金等）**是**时序的（`salary_fact` 闭开区间），payroll 算薪取历史值不受影响；本问题**仅影响业绩归属门店**。

### 2.5 结算月 `period` 与业务发生日 `business_date`

两组日期语义不同，**不可混用**：

| 字段 | 贝壳来源 | 本域字段 | 取值 | 用途 |
|---|---|---|---|---|
| 结算月 | `结算月`（`202608`） | **`period`** | YYYY-MM | 业绩归属月、封账维度、结佣分组维度 |
| 签约时间 | `签约(成销)时间`（`2026-08-05 18:09:33`） | **`business_date`** | 日期部分 | 取员工时点快照 |

> **业绩归属月 = 结算月**（贝壳口径，与结佣和算薪周期一致）；**快照取数日 = 签约日**（反映成交发生时该员工的归属与状态）。

**已验证必须分离** —— 本样本 318 行的签约月分布：

| 签约月 | 行数 |
|---|---|
| 202608（与结算月同月） | 269 |
| 202607 | 39 |
| 202606 | 10 |

> 49 行（15%）签约月早于结算月。若用结算月取快照，这部分业绩会取到错误的时点状态。

**`business_date` 取值优先级：**

| 优先级 | 条件 | 取值 |
|---|---|---|
| ① | 有 `签约(成销)时间`（CR-2 落地后） | 该日期 |
| ② | 仅有 `过户日期` / `完结日期`（少量二手单有） | 该日期 |
| ③ | 以上皆无（兜底） | `LAST_DAY(period)` |

> 本样本 `签约(成销)时间` 覆盖全部 318 行，故 ① 即可满足，③ 仅为兜底。

### 3.1 聚合根：`PerformanceFact`

**关键不变量：**

- **只有金额、没有系数**：表内不含任何 rate / ratio 字段（§2.1）；
- **`raw_payload` 永不裁剪、永不修改**；
- **禁止 UPDATE `amount`** —— 修正一律"旧事实 expire + 新事实生成"；
- 部分唯一索引 `uk_perf_fact_record(normalized_record_id, fact_type)` → **重复消费不翻倍**；
- 旧事实 `REVERSED` 后**永久保留**，审计可看完整时间线；
- **禁止出现提成 / 工资金额字段**（CI 扫描）。

#### 业务主键 `source_key` 规则

已验证：**合同号 + 角色人系统号**（157）与**再加费用项**（159）**都不唯一**，必须四要素齐备才唯一（318）：

```
source_key = contract_no + "|" + 角色人系统号 + "|" + fee_item + "|" + role_type + "|" + fact_type
```

| 组合 | 唯一数（318 行） | 是否可用 |
|---|---|---|
| 合同号 + 角色人 | 157 | ✗ 重复 |
| + 费用项 | 159 | ✗ 重复 |
| **+ 角色类型** | **318** | **✓ 唯一** |
| + fact_type（2 条事实/行） | 636 | ✓ 唯一 |

> **为什么必须拼费用项与角色类型**：同一合同同一角色人会以**不同角色身份、在不同费用项下**各贡献一笔业绩（如王聪在合同 `100015972443` 下有 7 行），缺任一要素都会**漏建或误合并事实**。
>
> **为什么拼 fact_type**：同一原始行生成应收、实收两条事实，需可区分。
>
> **缺角色人时**（本样本无，但需防御）：无法生成有效 `source_key` → 该行进「待对齐」列表（§4.5）。

### 3.2 事实状态机（两态）

```
（生成）──▶ ACTIVE ──▶ REVERSED（终态）
```

`REVERSED` 为终态，**不可回到 ACTIVE** —— 需要恢复则生成新事实。

### 3.3 实体：`PerformanceAdjust`（调整单，审批载体）

依据 V4.2 权限表"各角色可发起业绩调整申请"，审批走 Warm-Flow。

| 字段 | 说明 |
|---|---|
| `adjust_no` | `PADJ + yyyyMMdd + 序列` |
| `fact_id` / `period` / `employee_id` / `dept_id` | 变更对象（冗余便于检索与鉴权） |
| `adjust_type` | `AMOUNT`（改金额）/ `VOID`（整笔作废）/ `TRANSFER`（门店纠偏） |
| `payload_json` | 变更前后值快照 |
| `new_amount` / `target_dept_id` | `AMOUNT` 用（调整后的最终金额，非增量）/ `TRANSFER` 用 |
| `reason` | 必填，审计 |
| `status` | `SUBMITTED → APPROVED → EXECUTED`（终态）／`REJECTED`／`CANCELLED` |
| `process_instance_id` / `applicant_id` / `approver_id` | Warm-Flow / 发起人 / 审批人 |

**EXECUTED 同事务动作：**

| 类型 | 动作 |
|---|---|
| `AMOUNT` | 旧事实 expire + 新事实（`amount` = 调整后金额；**`raw_payload` 继承原行**，`payload_json` 记变更前后） |
| `VOID` | 旧事实 expire（`reversed_reason = PERIOD_VOID`） |
| `TRANSFER` | 旧事实 expire + 新事实（`dept_id` = 目标门店，金额与 `raw_payload` 不变） |

> **调整永不丢原始**：新事实必须继承原事实的 `raw_payload`；调整内容另记在 `payload_json`。

**前置校验：** ① `period` 未封账；② 原事实为 `ACTIVE`；③ 同一 `fact_id` 无未完成调整单；④ 幂等（重复回调先查状态）。

### 3.4 `PerformanceConsumeLog`（消费日志）

一表三用：**幂等锚点、行数对账、失败留痕**。

| 字段 | 说明 |
|---|---|
| `batch_id` + `event_type` | **联合唯一** → 幂等（`ARCHIVED` / `RENORMALIZED`） |
| `event_id` | 事件全局唯一 ID（CR-3），兜底幂等 |
| `period` / `source_type` | 检索与展示 |
| `status` | `RUNNING` / `SUCCESS` / `PARTIAL` / `FAILED` |
| `total_rows` / `normal_rows` / `abnormal_rows` | NR 条数 / 生成事实条数 / 跳过行数 → **差异即告警**（§6.5） |
| `pending_align_json` | **待对齐行明细**（角色人系统号 / 姓名 / 金额 / 原始行号 / `raw_payload`），见 §4.5 |
| `message` | 失败原因 |

> **行数口径**：`total_rows` 为 NormalizedRecord 行数；`normal_rows` 为**生成的事实条数（= 行数 × 2）**。对账时按 `normal_rows ÷ 2` 与 `total_rows` 比对。

### 3.5 `PerformancePeriodClose`（期间封账）

| 字段 | 说明 |
|---|---|
| `period` | UK（结算月） |
| `status` | `OPEN` / `CLOSED` |
| `close_reason` | `MANUAL` / `PAYROLL_LOCKED` |
| `ref_batch_id` / `operator_id` / `close_time` | 溯源 |

**★ 封账语义（唯一，不得二义）：`CLOSED` = 该结算月终态关闭，不是"数据定稿可以结佣了"。**

| 状态 | 含义 | 禁止清单 |
|---|---|---|
| `OPEN` | 数据未定稿，仍可导入 / 补录 / 冲销 | — |
| `CLOSED` | 该结算月**终态关闭**（通常已由 `PayrollLockedEvent` 自动触发） | ① 重新消费批次；② 业绩调整单 `EXECUTED`；③ 手工录入作废；④ 业绩域人工调整；⑤ **结佣域发起结佣**；⑥ **结佣域增量重拉**；⑦ **结佣调整单 `EXECUTED`** |

> ⑤~⑦ 由结佣域经 `PeriodCloseQueryPort.isClosed(period)` 自行判定（§4.7），本域不感知结佣。
> 解封需总监二次确认 + `AuditPort` 留痕；解封后 `isClosed` 实时返回新状态，**消费域每次实时查，禁止缓存**。

> ⚠ **由此推出的结佣时间窗**：结佣必须在 `CLOSED` **之前**完成（导入 → 发起结佣 → 审批锁定 → payroll 锁定 → 自动封账）。某月已 `CLOSED` 仍有实收未结时，只能以 `DIFF` 补发到未封账月份，或解封后重走 —— 详见结佣域 §2.5。

## 四、核心流程

### 4.1 消费主流程（幂等、可重跑）

```
① 消费 ImportBatchArchivedEvent(batchId, sourceType, supersededBatchIds, eventId)
     ├─ sourceType == EMPLOYEE              → 忽略（防御性过滤，对齐导入域）
     └─ sourceType ∈ ATTENDANCE/POINTS/OTHERS → 忽略（非业绩类，归 payroll 扣款项）
② 幂等：consume_log(batchId, eventType) 已 SUCCESS → 跳过
③ 期间校验：period 已 CLOSED → 拒绝 + 告警
④ 【冲销旧批次】supersededBatchIds 非空 → 其全部事实 expire（§4.2）
⑤ 拉 NormalizedRecord（ImportNormalizedRecordQueryPort，只读，分页 500）
⑥ 逐行：业务校验 → 员工/门店归属 → 生成 2 条事实
       PERF_EXPECT ← 当月应收业绩
       PERF_REAL   ← 当月实收业绩
       （金额原样取，不做任何加工）
⑦ 写 consume_log（total / normal / abnormal）→ 差异告警
⑧ 发布 PerformanceFactCreatedEvent（只传 factId 列表）
```

> **落地细节见附录 A** —— 含链路总览、`NormalizedRecord` 结构、**30 列字段映射表**、代码骨架与三个常见坑。

**幂等实现：** 重跑 = 先按 `batch_id` 删除派生行（`source = IMPORT`），再重建。**绝不删 `source = MANUAL` 的行**（人工成果）。`normalized_record_id` 唯一索引做 DB 兜底。

### 4.2 supersede（批次替换）

```
ImportBatchArchivedEvent.supersededBatchIds = [旧批次...]
   ↓ 同一事务，串行
① 旧批次全部 Fact → REVERSED（reversed_reason = SUPERSEDE）
② 基于新批次重建
③ 发布 reversed（旧 id）+ created（新 id）事件
```

默认 **全量替换** —— 旧批次被 supersede 即其全部事实作废。增量模式留参数 `panjia.perf.supersede-mode=INCREMENTAL`。

> **唯一触发源是事件**，禁止轮询 import 库。

### 4.3 重归一化（reNormalize）

独立事件 `ImportBatchRenormalizedEvent`（CR-5）→ 冲销本批次全部事实（`reversed_reason = RENORMALIZE`）→ 重建。与 supersede 复用同一冲销闭环，仅 `reversed_reason` 不同（审计可区分）。

### 4.4 手工录入业绩

| 环节 | 规则 |
|---|---|
| 来源 | `source = MANUAL`，`batch_id = null`，`normalized_record_id = null`；`raw_payload` 存录入内容快照，`import_file_name = null` |
| 流水线 | **必须复用** §4.1 ⑥ 同一套（校验 → 归属 → 原样记录金额 → Fact） |
| 单号 | 无外部单号时 `source_key = "MANUAL-" + UUID` |
| 作废 | **禁止物理删除** → 走调整单 `VOID` 或直接冲销（`reversed_reason = PERIOD_VOID`） |
| supersede | **不参与**（仅针对 `source = IMPORT`） |

### 4.5 业务语义校验

区别于 import 域的**格式/类型校验**，业绩域做**业务语义校验**：

| 校验 | 处置 |
|---|---|
| `source_key` 批次内重复 | 整批拒绝 |
| 业务日期非法（空 / 早于上线日） | 整批拒绝 |
| `biz_type` 不在六类枚举内 | 整批拒绝 |
| `role_type` 不在 16 种枚举内 | 整批拒绝 |
| `fee_item` 不在四类枚举内 | 整批拒绝 |
| 金额为负或空 | 整批拒绝 |
| ★ **员工匹配失败**（工号在系统内找不到） | **进「待对齐」列表** |
| ★ 快照缺 `dept_id` | **进「待对齐」列表** |

**默认策略：整批原子** —— 任一失败则本批次不生成任何 Fact，原因写 `consume_log.message`，人工修正后重跑。

> 理由：财务系统最危险的是"看似导入成功、实则少业绩"，部分成功会让对账差异延迟暴露。
> 开关 `panjia.perf.partial-accept-enabled = false`，置 true 时切"合法单据生成、非法跳过"。

#### ★「待对齐」机制（V4.2 §13.1 硬性验收项）

> V4.2 §13.1：*"导入时按工号匹配员工档案；匹配失败人员进入「待对齐」列表，可手动指定对应员工"*

分两步执行：

```
① 消费时：按角色人系统号（工号）匹配员工
     ├─ 匹配成功          → 正常生成 Fact
     └─ 匹配失败          → 该行不生成 Fact，落入「待对齐」列表（pending_align_json）
② 人工在「待对齐」页面：
     ├─ 指定已有员工      → 该行重新入流水线，生成 Fact
     └─ 确认为新员工/无效 → 标记忽略，记 consume_log.abnormal_rows
```

| 设计点 | 说明 |
|---|---|
| **本样本无缺角色人** | 318 行角色人系统号与姓名均非空，故待对齐主要因**员工匹配失败**触发 |
| 落库位置 | `consume_log.abnormal_rows` 计数 + `pending_align_json` 存明细 |
| 不建独立表 | 与"不建 issue 表"决策一致（ADR A8） |
| 待对齐期间 | 批次状态 `PARTIAL`，**不阻断**其他正常行入库 |
| 人工指定后 | 走同一流水线，事实 `source = IMPORT`，仍带原 `batch_id` 与 `raw_payload` |

> **为什么不能整批拒绝**：员工匹配失败多因新入职/离职，整批拒绝会导致"一个人没建档 → 全店业绩停摆"。

## 六、事务、并发、幂等、重算

### 6.1 事务边界

| 场景 | 策略 |
|---|---|
| 批次消费 | 分页 500 拉取、批量 INSERT 300；`MAX_ROWS_PER_BATCH = 5000`；**单批次一个事务** |
| supersede 冲销 + 重建 | **同一事务**：先冲销旧事实再建新事实，杜绝"旧已过期、新未生成"中间态 |
| 业绩调整单 `EXECUTED` | 单事务：冲销 + 新建 + 状态变更 |

> 进程内 Port 调用失败直接抛异常 → `consume_log = FAILED` → 重跑（幂等）。**不引入 MQ / 死信队列**（模块化单体，Spring 事件 + Outbox 已足够）。

### 6.2 并发控制

| 风险 | 防护 |
|---|---|
| 同一 `eventId` / 批次重复消费 | `uk_pcl_batch_event` + `uk_pcl_event_id` |
| 重复导入同一归一化记录 | `uk_perf_fact_record(normalized_record_id, fact_type)` |
| 同一事实并发调整 | Fact `version` 乐观锁；冲突重试 3 次后告警 |

### 6.3 幂等锚点

| 入口 | 锚点 |
|---|---|
| `ImportBatchArchivedEvent` | `uk_pcl_batch_event(batch_id, event_type)` |
| `ImportBatchRenormalizedEvent` | 同上 |
| 批次重跑 | 先删 `batch_id` 派生行（`source = IMPORT`）再重建，**绝不删 MANUAL** |
| 业绩调整单回调 | 调整单 `status` + `version` |

### 6.4 四类重算（隔离定义，不提供"一键重算"）

| # | 场景 | 触发源 | 范围 | 是否改写历史事实 | 默认策略 |
|---|---|---|---|---|---|
| 1 | supersede / reNormalize | import 事件 | 本 `batchId` | ✅ 冲销 + 重建 | 自动执行 |
| 2 | 手工修改 / 作废单据 | 页面 + 审批 | 单条 Fact | ✅ 冲销 + 重建 | 需审批；**已封账期间禁止** |
| 3 | 折算配置变更 | 实施改配置 | — | ❌ **不回溯** | 折算在 payroll 规则层，本域无系数，**天然不受影响** |
| 4 | 员工主数据回溯修复 | people 域变更 | — | ❌ **不重算** | 事实冻结取数时结果；确需重算走**人工审批专项任务** |

### 6.5 对账（消费时比对，不建表不跑批）

`consume_log` 中 `total_rows`（NR 行数）与 `normal_rows ÷ 2` 不一致 → **立即写 `FAILED` / `PARTIAL` + 告警**。不建离线对账任务、不自动修复。

> **额外校验**：批次内 `∑ amount` 与贝壳 Excel 页脚合计比对，可捕获"少导行"这类最危险的问题（开关：`panjia.perf.footer-check-enabled`，默认 true）。
> 本样本基准值：`PERF_EXPECT` 合计 **206,274.04**、`PERF_REAL` 合计 **192,556.89**。

### 7.1 事件

## 十一、架构决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| **A1** | 单层 Fact 模型，**不引入 Bill / SplitItem** | 贝壳已按"角色 × 合同 × 费用项"拆行；系统再拆分属重复 |
| **A2** | **零加工**：只原样记录金额，不存 `share_ratio` / `conversion_rate`，只有一个 `amount` | 已验证贝壳用"业绩比例 × 角色类型"完成拆分（1113.71 × 2 = 2227.42），自算必错 |
| **A3** | 事实**闭开区间不可原地修改**，修正 = 旧事实 expire + 新事实 | 财务审计刚需；与员工域 `salary_fact` 同构 |
| **A4** | 双口径独立：**一行原始记录生成 2 条事实** | 真实数据显示实收可大于应收（35 行）、应收=0 但实收>0（34 行），二者是独立指标，合并会丢失信息、无法独立冲销 |
| **A5** | **业绩事实正源 = 经纪人业绩结算明细表**，另两张表全部归档 | 三表金额完全勾稽（应收 206,274.04 / 实收 192,556.89，逐人差异 0.00）；结算表粒度最细且**唯一含费用项、角色类型、业绩比例、到账金额、支付手续费** |
| **A6** | `period` = **结算月**，`business_date` = 签约日，两者分离 | 已验证 49 行（15%）签约月早于结算月；前者是归属与结佣口径，后者是快照取数口径 |
| **A7** | 归属用**门店**；店组与加盟商仅冗余 | 已验证**同一人不跨门店**（0 人）但**可跨加盟商**（2 人），加盟商不能作归属维度 |
| **A8** | **不建 issue 表 / change_log 表 / 对账表**，合并进 `consume_log` + Fact 行字段 + `AuditPort` | 闭开区间本身即审计轨迹；消费时即可比对行数 |
| **A9** | 四类重算隔离；场景 3 / 4 **默认不回溯** | 防"一键重算"误改历史，合规优先 |
| **A10** | supersede 全链路：事件携 `supersededBatchIds`，**禁止轮询 import 库** | 防新旧业绩并存导致提成重复计算 |
| **A11** | 归属部门 = **取数时冻结**，`TRANSFER` 调整单纠偏 | 部门非时序（`fact_type` 无 `DEPT`），无法取历史时点值 |
| **A12** | `CommissionPerformanceQueryPort` 为唯一出口；commission 禁直连 `pj_perf_*` | 防两套业绩逻辑、防审计数据污染结算 |
| **A13** | 门店汇总返回**全员合计（含店长）**，社保成本 / 店长个人扣减归 payroll | 保持"业绩域不做薪酬语义" |
| **A14** | 不做分表 / 归档 / 物化视图 / MQ 死信 | 数据量不支撑；模块化单体，Spring 事件 + Outbox 已足 |
| **A15** | **Fact 落 `raw_payload` jsonb 存原始行全 30 列**，永不裁剪、永不修改 | 追溯底线；贝壳改版新增列时自动承接，无需改表结构 |
| **A16** | 落 `import_file_name` / `sheet_name` / `row_no` 溯源元数据 | 能定位到"这条业绩来自哪个文件的第几行" |
| **A17** | `biz_type` 六类（含一手房与写字楼租赁） | 本样本 5 种；一手房因 V4.2 §5.2 折算规则不同必须保留，写字楼租赁为本样本实际出现 |
| **A18** | `source_key = 合同号 + 角色人 + 费用项 + 角色类型 + fact_type` | 已验证三者组合均不唯一（157 / 159），四要素才唯一（318）；加 `fact_type` 区分双口径 |
| **A19** | `uk_perf_fact_record` **必须包含 `fact_type`** | 同一 NR 生成两条事实，不含则第二条插入即撞键失败 |
| **A20** | 加盟商编码与 mdmCode 都存，且不作归属 | 真实数据显示两者可不同；且同一人可跨加盟商 |
| **A21** | 新增 `fee_item`（费用项）字段 | 结算明细表独有列；同一合同同一角色人可跨费用项贡献业绩，缺此字段会漏建或误合并 |
| **A22** | `NormalizedRecord` **必须 `payload_json` 全列透传**，禁止只映射业务字段 | 归一化环节丢字段则全链路追溯不可恢复；字段映射表固化在附录 A.3 |
| **A23** | **封账语义唯一：`CLOSED` = 该结算月终态关闭**，`isClosed` 经 `PeriodCloseQueryPort` 暴露给 commission | 消除"数据定稿可结佣"与"终态关闭禁止写入"的二义；两域共用一个 `pj_perf_period_close`，避免两套封账状态 |
| **A24** | 查询 Port **原样返回 `amount = 0` 的事实**，由消费域决定是否过滤 | 0 值行是有效事实（已签约未实收），业绩域不做业务性裁剪；结佣域按自身 ADR B14 过滤 |

## 附录 A：数据落地全链路（import → performance）

> 本附录回答"**数据是怎么从导入域落到业绩域的**"，是 T4 / T5 的直接编码依据。

### A.1 链路总览：谁在什么时机做什么

```
① 用户上传贝壳 Excel（4 个 Sheet）
        ↓
【panjia-import】
② 多 Sheet 识别 → 跳过「导出说明」                       （CR-10）
③ 双层表头解析 → 第 1 行分组名 + 第 2 行真实列名          （CR-12）
④ 逐行归一化 → 一条原始行 = 一条 NormalizedRecord
⑤ 落 pj_normalized_record（权威源，永久保留，含 payload_json 全列）
⑥ 归档 → 发布 ImportBatchArchivedEvent
        { batchId, sourceType, period, supersededBatchIds, eventId }
        ↓
【panjia-performance】消费事件
⑦  幂等检查（uk_pcl_batch_event）
⑧  期间封账检查
⑨  冲销旧批次（supersededBatchIds 非空时）
⑩  分页拉 NormalizedRecord（每批 500）
⑪  逐行：业务语义校验 → 员工/门店归属 → 生成 2 条 PerformanceFact
⑫  写 consume_log（行数对账）
⑬  发布 PerformanceFactCreatedEvent
```

**职责分界：**

| import 域 | performance 域 |
|---|---|
| 知道 Excel、Sheet、表头、行数 | **不碰 Excel**，只认 `NormalizedRecord` |
| 做**格式 / 类型校验** | 做**业务语义校验** |
| 不知道什么是"应收 / 实收" | 知道业绩口径、归属、冲销 |

### A.2 `NormalizedRecord` 必须长什么样

> **★ 关键约束：import 域必须整行透传，禁止只映射"业务需要的字段"**（CR-9）。
> 归一化环节丢掉的字段，业绩域再怎么留存也补不回来 —— 这是追溯链路上最脆弱的一环。

```
pj_normalized_record
├── batch_id        ← 批次
├── row_no          ← Excel 物理行号
├── sheet_name      ← 来自哪个 Sheet
├── source_type     ← 区分三张数据表
├── period          ← 结算月（从「结算月」列提取）
├── employee_code   ← 角色人系统号（用于匹配员工）
├── bill_no         ← 合同号（source_key 要素）
├── bill_date       ← 签约(成销)时间（CR-2，快照取数用）
├── status          ← NORMAL / ABNORMAL
└── payload_json    ← ★ 原始行全 30 列，一个不落
```

### A.5 落地代码骨架（`PerformanceEngine.build`）

```java
@Transactional
public void build(Long batchId, String eventId, List<Long> supersededBatchIds) {
    // ① 幂等（uk_pcl_batch_event）
    if (!consumeLog.tryLock(batchId, "ARCHIVED")) return;

    // ② 期间封账校验
    if (periodClose.isClosed(period)) throw new PeriodClosedException(period);

    // ③ 冲销旧批次（与重建同一事务）
    reverseService.reverseByBatches(supersededBatchIds, SUPERSEDE);

    // ④ 分页拉取 + 逐行处理
    int total = 0, normal = 0, abnormal = 0;
    for (List<NormalizedRecordDTO> page : importPort.page(batchId, 500)) {
        for (NormalizedRecordDTO nr : page) {
            total++;
            try {
                validate(nr);                                   // 业务语义校验
                EmployeeSnapshot emp = peoplePort.snapshotAt(     // 按签约日取快照
                        nr.getEmployeeCode(), nr.getBillDate());
                save(factOf(nr, emp, PERF_EXPECT, amt(nr, "当月应收业绩")));
                save(factOf(nr, emp, PERF_REAL,   amt(nr, "当月实收业绩")));
                normal += 2;
            } catch (AlignPendingException e) {
                abnormal++;      // 进待对齐，不阻断其他行（§4.5）
            }
        }
    }
    // ⑤ 行数对账：normal ÷ 2 应等于 total - abnormal
    consumeLog.finish(batchId, total, normal, abnormal);
}
```
