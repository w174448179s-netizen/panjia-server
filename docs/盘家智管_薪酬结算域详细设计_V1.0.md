## 一、定位与职责边界

### 1.1 一句话目标

> **把「已锁定的结佣事实 + 新签事实 + 员工事实 + 考勤积分发生量」按薪酬规则算成工资，全程快照锁定，锁定后不可改、只可追加调整。**

本域是整条业务链的**唯一算钱出口**：上游（performance / commission / people / import）只产事实，规则与计算全部在此闭环。

### 1.2 算薪输入全景（五类输入）

```
┌──────────────────────────────────────────────────────────────────┐
│                       panjia-payroll（本域）                       │
│                                                                   │
│  ① 结佣事实（已锁定）  ← CommissionQueryPort.findLocked           │
│     PERF_REAL，按 **period（业绩归属月 = 批次月）** 取            │
│                                                                   │
│  ② 新签事实（透传）    ← CommissionQueryPort.findNewSignByDept    │
│     PERF_EXPECT，按 period 取                                     │
│                                                                   │
│  ③ 员工事实（快照）    ← EmployeeSnapshotQueryPort                │
│     职级 / 兼职 / 社保开关 / 参保标签 / 师徒                       │
│                                                                   │
│  ④ 考勤积分发生量      ← PayrollImportQueryPort（只读）            │
│     迟到次数 / 旷工天数 / 请假金额 / 每日积分 / 处罚次数           │
│                                                                   │
│  ⑤ 薪酬规则（本域自管） ← 三类规则表 → RuleSnapshot 冻结           │
│     职级规则 / 客户政策规则 / 业绩折算规则                          │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
              SalaryCalculationEngine（纯计算）
                              │
                              ▼
              CalculationResult → PayrollBatch / PayrollDetail
                              │
                              ▼
                    PayrollLockedEvent → ledger
```

| 输入 | 来源域 | Port | 是否本域加工 |
|---|---|---|:---:|
| 结佣金额 | commission | `CommissionQueryPort.findLocked` | ❌ 原样取用（不折算） |
| 新签金额 | commission（透传 performance） | `CommissionQueryPort.findNewSignByDept` | ✅ **按 `biz_type` 折算** |
| 职级/兼职/社保开关 | people | `EmployeeSnapshotQueryPort` | ❌ 事实 |
| 考勤/积分发生量 | import | `PayrollImportQueryPort` | ✅ 按规则算扣款与绩效等级 |
| 提点/社保/公积金/个税/折算 | **本域** | 三类规则表 | — |

### 1.3 职责边界

| 本域**负责** | 本域**不负责** |
|---|---|
| 算薪引擎（纯计算、可复现） | 业绩事实的生成与冲销（performance） |
| 工资批次状态机 + 乐观锁 | 结佣申请与审批（commission） |
| **全部薪酬规则配置**（职级/政策/折算三类） | 员工主数据与快照生成（people） |
| 规则快照 `RuleSnapshot` 冻结 | 考勤/积分原始采集（外部系统 + 人事 Excel） |
| 业绩折算（按 `biz_type`） | 部门收支台账与利润（ledger） |
| 递延发放台账、负工资结转、调整/补发 | 个税申报（只算金额） |
| 个税累计预扣计算 | 钉钉 / 税务系统对接 |
| 发布 `PayrollLockedEvent` | 工资实付（银行代发） |

### 1.4 规则归本域（架构 §2.3.1 / ADR-023）

```
规则 = 数据（客户可配，零代码）    → 三类规则表
计算器 = 代码（SPI 插件）          → CommissionCalculator / DeductionCalculator
```

| 规则类 | 表 | 内容 | 生效维度 |
|---|---|---|---|
| ① 职级/提成 | `pj_payroll_rank_rule` | 底薪、基础提点、跳点 brackets、保底、团队提点、个人提点 70%、招聘奖励模式 | 职级 × 生效区间 |
| ② 客户政策 | `pj_payroll_policy_rule` | 社保基数/比例、公积金、个税参数、商保/宿舍金额、兼职豁免、考勤单价、积分规则、A/B/C 扣点 | 全局 → 标签 → 工号 |
| ③ 业绩折算 | `pj_payroll_conversion_rule` | 按 `biz_type` 的折算系数 | 业务类型 × 生效区间 |
| ④ 规则快照 | `pj_payroll_rule_snapshot` | 三类规则在批次锁定时的合并冻结 | 批次 |

> **红线**：算法不进 JSONB。复杂算法走 Level 3 计算器 SPI，保证规则表不退化成脚本（ADR-016）。

### 1.5 双口径取数（★ 第一铁律）

V4.3 §9.1 / §10.2：不同角色的提成基数来自**不同口径**，取数月份也不同。

| 用途 | 口径 | 事实类型 | 取数月份 | 是否折算 |
|---|---|---|---|:---:|
| 经纪人业绩提成 | 结佣业绩 | `PERF_REAL` | **业绩归属月 `period`** | ❌ 不折 |
| 店长个人结佣提成 | 结佣业绩 | `PERF_REAL` | `period` | ❌ 不折 |
| 总监个人成交提成 | 结佣业绩 | `PERF_REAL` | `period` | ❌ 不折 |
| 店长团队提成 | 新签业绩 | `PERF_EXPECT` | **业绩归属月 `period`** | ✅ 折 |
| 店长保底判断 | 新签业绩 | `PERF_EXPECT` | `period` | ✅ 折 |
| 店长个人新签提成（递延） | 新签业绩 | `PERF_EXPECT` | `period` | ✅ 折 |
| 总监门店提成 | 新签业绩 | `PERF_EXPECT` | `period` | ✅ 折 |
| 招聘奖励（店长/总监） | 结佣业绩 | `PERF_REAL` | `period` | ❌ 不折 |

> **★ 结佣按 `period`（业绩归属月）取，不是 `approved_month`**。
>
> 实际作业节奏是「**N 月业绩 → N+1 月核对、结佣、算 N 月工资并发放**」：8 月业绩在 **9 月**核对与审批，但算的是 **8 月工资批次**（`PayrollBatch.period = 202608`），9 月只是**发放月**。
>
> 因此结佣取数必须按 `period = 202608` 与批次对齐。若按 `approved_month = 202609` 取，这批结佣会掉进 9 月批次——而 8 月工资已按"未含这批结佣"算完并发放，导致**漏发**。
>
> **两个口径统一为 `period`**：结佣与新签都按业绩归属月取，批次 `period` 与之对齐，链路自洽。
>
> `approved_month` 仅作**审计字段**记录审批发生在哪个月（9 月），**不参与取数**。

### 1.6 与上下游的接口

```
panjia-performance ──(PeriodCloseQueryPort)──▶ panjia-payroll   【封账状态只读】
panjia-commission  ──(CommissionQueryPort)──▶ panjia-payroll    【结佣+新签事实】
panjia-people      ──(EmployeeSnapshotQueryPort)─▶ panjia-payroll【员工事实】
panjia-import      ──(PayrollImportQueryPort)──▶ panjia-payroll 【考勤积分发生量】
panjia-payroll     ──(PayrollQueryPort)──▶ ledger / 报表        【工资结果只读】
panjia-payroll     ──(PayrollLockedEvent)─▶ ledger              【Outbox 事件】
```

## 二、算薪口径与数据处理原则

### 2.1 核心原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **规则快照锁定** | 算薪时冻结当时整套规则；后续调规则/员工升职，不影响已算月份（V4.2 §10.1） |
| 2 | **纯计算、无副作用** | `SalaryCalculationEngine` 不写库；输入不可变 → 输出不可变 |
| 3 | **不可变结果** | 重算 = 新建 `CalculationResult`，不改原结果；调整/补发走新增单据 |
| 4 | **事实零加工取用** | 结佣金额原样取用；**只在 payroll 折一次**，上游不得折算 |
| 5 | **金额精度** | 全程 `BigDecimal`，禁 `double`/`float`；统一走 `MoneyUtil` |
| 6 | **锁定即终态** | `LOCKED` 后禁止改明细，只能追加调整/补发（V4.2 §10.4） |

### 2.2 工资归属月与批次

| 概念 | 定义 | 示例 |
|---|---|---|
| 批次 `period` | **工资归属月 = 业绩归属月**（这笔钱是"哪个月的业绩挣来的"） | `2026-08` |
| 发放月 | 批次核算与发放发生在 **N+1 月**，但**不改变批次 `period`** | 2026-09 发放 |
| 结佣取数月 | **`period` = 批次 period** | 取 8 月归属的结佣业绩 |
| 新签取数月 | **`period` = 批次 period** | 取 8 月归属的新签业绩 |
| 封账触发 | 锁定后发布 `PayrollLockedEvent(period)` → 业绩域封 **`period`** | 8 月工资锁定 → 封 **2026-08** ✅ |

> **★ 批次 `period` ≠ 发放月**。8 月工资在 9 月发放，但批次仍记 `2026-08`；锁定该批次即封 `2026-08` 的业绩——恰好封住"钱已发完"的那个月，语义自洽。
> 若把批次记成发放月 `2026-09`，则封的是 9 月，而 9 月业绩要 10 月才结佣，会被提前封死（**这是错的**）。

**时序约束（★ 易踩坑）**：

```
8 月业绩（period=2026-08）
   │
   └──▶ 9 月：核对 → 结佣审批（approved_month=2026-09，仅审计）
                → 算【8 月工资批次】(period=2026-08) → 发放
                → 锁定 → 封【2026-08】业绩
```

**时序自洽**：8 月业绩的核对与结佣全部在 9 月完成，9 月底锁定 8 月批次并封 `2026-08`。10 月再算 9 月工资，此时 `2026-09` 仍开放，9 月业绩可正常结佣。**不存在"钱已发、还要回头改该月业绩"的情形**——核对窗口在发薪之前。

因此 **8 月工资批次必须在"8 月归属业绩的结佣全部审批完成"之后才能锁定**。操作上：

- 算薪前提供「**未结佣提示**」：列出该 `period` 下仍为 `DRAFT`/`PENDING_VERIFY`/`SUBMITTED` 的申请单，阻止带病锁定；
- 若确已封账仍有漏结，按结佣域 §2.5：`DIFF` 补发到未封账月份，或总监解封后重走。

### 2.3 业绩折算（V4.2 §5.2 / §7.2）

| 业务类型 | 折算后计薪业绩 | 系数 |
|---|---|---|
| 一手房（新盘） | 应收业绩 × 94% × 96% | **0.9024** |
| 其他业务（二手买卖 / 租赁 / 轻托管 / 写字楼租赁等） | 应收业绩 × 96% | **0.96** |

**适用范围：只折新签，不折结佣。**

| 口径 | 是否折算 | 理由 |
|---|:---:|---|
| 新签业绩（`PERF_EXPECT`）→ 团队提成 / 保底 / 总监门店提成 | ✅ | V4.2 §5.2 / §7.2 / §9.1 一致要求"新签**计薪**业绩" |
| 结佣业绩（`PERF_REAL`）→ 个人提成 | ❌ | 贝壳实收值已是到手值（V4.2 §7.1「系统直接采用贝壳结佣金额」） |

> **不二次折算**：业绩域原样落库 → 结佣域原样透传 → **本域折一次**。契约测试需断言"结佣 100,000 → 计薪业绩仍 100,000"。

配置：系数落 `pj_payroll_conversion_rule`，总开关 `panjia.payroll.conversion-enabled`（默认 `true`），系数随 `RuleSnapshot` 冻结。

### 2.4 金额精度红线

| 规则 | 说明 |
|---|---|
| 类型 | 金额一律 `BigDecimal`，**禁 `double` / `float`**（CI 拦截） |
| 中间值 | 计算过程保留 ≥ 6 位小数，不中途取整 |
| 落地 | 各项金额经 `MoneyUtil.roundHalfUp2()` 取整到分 |
| 取整时机 | **只在最终落地时取整一次**，避免逐项取整累积误差 |
| 合计校验 | `∑各项 = 应发 / 实发 / 最终发放`，差 0.01 即失败 |

### 2.5 规则快照 `RuleSnapshot`

```
批次启动（LOCKED 前）
  ├─ 取当时生效的 rank_rule + policy_rule + conversion_rule
  ├─ 合并为一个不可变 JSON → pj_payroll_rule_snapshot
  └─ 与 PayrollBatch / PayrollDetail 同事务写入
```

| 约束 | 说明 |
|---|---|
| 合并后冻结 | 对外是一个不可变锚点，算薪引擎**只读快照**，不回头查规则表 |
| 与员工快照同源 | `EmployeeSnapshot` + `RuleSnapshot` 必须同事务写入（架构 §11.3） |
| 反模式 | `CalculationResult` 存 `rule_id` 而在复现历史时回查当前规则 → CI 拦截 |

### 2.6 算薪顺序（V4.2 §10.3，本域落地版）

| 步 | 项目 | 计算方式 | 适用 |
|---|---|---|---|
| 1 | 业绩汇总 | 按人汇总结佣计薪业绩；按店汇总新签计薪业绩（含折算） | 全体 |
| 2 | 绩效等级判定 | 出勤日平均积分 → A/B/C | 全体 |
| 3 | 最终提点 | 基础提点 + 绩效扣点 + 招聘奖励加点（上限 +10%） | 经纪人 / 总监个人 |
| 4 | 业绩提成 | ∑（结佣计薪业绩 × 最终提点） | 经纪人、店长个人结佣、总监个人 |
| 5 | 团队提成 | 团队新签计薪业绩 × 10% | 店长 |
| 6 | 个人新签提成 | 个人新签计薪业绩 × 70% → **全额递延** | 店长 |
| 7 | 保底补足 | `MAX(保底, 团队提成 + 个人新签提成) − 个人新签提成` 的补足部分 | 店长 |
| 8 | 门店提成 | ∑（各店新签计薪业绩 × 跳点比例） | 总监 |
| 9 | 底薪 | A0 = 2500 + 2000 绩效；总监 = 6000 | A0 / 总监 |
| 10 | 招聘奖励 | 经纪人=提点加点（已入 3）；店长/总监 = 徒弟结佣业绩 × 2% | 店长 / 总监 |
| 11 | 奖金 | 审批单金额 | 全体 |
| 12 | 其他收入 | 录入金额 | 全体 |
| 13 | **应发工资** | 4~12 之和（含补足） | 全体 |
| 14 | 社保扣款 | 1637.15 × 职级比例（兼职/不参保跳过） | 非兼职 |
| 15 | 公积金扣款 | 员工自缴金额（规则侧工号覆盖） | 自愿购买 |
| 16 | 考勤扣款 | 迟到×20 + 旷工按标准 + 请假按导入金额 | 全体 |
| 17 | 积分扣款 | 处罚次数 × 5 | 全体 |
| 18 | 商业保险费 | 规则金额（当前 21） | 购买者 |
| 19 | 宿舍管理费 | 规则金额 | 住宿者 |
| 20 | 往月负工资结转 | 上月结转余额 | 有余额者 |
| 21 | 其他支出 | 录入金额 | 全体 |
| 22 | **实发工资** | 13 − 14~21 | 全体 |
| 23 | 个税扣除 | 累计预扣法（基于已扣各项的应纳税所得额） | 全体 |
| 24 | **最终发放** | 22 − 23 | 全体 |

> **术语对齐 V4.2 §3.2**：`应发 = ∑收入`；`实发 = 应发 − ∑支出(不含个税)`；`最终发放 = 实发 − 个税`。

### 2.7 人员角色与算薪策略

| 角色 | 收入项 | 支出项 | 特殊 |
|---|---|---|---|
| 经纪人 A0 | 提成 + 底薪 2500+2000 + 招聘加点 + 奖金 + 其他收入 | 全部 9 项 | 底薪≠0 |
| 经纪人 A1~A5 | 提成 + 招聘加点 + 奖金 + 其他收入 | 全部 9 项 | 无底薪 |
| 兼职经纪人 | 提成（正常算） | 商保/宿舍/考勤/积分/其他（**跳过社保、公积金、底薪**） | `isPartTime=true` |
| 店长 S1/S2 | 团队提成 + 保底补足 + 个人结佣提成 + 递延释放 + 招聘奖励 + 奖金 + 其他收入 | 全部 9 项 | 个人新签提成**永远递延** |
| 总监 | 底薪 6000 + 门店提成 + 个人成交提成 + 招聘奖励 + 奖金 + 其他收入 | 全部 9 项（无积分扣款，见 V4.2 §6.3） | 多店跳点逐店算 |

> **总监支出项**：V4.2 §6.3 未列「积分扣款」，按需求执行——总监不参与积分扣款。

### 2.8 社保双口径（V4.2 §8.1 / §14.2）

| 口径 | 公式 | 去向 |
|---|---|---|
| 个人承担 | `1637.15 × 职级比例` | 从工资扣（支出项「社保扣款」） |
| 公司承担 | `1637.15 ×（1 − 职级比例）` | **不进工资**，随 `PayrollLockedEvent` 归集到部门收支表 |

| 职级 | 个人比例 | 个人月扣 | 公司比例 | 公司月承担 |
|---|:---:|---:|:---:|---:|
| A0 | 20% | 327.43 | 80% | 1,309.72 |
| A1 | 55% | 900.43 | 45% | 736.72 |
| A2 | 60% | 982.29 | 40% | 654.86 |
| A3 | 65% | 1,064.15 | 35% | 573.00 |
| A4 | 67% | 1,096.89 | 33% | 540.26 |
| A5 | 70% | 1,146.01 | 30% | 491.15 |
| S1 / S2 / 总监 | 30% | 491.15 | 70% | 1,146.01 |

- 兼职：不买社保，个人与公司**均不承担**；
- 挂靠人员：个人全额承担（`socialTag = FULL`）；
- 基数 1637.15 为**动态标准，可配置**。

> **实施标注**：该组比例与基础提成比例数值相同，且公司承担随职级升高而减少，属客户的**内部人工成本结算口径**，非法定社保缴费比例。参数键名定为 `socialSettlementRatio`，**对客与实施沟通时不得表述为"社保比例"**。

### 2.9 个税计算

累计预扣预缴法（V4.2 §8.9，只算金额不申报）：

```
累计应纳税所得额 = 累计收入 − 累计减除费用(5000 × 任职月数) − 累计专项扣除 − 累计专项附加扣除
本期应预扣税额   = 累计应纳税所得额 × 预扣率 − 速算扣除数 − 累计已预扣税额
```

| 参数 | 位置 | 默认 |
|---|---|---|
| 起征点 5000 | `policy_rule.tax.threshold` | 5000 |
| 税率表 brackets | `policy_rule.tax.brackets` | 现行七级超额累进 |
| 社保是否税前扣除 | `policy_rule.tax.deductSocial` | **`true`**（V4.2 §3.2 公式结构：个税基于实发工资） |
| 专项附加扣除 | 员工申报，落 `policy_rule.employee_override` | 0 |

累计数据从本域历史 `PayrollDetail` 汇总（本域自管，不跨域）。

### 2.10 退单回退与工资抵扣（★ 核心）

> **业务现实**：单子可能**退一部分业绩**，也可能**整单退完**。**退单必须回溯到该合同当月的情况**，回退的是**当时的提成金额**，而**不是按最新提成比例重算**。

#### 三条铁律

| # | 铁律 | 说明 |
|---|---|---|
| 1 | **按合同回溯到原归属月** | 退单一律回溯到「该合同原业绩归属月」的结佣记录，不是记在发现退单的月份 |
| 2 | **回退当时的提成金额** | 用**原结佣时冻结的 `RuleSnapshot`** 重算，**严禁取当前规则** |
| 3 | **不回改已锁定批次** | 原月工资未锁定 → 重算自然吸收；已锁定/已发 → 负向补发单并入未锁定月（**金额仍按原快照**） |

#### 为什么必须用原快照（关键）

```
8月：A2 职级（提点 60%），结佣 10,000 → 提成 6,000
9月：该员工升 A3（提点 65%），规则表已改为 65%
10月：该合同退单 10,000

✗ 按最新比例：回退 10,000 × 65% = 6,500   ← 多扣 500（错）
✓ 按原快照  ：回退 10,000 × 60% = 6,000   ← 与当时发的完全一致（对）
```

> 直接原因是 V4.4 §10.1「规则快照锁定」：快照对象是**合同角色人业绩行**，同一合同下的不同结佣批次各自独立快照。退单回退的是"那一次结佣产生的提成"，必须用那一次的快照。

#### 回退金额算法

| 场景 | 算法 |
|---|---|
| **整单退完** | 回退金额 = **该次结佣时算出的提成金额**（原 `CalculationResult` 中该项），取负 |
| **部分退单** | 回退金额 = 原提成 × **退单业绩 ÷ 原业绩**（按业绩占比等比回退） |

**部分退单示例：**

```
原：结佣 10,000，提成 6,000（60%）
退：3,000（占 30%）
回退 = 6,000 × 30% = 1,800
```

> ⚠ **跳点场景需确认**：若该月为跳点档位（如门店新签 ≥10万按 7%），退单后档位可能下降（如降到 6%）。此时"等比回退"与"按退后业绩重算差额"结果不同（见 §13.1 待确认 J）。

#### 与原月工资批次的衔接（依赖 §2.9 时序）

```
8月  ：业绩 10,000 → 结佣 → 提成 6,000（快照 S1，60%）
9月上旬：核对发现该合同退单 3,000
        → 回溯到【8月批次】（此时尚未发放）
        → 用快照 S1 重算：回退 1,800
        → 8月工资按 4,200 发放 ✓
```

**因为核对窗口在发薪之前，回溯与"不回改已发工资"不冲突**——回溯到的是还未发放的当前核算批次，重算即可自然吸收。

| 原月批次状态 | 处置 |
|---|---|
| `DRAFT` / `CALCULATED` / `FAILED` | **直接重算**，回退金额自然吸收（§4.9） |
| `REVIEWING` / `APPROVED` | 退回后重算，或提示先退回 |
| `LOCKED` / `PAID` | **不回改**；生成负向补发单（金额按原快照）并入未锁定月份 |

#### 连带影响：店长 / 总监的汇总类提成

单合同退单会改变**当月门店汇总**，进而影响：

| 项目 | 基数 | 是否连带重算 |
|---|---|---|
| 店长团队提成 | 门店新签合计 × 10% | ✅ 是 |
| 店长保底判断 | 团队新签 + 个人新签 vs 保底 | ✅ 是 |
| 总监门店提成 | 逐店新签 × 跳点档位 | ✅ 是（**档位可能下降**） |
| 经纪人个人提成 | 本人结佣 | ✅ 是（本笔直接回退） |

> 重算一律**用原月批次的 `RuleSnapshot`**，不取当前规则。
> 汇总类提成（跳点档位）是否重算待客户确认（§13.1 待确认 K），默认**全部重算**。

#### 已离职与坏账

| 情形 | 处置 |
|---|---|
| 员工在职，工资够扣 | 当期/补发单直接抵扣 |
| 工资不够扣 | 转**负工资结转**，下月继续抵扣（§3.6） |
| **已离职** | 生成回退单并标记 **坏账**（`bad_debt_flag = true`），留痕不追缴 |

#### 退单对递延台账的影响

| 递延项状态 | 处置 |
|---|---|
| `PENDING` | 用**原快照**重算（金额减少） |
| `RELEASED` | **按原快照回退已发部分**（不是不追回） |

> 与上一版"RELEASED 不回溯"不同：既然退单要回溯到当月、回退当时的金额，已释放的递延提成同样应按原快照回退。

#### 追溯要求（硬约束）

退单回退**必须关联** `contract_id` + 原 `fact_id` + 原 `rule_snapshot_id`，**禁止**用手工"其他支出"科目记账。必须能回答：

> 这笔扣款，是**哪个合同的哪次结佣**、按**哪版规则**、退了**多少业绩**、回退了**多少提成**。

### 3.2 批次状态机

```
DRAFT ──calculate──▶ CALCULATING ──success──▶ CALCULATED
                            │
                            └──failure──▶ FAILED ──retry──▶ CALCULATING
CALCULATED ──submit──▶ REVIEWING ──approve──▶ APPROVED ──lock──▶ LOCKED ──pay──▶ PAID

                                  └──reject──▶ CALCULATED
```

**与 V4.2 §10.4 的映射：**

| V4.2 四态 | 本域状态 | 对客展示 |
|---|---|---|

| 待审核 | `REVIEWING` | 待审核 |
| 已确认 | `APPROVED` | 已确认 |
| 已锁定 | `LOCKED` | 已锁定 |

### 3.5 递延台账 `DeferredItem`（★ 匹配键修正）

**场景**：V4.2 §5.2 —— 店长「个人新签提成」无论是否触发保底，**都不在新签当月发放**，要等该笔业绩「结单」（结佣审批通过）后才发。

> ⚠ **架构 §6.7 的"按 `fact_id` 匹配"是错的，本设计修正**：同一笔业绩的应收（`PERF_EXPECT`）与实收（`PERF_REAL`）是**两条不同事实，各有不同 `fact_id`**，按 id 永远匹配不上。必须用业务键。

**匹配键 `deal_key`**：取业绩域 `source_key` 去掉末尾 `fact_type` 后缀：

```
source_key = contract_no | 角色人系统号 | fee_item | role_type | fact_type
deal_key   = contract_no | 角色人系统号 | fee_item | role_type     ← 去掉 fact_type
```

同一笔业绩的应收与实收，`deal_key` **完全相同**，据此关联。

**流程：**

```
新签月（2026-08）
  ├─ 个人新签提成 = 个人新签计薪业绩 × 70%
  ├─ 金额【不进当月应发】
  └─ 写 pj_payroll_deferred_item：
        employee_id / dept_id / period=2026-08
        deal_key / deferred_amount / final_rate（冻结提点）
        status = PENDING

结单月（该笔实收并完成结佣审批，如 2026-10）
  ├─ 消费 CommissionApprovedEvent（携带 deal_key 集合）
  ├─ 按 deal_key 匹配 PENDING 递延项 → status = RELEASED
  └─ 金额以「个人新签提成」科目【单独列示】并入结单月工资
```

| 字段 | 说明 |
|---|---|
| `deal_key` | ★ 业绩业务键（应收与实收共有） |
| `source_fact_id` | 对应 `PERF_EXPECT` 事实 ID（溯源） |
| `deferred_amount` | 递延的个人新签提成 |
| `final_rate` | 冻结时的提点（释放时**不重取规则**） |
| `status` | `PENDING` / `RELEASED` / `VOID` |
| `released_period` | 实际发放月 |

| 约束 | 说明 |
|---|---|
| 金额不可手工改 | 系统计算、只读；修正走调整单 |
| 按 `deal_key` 精确匹配 | 一笔业绩一条递延项，避免按人汇总混淆 |
| 随 `RuleSnapshot` 冻结 | 释放时不重取当前规则 |
| 结单月**单独列示** | V4.2 §5.4 汇总表第 2 项，不并入「个人结佣提成」（基数口径不同） |
| 员工离职 | 未结单即离职 → 默认作废（未结单不产生应付），可配 `panjia.payroll.deferred.pay-on-leave` |
| **退单** | 一律用**原 `RuleSnapshot`** 回退：`PENDING` 重算减少；`RELEASED` 回退已发部分（§2.10） |

### 3.6 负工资结转 `NegativeBalance`

| 规则 | 说明 |
|---|---|
| 触发 | 当月**实发工资 < 0**（∑收入 − ∑支出项(不含个税)）；**退单红冲是主要触发源之一**（§2.10） |
| 处理 | 差额存入结转余额，当月最终发放记 0 |
| 抵扣 | 下月算薪自动抵扣；抵扣后余额清零 |
| 不可改 | 余额禁止手工修改，修正走调整单 |

### 3.7 手工录入项 `ManualItem`

| 类型 | 审批 | 说明 |
|---|---|---|
| 奖金 `BONUS` | **需总监审批** | V4.2 §7.5，支持按个人/门店批量 |
| 其他收入 `OTHER_INCOME` | 无需审批 | 算薪人员直接录入（V4.2 §7.6） |
| 其他支出 `OTHER_DEDUCT` | 无需审批 | 算薪人员直接录入（V4.2 §8.8） |

> 记录**永久存档、不可修改**；错误通过补发/扣减修正。

### 3.8 调整单 / 补发单 `Adjust`

```
原批次 PayrollBatch #100（LOCKED，不可变）
   ├── Adjust #101（ADJUST，+500）→ 新 CalculationResult
   └── Adjust #102（SUPPLEMENT，-200，并入指定月）→ 新 CalculationResult
```

| 类型 | 用途 | 目标月 |
|---|---|---|
| `ADJUST` | 金额差异修正 | 当期 |
| `SUPPLEMENT` | 锁定后发现少发 | **指定目标月**（V4.3 §10.5） |
| **负向追回** | **退单追回**（金额为负） | 未锁定月份（§2.10） |

> 退单追回**必须关联** `contract_id` / 业绩行，禁止用手工"其他支出"记账。
> 追不回（离职/长期不足抵扣）→ 标记 `bad_debt_flag = true` + `bad_debt_amount`，留痕给财务。

> 补发**不回写**历史已锁定月份；各自独立产出 `CalculationResult`，保证可复现。

## 四、核心流程

### 4.1 算薪主流程

```
① 创建批次（period = 工资归属月）
② 前置校验
   ├─ 该 period 无未结佣申请单（DRAFT/PENDING_VERIFY/SUBMITTED）→ 否则告警
   └─ 规则种子齐全（rank/policy/conversion）
③ 冻结快照（同事务）
   ├─ RuleSnapshot ← 三类规则当时版本
   └─ 对每个员工：EmployeeSnapshot ← people 按时点取数
④ SalaryCalculationEngine 纯计算（无 DB 写入）
   输入：快照 + 结佣事实 + 新签事实 + 考勤积分发生量 + 递延释放项
   输出：CalculationResult（一人一份）
⑤ PayrollResultAssembler 组装落库
   ├─ 写 PayrollDetail + CalculationResult
   ├─ 写/更新 DeferredItem、NegativeBalance
   └─ 推进状态机 CALCULATING → CALCULATED
⑥ 提交审核 → 审批 → 锁定
⑦ 锁定时同事务写 Outbox：PayrollLockedEvent（含 deptCosts）
```

### 4.2 经纪人算薪

```
最终提点 = 基础提点(职级) + 绩效扣点(A/B/C) + 招聘奖励加点(≤+10%)
业绩提成 = ∑(每笔结佣计薪业绩 × 最终提点)
底薪     = A0: 2500 + 2000绩效；A1~A5: 0
应发     = 提成 + 底薪 + 奖金 + 其他收入
实发     = 应发 − 社保 − 公积金 − 考勤 − 积分 − 商保 − 宿舍 − 负工资结转 − 其他支出
最终发放 = 实发 − 个税
```

| 绩效等级 | 判定（出勤日平均积分） | 扣点 |
|---|---|---|
| A | ≥ 8 分 | 0% |
| B | 6 ≤ 平均分 < 8 | −2% |
| C | < 6 分 | −4% |

**兼职处理**（V4.2 §4.5）：提成正常算；**跳过**底薪、社保、公积金。底薪=0 ≠ 兼职，判定依据是 `isPartTime`。

### 4.3 店长算薪（★ 含递延）

```
团队新签计薪业绩 = 门店全部人员新签计薪业绩之和
                − 社保成本
                − 店长个人新签计薪业绩

社保成本   = 1637.15 × 计缴人数
计缴人数   = 本店「个人社保比例 > 30%」且「非兼职」的人数
             · A0(20%) 不计入    · S1/S2/总监(30%) 不计入（30% 不 > 30%）
             · 兼职不计入

团队提成       = 团队新签计薪业绩 × 10%
个人新签提成   = 个人新签计薪业绩 × 70%          ← 【全额递延，当月不发】
保底工资       = S1: 7000 / S2: 8000

★ 统一发放公式：
   当月发放（新签部分）= MAX(保底, 团队提成 + 个人新签提成) − 个人新签提成
   个人新签提成        → 递延台账，待结单月发放

个人结佣提成   = 本人结佣计薪业绩 × 70%（当月有结佣时）
招聘奖励       = 徒弟结佣业绩 × 2%
应发           = 团队提成 + 保底补足 + 个人结佣提成 + 递延释放 + 招聘奖励 + 奖金 + 其他收入
```

> **口径要点**：`实际缴费金额` 是**每人全额 1637.15**（个人 + 公司合计），不是个人扣款额；计缴人数按 `> 30%` **严格大于**判定。两项写反会导致团队提成偏大/偏小。

### 4.4 总监算薪

```
门店提成   = ∑(各门店新签计薪业绩 × 对应跳点比例)
跳点：<10万 6%  |  ≥10万 7%  |  ≥20万 8%   ← 逐店判定后汇总
个人成交提成 = 本人结佣计薪业绩 × 对应 A 序列提点
底薪       = 6000
招聘奖励   = 徒弟结佣业绩 × 2%
支出项     = 社保/公积金/考勤/商保/负工资结转/其他支出（★ 无积分扣款，V4.2 §6.3）
```

> V4.2 §6.5 验算表不作为验收锚点（6 店 5 店对不上，见结佣域 §13.1 第 2 条）。

### 4.5 招聘奖励（双模式）

| 模式 | 适用 | 算法 |
|---|---|---|
| `RATE_ADD` | 经纪人 | 最终提点 += 2% × 合格徒弟数，**上限 +10%**（最多 5 人） |
| `AMOUNT_RATIO` | 店长 / 总监 | 招聘奖励 = 徒弟结佣业绩 × 2% |

**共同规则**：徒弟须从业 ≥ 2 年；**离职当月起不再计算，已发不追回**。

> **师傅视角问题**：`EmployeeSnapshot.mentorId` 是"我的师傅"，而奖励给师傅 → 需**反向查徒弟**。见 CR-P1。

### 4.6 考勤与积分扣款

**考勤**（发生量来自 import，标准来自本域规则）：

| 项目 | 公式 |
|---|---|
| 迟到 | 次数 × 20 元 |
| 旷工（有底薪） | 天数 × 3 × 日工资；日工资 = 月底薪 ÷ 当月应出勤天数 |
| 旷工（无底薪） | 天数 × 50 元 |
| 请假 | 直接取人事 Excel 填写金额 |

**积分**：

| 项目 | 公式 |
|---|---|
| 处罚 | 次数 × 5 元 |
| 绩效等级 | 出勤日平均积分 → A(≥8) / B(6~8) / C(<6)；只考核出勤当日 |

> 导入只带**发生量**，单价与判定规则由本域 `policy_rule` 维护（V4.2 §9.5 边界）。

### 4.7 规则取值：三级兜底

```
全局 global → 标签/职级覆盖 tag_override / level_override → 工号覆盖 employee_override
```

`RuleResolver` 统一实现，算薪引擎**不感知兜底逻辑**（避免散落到各 Calculator）。

### 4.9 重算与幂等

| 状态 | 可否重算 | 行为 |
|---|---|---|
| `DRAFT` / `CALCULATED` / `FAILED` | ✅ | 重跑引擎 → **新建** `CalculationResult`（`attempt+1`），覆盖当前明细 |
| `REVIEWING` / `APPROVED` | ❌ | 需先退回 |
| `LOCKED` / `PAID` | ❌ | 只能追加调整/补发 |

`input_hash` 相同则跳过重算（幂等）。

## 六、事务、并发、幂等、重算

### 6.1 事务边界

| 操作 | 事务范围 |
|---|---|
| 算薪（整体） | **一个批次一个事务**：冻结快照 → 计算 → 落 detail/result/deferred/negative → 推进状态机 |
| 快照冻结 | 与批次同事务（架构 §11.3：两个快照必须同源同事务） |
| 锁定 + 事件 | 同事务写 `pj_payroll_batch` + `pj_event_outbox` |
| 调整/补发执行 | 同事务：新增单据 + 新 `CalculationResult` + 更新余额 |
| 递延释放 | 同事务：更新 `DeferredItem` + 计入目标月 detail |

> 算薪引擎**本身不参与事务**（纯计算，无 DB 写入）。

### 6.2 并发控制

```sql
UPDATE pj_payroll_batch
SET status = #{target}, version = version + 1, update_time = now()
WHERE id = #{id} AND status = #{expected} AND version = #{expectedVersion}
```

- 更新行数 = 1：成功
- 更新行数 = 0：抛 `StateTransitionConflictException`，由调用方重试或提示

明细级并发（调整单）用 `PayrollDetail.version` 乐观锁，冲突重试 3 次后告警。

### 6.3 幂等锚点

| 场景 | 锚点 |
|---|---|
| 批次唯一 | `uk_batch_period_scope (period, dept_scope)` |
| 明细唯一 | `uk_pdetail_batch_emp (batch_id, employee_id)` |
| 计算结果 | `uk_pcalc_biz (batch_id, employee_id, attempt)` |
| 递延项 | `uk_pdefer_deal (employee_id, deal_key)` |
| 规则快照 | `uk_prulesnap_batch (batch_id)` |
| 算薪重跑 | `input_hash` 相同则跳过 |

### 6.4 重算规则

| 批次状态 | 重算 | 说明 |
|---|:---:|---|
| `DRAFT` / `CALCULATED` / `FAILED` | ✅ | `attempt+1`，新建 `CalculationResult`，覆盖 detail |
| `REVIEWING` / `APPROVED` | ❌ | 先退回 |
| `LOCKED` / `PAID` | ❌ | 只能追加调整/补发（不改原明细） |

**重算不改已释放的递延项**：释放是终态动作，重算只影响未释放项与当期金额。

## 十一、架构决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| **P1** | **规则归本域，不独立成顶层域**（架构 ADR-023） | 单一消费者 + 快照归属 + 同事务冻结三条铁律 |
| **P2** | 规则拆**三类四表**（架构 ADR-024） | 职级 / 全公司政策 / 业务折算三者正交，避免上帝 JSON |
| **P3** | **规则 = 数据，计算器 = 代码**（SPI） | 换客户只改数据；复杂算法不进 JSONB |
| **P4** | **结佣与新签一律按 `period`（业绩归属月）取**；`approved_month` 仅作审计 | 实际节奏是「N月业绩 → N+1月核对并发 N月工资」，批次 `period` = 业绩归属月。按 `approved_month` 取会让结佣掉进下一个批次，而该月工资已发完 → 漏发 |
| **P5** | **折算只作用于新签，结佣不折** | 结佣是贝壳实收到手值；双口径适用范围不同（V4.2 §7.1 尾注 vs §5.2） |
| **P6** | **递延台账按 `deal_key` 匹配，不按 `fact_id`** | 同一笔业绩的应收/实收是两条事实、不同 `fact_id`，按 id 永远匹配不上（**修正架构 §6.7**） |
| **P7** | **店长发放用统一公式 `MAX(保底, 团队+个人新签) − 个人新签`** | 一个公式覆盖"触发/未触发保底"两种分支，避免分支遗漏 |
| **P8** | **递延提成在结单月以「个人新签提成」单独列示** | V4.2 §5.4 与「个人结佣提成」是并列科目，基数口径不同，合并破坏列级核对 |
| **P9** | 招聘奖励**双模式**（`RATE_ADD` / `AMOUNT_RATIO`） | V4.2 §7.4：经纪人提点加点、店长/总监按徒弟结佣业绩 ×2% |
| **P10** | 社保参数名 `socialSettlementRatio` | 该比例与提成比例数值相同、非法定社保，避免后续维护者误"修正" |
| **P11** | `employer_social` 单独字段，**不进 `net`** | 公司成本 ≠ 员工工资；只随事件归集 ledger |
| **P12** | 算薪引擎**纯计算、无 DB 写入** | 易测试、可无限次重算、可差异比较（架构 §5.2） |
| **P13** | 重算 = **新建** `CalculationResult` | 不改原结果，调整前后可 diff（架构 §5.2） |
| **P14** | 锁定后**只追加**调整/补发 | V4.2 §10.4 铁律；直接改破坏审计 |
| **P15** | 个税**基于实发工资**（社保税前扣除） | V4.2 §3.2 公式结构：个税是最后一步扣除 |
| **P16** | 总监**不计积分扣款** | V4.2 §6.3 支出项未列积分扣款 |
| **P17** | 快照冻结与批次落库**同事务** | 架构 §11.3；防止快照与工资不一致 |
| **P18** | 只传**汇总数**给 ledger | 事件只做通知，穿透调 `PayrollQueryPort`（架构 §7.3） |
| **P19** | **退单按合同回溯到原业绩归属月**，不记在发现退单的月份 | 用户明确要求：退单必须回到该合同当月的情况，回退当时的提成 |
| **P20** | **回退金额用原结佣时的 `RuleSnapshot` 重算，严禁取当前规则** | 员工可能已升职、规则已调整；按最新比例回退会多扣/少扣。例：8月 A2(60%) 发 6000，10月升 A3(65%) 后退单，必须回退 6000 而非 6500 |
| **P21** | 退单回退**必须关联** `contract_id` + 原 `fact_id` + 原 `rule_snapshot_id` | 否则无法回答"这笔扣款按哪版规则、退了多少业绩、回退多少提成" |
| **P22** | 原月批次未锁定 → 重算吸收；已锁定 → 负向补发单并入未锁定月（**金额仍按原快照**） | 核对窗口在发薪之前，常规情况重算即可；已发的不回改，但金额口径不变 |

| **CR-A1** | 架构 | 修正 §6.7「按 `fact_id` 匹配」→ **按 `deal_key` 匹配** | 应收/实收是两条事实、不同 `fact_id`，按 id 永远匹配不上 |
