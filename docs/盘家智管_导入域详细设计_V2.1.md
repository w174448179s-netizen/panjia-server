## 〇、设计目标与边界（一句话对齐）

导入域负责 **`业务单据 Excel → RawData（只读归档）→ NormalizedRecord（标准化）`**；**不构造业务事实、不理解业绩/薪酬语义、不做员工主数据导入**。

贝壳模板/格式变更**只影响本域内部**（新增/调整 DataSource 实现），不波及其他域——这是本域独立的全部价值。

### 0.1 与员工导入的边界（★ V2.0 关键）

| 导入类型 | 归属 | 本域是否负责 |
|---------|------|:----------:|
| 业绩（贝壳结佣/新签） | `panjia-import` | ✅ |
| 考勤 / 积分 / 费用（OTHERS） | `panjia-import` | ✅ |
| **员工主数据（Excel）** | **`panjia-people`** | ❌ **本域不负责** |

**两套导入的复用关系：**

```
                ┌──────────────────────┐
                │  common-import-util  │  工具层：解析/模板/归档/基础校验
                └──────────┬───────────┘
                           │ 仅工具层复用
              ┌────────────┴────────────┐
              ▼                         ▼
      ┌───────────────┐        ┌────────────────┐
      │ panjia-import │        │ panjia-people  │
      │  业务单据      │        │  员工主数据     │
      │ 批次/Raw/NR   │        │ 批次/Raw/Issue │
      │ 单据状态机     │        │ 员工导入状态机  │
      └───────────────┘        └────────────────┘
         业务层不复用              业务层不复用
```

> **仅工具层复用，业务层不复用** —— 主数据（不可物理删、需演进）与单据（可逻辑失效）语义不同，强行复用会混杂；保护 V1.8 基线 ADR-007 / ADR-021 / ADR-022。

### 0.2 三不原则

| 环节 | 职责 | 禁止 |
|---|---|---|
| 导入域 | 单据 Excel → RawData → NormalizedRecord | 构造 PerformanceFact / 员工业务对象 / 理解业绩语义 |
| 业绩域 | 消费 NormalizedRecord → PerformanceFact | 解析 Excel / 依赖数据源格式 |
| 员工域 | 员工 Excel → Employee/salary_fact（**本域自建**） | 调用本域业务接口 |
| 工具层 | 文件解析/模板/归档/基础校验 | 落库 / 业务语义校验 |
| 导入域金额 | 只做**类型转换**，原值透传 | 业绩折算、分成、金额二次加工 |

## 一、数据源与模板全景（5 类，均为业务单据）

| 编码（source_type） | 中文名 | 文件/来源 | 归一化产物 | 对应下游业务 |
|---|---|---|---|---|
| `KE_SIGNED` | 贝壳·理房通到账明细（结佣） | 贝壳后台 Excel | `NormalizedRecord`（SIGNED） | 经纪人/店长/总监个人结佣提成 |
| `KE_NEW_SIGN` | 贝壳·新签业绩明细（应收） | 贝壳后台 Excel | `NormalizedRecord`（NEW_SIGN） | 店长团队提成、保底、总监门店提成 |
| `ATTENDANCE` | 考勤 Excel | 人事整理标准模板 | `NormalizedRecord`（ATTENDANCE） | 考勤扣款 |
| `POINTS` | 积分 Excel | 人事整理标准模板 | `NormalizedRecord`（POINTS） | 积分扣款 + 绩效等级（A/B/C） |
| `OTHERS` | 手工录入/其他费用 | 系统手工录入兜底 | `NormalizedRecord`（MANUAL） | 商业保险、宿舍管理、其他支出 |

> **重要口径（V4.2 §7.1、§9.1）：**
> - **结佣**（实收）走 `KE_SIGNED`；**新签**（应收）走 `KE_NEW_SIGN`；两者**同源但语义不同**，必须拆成两个 DataSource，**绝不可混为一张"业绩表"**。
> - 考勤/积分**不对接钉钉**（V4.2 修订说明第7条），由人事整理为标准模板导入。
> - **员工主数据不属于本域**（V2.0 移除 `EMPLOYEE`）。

### 1.1 贝壳到账明细关键字段（RawData 原始列）

| 原始列（raw） | 类型 | 说明 | 归一化映射 |
|---|---|---|---|
| `arrive_month` | varchar | 到账月 | `period`（YYYY-MM） |
| `biz_type` | varchar | 业务类型（一手房/二手买卖/租赁/...） | `biz_type` |
| `order_no` | varchar | 订单号（一手房/房产金融/家装荐客关联键） | `source_key`（之一） |
| `contract_no` | varchar | 合同号（二手买卖/租赁/轻托管等关联键） | `source_key`（之一） |
| `role_sys_no` | varchar | 角色人系统号（经纪人唯一标识） | `employee_external_code` → 匹配 Employee |
| `role_name` | varchar | 角色人姓名 | `employee_name`（校验用） |
| `role_type` | varchar | 角色类型（客源成交人/房源维护人/...） | `role_type` |
| `share_ratio` | numeric | 业绩比例 | `share_ratio` |
| `current_receivable` | numeric(18,2) | 当月应收业绩 | `receivable_amount`（原值） |
| `current_received` | numeric(18,2) | 当月实收业绩 | `received_amount`（原值） |

> RawData **原样存原始列名与原始值**，仅做类型规整；业务语义解析下沉到 Normalize 阶段，由模板配置驱动——贝壳改列名只改模板。

### 1.2 手工录入兜底（OTHERS）

无 Excel 时由算薪人员逐条录入（商业保险费、宿舍管理费、其他支出等）。不产 RawData 文件，仍生成 `NormalizedRecord`（`raw_data_id = null`），受同一批次与校验约束。**强制走 `AuditPort`** 留痕。

**去重为编码硬约束**：判重键 `(batch_id, employee_external_code, period, item_type)`；插入前先 SELECT，命中抛 `BizException`；跨批允许共存。规则在 DO 字段注释、`uk_norm_source_key` SQL 注释、本文档三处同步。

### 1.3 关联键 `source_key` 规则骨架

由 `biz_type` 决定：一手房/房产金融/家装荐客用**订单号**；二手买卖/租赁/轻托管用**合同号**；同一合同多角色拼接 `contract_no + role_type` 保证行级唯一。

> **待确认**：完整映射（租赁轻托管/写字楼租赁等细分）**待贝壳真实 Excel 样本到位后固化**（§9.2-1）。在此之前 `SourceKeyGenerator` 以接口契约先行，规则实现可注入。

## 三、领域对象设计

### 3.1 聚合根：`ImportBatch`（一次导入的批次）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long（雪花） | 主键 |
| `batchNo` | varchar(32) | 批次号（`IMP + yyyyMMdd + 序列`） |
| `sourceType` | varchar(20) | 数据源类型（**5 类，无 EMPLOYEE**） |
| `templateVersion` | varchar(20) | **创建/解析时快照冻结** |
| `fileName` / `originalFileName` | varchar | 存储文件名 / 原名 |
| `storagePath` | varchar | 归档路径（工具层 `FileArchiver` 返回） |
| `period` | varchar(7) | 归属月（YYYY-MM），唯一性核心维度 |
| `totalRows` / `successRows` / `failedRows` | int | 行数统计 |
| `status` | smallint | 状态机（§3.5） |
| `archiveStatus` | smallint | 归档状态 |
| `operatorId` / `deptId` | Long | 操作人 / 归属部门 |
| `version` | int | 乐观锁 |
| `supersededByBatchId` | Long | 被新批次废弃后回填，指向新批次 |
| **`revokeReason`（V2.1）** | varchar | **撤销原因**（必填，§5.6） |
| **`revokedBy` / `revokedTime`（V2.1）** | Long / Timestamp | 撤销操作人 / 撤销时间 |

**关键不变量：**
- `source_type + period + dept_id` 决定业务唯一性；重复导入走"归档旧 + 新建"（§5.5）。
- `template_version` **创建/解析时**快照冻结（非归档时），避免解析逻辑与模板版本不一致。
- `superseded_by_batch_id` 仅由重复导入流程在新批次归档成功**后**回填，一经设置不可改。

### 3.2 实体：`RawData`（原始记录 · 只读）

**只追加、不可 UPDATE/DELETE**（应用层 insert-only + AuditPort；**禁止触发器**）。按 source_type 分表：

| 表 | 承载 |
|---|---|
| `pj_import_raw_signed` | KE_SIGNED 结佣明细 |
| `pj_import_raw_new_sign` | KE_NEW_SIGN 新签明细 |
| `pj_import_raw_attendance` | 考勤 |
| `pj_import_raw_points` | 积分 |
| `pj_import_raw_manual` | 手工录入 |

公共列：`id, batch_id, row_no, raw_json(jsonb), create_time`。**所有原始列允许 NULL（原样保留）**。

> `raw_json` 全量冗余存储，是审计与重归一化的锚点。**V2.0 移除 `pj_import_raw_employee`** —— 员工原始归档由 people 域 `pj_people_import_raw` 承载。

### 3.3 实体：`NormalizedRecord`（归一化记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long（雪花） | 主键 |
| `batchId` | Long | 所属批次 |
| `recordType` | varchar(20) | SIGNED / NEW_SIGN / ATTENDANCE / POINTS / MANUAL |
| `period` | varchar(7) | 归属月 |
| `employeeId` | Long | 关联 Employee.id；匹配不到为 null + ImportIssue |
| `employeeExternalCode` | varchar | 外部编码（角色人系统号/工号） |
| `sourceKey` | varchar | 业务唯一键（订单号/合同号/考勤日期） |
| `bizType` | varchar | 业务类型 |
| `receivableAmount` | numeric(18,2) | 应收业绩（原值） |
| `receivedAmount` | numeric(18,2) | 实收业绩（原值） |
| `shareRatio` | numeric(10,4) | 业绩比例 |
| `roleType` | varchar | 角色类型 |
| `extraJson` | jsonb | 扩展字段 |
| `rawDataId` | Long | 对应 RawData 行（手工录入为 null） |
| `validationStatus` / `validationMsg` | smallint / varchar | 校验状态与原因 |

> **不含业务语义字段**（提点/提成金额），只有结构化数据 + 关联键 + 金额原值。

### 3.4 值对象：`ImportIssue`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `batchId` / `rowNo` | Long / Long / int | |
| `issueType` | varchar(20) | `EMPLOYEE_NOT_MATCH` / `COLUMN_TYPE_ERR` / `REQUIRED_MISSING` / `DUPLICATE_KEY` / `PERIOD_MISMATCH` |
| `fieldName` / `rawValue` / `message` | varchar | |
| `status` | smallint | `OPEN / RESOLVED / IGNORED` |

- `RESOLVED`：已人工修复数据（补齐员工档案后重归一化）；
- `IGNORED`：业务确认可忽略，**仅限算薪人员/总监**标记，Controller 鉴权 + AuditPort 留痕。

> **V2.0 移除** `DEPT_NOT_MATCH` / `POST_NOT_MATCH`（属员工导入，归 people 域）。

### 3.5 状态机：`ImportBatchStatus`

```
  PARSING ──▶ NORMALIZING ──▶ PENDING_CONFIRM ──▶ ARCHIVED ──▶ 【REVOKED】（终态・撤销）
                                  │                     │
                                  └──▶ FAILED           └── 仅当"下游未生效"时可撤销
                                    （终态，可新建批次重试）

★ REVOKED 与 FAILED 均为终态，但语义不同：
  FAILED  = 导入过程失败，数据从未对外生效
  REVOKED = 导入成功后发现归属月选错，主动整批作废
```

| code | desc |
|---|---|
| `PARSING` | 解析中（读取文件、落 RawData） |
| `NORMALIZING` | 归一化中 |
| `PENDING_CONFIRM` | 待确认（有 ImportIssue） |
| `ARCHIVED` | 已归档（对外可见/可被消费） |
| `FAILED` | 失败（终态） |
| **`REVOKED`（V2.1 新增）** | **已撤销**（归属月选错整批作废；终态） |

```java
public enum ImportBatchStatus {
    PARSING(0, "解析中", Set.of(NORMALIZING, FAILED), false, true),
    NORMALIZING(1, "归一化中", Set.of(PENDING_CONFIRM, FAILED), false, true),
    PENDING_CONFIRM(2, "待确认", Set.of(NORMALIZING, ARCHIVED, FAILED), false, false),
    ARCHIVED(3, "已归档", Set.of(REVOKED), true, false),
    FAILED(4, "失败", Set.of(), true, false),
    REVOKED(5, "已撤销", Set.of(), true, false);   // ★ V2.1 新增：终态

    private final int code;
    private final String desc;
    private final Set<ImportBatchStatus> next;
    private final boolean terminal;
    private final boolean running;

    public boolean canTransitTo(ImportBatchStatus t) { return next.contains(t); }
    public boolean isTerminal() { return terminal; }
    public boolean isRunning()  { return running; }
}
```

**强制规则：**
1. `FAILED` / `REVOKED` 均为终态（`canTransitTo` 恒 false，单测固化），只能新建批次重试；
2. **重归一化只重建派生数据**：RawData 完全不动，只重建 NormalizedRecord + ImportIssue；
3. 跨月检测在 `PARSING` 前置，命中即 `FAILED`；
4. **★ 仅 `ARCHIVED` 可撤销**（`ARCHIVED → REVOKED`）；`PENDING_CONFIRM` 及之前状态**不可撤销**（数据尚未对外生效，直接重导或删批次即可，无需撤销语义）；
5. **★ 撤销必须经前置校验**（§5.6 校验②）：下游已生效则拒绝，由 `BatchConsumptionQueryPort` 判定；
6. **★ 撤销不可回滚**：`REVOKED` 是终态，误撤销只能通过"重新导入正确月份"补救，**不支持反向恢复**。

## 五、导入流程

### 5.1 通用主流程（两段式事务）

```
UploadFile / ManualEntry
  ↓
① 创建 ImportBatch（快照冻结 templateVersion）
  ↓
② 【事务 A】解析 + 分批落 RawData
   - 分批 BATCH_INSERT_SIZE = 300；单批上限 MAX_ROWS_PER_BATCH = 5000
   - 失败仅回滚当前子批次；残留 RawData 属审计保留
   - 跨月检测前置（命中 → FAILED）
  ↓
③ 【事务 B】归一化 → NormalizedRecord + ImportIssue
  ↓
④ 状态推进：全通过 → ARCHIVED；有 issue → PENDING_CONFIRM
```

### 5.2 归一化流水线

```
NormalizeService.normalize(batch)
  ↓
列映射（按 pj_import_template）→ 类型转换 → 员工匹配（external_code → Employee.id）
  → 生成 NormalizedRecord
  → 匹配失败 → ImportIssue(EMPLOYEE_NOT_MATCH)，employee_id = null
```

### 5.3 校验规则

- `REQUIRED_MISSING`：关键列缺失（employee_external_code / period / 金额）
- `COLUMN_TYPE_ERR`：类型转换失败
- `DUPLICATE_KEY`：`source_key` 重复；手工录入走业务判重键
- `PERIOD_MISMATCH`：同批次 `arrive_month` 不一致 → FAILED
- `EMPLOYEE_NOT_MATCH`：external_code 在 people 域查不到

### 5.4 重归一化

`PENDING_CONFIRM → NORMALIZING`：RawData 不动；先按 `batch_id` 删旧 NormalizedRecord + ImportIssue，再重新生成；全程 `AuditPort` 留痕。

### 5.5 重复导入与 SUPERSEDED（单据：逻辑失效）

新批次归档成功后回填旧批次 `superseded_by_batch_id`；**RawData 保留**，下游按 `archive_status = ARCHIVED AND superseded_by_batch_id IS NULL` 过滤。

> **与员工主数据的差异（V2.0 明确）**：单据走**逻辑失效**（保留审计）；员工主数据走**演进**（upsert + 变更入口，不物理删），由 people 域独立实现。两者策略不同，**业务层不复用**。

### 5.6 导入撤销（归属月选错）★ V2.1 新增

**场景**：导入时**归属月（`period`）选错**（如 8 月业绩误选为 7 月）。归属月是**批次级**属性，选错则整批数据归属全错，必须**整批撤销后重新导入**。

> **为什么不能只改 `period`**：直接改写会破坏 ① `source_key` 唯一性（与正确月份数据冲突）② `template_version` 快照与解析逻辑的对应 ③ 已消费该批次的下游单据归属（实收确认单 / 结佣申请单全部错位）④ `uk_import_batch_type_period_dept` 唯一索引语义。**撤销 + 重导**是唯一自洽路径。

#### 5.6.1 前置校验（任一不满足则拒绝，抛 BizException）

| # | 校验 | 不满足时 |
|---|------|---------|
| ① | 批次状态为 `ARCHIVED`（唯一可撤销态） | 拒绝，提示"仅已归档批次可撤销" |
| ② | **下游未生效**：该批次 `NormalizedRecord` 未被任何**已生效**业务单据引用 | **拒绝**，提示先处理下游单据（详见 §5.6.3） |
| ③ | 该批次 `period` **未封账** | 拒绝，提示先解封 |
| ④ | `superseded_by_batch_id IS NULL`（未被后续批次取代） | 拒绝，被取代的批次无需撤销 |
| ⑤ | 操作人具备权限（财务 / 总监） | 拒绝，403 |

#### 5.6.2 撤销动作（同一事务）

```
① ImportBatch.status：ARCHIVED → REVOKED（终态）
② 写撤销留痕：revoke_reason（必填）+ operator_id + revoke_time（AuditPort）
③ 【发事件】import.revoked（§8.3）→ 下游各自级联处理
④ 【本域内】NormalizedRecord 停止对外可见：
   NormalizedRecordQueryPort 默认实现增加过滤
   → status = ARCHIVED AND superseded_by_batch_id IS NULL
     AND batch.status <> 'REVOKED'
⑤ RawData 保留不动（只读铁律，§3.2）
```

> **④ 是关键**：下游通过 `NormalizedRecordQueryPort` 取数，撤销后必须立即不可见，否则已撤销的数据仍会被新查询读到。
>
> **⑤ 不删 Raw**：撤销是**逻辑失效**，与 SUPERSEDED 策略一致（§5.5），保留审计锚点。

#### 5.6.3 下游"是否已生效"的判定（★ 依赖反转设计）

**问题**：本域**被** `panjia-performance` 依赖（§四），若直接调用 performance 查询"是否已消费"，会形成 **import → performance → import** 的循环依赖。

**解法：经 `panjia-contracts` 接口反转（DIP）**

```
      panjia-contracts
   ┌──────────────────────────┐
   │  BatchConsumptionQueryPort │  ← 接口定义在 contracts
   └────────┬──────────┬───────┘
            │ implements│ calls
            ▼           ▼
   panjia-performance  panjia-import
   （适配器实现）      （调用方）

依赖方向：import → contracts ← performance  ✅ 无环
```

```java
// panjia-contracts
public interface BatchConsumptionQueryPort {
    /** 该批次数据是否已被【已生效】业务单据引用 */
    boolean isConsumedByEffectiveDoc(Long batchId);

    /** 被引用情况明细，用于拒绝时给前端提示"需先处理哪些单据" */
    ConsumptionDetail detail(Long batchId);
}

public record ConsumptionDetail(
    Long batchId,
    boolean consumed,
    List<String> effectiveDocs   // 如 ["实收确认单 RC2026080001(已确认)", "结佣申请单 CA2026080003(已审批)"]
) {}
```

**performance 侧实现语义**（本域不关心其内部）：

| 下游单据状态 | 是否算"已生效" |
|---|:---:|
| 实收确认单 `CONFIRMED` | ✅ 是 |
| 结佣申请单 `APPROVED` / `LOCKED` | ✅ 是 |
| 仅 `PerformanceFact`（未生成单据） | ❌ 否（可被撤销级联冲销） |
| `DRAFT` / 审批中的单据 | ❌ 否（可被级联取消） |

> **设计约束**：本域**只依赖接口、不依赖实现**；若下游未部署或适配器缺失，Port 默认返回 `consumed = true`（**保守拒绝**），宁可不撤也不误撤。

#### 5.6.4 与 SUPERSEDED 的区别

| | 触发场景 | 旧批次 | 新批次 | 状态 |
|---|---|---|---|---|
| **SUPERSEDED** | 重复导入**同一 `period`** | 保留 + `superseded_by_batch_id` 回填 | **自动**建立 | 旧批次仍 `ARCHIVED`，靠过滤隐藏 |
| **REVOKED（本节）** | 归属月（`period`）**选错** | `REVOKED` 终态 | **需人工重新导入**（可换月） | 旧批次 `REVOKED` |

| 维度 | SUPERSEDED | REVOKED |
|---|---|---|
| 本质 | 被新数据取代 | 主动作废 |
| 状态字段 | `superseded_by_batch_id` | `status = REVOKED` |
| RawData | 保留 | 保留 |
| 是否发布事件 | 否（V1 不发布） | **是**（`import.revoked`） |
| 下游处理 | 自行过滤 | 消费事件级联处理 |

#### 5.6.5 撤销后的重新导入

以**正确归属月**重新导入：

- 新批次 `period` = 正确月份；若该月已有 `ARCHIVED` 批次 → 走 **SUPERSEDED**（§5.5）
- 被撤销批次的 `period`（错误月份）因状态为 `REVOKED`，**不占用** `uk_import_batch_type_period_dept` 唯一索引（见 §6.1 索引 `WHERE` 条件已排除 `REVOKED`）
- 下游重新消费新批次，按正确月份生成单据

#### 5.6.6 已生效下游单据的处置（本域只拒绝，不处理）

若校验②不通过，本域**拒绝撤销并给出明细**，由用户先到下游域处理：

| 下游状态 | 处置（在 performance / commission 域） |
|---|---|
| 实收 `CONFIRMED`（尚未结佣） | 先作废确认单 → 再回来撤销批次 |
| 结佣 `APPROVED` / `LOCKED` | **不可撤销**；业绩错误一律走**调整单 / 退单红冲** |

> **底线：已审批、已发工资的月份永不回改。** 导入撤销仅适用于"数据尚未流入下游生效单据"的情形。
> 本域**不提供**"强制撤销"开关 —— 避免绕过内控。

| **★ 部分数据被下游引用（V2.1）** | 当前：**整批拒绝撤销** | 另一做法：允许撤销未引用部分，但会造成批次内数据不一致、溯源困难 |
| **`BatchConsumptionQueryPort` 实现方** | performance 域 | V2.1 需与 performance 域约定适配器交付时序（CR-I1） |
