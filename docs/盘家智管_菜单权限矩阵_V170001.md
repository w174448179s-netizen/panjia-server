## 一、问题根因：为什么「按钮配置的链接都是错的」

### 1.1 现象

「我的任务 → 我的待办」点【去处理】，跳转到了 **工作流 → 流程定义列表页**（`/workflow/processDefinition/index`），而不是对应的业务单据页面，业务流程完全走不下去。

### 1.2 链路原理

前端跳转链路只有三跳，问题出在第一跳的数据源：

```
taskWaiting.vue / myDocument.vue
   └─ workflowCommon.routerJump({ businessId, taskId, type, formCustom, formPath })
        └─ router.push({ path: formPath, query: { id, type, taskId } })
             └─ 业务页 onMounted → openFromWorkflow() 读 route.query
```

其中 `formPath` 来源于 **`flow_definition.form_path`**（节点级 `flow_node.form_path` 覆盖优先，实测全为 NULL）。
所以 `form_path` 必须等于 `sys_menu` 算出来的真实路由，路由拼接规则为：

> **父菜单 path + '/' + 子菜单 path**（`src/store/modules/permission.ts:114`）

### 1.3 真实根因：V100006 修过，但被 4 条高版本脚本覆盖回去

`V100006__fix_workflow_form_path_and_menu_perms.sql` 的内容是**正确的**，但它跑在 `installed_rank = 7`。
实测 `flyway_schema_history` 显示：**全部 29 条迁移在同一分钟内一次性执行完毕**，V100006 之后还有 22 条迁移，其中 4 条把它的成果覆盖回去：

| 覆盖者 | rank | 被覆盖的内容 |
| --- | --- | --- |
| `V120006__pj_import_template_menu_v2.sql` | 17 | 重插「模板管理」(2510)，`parent_id` 写回 系统管理(1) → 财务/人事菜单树再次断裂 |
| `V140002__pj_perf_init.sql` | 23 | 重插 `perf_adjust` / `perf_received`，`form_path` 写回占位错误值 |
| `V140003__pj_perf_menu.sql` | 24 | 重插空壳顶级目录「数据管理」(2530)—— V100003、V100006 都删过它 |
| `V150001__pj_commission_init.sql` | 26 | 删旧建新 `commission_apply`，`form_path` 写回占位错误值 |

**净结果（V170001 执行前实测）：**
- `form_path` 7 条中 **3 条**仍指向 `/workflow/processDefinition/index`
- 顶级空壳目录「数据管理」复活，侧边栏多一个点不开的空目录
- 菜单树断裂 **2 条**（财务、人事各 1 条，均为「模板管理」无父目录）

### 1.4 关键结论（固化为规范）

> Flyway 按**版本号升序**执行，`out-of-order: true` 只允许「补执行」低版本，**不会重排顺序**。
> 后执行的脚本会覆盖先执行的结果。**任何修正脚本必须放在版本号最大处**，否则会被后续种子脚本静默覆盖。

因此 V170001 置于段位 17（> 现有最大 160002）。
（2026-09-14 更新：原置于脚本末尾的 `DO $$` fail-fast 守卫块已按用户决策移除——
权限后续会通过界面持续调整，硬编码断言会在调整后误伤启动；`validate-on-migrate` 已同步关闭。）

## 四、「审核时看不清在审什么」的成因与处置

### 4.1 成因一：待办列表只有流程名，没有业务信息

原「我的待办」只有 `flowName` + `businessId`，看不出审的是哪份合同、哪个账期、多少钱。

**处置（前端）** —— `src/views/workflow/task/taskWaiting.vue`：

1. 新增「待办事项」列：`<biz-tag>业务类型</biz-tag>` + 「业务明细」+ 「单号」
2. 新增业务类型快捷切换 Tab（全部 / 结佣审批 / 结佣调整 / 业绩调整 / 实收审批 / 奖金录入 / 算薪批次 / 补发单），按 `flow_code` 过滤
3. 新增「当前环节」列：节点名 + 流程名双行展示，一眼看清「我要做什么」
4. 「去处理」按钮图标改 `EditPen`，语义从「查看」变「处理」

### 4.2 成因二：`businessTitle` 后端从未写入

`FlowTaskVo` / `FlowHisTaskVo` 有 `businessCode` / `businessTitle` 字段，`FlwTaskMapper.getListRunTask()` 也确实 `LEFT JOIN flw_instance_biz_ext` 取这两个字段 —— 但业务侧发起流程时**没有传 `bizExt`**，导致列表里永远是空的，前端只能退化显示流程名。

**处置（后端）** —— 4 个 Service 补 `buildBizExt()`，格式统一为 `业务类型｜主键信息｜账期｜金额`：

| 模块 | Service | 目标流程 |
| --- | --- | --- |
| panjia-commission | `CommissionApplicationService.java:759` | `commission_apply` |
| panjia-commission | `CommissionAdjustService.java:251` | `commission_adjust` |
| panjia-performance | `PerformanceAdjustServiceImpl.java:438` | `perf_adjust` |
| panjia-performance | `ReceivedApplyServiceImpl.java:365` | `perf_received` |

示例（实收审批）：

```java
private FlowInstanceBizExtDTO buildBizExt(ReceivedApply apply) {
    FlowInstanceBizExtDTO bizExt = new FlowInstanceBizExtDTO();
    bizExt.setBusinessId(String.valueOf(apply.getId()));
    bizExt.setBusinessCode(text(apply.getApplyNo()));
    bizExt.setBusinessTitle("实收审批｜" + text(apply.getContractNo())
        + " " + text(apply.getPropertyAddress())
        + "｜账期" + text(apply.getPeriod())
        + "｜实收" + text(apply.getReceivedAmount()));
    return bizExt;
}
```

> 落库路径：`workflowService.startCompleteTask(start)` → LiteFlow `startPrepareInstance` 组件
> → `flw_instance_biz_ext`。`businessCode` 非空时原样保留（不用时间戳兜底）。
> **编译验证**：`./mvnw -o -pl panjia-modules/panjia-commission,panjia-modules/panjia-performance -am compile` → `EXIT=0`。
> **数据现状**：`flw_instance_biz_ext` 当前 0 行、`flow_instance` 0 行、`flow_task` 0 行 —— 尚无任何流程实例跑过，故**无需回填存量数据**；新发起的单据自动带出。

### 4.3 成因三：业务页收到审批入参后不打开单据

即使 `form_path` 修好，若业务页不解析 `route.query`，跳过去也只是一个空白列表。

**处置（前端）** —— 7 个业务页统一实现 `openFromWorkflow()`，`onMounted` 时读取 `route.query.id / type / taskId`：

| 业务页 | 路由 | 状态 |
| --- | --- | --- |
| `commission/apply/index.vue` | `/performance/apply` | 已有 |
| `commission/adjust/index.vue` | `/performance/adjust` | 已有 |
| `performance/adjust/index.vue` | `/performance/adjustment` | 已有 |
| `payroll/batch/index.vue` | `/payroll/batch` | 已有 |
| `payroll/bonus/index.vue` | `/payroll/bonus` | 已有 |
| `payroll/adjust/index.vue` | `/payroll/adjust` | 已有 |
| **`performance/received/index.vue`** | `/performance/received` | **本次补齐** |

`performance/received/index.vue` 本次四处改造：

1. **顶部审批态提示条**：`flowType === 'approval'` 时显示 `申请单号 | 合同号 · 房源 · 账期 · 实收金额`，滚动表格时仍能确认在审什么
2. **详情补字段**：新增「发起人 / 审批人 / 审批时间」，移除与明细表重复的「明细数」
3. **底部按钮按态分流**：审批态走工作流（`useWorkflowTask().passTask / rejectTask(taskId)`），**不再调用业务接口** `receivedApi.approve/reject` —— 避免越权与状态错位
4. **`script` 补依赖**：`useRoute`、`useWorkflowTask`、`flowType` / `flowTaskId` 状态、`handleFlowPass` / `handleFlowReject` / `openFromWorkflow`

### 4.4 审批态入参契约（三页对齐后固化）

| 参数 | 来源 | 含义 |
| --- | --- | --- |
| `id` | `flow_instance.business_id` | 业务主键 |
| `type` | `taskWaiting.vue` 传 `approval`；`myDocument.vue` 传 `view` / `update` | 打开模式 |
| `taskId` | `flow_task.id`（审批态）/ `flow_instance.id`（视图态） | 工作流任务 ID |

- `type = 'approval'` → 打开详情 + 底部「通过 / 驳回」
- `type = 'view'` → 打开详情只读，底部「关闭」
- `type = 'update'` → 进入编辑（仅 `draft / cancel / back` 状态单据提供）

## 六、后续新增迁移的强制约定

1. **凡 `INSERT / UPDATE` `flow_definition.form_path`，必须直接写业务页绝对路径**，不要再写 `/workflow/processDefinition/index` 占位（守卫已移除，不会再自动拦截，写错只能靠人工核对发现）。
2. **凡 `INSERT` `sys_menu` 且 `parent_id` 指向某个目录，必须同时确认该目录已被相关角色绑定**，否则子菜单整枝不可见。
3. **禁止新建无子菜单的顶级 M 目录**。
4. **修正类脚本一律用高段位**（≥ 17），不要依赖低段位脚本「跑得早就能生效」。
5. **不要写 `U*.sql` 回滚脚本**（Flyway 社区版不识别 U 前缀，保留的唯一后果是被人手动误执行）。

## 七、遗留清单（需产品/后续迭代确认）

| # | 事项 | 影响 | 建议 |
| :-: | --- | --- | --- |
| 1 | `bonus_apply` / `payroll_batch` / `payroll_supplement` 三条流程「已发布未接线」 | 流程定义存在、`form_path` 已修好，但 Java 侧无 `startCompleteTask` 调用方，点不进去也发不起来 | 业务侧补发起入口（`panjia-payroll` 模块内），接上即可正常跳转 |
| 2 | 店长持有 `commission:apply:add / submit / cancel` | V4.6 未明确授予店长「发起结佣」，但后端 `@SaCheckPermission` 强制校验，贸然删除会让店长点击即 403 | 产品确认后，连同前端按钮显隐一起改 |
| 3 | 总监挂着整套「系统管理」（12 子项） | 越权面较大，但总监 = 廖明 是本租户实际管理者，直接摘除有锁死风险 | 拆出独立「系统管理员」角色，再逐步摘除 |

| 6 | 经纪人持有 `commission:apply:query` / `commission:item:list` 两个按钮权限，但未授权其父页面「结佣申请」(2202) | F 按钮不参与侧边栏渲染，但若这两个权限被其它页面复用则有效，否则为悬空授权 | 若「我的佣金明细」确需独立入口，应新增经纪人专用页面而非挂 2202 之下 |
