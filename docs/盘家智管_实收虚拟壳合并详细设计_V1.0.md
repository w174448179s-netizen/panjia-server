# 实收虚拟壳与真实实收合并（作废重开 + 虚拟行回绑）详细设计 V1.0

> 适用范围：实收域（panjia-received）与业绩调整联动（panjia-performance）
> 触发场景：新签调整先执行、真实实收后到账，导致「同一合同同一归属月」出现虚拟实收壳 + 真实实收壳两条实收
> 文档状态：待评审

---

## 1. 背景与问题

### 1.1 现象

测试环境订单 `100015671805`（合同号 `100015671805`，真实订单号 `14567723`）在实收列表出现两笔实收：

| 时间 | 来源 | 合同壳 ID | 订单号 | 实收金额 | 审批单 |
|---|---|---|---|---|---|
| 2026-10-31 21:25:28 | 新签调整联动（MANUAL） | 2116521943131762689 | 100015671805（合同号） | 0.00 | RCV20261031212529025（0 元 APPROVED） |
| 2026-10-31 21:26:04 | 贝壳实收导入（KE_RECEIVED） | 2116522090603491331 | 14567723 | 2927.11 | 无（待匹配新签） |

虚拟壳下 8 条虚拟明细净额 0（`A 减 / B 增`），真实壳下 8 条真实到账明细合计 2927.11。

### 1.2 根因链

1. **订单号口径不一致**：新签导入（含新签调整）使用 `order_no = 合同号`，贝壳实收导入使用真实订单号 `14567723`。
2. **虚拟壳污染退化闸门**：[ReceivedContractMapper.countDistinctOrderNos](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/mapper/ReceivedContractMapper.java#L27-L35) 把虚拟壳的 `order_no=合同号` 也计入，导致该合同实收侧去重订单号 = 2，[双侧闸门](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/service/impl/ReceivedApplyServiceImpl.java#L1534-L1553) 判定不唯一 → 拒绝按合同号退化匹配 → 真实到账匹配不到新签应收 → 不建审批单，变「待匹配新签」。
3. **0 元单作废逻辑按 order_no 精确命中**：[ReceivedApplyServiceImpl.autoCreateForReceivedBatch](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/service/impl/ReceivedApplyServiceImpl.java#L710-L728) 只处理 `order_no` 相同的 0 元单。本单场景虚拟单 `order_no=100015671805`、真实分组 `order_no=14567723`，命中失败 → 0 元单未作废、真实单未创建。
4. **导入壳查找只认同来源**：[ImportToReceivedServiceImpl.loadExistingContracts](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/service/impl/ImportToReceivedServiceImpl.java#L374-L400) 按 `source_type=KE_RECEIVED` 过滤，永远看不到 MANUAL 虚拟壳 → 必然新建第二个壳。

### 1.3 本次方案

采用「**作废重开 + 虚拟行回绑**」：真实实收到账时复用虚拟壳，作废 0 元审批单并按正常流程重建真实审批单，再把虚拟调整行回绑到新单。最终形态：

- `pj_received_contract`：1 条（KE_RECEIVED，真实订单号）
- `pj_perf_received_apply`：1 条 APPROVED（或按金额分流为 SUBMITTED），实收 2927.11、应收 2742.20
- `pj_received_detail`：16 条 ACTIVE（8 条真实 + 8 条虚拟调整），合计 2927.11，人员/角色口径保留新签调整结果
- `pj_perf_received_adjust`：保留 `ADJ20261031262748` 镜像单，追溯不变

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 |
|---|---|
| G1 | 同一合同 + 同一 period 下，纯虚拟 MANUAL 壳与真实 KE 实收到账合并为一个合同壳 |
| G2 | 0 元联动审批单作废，真实到账按既有分流规则重建审批单（自动通过 / 转人工） |
| G3 | 虚拟调整行回绑到新审批单，保证人员与金额口径不丢 |
| G4 | 重导幂等、批次撤销、后续新签调整均不被破坏 |
| G5 | 生产无存量重复；测试环境存量单可安全修复 |

### 2.2 非目标（明确不做）

- **同合同多订单不自动合并**：订单维度不唯一时继续分单/人工，禁止按合同号盲并。
- **跨归属月不合并**：不同 `period` 的虚拟壳与真实壳保持独立，避免跨月串账。
- **不回溯结佣**：已人工发起结佣的历史单不回滚、不重算。
- **不改变新签导入的订单号口径**：本次不修新签导入映射，只做实收侧兼容（另立需求）。
- **不新增数据库表/索引**。

## 3. 关键概念与数据约束

### 3.1 纯虚拟壳判定

一条 MANUAL 合同壳满足以下全部条件时，视为「纯虚拟壳」：

1. `source_type = 'MANUAL'`
2. `order_no = contract_no`（新签联动建壳特征）
3. 其全部 ACTIVE 明细满足：`source_batch_id IS NULL`、`normalized_record_id IS NULL`、`adjust_id IS NOT NULL`
4. 其全部 ACTIVE 明细金额合计 = 0

> 任一条件不满足 → 不进入自动合并，保持现状并记录告警，交人工处理。

### 3.2 唯一约束

| 索引 | 定义 | 影响 |
|---|---|---|
| `uk_received_contract_anchor` | `(order_no, period, source_type)` | 壳复用需改 `order_no`/`source_type`，可能撞键，必须捕获 |
| `uk_received_detail_anchor` | `(source_key) WHERE detail_status='ACTIVE'` | 虚拟行 `source_key` 含 `MANUAL-RADJ`，与真实行不撞 |
| `uk_rapp_period_order` | `(period, order_no) WHERE status IN ('DRAFT','SUBMITTED','APPROVED') AND apply_no NOT LIKE 'TD%'` | 作废 0 元单后释放键，再建真实单 |
| `uk_rapp_period_order` 补充 | V140016 起排除 `TD%` 退单冲减单 | 退单单可与正常单并存，不影响本次 |

## 4. 合并判定规则

导入时对每个「订单号（缺失退合同号）」分组，执行以下判定：

```
canMerge(group, virtualShell, realShell):
  1. virtualShell 必须是纯虚拟壳（§3.1）
  2. virtualShell.period == 本次导入 period
  3. virtualShell.contract_no == group.contract_no
  4. 该合同在「排除纯虚拟壳后」的实收去重订单号 == 1（即真实订单唯一）
  5. group.order_no 等于该唯一真实订单号
  6. 该 period + 真实订单号不存在活跃审批单（若有则直接复用该单，不再新建）
  7. 该 period + 合同号不存在结佣申请（有则跳过合并，走人工）
```

任一条不满足：不做合并，保持原逻辑（可能产生第二壳，但不会串单）。

## 5. 总体流程

### 5.1 新数据（导入顺序：先调整、后到账）

```
[新签调整执行]
  └─ 合同无实收 → 建 MANUAL 虚拟壳(order_no=合同号) + 虚拟明细(净额0)
  └─ autoCreateApprovedForAdjust → 0 元 APPROVED 审批单（绑定虚拟行）

[贝壳实收导入 ImportBatchArchivedHandler]
  ├─ consumeBatch(KE_RECEIVED)
  │    ├─ 阶段2.0：加载同期间 KE 壳 + MANUAL 壳
  │    ├─ 命中纯虚拟壳 → 复用并重键：order_no=真实订单号, source_type=KE_RECEIVED, batch_id=新批次
  │    ├─ 若 KE 壳与 MANUAL 壳并存 → 合并（虚拟行迁到 KE 壳，删空壳）
  │    ├─ 写入真实明细
  │    └─ 重算合同聚合
  └─ autoCreateForReceivedBatch
       ├─ 按退化闸门匹配新签应收 2742.20
       ├─ 命中 0 元 APPROVED 单 → 收集虚拟行 → 作废该单
       ├─ 按金额/人数分流 → 新建 APPROVED 或 SUBMITTED 真实单
       ├─ 绑定真实行 + 回绑虚拟行 → item_count 合并
       └─ 自动通过时发 ReceivedApprovedEvent（0 元单从未发过）
```

### 5.2 存量已双壳（如测试单）

优先「**撤销实收批次 → 重新导入**」，让新代码走一遍合并流程；不满足条件时使用 §8 的兜底 SQL。

## 7. 幂等、撤销与结佣影响

### 7.1 重导幂等

- 组指纹 [dbFingerprints](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/service/impl/ImportToReceivedServiceImpl.java#L592-L605)：
  - 人员/角色/费项只取 `normalized_record_id != null` 的真实行；
  - 合计取全部 ACTIVE 行（虚拟净额 0）。
- 结论：文件未变时指纹稳定命中，不会因虚拟行反复重写。

### 7.2 批次撤销

- 撤销按 `source_batch_id` 删除真实行，虚拟行（无批次）保留。
- 合并后的审批单含「批次行 + 虚拟行」，撤销时走 [ReceivedRevokedHandler](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/listener/ReceivedRevokedHandler.java#L198-L235) 的「合并单重算」分支：审批单保留并重算为虚拟行合计（0 元），等于回到未到账前状态。
- 合同仍有虚拟明细 → 不被删除；聚合重算为 0。

### 7.3 结佣

- 0 元联动单 [autoCreateApprovedForAdjust](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-received/src/main/java/com/panjia/received/service/impl/ReceivedApplyServiceImpl.java#L539-L554) 直接 INSERT，**不发** `ReceivedApprovedEvent`，不会误发结佣。
- 真实审批单 APPROVED 时照常发事件；二手买卖在 [ReceivedApplyApprovedHandler](file:///Users/shengwei/workspace/panjia-server/panjia-modules/panjia-commission/src/main/java/com/panjia/commission/handler/ReceivedApplyApprovedHandler.java#L47-L66) 中跳过。
- 已人工发起结佣的历史单不在本次回溯范围。

### 8.3 兜底：guarded SQL（仅测试，需先备份）

不满足 8.2 时执行，事务内按以下顺序（示例值以实际查询为准）：

```sql
BEGIN;

-- 2) 真实行回绑现有 0 元单（存量直接归并；未来新数据由代码作废重开）
UPDATE pj_received_detail
SET received_apply_id = 2116521943341477889,
    update_time = CURRENT_TIMESTAMP
WHERE contract_id = 2116522090603491331
  AND received_apply_id IS NULL
  AND detail_status = 'ACTIVE';

-- 3) 审批单归并：订单号改真实、金额取真实到账、条数合并
UPDATE pj_perf_received_apply
SET order_no = '14567723',
    received_amount = 2927.11,
    expected_amount = 2742.20,
    item_count = 16,
    update_time = CURRENT_TIMESTAMP
WHERE id = 2116521943341477889;

-- 4) 合同壳收口
UPDATE pj_received_contract SET received_apply_id = 2116521943341477889
WHERE id = 2116522090603491331;

DELETE FROM pj_received_contract
WHERE id = 2116521943131762689
  AND NOT EXISTS (SELECT 1 FROM pj_received_detail d WHERE d.contract_id = 2116521943131762689);

-- 5) 重算聚合
UPDATE pj_received_contract c
SET period_total_received = COALESCE(a.total, 0),
    item_count = COALESCE(a.cnt, 0),
    update_time = CURRENT_TIMESTAMP
FROM (
    SELECT contract_id, SUM(performance_amount) AS total, COUNT(*) AS cnt
    FROM pj_received_detail
    WHERE detail_status = 'ACTIVE' AND contract_id = 2116522090603491331
    GROUP BY contract_id
) a
WHERE c.id = a.contract_id;

COMMIT;
```

> 兜底 SQL 与代码路径的差异：存量单不新建审批单，直接归并原 0 元单（避免手工生成雪花 ID/单号）。最终业务形态一致；未来新数据走 6.2 的作废重开。

## 9. 风险与对策

| 风险 | 对策 | 残余 |
|---|---|---|
| 同合同多订单错并 | §4 第 4 条订单唯一闸门；不唯一不合并 | 多订单保持人工（设计取舍） |
| 重键撞 `uk_received_contract_anchor` | 事务内先查目标锚点；捕获 `DuplicateKeyException` 后降级为双壳合并 | 极小 |
| 作废/新建撞 `uk_rapp_period_order` | 作废后键释放；新建代码已有 `DuplicateKeyException` 兜底跳过 | 极小 |
| 跨月串账 | 只允许同 period 合并 | 跨月保持分单（设计取舍） |
| 撤销批次后单据状态异常 | 复用「合并单重算」分支；审批单保留并重算为虚拟净额 0 | 需回归 |
| 重导重复写 | 组指纹含 ACTIVE 合计；虚拟净额 0，指纹稳定 | 无 |
| 虚拟行净额非 0 | 不合并，记录问题清单，人工处理 | 需人工 |
| 后续调整挂不上单 | 6.4 增加 contractNo 回退 | 无 |
| 结佣误发 | 0 元单不发事件；真实单正常发 | 无 |
| 并发导入 | 事务 + 唯一索引 + `DuplicateKeyException` 兜底 | 极小 |

## 13. 假设与待确认

1. 「纯虚拟壳」金额必须净额 0；若业务出现净额非 0 的联动场景，需另行定义合并口径。
2. 新签导入 `order_no=合同号` 的口径本次不调整，仅实收侧兼容；后续建议单独立项修正源头。
3. 存量单采用 8.2 重放路径；若批次不可撤销，再使用 8.3 SQL。
4. 二手买卖不自动结佣；其它业务类型沿用现有事件规则。
