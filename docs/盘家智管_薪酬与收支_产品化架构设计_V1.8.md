## 一、架构设计目标与核心原则

### 1.1 产品化愿景

本产品族是"盘家智管"平台的首个业务产品族，定位为**房产中介行业通用的薪酬与经营结算引擎**。核心目标：

> **一套代码、一套数据模型，适配 N 家中介公司——从 1 家门店到 100 家门店，从简单提成到复杂多级分销，无需改代码即可上线。**

### 1.2 架构原则

| 原则 | 说明 | 落地手段 |
|------|------|----------|
| **配置驱动** | 所有业务规则外置为可配置项，适配新客户不改代码 | 职级规则表 + 规则引擎 + 参数配置中心 |
| **插件式数据源** | 不同客户的业绩数据来源各异（贝壳/安居客/自研/Excel） | 数据源适配器（SPI 机制） |
| **快照冻结** | 算薪必须"按历史时点取值"，规则变更不影响已结算月份 | 员工快照 + 职级规则快照 + 算薪版本锁定 |
| **可追溯闭环** | 每一笔工资都能追溯到原始业务事实 | 工资-结佣溯源子表 + 全链路审计 |
| **可扩展科目** | 收入项/支出项可增减，不 ALTER 主干表 | 分项列 + 扩展科目表（双轨制） |
| **顶层域独立** | 每个业务主题（员工/业绩/结佣/结算）是独立顶层模块 | `panjia-{domain}` 一级包 |
| **领域单向依赖** | 领域之间严格单向依赖，无环；新增域只增不改造型 | 领域包结构 + 架构图 + CI 依赖校验 |
| **计算与结果分离** | 算薪引擎只算"金额"，不负责"存储/状态/审批" | `CalculationEngine → CalculationResult → PayrollResult` |
| **进程内事件协作** | V1 用 Spring 进程内事件解耦域；Outbox 保证可靠性 | `ApplicationEvent` + Event Outbox 表 |
| **命名与归属一致** | 包名、表前缀、领域名三者归属一致 | 命名规约 + CI 校验（见 §2.5） |

### 1.3 适配范围矩阵

| 维度 | 当前客户（盘家·富房） | 典型目标客户 A（中型连锁） | 典型目标客户 B（大型集团） |
|------|---------------------|------------------------|------------------------|
| 门店数 | 6 家 | 20~50 家 | 100+ 家 |
| 职级体系 | A0~A5 + S1/S2 + 总监 | 可能自定义（如 L1~L10） | 多品牌、多体系并存 |
| 业绩来源 | 贝壳（理房通） | 贝壳 + 自研 + 其他平台 | 多平台聚合 |
| 提成规则 | 固定比例 + 绩效扣点 | 跳点 + 阶梯 + 团队池 | 规则表 + 计算器策略 |
| 社保口径 | 固定基数 1637.15 | 各地差异 | 多地区、多政策 |
| 审批流程 | 简单通过/驳回 | 多级审批 | 流程编排 |
| 部署方式 | 单租户独立实例 | 单租户 / 私有化 | 单租户独立实例 |

### 1.4 部署形态

- **一客户一实例一数据库**：每个客户独立 Docker Compose 部署，独立 PostgreSQL 库，物理隔离
- **不引入 `tenant_id`**：V1 业务表不加 `tenant_id` 字段；部署身份即隔离边界
- **未来演进**：若演进为多租户 SaaS，再统一引入 `tenant_id`、重构唯一索引、加 RBAC tenant scope；事件契约中预留 `tenantId()` 方法，发布方无需改动

## 二、整体架构：顶层业务域划分

### 2.1 业务事实链路

```
贝壳 Excel
   ↓（导入域）
原始记录 → 归一化记录
   ↓（业绩域）
业绩事实（确认/折算）
   ↓（结佣域）
结佣申请 → 审批 → 结佣锁定（快照）
   ↓（薪酬结算域）
算薪 → 工资批次 → 锁定/发放
   ↓（经营结算域，事件驱动）
收入/支出/部门台账/利润
```

这条链路决定领域依赖方向（§2.3）：下游域只依赖上游域的**事实接口**，不依赖其内部实现。

### 2.2 顶层业务域划分

> **命名约定**：`panjia-{domain}` 为顶层业务域，`{domain}-` 前缀为子包/子组件。所有表前缀统一为 `pj_{domain}_*`。

### 2.3 顶层域职责定义

| 顶层域 | 包路径 | 核心职责 | 输入 | 输出 | 直接依赖 |
|--------|--------|---------|------|------|---------|
| **员工域** `panjia-people` | `panjia-modules/panjia-people/`（传统三层） | 员工主数据 + **算薪事实**（salary_fact，一项一条，闭开区间）；工号、入职/离职、职级、社保/公积金/商业/宿舍开关、师徒关系；Excel 导入建员工+部门树+账户+岗位+角色 | Excel 导入文件 / 手工变更 | `EmployeeId` + `EmployeeSnapshot`（contracts）+ 时点算薪事实查询 Port | 无（被所有域依赖）；经 `port/AccountPort` 等协作 RuoYi（Adapter 实现） |
| **导入域** `panjia-import` | `panjia-modules/panjia-import/` | 多源数据导入：Excel → 原始归档 → 归一化为 `NormalizedRecord` | Excel 文件 / API 流 | `ImportBatch` + `NormalizedRecord` | people |
| **业绩域** `panjia-performance` | `panjia-modules/panjia-performance/` | 消费 `NormalizedRecord` → 生成业绩事实；业绩口径/折算/确认 | 导入域 `NormalizedRecord` | `PerformanceFact`（确认后的业绩事实） | people、import |
| **结佣域** `panjia-commission` | `panjia-modules/panjia-commission/` | 结佣申请、审批（Warm-Flow）、结佣锁定、工资-结佣溯源、调整/补发 | `PerformanceFact` | 锁定的结佣事实 + 溯源记录 | performance、people |
| **薪酬结算域** `panjia-payroll` | `panjia-modules/panjia-payroll/` | ⭐ 算薪引擎（计算）、工资批次（状态机）、计算器插件、负工资结转、锁定/调整/补发 | 结佣事实 + `EmployeeSnapshot` + 规则快照 | `CalculationResult → PayrollResult → PayrollBatch/PayrollDetail` + `PayrollLockedEvent` | **people、commission**（仅此两个） |
| **经营结算域** `panjia-ledger` | `panjia-modules/panjia-ledger/` | 收入/支出科目、部门收支台账、营业利润、经营分析底座 | `PayrollLockedEvent`（Outbox 投递） + 费用导入 | `DeptLedger`、`IncomeExpense`、利润汇总 | contracts（事件契约） |
| **协作契约层** `panjia-contracts` | `panjia-modules/panjia-contracts/` | 跨域事件契约、共享 ID/Snapshot/DTO；不含业务逻辑与持久化 | — | 接口与记录类型 | 无 |

> **payroll 依赖收敛**：`panjia-payroll` **只直接依赖 `people` 与 `commission`**。它通过 `commission` 获取已准备好的结佣事实，不再穿透依赖 `performance` / `import`。`Employee` 聚合根不离开 people 域——payroll 只接收 `EmployeeSnapshot`（历史冻结值）。

**依赖铁律（架构红线）：**

| 规则 | 说明 | 违反（CI 拦截） |
|------|------|------|
| 顶层域间依赖必须单向 | 不允许 A → B → A 的环 | 编译期包结构 + 依赖图校验 |
| 高层域不得反向依赖低层 | payroll 不能依赖 import 的内部类型 | CI 依赖图校验 |
| 业务域禁止 import 其他域的 `domain` 聚合根 | 只允许经 `contracts`（Id/Snapshot/DTO/Event） | 静态检查报错 |
| `Employee` 聚合根不得离开 people 域 | payroll/performance 等只接收 `EmployeeSnapshot` | 静态检查报错 |
| ledger 只依赖 contracts | ledger 不得 import payroll/commission 的具体类 | CI 依赖图校验 |
| 业务域禁止直接 import `panjia-license` / `panjia-backup` 具体类 | 只允许经 Port 接口 | 静态检查报错 |
| people 不依赖任何业务域 | 它是根 | 违反即架构错 |

### 2.5 命名规约与 CI 校验

| 规约 | 规则 | 示例 |
|------|------|------|
| 包命名 | 顶层域 = `com.panjia.{domain}`，子组件 = `com.panjia.{domain}.{component}` | `com.panjia.payroll.domain` |
| 表前缀 | 所有业务表 = `pj_{domain}_*`，快照归属计算域 | `pj_payroll_batch`、`pj_payroll_employee_snapshot` |
| 领域事件 | `{Domain}{Action}Event`，定义在 `panjia-contracts` | `PayrollLockedEvent` |
| 跨域数据 | 只通过 `Port` / `Id` / `Snapshot` / `DTO` / `Event`；禁止跨域 import 聚合根 | CI 扫描 |
| 快照归属 | 历史冻结快照按其**消费域**命名，不按主数据域 | `pj_payroll_employee_snapshot`（非 `pj_people_*`） |

**CI 校验脚本：**
- `check-domain-deps.sh`：解析各域 `pom.xml` / `build.gradle` 依赖 + Java import，断言依赖图 = §2.4 定义图（含禁止 import 聚合根规则）

- `check-event-payload.sh`：扫描 `*Event.java`，断言字段不含其他域的 `@Entity` 类型
- `check-snapshot-owner.sh`：断言快照表归属其消费域（如 `employee_snapshot` 只能属于 `pj_payroll_*` / `pj_commission_*`）

### 2.6 模块命名域与依赖

包命名遵循 `panjia-*` 顶层域规约，`ruoyi-*` 为底座内核（原则上零 diff）。`panjia-contracts` 为纯接口模块，不含业务逻辑与持久化。CI 守卫：

- `ruoyi-*` 目录不得出现 `com.panjia` 包

新增顶层域（`panjia-people` / `panjia-performance` / `panjia-commission` / `panjia-payroll` / `panjia-ledger`）已纳入 CI 依赖图与表前缀白名单校验。

> **关于未来房源/客源域**

## 三、协作契约层（panjia-contracts）

### 3.1 定位

跨域协作需要共享的类型（事件、ID、只读快照）集中放在 `panjia-contracts`。它是**所有业务域共同依赖的叶子模块**，自身不依赖任何业务域、不含业务逻辑与持久化。

```
                 ┌──────────────────────┐
                 │  panjia-contracts    │
                 │  （协作契约层 · 叶子） │
                 └──────────┬───────────┘
                            ▲
                ┌───────────┼───────────┐
                │           │           │
            payroll      ledger     commission ...
              （均依赖 contracts，contracts 不依赖任何域）
```

### 3.2 事件契约

```java
// panjia-contracts/event/DomainEvent.java
public interface DomainEvent {
    String eventType();
    long businessId();
    default Long tenantId() { return null; }  // V1 未启用；预留，发布方无需改动
}

// panjia-contracts/event/PayrollLockedEvent.java
public record PayrollLockedEvent(
        long batchId,
        Long tenantId,                    // V1 恒为 null
        Map<Long, BigDecimal> deptCostMap // 部门 → 人工成本
) implements DomainEvent {
    @Override public String eventType() { return "payroll.locked"; }
    @Override public long businessId()   { return batchId; }
}
```

> **payload 约束**：事件字段只用基础类型、`Id`、不可变 `record` 与 `Snapshot`；**禁止**持有其他域的 `@Entity`。这保证事件契约与发布/订阅双方可独立演化。

### 3.3 跨域只读类型

| 类型 | 定义位置 | 用途 | 不可做的操作 |
|------|---------|------|------------|
| `EmployeeId` | contracts | 强类型员工标识，替代裸 `Long` | — |
| `EmployeeSnapshot` | contracts | 某业务过程冻结的员工历史状态 | 不可回写 people 域 |
| `BatchId` / `CommissionOrderId` | contracts | 强类型业务标识 | — |

> **契约精度要求（V1.8 补充）**：`EmployeeId` 与 `EmployeeSnapshot` 的定义必须**精确到字段级别**，下游域（payroll / commission）据此编码，避免字段口径不一致。**`EmployeeSnapshot` 只含员工事实字段**（身份、职级、社保开关、师徒关系等），**不含算薪规则参数**（社保基数/比例、公积金金额/比例、兼职豁免等均归 payroll 客户级规则，见 §10.6、§10.9）。

### 3.4 Snapshot 的归属规则

- **主数据（当前状态）** 归其所在域：`Employee` 归 people 域（`pj_people_employee`）
- **历史冻结快照（某次业务过程的时点副本）** 归**消费域**：算薪时冻结的员工快照归 payroll → `pj_payroll_employee_snapshot`；结佣时冻结的归 commission → `pj_commission_employee_snapshot`

> **理由**：员工"当前状态"与"某月算薪时的历史状态"是不同概念。快照由消费域拥有，主数据域（people）不承担所有消费者的历史版本，避免 people 域随业务域膨胀。

## 四、数据导入架构

> **理由**：员工"当前状态"与"某月算薪时的历史状态"是不同概念。快照由消费域拥有，主数据域（people）不承担所有消费者的历史版本，避免 people 域随业务域膨胀。


**`EmployeeSnapshot` 字段契约（完整定义见 §10.6）：**

| 分类 | 字段 |
|------|------|
| 身份（事实） | `employeeId` / `employeeCode` / `employeeName` / `userId`（可 null）/ `deptId` / `isPartTime` / `employeeRole` |
| 职级（时点生效） | `levelCode` / `baseSalary` / `personalRatio` / `companyRatio` |
| 社保（事实） | `socialBase` / `housingFund` / `commercialInsuranceAmount` / `dormitoryFee` |
| 师徒（师傅视角） | `mentorId` / `qualifiedApprenticeCount` |
| 快照元数据 | `snapshotDate` / `snapshottedAt` / `snapshotVersion` |

> **事实字段 vs 规则字段分离**：快照只携带**员工事实**（如 `isPartTime`、`socialBase`）；"兼职是否豁免商业保险/宿舍费"等**业务规则**归算薪域 `RuleSnapshot`（见 §5.3 `rule_content` JSONB），**不进快照**。这样规则变更不影响历史月份复现。

## 四、数据导入架构

### 4.1 为什么导入要独立

业务高度依赖贝壳 Excel，且贝壳模板/格式会变更。若导入塞进薪酬域，会导致：

- 薪酬域耦合"Excel 解析"细节
- 贝壳格式变更 → 影响算薪（不该是这样的耦合方向）
- 导入与业务域耦合，不利于独立开发与测试

**结论**：导入是独立顶层域 `panjia-import`，负责"把任意来源的裸数据变成归一化记录"；**不负责把数据变成业务事实**——那是下游域的职责。

### 4.2 导入数据链路

```
                    ┌─────────────────────────────────────────┐
                    │           panjia-import（导入域）         │
                    └─────────────┬───────────────────────────┘
                                  │
          ┌────────────┬───────────┼───────────┬────────────┐
          ▼            ▼           ▼           ▼            ▼
     ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
     │ 贝壳Excel│ │ 考勤Excel│ │ 积分Excel│ │ 费用Excel│ │ 手工录入 │
     │ 适配器   │ │ 模板引擎  │ │ 模板引擎  │ │ 模板引擎  │ │ 兜底录入 │
     └────┬────┘ └─────┬─────┘ └────┬─────┘ └────┬─────┘ └─────┬─────┘
          └────────────┴─────┬──────┴────────────┘            │
                               ▼                               │
                    ┌───────────────────────────────────────┐  │
                    │  RawData（原始数据，只读归档）          │  │
                    │  • 文件原文存 S3/MinIO（防篡改）        │  │
                    │  • 解析结果存 pj_import_raw_*（不可 UPDATE/DELETE）│
                    │  • 触发器 + 应用拦截双保险              │  │
                    └──────────────┬─────────────────────────┘  │
                                   ▼
                    ┌───────────────────────────────────────┐  │
                    │  Normalize（归一化 → NormalizedRecord） │  │
                    │  • 列映射（按 pj_import_template 配置）  │  │
                    │  • 数据类型转换、空值处理、校验         │  │
                    │  • 输出：标准化结构化记录               │  │
                    └──────────────┬─────────────────────────┘  │
                                   ▼
                    ┌───────────────────────────────────────┐  │
                    │  返回 NormalizedRecord（导入域边界止步） │  │
                    └──────────────┬─────────────────────────┘  │
                                   │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
        panjia-performance               其他消费域
        （NormalizedRecord                 （按需扩展）
         → PerformanceFact）
```

**边界规则：**

| 环节 | 职责归属 | 不允许做的事 |
|------|---------|------------|
| 导入域 | Excel → RawData → NormalizedRecord | 不得构造 `PerformanceFact` / 理解业绩业务语义 |
| 业绩域 | 消费 NormalizedRecord → 生成 `PerformanceFact` | 不得解析 Excel / 依赖具体数据源格式 |

这样贝壳 Excel 模板变化**只影响 panjia-import 内部**（加一个 DataSource 实现），不影响 performance / payroll / ledger。

### 4.3 导入域核心领域对象

| 对象 | 说明 | 关键约束 |
|------|------|---------|
| `ImportBatch` | 一次导入的批次聚合（含来源类型、文件、状态、行数） | 批次级幂等；重复导入先归档旧批次 |
| `RawData` | 解析后的原始记录（保留原始字段，不做业务语义转换） | **只读**：不可 UPDATE/DELETE（触发器 + 应用拦截） |
| `NormalizedRecord` | 归一化后的标准化记录（已按模板映射、类型转换） | 无业务语义，只描述"结构化数据" |

### 4.4 与下游的契约

导入域**不依赖**任何下游域（它是最底层）。它通过**返回 `NormalizedRecord`** 供下游消费；事件发布也只使用 `contracts` 中的类型。

**架构保障**：原始导入数据只读——触发器防 UPDATE/DELETE + 应用层拦截（抛异常）+ 审计留痕，三重保险。

## 五、核心业务架构：算薪引擎

### 5.1 业务事实链与规则三层

"薪酬规则 → 规则版本 → 规则快照 → 业务单据"是本架构的核心概念。工资结果不得依赖当前规则——即不得出现"payroll 里存 `salary_rule_id`、算历史时重新读取当前规则"的反模式。

```
  薪酬规则（当前版，可变）
        │  create / update / effective_from
        ▼
  ┌─────────────────┐
  │  RankRule（当前） │  ← pj_payroll_rank_rule，含 rule_content(JSONB)
  └────────┬────────┘
           │  snapshot（结佣/算薪时冻结"当时版本"）
           ▼
  ┌─────────────────┐
  │ RuleSnapshot     │  ← 规则的时间点副本
  │ （时间点副本）    │    包含：base_salary / commission_rate /
  └────────┬────────┘      team_rate / brackets / social_insurance_*
           │  embed（算薪时内嵌进工资单，不回头查库）
           ▼
  ┌─────────────────────────────────────────┐
  │  CalculationResult（算薪结果，纯数据）     │
  │  • 每项收入金额 / 每项支出金额            │
  │  • 溯源记录（工资项 → 结佣单/业绩）       │
  │  • gross / deduct / tax / net           │
  └─────────────────────────────────────────┘
           │  assemble（组装 + 状态机推进）
           ▼
  ┌─────────────────────────────────────────┐
  │  PayrollResult（工资结果，含状态/批次）    │
  │  → PayrollBatch / PayrollDetail         │
  └─────────────────────────────────────────┘
```

> 此链属于 `panjia-payroll` 域内部，表前缀统一为 `pj_payroll_*`（见 §11 数据架构）。

### 5.2 计算与结果分离（三层）

```
  输入（均为不可变快照）：
  EmployeeSnapshot + CommissionFact + RuleSnapshot + 调整项
                          ▼
        ┌──────────────────────────────────────┐
        │  SalaryCalculationEngine（纯计算）     │  ← 无 DB 写入，纯函数式
        │  • 不可变输入 → 不可变输出             │
        │  • 易测试、可无限次重算、可模拟/差异比较│
        └────────────┬─────────────────────────┘
                     ▼
        ┌──────────────────────────────────────┐
        │  CalculationResult（纯数据，不可变）    │  ← 不含状态、不含审批
        │  • 各项金额 / 溯源 / gross-deduct-tax-net│
        └────────────┬─────────────────────────┘
                     ▼
        ┌──────────────────────────────────────┐
        │  PayrollResultAssembler（组装+状态机）  │  ← 唯一落库点
        │  • Result → PayrollBatch / PayrollDetail│
        │  • 推进状态机                          │
        └──────────────────────────────────────┘
```

| 约束 | 说明 |
|------|------|
| `SalaryCalculationEngine` 纯计算 | 不持有 DB Session，不写任何表；输入不可变，输出不可变 |
| `CalculationResult` 不可变 | 无 setter；算一次即定格，可作为审计证据 |
| `PayrollResultAssembler` 是唯一落库点 | 负责状态机推进 + 写 `PayrollBatch` / `PayrollDetail` |
| 重算 = 新建 `CalculationResult` | 不修改原结果；调整后对比用两个 Result 做 diff |

### 5.3 规则配置层级

| 层级 | 适用场景 | 存储 | V1 是否支持 |
|------|---------|------|:----------:|
| Level 1：基础参数（列化字段） | 90% 客户：底薪、基础提点、社保比例、团队提点 | `pj_payroll_rank_rule` 稳定列 | ✅ |
| Level 2：区间规则（JSON） | 阶梯提点（如 <10万6% / ≥10万7%） | `rule_content` 中的 brackets 数组 | ✅ |
| Level 3：计算器策略（SPI） | 复杂客户自定义算法 | `CommissionCalculator` SPI 实现 | ✅ |

> **V1 不提供脚本引擎**
> **规则存储单一来源（V1.7 澄清）**：**不新建** `pj_payroll_rule_config` 独立表。所有算薪参数（兼职豁免开关、徒弟奖励比例/上限、社保比例等）统一纳入 `pj_payroll_rank_rule.rule_content`（JSONB），算薪时随 `RuleSnapshot` 冻结。避免规则双轨存储。
>
> **参数分级约定（JSONB 结构）**：
> ```json
> {
>   "global": { "parttimeExemptCommercial": true, "parttimeExemptDormitory": true },
>   "level_override": { "A5": { "baseSalary": 5000 } }
> }
> ```
> - `global`：跨职级共享参数（如"所有职级兼职均免商业保险"）
> - `level_override`：按职级覆盖（如 A5 底薪 5000）
>
> **新客户接入**：仅修改 `rule_content` 种子数据，**零代码改动**。

> **V1 不提供脚本引擎**：自定义脚本（Groovy/JS）涉及沙箱、超时、CPU/文件/网络限制、类加载隔离、脚本版本与审计，复杂度高且与"配置驱动"承诺相冲突。V1 通过 **Level 1 + Level 2 + Level 3（Java SPI 计算器）** 覆盖从简单到复杂的全部场景。若未来确有客户需要任意公式，再单独设计脚本引擎子域。

### 5.4 算薪引擎内部结构

（计算器插件化、`IncomeCalculator` / `DeductionCalculator` 注册中心、人员角色策略映射、经纪人/店长/总监策略工厂，包路径为 `com.panjia.payroll.*`。）

### 5.5 人员角色与算薪策略映射

（策略模式 + 经纪人/店长/总监策略图，包路径 `com.panjia.payroll.strategy.*`。）

## 六、PayrollBatch 状态机

### 6.1 状态机定义

```
  DRAFT ──calculate──▶ CALCULATING ──success──▶ CALCULATED
                                          │
                                          └──failure──▶ FAILED ──retry──▶ CALCULATING
  CALCULATED ──submit──▶ REVIEWING ──approve──▶ APPROVED ──lock──▶ LOCKED ──pay──▶ PAID
                                                       │
                                                       └──reject──▶ CALCULATED

  调整/补发（LOCKED 后禁止直接修改）：
  LOCKED ──create adjustment/supplement──▶ 新增 Adjustment / Supplement（指向原批次，不修改原明细）
```

### 6.2 转换规则

| 当前状态 | 动作 | 目标状态 | 前置条件 |
|---------|------|---------|---------|
| DRAFT | calculate | CALCULATING | — |
| CALCULATING | success | CALCULATED | 全部员工算完且无致命错误 |
| CALCULATING | failure | FAILED | 有致命错误 |
| FAILED | retry | CALCULATING | — |
| CALCULATED | submit | REVIEWING | — |
| REVIEWING | approve | APPROVED | 审批通过（Warm-Flow） |
| REVIEWING | reject | CALCULATED | 退回修改 |
| APPROVED | lock | LOCKED | 二次确认 |
| LOCKED | pay | PAID | 发放完成 |
| 任意（含 LOCKED） | createAdjustment | （不变 + 新增调整单） | 只新增，不改原批次 |
| 任意（含 FAILED） | retry | CALCULATING | — |

### 6.3 并发控制（乐观锁）

状态转换通过**乐观锁**保证原子性，杜绝并发双写：

```sql
UPDATE pj_payroll_batch
SET status = #{target},
    version = version + 1,
    updated_at = now()
WHERE id = #{id}
  AND status = #{expected}
  AND version = #{expectedVersion}
```

- 更新行数 = 1：转换成功
- 更新行数 = 0：并发冲突，抛 `StateTransitionConflictException`，由调用方决定重试或提示

所有状态转换（含 lock/pay/retry）统一走状态机 API，禁止业务代码直接 `setStatus`。

### 6.4 状态校验与 RBAC 分离

**状态机校验 ≠ 权限校验**，两者分开：

| 维度 | 校验内容 | 实现位置 |
|------|---------|---------|
| **RBAC 权限** | 当前用户是否有权执行"算薪/锁定/发放"操作 | `@PreAuthorize` 权限表达式 |
| **领域状态** | 当前批次是否处于允许该操作的状态 | Service 内 `batch.assertCan(...)` / 状态机 |

```java
// RBAC：用 @PreAuthorize（Spring Security 权限表达式）
@PreAuthorize("@ss.hasPermi('payroll:batch:calculate')")
public void calculate(Long batchId) {
    PayrollBatch batch = repository.load(batchId);
    batch.assertCanCalculate();   // 领域状态校验：DRAFT → CALCULATING
    // ...
}
```

> **禁止**把业务状态机写进 `@PreAuthorize` SpEL 表达式（如 `@PreAuthorize("batch.status == DRAFT")`）。权限表达式只管"有没有权限"，状态合法性由领域模型自身保证——这样状态规则可单测、可复用、可演进。

### 6.5 调整与补发模型

调整/补发**不修改** `LOCKED` 批次的原始明细，而是新增单据，其自身也是一个 `CalculationResult`：

```
原工资批次  PayrollBatch #100  = 原始工资（不可变）
       │
       ├── Adjustment   #101  → CalculationResult（+500）
       └── Supplement   #102  → CalculationResult（-200）

某员工当期应发 = #100 明细 + Σ(调整/补发 CalculationResult)
```

- `Adjustment` / `Supplement` 各自走算薪引擎产出 `CalculationResult`，保证金额可复现
- 审计与财务追溯清晰：每一笔都对应一个不可变 Result
- 锁定批次的明细永远不被 UPDATE

### 6.6 负工资结转与状态机的关系

负工资结转是 **CalculationResult 计算阶段的内部逻辑**（在计算 net 时处理），不是独立状态。它产出的是 `PayrollDetail` 上的一个字段（结转余额滚存到下月），不影响 Batch 状态机。

## 七、经营结算域架构（panjia-ledger）

### 7.1 为什么收支要独立

工资**只是部门经营成本的一部分**。未来需支撑"房源收入 / 佣金收入 / 其他收入"与"人工成本 / 房租 / 水电 / 平台费用 / 招聘费用 / 其他支出"的完整经营视角。命名与职责若继续挂在薪酬下，会阻碍扩展。

**结论**：命名为 **`panjia-ledger`（经营结算域）**，与薪酬结算域**平级**。

### 7.2 经营结算域结构

```
  panjia-ledger（经营结算域·顶层·平级）
  │
  ├── income
  │   ├── commission_income（佣金收入）
  │   └── other_income（其他收入）
  │
  ├── expense
  │   ├── payroll_cost（人工成本·来自 payroll 事件）
  │   ├── rent（房租）
  │   ├── utilities（水电）
  │   ├── platform_fee（平台费用）
  │   ├── recruitment（招聘费用）
  │   └── other_expense（其他支出）
  │
  └── department-settlement
      ├── DeptLedger（部门收支台账）
      ├── ProfitSummary（营业利润汇总）
      └── SettlementReport（部门经营报表）

  利润 = 收入 - 支出（可自定义公式，配置驱动）
```

> **V1 范围**：仅 `commission_income` / `payroll_cost` / 部门台账。事件契约（`PayrollLockedEvent`）先定义，未来扩展收入来源无需改动 payroll。

### 7.3 与薪酬结算域的依赖方向

```
   panjia-payroll                        panjia-ledger
   ┌────────────┐                        ┌────────────┐
   │ PayrollBatch(LOCKED)               │ DeptLedger  │
   │     │ 发布事件（写入 Outbox）         │     │ 被写入  │
   │     ▼                               │     ▼      │
   │ PayrollLockedEvent                  │ LedgerService│
   └────────────┘                        └────────────┘

   ledger ──依赖──▶ contracts ：仅通过事件契约（反向 0 直接调用）
   payroll ──依赖──▶ ledger ：❌ 不允许（薪酬不应知道结算存在）
```

`panjia-payroll` 代码里**不 import `panjia-ledger` 的任何类**。它只发布通用事件 `PayrollLockedEvent`。`panjia-ledger` 通过 Outbox 机制消费事件。

## 八、事件驱动与可靠性（Event Outbox）

### 8.1 问题：进程内事件不是可靠的

Spring `@TransactionalEventListener(AFTER_COMMIT)` 在以下场景会丢事件：

```
payroll 事务 commit
   → AFTER_COMMIT listener 执行（写入 ledger）
   → 若 JVM 在两者之间宕机
→ Payroll 已 LOCKED，ledger 未收到事件，事件永久丢失
```

Redis 幂等键只能去重，无法恢复丢失的事件。因此需要 **Transactional Outbox** 模式。

### 8.2 Outbox 模式

```
Payroll 事务（同库，原子提交）
       │
       ├── pj_payroll_batch         = LOCKED
       ├── pj_payroll_employee_snapshot（冻结）
       └── pj_event_outbox          = PENDING  ← 与业务数据同事务
                    │
                    ▼ （事务提交后，事件已持久化，不丢）
            Event Dispatcher（Spring Scheduler 轮询）
                    │
          ┌─────────┴─────────┐
          │                   │
      成功发送             失败/异常
          │                   │
    status = SENT       status = PENDING（保留，下次重试）
          │              + 指数退避 / 死信阈值
          ▼
      Ledger 消费（业务幂等，按 eventId 去重）
```

**关键性质：**

- Outbox 与业务数据**同库同事务**：业务成功则事件必存在，不丢
- Dispatcher 独立轮询 `pj_event_outbox where status = PENDING`，失败自动重试
- Ledger 侧按 `eventId` 做幂等，重复投递不会产生重复数据
- **无需 MQ**：V1 用 Spring Scheduler + 单实例轮询即可；未来多实例只需把 Dispatcher 换成 MQ 生产者，**事件契约与 ledger 消费逻辑不变**

### 8.3 Outbox 表结构

```sql
create table pj_event_outbox (
    id            bigserial primary key,
    event_id      varchar(64)  not null unique,   -- 全局唯一，幂等键
    event_type    varchar(64)  not null,          -- 如 payroll.locked
    aggregate_type varchar(64) not null,          -- 如 payroll_batch
    aggregate_id  varchar(64)  not null,
    payload       jsonb        not null,          -- 事件序列化体
    status        smallint     not null default 0, -- 0 PENDING 1 SENT 2 FAILED
    retry_count   int          not null default 0,
    next_retry_at timestamp,
    created_at    timestamp    not null default now(),
    sent_at       timestamp
);
create index idx_outbox_status_retry on pj_event_outbox(status, next_retry_at);
```

### 8.4 事件发布/消费代码骨架

```java
// ===== 发布方（panjia-payroll，在业务事务内写入 Outbox）=====
@Transactional
public void lockBatch(BatchId batchId) {
    PayrollBatch batch = repository.load(batchId);
    batch.assertCanLock();
    batch.lock();                              // 状态机：APPROVED → LOCKED
    repository.save(batch);
    // 同事务写入 Outbox，eventId 全局唯一
    outboxRepository.save(new OutboxEvent(
        UUID.randomUUID().toString(),           // eventId（幂等键）
        "payroll.locked",
        "payroll_batch",
        batchId.toString(),
        serialize(new PayrollLockedEvent(batch))
    ));
}

// ===== Dispatcher（Spring Scheduler，单实例轮询）=====
@Scheduled(fixedDelay = 5_000)
public void dispatch() {
    List<OutboxEvent> pending = outboxRepo.findPending(100);
    for (OutboxEvent e : pending) {
        try {
            eventPublisher.publish(e);         // Spring ApplicationEvent → listener
            e.markSent();
            outboxRepo.save(e);
        } catch (Exception ex) {
            e.incrementRetry();                 // 退避后重试
        }
    }
}

// ===== 订阅方（panjia-ledger，业务幂等）=====
@Component
public class DeptLedgerListener {
    @Autowired private LedgerRepository ledgerRepo;
    @Autowired private IdempotencyStore idem;

    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void onPayrollLocked(PayrollLockedEvent event) {
        if (idem.exists(event.eventId())) return;   // 按 eventId 幂等
        ledgerRepo.aggregateCost(event.batchId(), event.deptCostMap());
        idem.mark(event.eventId());
    }
}
```

> **可靠性保证**：业务提交 + 事件持久化原子；Dispatcher 重试 + Ledger 幂等 = 最终一致。`eventId` 是唯一幂等键（V1 用数据库唯一约束 + Redis 辅助，未来 SaaS 演进时再引入分布式方案）。

### 8.5 未来房源域的接入方式

房源管理（`panjia-listing`）是房产中介核心业务，未来必然进入平台。接入方式规定如下（**V1 不创建模块**）：

| 项 | 规约（V1 仅文档化） |
|----|------|
| 命名 | 包 `com.panjia.listing`，表前缀 `pj_listing_*` |
| 事件契约 | `ListingDealEvent` 定义在 `panjia-contracts`（与 `PayrollLockedEvent` 同级） |
| 依赖方向 | listing → people（经纪人）；发布 `ListingDealEvent` → performance / ledger |
| 接入动作 | ① 建 `panjia-listing` 模块；② 在 performance 新增 `ListingDealEventListener`；③ 在 ledger 新增对应 listener |

> **准确表述**：接入房源域时，**不改变既有核心业务模型和依赖方向，仅通过新增事件适配器/监听器接入**。这需要在 performance / ledger 中新增 listener 类——属于"新增代码"而非"改造既有逻辑"，既有域的核心路径与数据模型保持不变。

## 九、横切关注点架构规约：Port/Adapter

### 9.1 问题陈述

License 与 Backup 若直接侵入业务代码，会导致相关代码散落到每个业务方法，后续替换或扩展成本高。

### 9.2 Port/Adapter 模式

```
                    ┌─────────────────────────────────────────┐
                    │      各顶层域内部（payroll/ledger/...）   │
                    │                                         │
                    │  ┌─────────────────────────────────┐     │
                    │  │  Ports（Java Interface，业务声明）  │     │
                    │  │  • LicensePort                  │     │
                    │  │  • BackupPort                   │     │
                    │  │  • AuditPort                    │     │
                    │  │  • EventPort（Outbox 写入）      │     │
                    │  └─────────────────────────────────┘     │
                    │       │  （依赖倒置）                     │
                    │       ▼                                   │
                    │  ┌─────────────────────────────────┐     │
                    │  │  Adapters（具体实现，infra 层）    │     │
                    │  │  • LicenseAdapter  → /check HTTP │     │
                    │  │  • BackupAdapter   → panjia-backup│     │
                    │  │  • AuditAdapter    → sys_oper_log │     │
                    │  │  • OutboxEventAdapter → Spring AE  │     │
                    │  └─────────────────────────────────┘     │
                    └─────────────────────────────────────────┘
```

### 9.3 Port 接口签名

```java
public interface LicensePort {
    LicenseState check();
    boolean isRestricted(LicenseState state);
}

public interface BackupPort {
    void trigger(BackupReason reason);  // PRE_CALCULATE / PRE_UPGRADE / MANUAL
}

public interface AuditPort {
    void record(String action, Object businessKey);
}

public interface EventPort {
    void emit(OutboxEvent event);  // 写入 Outbox（同事务）
}
```

业务代码只依赖这些接口，具体实现在 infrastructure 层注入。

### 9.4 架构铁律（写进 CI 校验）

| 铁律 | 说明 | 违反（CI 拦截） |
|------|------|------|
| 业务域禁止 `import` `panjia-license` / `panjia-backup` 具体类 | 只允许经 Port 接口 | 静态检查报错 |
| `LicenseInterceptor` 只做横切拦截，不写业务逻辑 | 发现受限 → 抛异常/返回 403 | 代码评审 |
| 受限模式钩子只在 `SalaryCalculationEngine` 末端叠加 | 不在每个 Service 散落校验 | 静态检查 |
| Backup 只在 `PayrollApplication` 编排点触发 | 不在每个算薪步骤里调备份 | 代码评审 |

### 9.5 与现有 `LicenseInterceptor` 的关系

`LicenseInterceptor`（V2.10 已有）负责**粗粒度拦截**；Port 接口解决"业务方法内部还需判断授权状态"的问题。两者互补：Interceptor 管"能不能进"，Port 管"进了之后算不算数"。

## 十、员工域（panjia-people）

> **V1.8 重写说明**：本章将《员工域详细设计 V3.1》冻结决策上升到架构基线。核心思想——**people 域产出的是算薪规则的"原子事实"**：`salary_record` 供界面展示（当前态），`salary_fact` 供算薪（一项一条、闭开区间）；金额/比例一律归客户级规则，人身上只存开关/标签/关系。详细设计见《员工域详细设计 V3.1》。

### 10.1 员工独立成域的必要性

员工主数据是**所有域共享的根对象**。如果放在任何业务域内，会导致：导入/业绩/结佣/结算域都要"穿过"该域才能拿到员工数据；未来人事/房源/客源模块需要时，员工数据被锁在某个业务域内。

**结论**：员工独立为顶层域 **`panjia-people`**，作为所有业务域的**公共根**，自身不依赖任何业务域。

### 10.2 设计目标与核心原则

> **一套员工主数据 + 算薪事实模型，适配 N 家中介公司——换客户不改代码、只改导入数据与规则配置。**

| 原则 | 落地 |
|------|------|
| **事实归 people，规则归 payroll** | 人身上只存"是什么"，不存"怎么算"；社保基数/比例、公积金金额/比例、兼职豁免、徒弟奖励上限一律在 payroll 客户级规则 |
| **原子数据** | 本域产出的是算薪规则的**原子事实**，payroll 据此 + 规则配置 = 算薪 |
| **闭开区间** | 所有带时效的事实用 `[effective_date, expire_date)` 表达 |
| **变更即结束旧 + 新增** | 不 UPDATE 历史，只追加 |
| **底座协作走 Port-Adapter** | people 零 `import com.ruoyi.*`；账户/部门/岗位同步在事务内经 Port 完成 |
| **导入驱动** | 员工由 Excel 导入创建（不做初始化）；导入即建部门树、账户、岗位、角色 |

### 10.3 表结构总览（4 张表）

| 表 | 粒度 | 职责 |
|----|------|------|
| `pj_people_employee` | 一人一行 | 员工**基本信息**（当前态） |
| `pj_people_salary_record` | 一人一行 | **界面展示**用，永远最新（当前态物化视图） |
| `pj_people_salary_fact` | **一项一条** | **真正算薪用**，闭开区间 |
| `pj_people_change_log` | 一变更一行 | 变更审计（变更项 / 前 / 后 / 生效 / 结束） |

> **算薪永远读 `salary_fact`，不读 `salary_record`。** `salary_record` 是 `salary_fact` 按员工最新一条各 fact_type 的物化视图，可由 fact 全量重建，允许冗余。

**`salary_record` 与 `salary_fact` 的关系：**

```
salary_record  ── 当前态快照，界面查询快，冗余但方便
salary_fact    ── 历史真相，算薪唯一数据源
                ↑
         每次变更：刷新 record + 追加 fact + 写 log（同一事务）
```

### 10.4 算薪事实枚举（fact_type，冻结 8 类）

| fact_type | value 含义 | 示例 | 归属 |
|-----------|-----------|------|------|
| `LEVEL` | 职级编码 | `A2` / `S1` | 事实 |
| `STATUS` | 状态 | `ACTIVE`/`PARTTIME`/`LEFT` | 事实 |
| `SOCIAL` | 是否参保 | `true`/`false` | 事实（开关） |
| `HOUSING` | 是否缴公积金 | `true`/`false` | 事实（开关） |
| `COMMERCIAL` | 是否买商业保险 | `true`/`false` | 事实 |
| `DORMITORY` | 是否住宿舍 | `true`/`false` | 事实 |
| `PARTTIME` | 是否兼职 | `true`/`false` | 事实 |
| `MENTOR` | 师傅员工 ID | `1000148441` | 关系 |

**闭开区间协议：**

```
[effective_date, expire_date)
  effective_date = 闭（含）
  expire_date    = 开（不含），NULL = 至今
```

算薪取数标准 SQL（同日分组变更取最新）：

```sql
SELECT * FROM pj_people_salary_fact
WHERE employee_id = #{id}
  AND fact_type = 'LEVEL'
  AND effective_date <= #{point}
  AND (expire_date IS NULL OR #{point} < expire_date)
ORDER BY effective_date DESC
LIMIT 1;
```

> **无 `HOUSING_AMOUNT` / `SOCIAL_BASE` / `SOCIAL_RATIO`** —— 金额、比例全在规则侧（见 §10.9）。

### 10.5 主数据边界（CI 校验）

> **绝对红线**：不要让 `sys_user` 成为业务员工主表。

| 职责 | 归属 | 表 |
|------|------|-----|
| 登录账号、密码、角色、菜单权限 | **RuoYi**（`sys_user` / `sys_role` / `sys_menu`） | 底座表 |
| 部门树、岗位 | **RuoYi**（`sys_dept` / `sys_post`），**由导入事务维护** | 底座表 |
| 工号、入职/离职、职级、社保/公积金/商业/宿舍开关、师徒 | **`panjia-people`** | 业务表 |

**关系（单向引用）：**

```
sys_user ──user_id──▶ pj_people_employee
                         ├── employee_code = sys_user.username（= 工号）
                         ├── dept_id = sys_dept.dept_id（组别/门店）
                         └── position（职位）→ sys_post / sys_role 名称
                         
pj_people_employee  ──1:N──▶  pj_people_salary_record（当前态，界面）
                         ──1:N──▶  pj_people_salary_fact（历史，算薪）
                         ──1:N──▶  pj_people_change_log（审计）
```

**CI 校验：**
- ① `pj_people_*` 表**不得**出现 `sys_` 前缀字段
- ② `sys_user` **不得**出现业务字段（base_salary / rank_id / social_insurance_*）
- ③ `pj_people_employee.user_id` 是唯一跨域引用键

### 10.6 `EmployeeSnapshot` 字段契约（只含事实）

`EmployeeSnapshot` 定义在 **`panjia-contracts`**（普通 POJO，禁止 record），是只读 DTO，**禁止回写 people 域**：

```java

    // ===== 社保（事实 = 只有开关/标签，见 §10.9）=====
    private Boolean socialInsured;       // 是否参保
    private Boolean housingInsured;      // 是否缴公积金
    private Boolean commercialInsured;   // 是否买商业保险
    private Boolean dormitory;           // 是否住宿舍
    private String  socialTag;           // 参保标签（普通/HIGH，触发规则覆盖）

    // ===== 师徒（MENTOR 事实）=====
    private Long   mentorId;             // 师傅 employeeId（无则 null）

    // ===== 快照元数据 =====
    private LocalDate      snapshotDate;     // 业务时点
    private LocalDateTime  snapshottedAt;    // 生成时间
}
```

**字段完整性审计（算薪事实对账）：**

| 算薪用途 | 字段 | 快照 | 说明 |
|---------|------|:----:|------|
| 职级 | `levelCode` | ✅ | 取自 fact LEVEL |
| 社保开关 | `socialInsured` | ✅ | 社保基数/比例在规则侧 |
| 公积金开关 | `housingInsured` | ✅ | 金额/比例**不在人身上** |
| 商业保险 / 宿舍 | `commercialInsured` / `dormitory` | ✅ | 开关；具体金额在规则侧 |
| 招聘推荐关系 | `mentorId` | ✅ | 徒弟奖励上限在规则侧 |
| 兼职标记 | `isPartTime` | ✅ | 是否豁免由规则决定 |

> **明确不在快照中（归对应域/规则）**：社保基数/比例、公积金金额/比例、奖金、其他收入（payroll）；考勤扣款、积分扣款（import 域）；往月负工资结转、个税（payroll 计算）；绩效扣点 A/B/C（performance 域）。

### 10.7 `sys_user` 异常场景与账户同步（Port-Adapter）

> **核心结论：员工↔账户同步走 Port-Adapter 同事务，不走 panjia-contracts 事件。**

**为什么不是 contracts 事件？** 三个理由：
1. contracts 放的是**跨业务域**的事件契约；"员工↔账户"是 people 与 **RuoYi 底座**的协作，底座不算业务域；
2. 导入要**强一致**（员工建了账户必须同时建好），事件=最终一致会产生"员工已建、账户未建"中间态；
3. V1.7 §9 **已为"业务↔底座"场景定义 Port-Adapter 模式**（LicensePort/BackupPort），账户同步正是一个实例。

**Port 接口（domain 层，零 RuoYi）：**

```java
// panjia-people/port/AccountPort.java
public interface AccountPort {
    Long createUser(String username, String name, Long deptId);   // 返回 sys_user.id
    void assignRole(Long userId, String roleName);                // 角色名 = 岗位名
    void assignPost(Long userId, String postName);                // 岗位名 = 职位
}

// panjia-people/port/DeptPort.java
public interface DeptPort {
    Long findOrCreateDept(String deptName, Long parentId);  // 门店/组别
}
```

**导入事务（强一致）：**

```
@Transactional
void importEmployee(EmployeeRow row) {
    // 1. 部门树：按 "-" 拆解，门店一级、组别二级，自动建 sys_dept
    Long deptId = deptPort.findOrCreateDept(row.getStore());       // 门店
    if (row.getGroup() != null)
        deptId = deptPort.findOrCreateDept(row.getGroup(), deptId); // 组别挂门店下

    // 2. 建员工（pj_people_employee + salary_record）
    Employee emp = saveEmployee(row, deptId);

    // 3. 账户（employee_code = username，角色名 = 岗位名 = 职位）
    Long userId = accountPort.createUser(emp.getEmployeeCode(), emp.getName(), deptId);
    accountPort.assignPost(userId, row.getPosition());
    accountPort.assignRole(userId, row.getPosition());   // 角色名 = 岗位名
    emp.setUserId(userId);

    // 4. 生成 salary_fact（每个算薪项一条，change_field=ALL）
    // 5. 写 change_log
}
```

**`sys_user` 异常场景：**

| 场景 | 处理方式 |
|------|----------|
| 账号被**删除** | people `user_id` **保留**（历史关联不破坏），员工状态置 LEFT；**禁止置空** |
| 账号被**禁用** | people 不感知，快照照常生成 |
| **无账号员工** | **允许存在**，`user_id = null`；只参与算薪，无登录权限 |
| people 直接写 `sys_user` | **禁止**（含角色同步）；必须经 `AccountPort` → `RuoYiAccountAdapter` |

### 10.8 变更模型（通用入口）

**所有改动（入职/职级/社保开关/师徒/状态/离职）走同一个方法**——结束旧记录 + 新增记录，不 UPDATE 历史：

```java
@Transactional
public void changeFact(Long empId, String factType, String newValue, LocalDate effect) {
    // 1. 结束旧记录（把当前活跃记录的 expire_date 置为 effect）
    List<SalaryFact> active = repo.findActive(empId, factType, effect);
    for (SalaryFact f : active) { f.setExpireDate(effect); repo.update(f); }
    // 2. 新增记录（expire_date = NULL = 至今）
    repo.insert(new SalaryFact(empId, factType, newValue, effect, null, factType));
    // 3. 刷新 salary_record 对应字段
    recordRefresher.refresh(empId, factType, newValue);
    // 4. 写 change_log
    logRepo.insert(new ChangeLog(empId, factType, oldValue, newValue, effect, null));
}
```

> **分字段独立时间线**：职级改了只动 `fact_type=LEVEL` 的记录、保险改了只动 `COMMERCIAL`，生效时间各自独立，算薪时点自动取到正确切片——无需合并处理。

**变更日志类型（`change_field`）：**

| fact_type / 值 | 含义 |
|----------------|------|
| `ALL` | 入职（导入时初始化，生成全部 fact） |
| `LEVEL` / `STATUS` / `SOCIAL` / `HOUSING` / `COMMERCIAL` / `DORMITORY` / `PARTTIME` / `MENTOR` | 对应项变更 |
| `LEFT` | 离职（status=LEFT，置 leave_date） |

### 10.9 事实 vs 规则边界（★ 产品化命脉）

**绑定到人（salary_fact，只有开关 / 标签 / 关系）：**

`social_insured` / `housing_insured` / `commercial_insured` / `dormitory` / `is_part_time` / `social_tag` / `level_code` / `status` / `mentor_employee_id`

**归客户级规则（payroll `pj_payroll_rank_rule.rule_content` JSONB，规则兜底到人）：**

社保基数、社保比例（个人/公司）、公积金金额、公积金比例、**兼职是否豁免**、徒弟奖励上限/加点等。

**社保/公积金的分层规则：**

| 层 | 放什么 | 在哪 | 换客户改不改 |
|----|--------|------|:---:|
| **L1 绑定到人（事实）** | `social_insured`/`housing_insured`（是否购买）、`social_tag`（参保标签） | `salary_fact` | ❌ 不改 |
| **L2 规则参数** | 基数上下限、个人/公司比例、公积金比例、**兼职是否豁免** | `rank_rule.rule_content` | ✅ 只改这里 |
| **L3 特殊人覆盖** | 某个具体员工特殊基数 | 规则的 `overrides` 节点 | ✅ 规则侧 |

**算薪引擎取值（事实 BUT 规则优先）：**

```
最终是否参保 = social_insured(事实)  BUT  规则(兼职豁免/标签覆盖) 可能强制为 false
基数 / 比例   = 规则取值（全局 → social_tag 标签 → 工号覆盖 三级兜底）
```

> **换客户 = 只改规则 JSON，人身上 0 改动。** 规则按"全局 → 标签 → 工号"三级兜底，避免逐人配置。

### 10.10 职级生效时序与快照取数规则

> 同一员工可能存在多条同 fact_type 记录（含历史、当前、未来生效），取数必须**按业务时点精确选取**（见 §10.4 SQL）。

**`EmployeeSnapshotService#produceSnapshot(employeeId, pointInTime)` 取数规则：**

```
对每个"时点生效"类 fact_type（LEVEL / STATUS / SOCIAL / HOUSING / ...），统一按 §10.4 SQL 选取：
  - 无记录 → 抛 ServiceException（"该时点无有效记录"），不降级
  - 多条 → 取 effective_date 最大的一条（最新生效）
  - 边界：point = effective_date 恰好命中该记录（闭开区间 [effective, expire)）
```

**变更日志与 fact 的关系：** `change_log` 用于审计展示（变更项/前/后/生效/结束）；**算薪只读 `salary_fact`，不看 `change_log`**。

### 10.11 people 域的边界（明确"不做的事"）

| people 域**负责** | people 域**不负责** |
|-------------------|-------------------|
| 员工档案（基本信息） | 业务角色 → 系统权限（`sys_role`）映射（归部署/运维层） |
| `salary_record` 当前态 + `salary_fact` 算薪事实 | 直接写 `sys_user` / `sys_user_role`（必须经 Port） |
| 导入时建部门树、账户、岗位、角色绑定 | "兼职是否豁免"等业务规则判断（归 payroll 规则） |
| 变更通用入口（结束旧 + 新增）+ `change_log` | 社保基数/比例、公积金金额/比例（归客户级规则） |
| 按 `EmployeeId` + 时点产出 `EmployeeSnapshot`（纯事实） | 算薪参数配置、任何下游消费域的快照持久化 |
| `mentor_employee_id`（师徒关系事实） | 招聘奖励上限/加点计算（归 payroll 规则） |

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Phase 7：横切收尾 & 集成测试
  Task-7-1   LicenseInterceptor 复核（粗粒度拦截）
  Task-7-2   RestrictedAmountCalculator 集成（细粒度偏移）
  Task-7-3   Backup 触发点编排（算薪前/升级前）
  Task-7-4   Full Stack 集成测试（import→performance→commission→payroll→ledger，含 Outbox 重试/幂等）
  Task-7-5   AI 任务间契约对齐（Phase 间接口/数据结构核对）
```

**任务拆分的核心价值：**
- 每个 Task 上下文聚焦（纯计算 / 状态机 / 事件监听 / 表结构），AI 生成质量更高
- Phase 间有清晰契约（上游输出 = 下游输入数据结构），可独立验证
- 可并行：Phase 1-4 无相互依赖时可同时派给多个 AI 实例
- 可回滚：某个 Phase 出问题，不影响其他 Phase
- **未来房源域**作为独立 Phase 接入，仅新增 listener，**既有核心路径与数据模型不变**

## 十四、架构决策记录（ADR）

### ADR-001~006：基础架构决策

快照冻结 / 双轨制 / 独立实例 / 规则引擎（Level 1+2+3，不含脚本）/ 数据导入 / 受限模式钩子——与 V2.10 一致。

### ADR-007：顶层业务域划分

| 项目 | 内容 |
|------|------|
| **决策** | 拆分为 **6 个顶层业务域**：`panjia-people` / `panjia-import` / `panjia-performance` / `panjia-commission` / `panjia-payroll` / `panjia-ledger`，单向依赖，无环 |
| **背景** | 业务领域若全嵌套在薪酬模块下，命名暗示"都属于薪酬"，加入房源管理时无干净挂载位 |
| **选择理由** | 每个业务主题独立顶层域 → 新域只增不改造型 → 命名与职责一致 |
| **代价** | 包/表需批量重命名（结构不变） |

### ADR-008：经营结算域独立 `panjia-ledger`

| 项目 | 内容 |
|------|------|
| **决策** | 原"收支"升级为顶层域 **`panjia-ledger`**（经营结算），与 `panjia-payroll` 平级，通过事件协作 |
| **背景** | "收支"命名过窄，实际承载收入/支出/利润/部门结算；挂在薪酬下阻碍扩展 |
| **选择理由** | 命名准确 + 顶层独立 → 收入来源可任意扩展，payroll 无需改动 |

### ADR-009：员工域独立为 `panjia-people`

| 项目 | 内容 |
|------|------|
| **决策** | 员工域独立为顶层域 **`panjia-people`**，是所有业务域的公共根；外部只通过 `EmployeeId` / `EmployeeSnapshot` 访问 |
| **背景** | 员工主数据被所有域共享，置于任何业务域内都会造成跨域穿透依赖 |
| **选择理由** | 公共根独立 → 所有域通过 Id/Snapshot 访问 → 主数据边界清晰 |

### ADR-010：协作契约层 `panjia-contracts`

| 项目 | 内容 |
|------|------|
| **决策** | 跨域共享类型（事件、Id、只读 Snapshot）集中到独立模块 `panjia-contracts`；事件契约不放在发布域 |
| **背景** | 若 `PayrollLockedEvent` 定义在 payroll 内，ledger 订阅即形成对 payroll 的编译期依赖，并非真正解耦 |
| **选择理由** | 契约层为所有域共同依赖的叶子 → 事件发布/订阅双方只依赖 contracts → 可独立演化 |
| **代价** | 多一个模块；新增事件需在此定义 |

### ADR-011：跨域不共享聚合根

| 项目 | 内容 |
|------|------|
| **决策** | 业务域禁止 import 其他域的 `domain` 聚合根；域间只暴露 `Id` / `Snapshot` / `DTO` / `Event` |
| **背景** | 直接共享聚合根（如 payroll 引用 people 的 `Employee`）会把上游领域模型变化传导到下游所有域 |
| **选择理由** | 快照/Id 是不可变的历史事实，与上游当前状态解耦 → 上游演进不冲击下游 |
| **代价** | 需定义 Snapshot 映射与 CI 校验 |

### ADR-012：快照归属消费域

| 项目 | 内容 |
|------|------|
| **决策** | 历史冻结快照按其**消费域**命名与建表（如 `pj_payroll_employee_snapshot`），不归主数据域 |
| **背景** | 员工"当前状态"（people）与"某月算薪历史状态"（payroll）是不同概念；主数据域不应承担所有消费者的历史版本 |
| **选择理由** | 消费域自管快照 → 主数据域不膨胀 → 快照生命周期与业务过程一致 |

### ADR-013：Event Outbox 保证事件可靠性

| 项目 | 内容 |
|------|------|
| **决策** | 跨域事件采用 **Transactional Outbox**（`pj_event_outbox` + Spring Scheduler 轮询），不用裸 `@TransactionalEventListener(AFTER_COMMIT)` |
| **背景** | AFTER_COMMIT 在 JVM 宕机时会造成事件丢失，且无法重试；Redis 幂等键无法恢复丢失事件 |
| **选择理由** | 业务与事件同事务 → 事件必持久化 → Dispatcher 重试 + 消费方幂等 = 最终一致；无需 MQ |
| **未来演进** | 多实例时 Dispatcher 替换为 MQ 生产者，事件契约与消费逻辑不变 |

### ADR-014：PayrollBatch 状态机 + 乐观锁

| 项目 | 内容 |
|------|------|
| **决策** | `PayrollBatch` 状态转换一律通过状态机 API + `UPDATE … WHERE status=? AND version=?` 乐观锁；状态校验与 RBAC 分离 |
| **背景** | 仅应用层 if 判断无法防并发双写；`@PreAuthorize` 是权限表达式，不是状态机框架 |
| **选择理由** | 乐观锁保证原子转换 → 状态规则集中在领域模型 → 可单测、可复用 |

### ADR-015：调整/补发采用新增单据

| 项目 | 内容 |
|------|------|
| **决策** | LOCKED 后禁止修改原始明细；调整/补发新增单据，各自产出 `CalculationResult` |
| **背景** | 直接 UPDATE 历史工资破坏审计与可追溯性 |
| **选择理由** | 原始结果不可变 + 差额可复现 → 审计与财务追溯清晰 |

### ADR-016：V1 不引入脚本引擎

| 项目 | 内容 |
|------|------|
| **决策** | V1 规则扩展仅 **Level 1（基础参数）+ Level 2（区间 JSON）+ Level 3（计算器 SPI）**，不提供 Groovy/JS 脚本引擎 |
| **背景** | 脚本引擎涉及沙箱、超时、CPU/文件/网络限制、类加载隔离、版本与审计，与"配置驱动"承诺冲突 |
| **选择理由** | 三级机制覆盖现有客户全部场景；真正需要时再单独设计脚本引擎子域 |

### ADR-017：一客户一实例一数据库，暂不引入 tenant_id

| 项目 | 内容 |
|------|------|
| **决策** | V1 业务表不加 `tenant_id`；部署身份（独立库）即隔离边界；事件契约预留 `tenantId()` 方法 |
| **背景** | 一客户一 Docker Compose + 独立库已是既定策略；现在加 `tenant_id` 会污染所有表与索引 |
| **选择理由** | 与部署形态一致 → 简单直接；未来 SaaS 时再统一引入并重构唯一索引 |
| **代价** | 未来迁移需全表加列、重构唯一索引、加 RBAC tenant scope |

**代价** | 未来迁移需全表加列、重构唯一索引、加 RBAC tenant scope |


### ADR-019：强类型 ID 采用普通 POJO + Long（禁止 record / TypedId）

| 项目 | 内容 |
|------|------|
| **决策** | 所有跨域 `Id` 类型（`EmployeeId` / `BatchId` 等）均为**普通 POJO 包装 `Long`**；禁止使用 Java `record`、禁止 TypedId 库 |
| **背景** | AI 总规约 P0 红线禁止 record；早期架构文档曾设想 TypedId 原型 |
| **选择理由** | POJO + Long 与现有 MyBatis-Plus / 雪花 ID 体系一致，序列化无副作用，可承载校验逻辑 |
| **代价** | 牺牲部分类型安全（以命名约定 + ArchUnit 校验补偿） |

### ADR-020：快照只携带"业务事实"，业务规则归消费域

| 项目 | 内容 |
|------|------|
| **决策** | `EmployeeSnapshot` **只含员工事实字段**（`isPartTime`、`socialInsured` 等开关/标签/关系）；"兼职是否豁免"、社保基数/比例、公积金金额/比例等业务规则由算薪域通过 `RuleSnapshot`（`pj_payroll_rank_rule.rule_content` JSONB）承载，**不进快照、不落人身上** |
| **背景** | 早期设计曾把"兼职强制 `Enabled=false`"硬编码进 SnapshotFactory，导致客户规则泄漏到公共根域，换客户需改代码；后又一度把 `socialBase`/`personalRatio` 放入快照，违反"规则归规则"原则 |
| **选择理由** | 事实与规则分离 → people 域零客户差异化代码 → 换客户只改规则配置 → 历史月份复现准确（规则随 RuleSnapshot 冻结） |
| **关联** | 见 §5.3（规则三级）、§10.6（快照字段契约）、§10.9（事实 vs 规则边界） |

### ADR-021：算薪事实采用"一项一条 + 闭开区间"（V1.8 重写）

| 项目 | 内容 |
|------|------|
| **决策** | people 域算薪事实统一存 `pj_people_salary_fact`（**一个算薪项一条记录**），用 `(fact_type, effective_date, expire_date)` 闭开区间表达时效；同时保留 `pj_people_salary_record`（一人一行当前态，供界面展示）。原 `pj_people_level` / `pj_people_social_insurance` / `pj_people_mentor_relation` 三张表**合并废弃** |
| **背景** | 职级、社保开关、公积金开关、商业保险、宿舍、兼职、师徒关系的生效时间各不相同，若挤在一张宽表，分字段独立变更会产生大量 NULL 与"一次改一个、一次改另一个、生效时间不同"的取数混乱 |
| **选择理由** | 一项一条 → 每次变更只需"结束旧 + 新增"、不 UPDATE 历史；各 fact_type 时间线完全独立，算薪时点取数天然正确（同日变更靠 `LIMIT 1` 取最新）；新增算薪项不改表结构 |
| **代价** | 一行变多条（量可控，按员工×8 类）；`salary_record` 需随变更刷新（同事务保证一致） |
| **关联** | 见 §10.3（表总览）、§10.4（fact_type 枚举）、§10.8（变更通用入口） |

### ADR-022：员工↔账户同步走 Port-Adapter 同事务（V1.8 重写）

| 项目 | 内容 |
|------|------|
| **决策** | 员工导入/变更时，建账户、建部门树、绑岗位、绑角色一律经 `panjia-people/port/` 下的 `AccountPort` / `DeptPort` / `PostRolePort` 接口，**唯一实现在 `adapter/`**（`RuoYiAccountAdapter`，唯一允许 `import com.ruoyi.*` 之处）；导入整体在同一事务（强一致） |
| **背景** | 候选方案：A. people 直连 `sys_user`（违反"people 禁止写 sys_user"红线）；B. 走 `panjia-contracts` 事件（最终一致，导入需立即拿到 user_id，且账户属"业务↔底座"协作而非跨业务域）；C. Port-Adapter 同事务 |
| **选择理由** | 导入要强一致（员工建了账户必须同时建好）→ 同事务；账户是 people 与 **RuoYi 底座**协作，底座非业务域，正好复用 §9 Port-Adapter 模式（LicensePort/BackupPort 同款）→ people 业务代码零 RuoYi 依赖，换底座只换 Adapter |
| **关联** | 见 §9（Port/Adapter）、§10.5（主数据边界）、§10.7（账户同步） |
